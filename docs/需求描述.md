# 智能简历筛选系统 — 需求描述

> 本文是业务需求源头，描述系统要解决什么问题、有哪些角色、输入输出、核心流程和业务规则。后端实现见 `docs/后端设计.md`，数据库模型见 `docs/数据库设计.md`，前端页面与交互见 `docs/前端设计.md`。

> 文档分工：本文只定义业务目标、业务规则和验收边界；算法、状态流转和 API 以后端设计为准，字段与删除策略以数据库设计为准，页面与按钮以前端设计为准。四份核心设计文档保持分立，不通过复制整段实现细节互相替代。本文描述目标设计；当前落地状态统一在 `docs/前端设计.md` 的“实现状态速览”和各文档“待实现与风险”段标注。

## 一、目标与范围

建设网页版校招简历筛选系统，核心流程为：

`查重与志愿排序 → 简历分类、分配与下发`

院校分类和需求录入是分配前置数据准备，可提前独立维护。简历分配与下发支持 **Rule / AI（Agent）** 两种模式，由 HR 选择运行；AI 入口只有在真实模型调用、结构化输出、失败处置和禁止 Rule 回退均通过验收后，方可作为生产能力。每次处理规模约 **3 万条**简历。

项目采用 vibe coding，不安排固定排期。

系统需要支持：

- 4 张业务表和简历包导入。
- 候选人按人聚合，一名候选人可有多条投递。
- 当前有效志愿展示与按志愿顺序推进分配。
- Rule / AI 策略分配；达到复核阈值但未达到自动下发阈值的 AI 结果进入 HR 复核，低于复核阈值或最终失败时不生成分配尝试并按 `agent_no_recommendation` 归档。
- HR 下发、二级接口人转派、三级接口人反馈。
- 简历库归档筛选和 HR 手动强制分配。
- 用户、角色、权限配置。
- 各环节结果查看、表头筛选、分页、简历预览和导出；所有数据表格均支持拖拽调整列宽，可筛选业务列在表头提供文本或单选/多选选择器。

## 二、输入件

| 文件 | 关键字段 |
| ---- | -------- |
| 简历信息列表（xlsx / xls / csv） | 招聘主体、所属机构、姓名、应聘ID、手机号、性别、对外职位名称、学历、第一学历毕业院校、最高学历毕业院校、最高学历专业、应聘状态、户口所在地、应聘日期 |
| 校招岗位分类及专业要求（xlsx / xls / csv） | 主体、一层/二层部门、岗位类别、对外发布名称、是否对外发布、职位名称、岗位族、工作地点、学历、需求专业、需求数量 |
| 院校分类（xlsx / xls / csv） | 学校、平台/院校标签、所在省份（如有） |
| 部门接口人信息（xlsx / xls / csv） | 序号、招聘主体（仅兼容外部文件识别，导入后丢弃）、一层/二层/三级部门、姓名、工号、接口人层级/权限 |
| 简历包 | 命名格式 `姓名（应聘ID）`，如 `张三（12345）`；简历格式统一为 PDF |

身份口径：

- **规范化姓名 + 规范化手机号** 是候选人归并依据。
- **应聘ID** 是投递维度业务键。
- 手机号缺失的候选人直接舍弃，不入库、不进入分配，并在导入结果中提示。
- 部门接口人文件中的“招聘主体”仅用于兼容外部文件和辅助识别文件类型，导入后丢弃；不落为部门或接口人的主体归属或“主体来源”字段，也不提供相关筛选。部门主数据只维护组织层级，招聘主体保留在投递、岗位需求等业务记录上。

## 三、业务对象口径

### 候选人与投递

同一位同学可多次投递，单主体最多 2 个岗位，跨两主体最多 4 个岗位。`应聘ID` 按投递唯一，不能标识人，因此业务上区分：

- **Candidate（候选人 / 同学）**：按规范化姓名 + 规范化手机号归并。
- **Resume（投递 / 应聘）**：一条记录对应一个应聘ID，挂在某个候选人下。

展示口径：

- 简历库主列表按 `Candidate` 聚合，一名候选人只显示一行，是 HR 查看候选人当前流程、归档信息和主数据缺口的候选人级主入口。
- 候选人详情展示该候选人的手机号、全部投递、志愿顺序、分配尝试、匹配/手动理由和反馈结果；简历库主列表不展示手机号。
- 主列表只展示当前有效志愿：初始展示第一志愿；当前志愿被三级接口人反馈未通过后，再展示下一志愿；已通过候选人展示通过志愿；已归档候选人展示最后处理志愿与归档原因；当前志愿已匹配岗位和二级部门但缺可用二级接口人时，展示当前志愿和阻塞原因，不切换下一志愿。
- 简历库支持按姓名、姓名全拼、姓名拼音首字母、最高学历专业、当前志愿、当前应聘ID、招聘主体、当前岗位、岗位部门、岗位类别、院校标签、系统简历状态、流程状态、原因类型等主表字段筛选；系统简历状态和流程状态支持表头勾选多选；筛选在后端执行并参与分页和“导出当前筛选全部”。
- 简历库主列表和候选人详情都必须展示候选人的最高学历专业；该字段来自简历信息列表中的“最高学历专业”，落在 `Candidate.highest_major`，不从当前投递的岗位类别反推。
- 候选人详情支持预览该候选人的 PDF 简历；预览时必须先通过后端鉴权 API 获取 PDF Blob 和原始文件名，再由前端 PDF.js 渲染到 canvas，不直接暴露静态文件地址。无权限或越权时不可预览且不提供下载入口；PDF 渲染失败或非 PDF 文件时，可下载原文件。候选人删除只作为数据维护能力；仅存在尚未产生历史的空 `CandidateWorkflow` 时允许随候选人一并清理，存在分配尝试/反馈、AI 决策或转派历史中的任一项时必须禁止删除，并返回受保护历史类型。

系统简历状态是简历库面向 HR 的统一展示态，由投递、分类、分配尝试和反馈记录推导，不覆盖导入文件中的原始“应聘状态”字段：

- **待处理**：原始导入后尚未完成岗位类别和院校标签分类的候选人/当前投递。
- **已分类**：已完成岗位类别和院校标签分类，但尚未形成有效业务部门推荐。
- **已分配**：已形成业务部门推荐或 HR 待复核/待下发尝试，尚未下发给业务部门筛选。
- **待筛选**：已下发或转派给业务部门，尚未反馈筛选结果。
- **筛选通过**：业务部门反馈通过。
- **筛选不通过**：业务部门反馈未通过；若仍有下一志愿，系统可继续推进下一志愿。

招聘主体口径：

- 招聘主体如 GW / YLS 是主数据，不作为自由文本散落在投递和岗位需求中。
- 当前统一使用 `code` 作为主体标识和展示值。
- 部门与招聘主体不建立“属于”关系。

字典口径：

- `JobCategory`（岗位类别）保留 `code + name`，供岗位需求、简历分类、Rule/AI 分配和前端筛选引用。
- `SchoolTag`（院校标签）保留 `code + name`，供学校、候选人打标和院校准入规则引用。
- `School` 只保存学校名称、`province` 和院校标签引用；不保存南北归属，不维护南北省份字典。

## 四、前置数据准备

### 院校分类

用户需求：

- 按第一学历、最高学历对照院校清单打标签。
- 系统预置并保证存在编码为 `NON_TARGET` 的“非目标院校”标签。学校不在导入院校清单内时，第一学历和最高学历**始终**使用该标签；只有学校已在清单内但未配置标签时，才使用启用的默认院校标签，若无默认标签则使用“非目标院校”。
- 院校分类可在简历分配前提前运行；院校清单更新后也可独立重跑。
- 输出候选人的第一学历标签、最高学历标签，作为分配准入规则输入。

规则边界：

- 院校只存所在省份 `province`。
- 南北归属仅在志愿排序规则运行时判断，不落库、不作为配置项维护。

### 需求录入

用户需求：

- 将校招岗位分类及专业要求整理成结构化岗位需求。
- 维护岗位、部门、岗位类别、需求专业、需求数量等分配前置数据。
- 需求录入可在简历导入前提前维护；岗位需求、专业要求、二级/三级部门接口人更新后可独立重跑或手工维护。
- 岗位需求页面支持新增、编辑和删除岗位；删除采用失效/停用语义，不破坏历史投递和分配尝试中的岗位引用。
- 系统内置一版专业大类映射词表，并允许 HR/管理员在配置项中维护专业大类、专业别名和关键词。该词表用于 Rule 策略的专业匹配增强；AI 策略可读取同一词表作为后续提示词/校验上下文，但本阶段不继续演进 AI 能力。

## 五、候选人处理主流程

### Step1 查重与志愿排序

需求：

- 按 `Candidate` 聚合一个人的全部投递。
- 单一主体每人最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各投 2 个时，统一标第一至第四志愿。
- 排序规则：户籍北方优先 GW，南方优先 YLS；户籍缺失时按学校所在地同规则。
- 户籍或学校所在省份的南北判断只在规则运行时计算，不落库。

输出：

- 候选人维度的志愿排序结果。
- 主列表展示当前有效志愿，详情展示完整投递清单。

### Step2 简历分类、分配与下发

需求：

- 以候选人为粒度推进分配，一个候选人一个当前流程。
- 自动分配按志愿顺序依次尝试。第一志愿未反馈前，主列表和流程只暴露第一志愿；反馈未通过后，系统生成下一志愿尝试。
- 目标设计中，HR 可选择 **Rule** 或 **AI（Agent）** 策略。两种策略都完成岗位分类、岗位/部门匹配，并进入同一套候选人工作流；只有满足各自尝试生成条件时才创建 `AssignmentAttempt`。
- HR 可配置院校标签准入规则。存在启用规则时，Rule 与 AI 策略都必须先命中同一条启用规则，即第一学历标签和最高学历标签同时满足该规则；没有启用规则时，视为不做准入过滤，候选人全部通过该条件。
- Rule 策略在院校准入通过后，按志愿顺序逐个尝试；投递招聘主体与岗位需求主体双方都有值时必须一致；岗位名匹配按同主体优先、精确优先、对外发布名称优先于职位名称、包含匹配兜底的稳定顺序选择岗位。岗位配置需求专业时，先用启用的专业别名将候选人最高学历专业和岗位需求专业映射到专业大类；任一大类相交则专业通过。若大类无交集，或候选人/岗位任一侧未映射到启用大类，则再执行专业名双向包含兜底；词表和兜底都不命中时继续尝试下一个候选岗位。岗位未配置需求专业，或岗位需求专业为“专业不限 / 不限 / 不限专业”等通配表达时，直接放行。自动分配尝试需记录院校、志愿、岗位、专业大类/专业名、部门和接口人的匹配理由。
- AI 只优化简历理解、岗位适配和分流判断，不绕过院校准入、志愿顺序、反馈锁定等硬规则。
- AI 策略读取 PDF 简历，提取项目经历、实习经历、技能栈、专业方向等信息，并结合当前志愿岗位、岗位需求专业和部门信息生成建议。
- AI 推荐版的第一版定位是“受硬规则约束的分流建议器”：AI 只处理候选人的当前有效志愿，不主动跨志愿跳转；系统先做硬规则检查，再调用 AI 生成岗位/部门/接口人建议。
- AI 结果必须可审查，包含推荐动作、推荐岗位/部门/接口人、置信度、分项评分、推荐理由、简历证据和风险点。

AI 阈值：

> AI 能力必须按以下正式口径验收。AI 连接不可用时必须写入明确失败决策，不得通过复用 Rule 结果、固定置信度或元数据拼接伪装成可用的 AI 结论。

- `ai_dispatch_threshold` 默认 `0.75`。
- `ai_review_threshold` 默认 `0.5`。
- `recommendation=dispatch` 且 `confidence_score >= ai_dispatch_threshold`：生成 `source=ai, pending_dispatch` 的待下发尝试。
- `recommendation != archive` 且 `confidence_score >= ai_review_threshold`，但未达到自动下发条件：生成 `source=ai, pending_review` 的 HR 复核项，不自动下发。
- `recommendation=archive`、`confidence_score < ai_review_threshold`、简历缺失/解析失败或 AI 最终失败：只生成 AI 决策记录，不生成分配尝试；候选人流程进入 `archived`，归档原因为 `agent_no_recommendation`。该记录不混入「AI分配」的分配尝试表，HR/管理员从简历库详情或 AI 决策 API 进行重试 AI、切换 Rule 后重新处理或手动强制分配；二级、三级接口人不显示 AI 分配子页。
- AI 失败、超时、解析失败、输出不合法、推荐对象不存在或被硬规则拦截时，不自动回退 Rule，由 HR 选择重试 AI、切换 Rule 或手动强制分配。

分配和反馈：

- HR 将待下发尝试下发至二级部门接口人，支持单条、勾选批量、当前筛选全部下发。
- `pending_dispatch` / `pending_review` 等 HR 待处理尝试不对二级接口人展示；二级接口人只看到 HR 已下发给自己的简历尝试。
- 二级接口人只能在本二级部门范围内选择下属三级接口人并转派。
- 三级接口人反馈通过/未通过并可填写备注；反馈提交后锁定，不允许二次修改。
- 三级反馈通过后，候选人流程结束，并取消该候选人其他未反馈尝试。
- 三级反馈未通过后，系统自动进入下一志愿；志愿耗尽则归档。
- HR 可在简历库点击“处理简历”后，在弹窗中勾选一个或多个系统简历状态，并多选本次运行的「规则 / AI」模式（可选其一或两者），对当前表格其它筛选条件下命中的候选人重新执行 Step2 简历分类、分配与下发；AI 不可用时 AI 选项不可选。后端以 `ProcessingRun.scope.system_statuses` 和请求 `modes` 记录本次范围和模式。Step2 先锁定本次处理范围，再仅为范围内缺失院校标签的候选人按当前院校清单、默认院校标签和启用的“非目标院校”兜底标签补齐标签，避免未跑全量院校分类时被误判为非目标院校；完整重算全部候选人的院校标签仍由院校分类 Step3 负责。重新分配保留历史分配尝试和反馈记录，不删除审计；对已通过、已归档或已不通过候选人，重新分配视为 HR 主动重开当前候选人流程，清空当前通过指针/归档状态，并分别为所选来源生成自动分配尝试；同一次多选的 Rule 与 AI 尝试必须并存，不得互相取消。
- 自动处理任务创建时固化候选人范围及当前流程版本；不同候选人可并行处理，同一候选人的自动和人工流程写操作统一串行。后发任务遇到冲突时进入等待并重试；人工下发、转派、反馈、手动分配等操作优先完成，自动任务发现流程版本已变化时安全跳过并记录 `skipped_manual_change`，不覆盖人工结果。
- HR 可从任意投递发起手动强制分配，绕过院校规则、志愿顺序和自动筛选条件；已通过候选人不可再强制分配。手动强制分配与简历库“处理简历”是两个入口：前者不允许重开已通过候选人，后者在 HR 明确勾选系统简历状态后允许按筛选范围重开。
- 手动强制分配可选择二级接口人或三级接口人。选择二级接口人时进入待下发/已下发二级流程；直接选择三级接口人时，系统必须校验其所属三级部门存在有效父级二级部门：只有一个有效二级接口人时自动补齐，存在多个时由 HR 明确选择，随后进入待三级反馈流程，并记录“HR 到二级、二级到三级”两段转派历史。没有有效父级二级接口人时禁止直达三级。

归档口径：

- 志愿耗尽、未命中院校规则、找不到岗位、找不到部门、AI 无有效建议、全部志愿未通过等情况进入归档。
- 当前志愿已匹配岗位和二级部门但没有可用二级接口人时，不创建分配尝试、不归档、不推进下一志愿；流程保持进行中，并在简历库原因中提示 HR 补齐接口人或手动处理当前志愿。
- 归档候选人不再作为 HR 独立列表入口；归档筛选、归档原因和从具体应聘ID发起手动强制分配统一合并到简历库。
- 系统简历状态按当前活动流程优先推导：`筛选通过 > 待筛选 > 已分配 > 筛选不通过 > 已分类 > 待处理`。历史志愿的未通过记录不得覆盖下一志愿已生成的待复核、待下发或待筛选状态。

输出：

- 简历库候选人主清单：合并展示当前志愿、当前应聘ID、当前投递、岗位部门、流程状态、分配/归档/阻塞原因。
- 「简历分配」为菜单父级，包含真实子页「规则分配」(`/allocations/rule`) 和「AI分配」(`/allocations/ai`)；两页均展示同一 `AssignmentAttempt` 操作台，仅分别以 `source=rule`、`source=ai` 过滤。列、筛选、详情、PDF 预览、导出、下发至二级接口人、二级转派三级和三级反馈能力一致；批量/按筛选全部操作也必须继承当前 `source` 范围。未生成 `AssignmentAttempt` 的 AI 失败、低置信度或建议归档记录不应冒充为表格行，仍保留在 AI 决策记录中供 HR 从简历库或 API 处置。二级、三级接口人仅进入规则分配子页。
- 候选人简历文件预览和导出，支持单条、勾选批量、按筛选全部；预览时后端通过鉴权 API 返回 PDF Blob 和原始文件名，前端用 PDF.js 渲染到 canvas；详情默认预览当前投递的简历文件，当前投递无文件时回退到同候选人第一条有文件的投递，但不改变当前志愿展示口径；无权限或越权时不可预览且不提供下载入口，PDF 渲染失败或非 PDF 文件时可下载原文件；仅命中一个可用简历文件且没有缺失清单时直接下载原文件，命中多个文件或存在缺失清单时下载 zip；无文件的候选人进入缺失文件清单，导出完成后前端展示成功导出数量和缺失数量。

## 六、用户与权限

角色：

- **HR**：全流程业务操作，包括导入、处理、下发、手动分配、导出、查看反馈，以及维护获授权的院校准入、专业词表等业务规则。
- **二级部门接口人**：查看 HR 下发给自己的尝试，并转派给本部门下属三级接口人。
- **三级部门接口人**：查看转派给自己的尝试，并提交通过/未通过反馈。
- **管理员**：用户、角色、权限、认证与安全配置管理，也可维护业务规则。

权限要求：

- 权限管理采用 RBAC。
- 用户可绑定一个或多个角色。
- 角色绑定权限点，权限点覆盖菜单入口、页面查看、按钮操作、导出、下发、转派、反馈、系统配置等能力。
- 前端需要支持用户、角色、权限配置。
- 权限点由系统预置为树形清单，前端只允许勾选绑定，不允许随意新增未知权限码。
- 数据范围不单独建表，由角色权限、接口人绑定和部门关系推导。
- 前端权限控制只负责体验和误操作拦截，后端必须做接口级鉴权和数据过滤。
- 导入部门接口人信息时，系统按接口人工号自动创建或更新接口人登录账号：用户名使用工号，新账号默认密码为 `pass1234`，并按接口人层级绑定二级/三级接口人角色及对应 `Contact`。
- 已有同工号账号保留原可用密码和非接口人业务角色，仅替换二级/三级接口人角色；部门接口人 replace 导入时，本次文件中不存在的旧接口人及其账号停用。用户管理或接口人清单中的单条删除采用清理语义：删除用户时清空该用户的 Token、角色绑定、接口人绑定等账号相关内容；若用户绑定了接口人，则同步删除该接口人。删除接口人时同步删除绑定该接口人的用户信息。历史分配、转派和 AI 决策不级联删除，只保留已有快照文本和审计记录，不再保留对已删除用户/接口人的外键引用。
- 用户管理不单独维护姓名字段，不展示/编辑/同步 `first_name`、`last_name` 等 Django 姓名类字段；接口人身份展示以绑定的 `Contact.name` 为准。
- 用户管理支持删除用户。删除用户采用账号清理语义，不只是停用：删除后该账号不可登录，不再出现在用户管理列表；若后续公司 W3 或接口人导入重新同步同工号账号，按新账号重新创建和绑定。

登录认证：

- 本地正式开发阶段使用系统账号密码登录，后端签发 Token，登录后按 RBAC 权限点和接口人绑定推导数据范围。
- 系统账号已通过用户、角色、权限和接口人绑定映射 HR、管理员、二级接口人、三级接口人等身份。
- 公司 W3 认证仍待外部方案确认；接入后按工号识别登录用户，并只替换外部身份到系统 `User.username` 的适配层，RBAC、Contact 绑定和 `/api/me/` 消费口径保持不变。

## 七、系统需求

- 上传含候选人简历时固定创建 Rule `ProcessingRun`；仅当 `ai_config.is_ai_enabled`（系统设置中存在可用 Key）时额外创建 AI `ProcessingRun`。两条运行记录在任务中心独立可见，但由同一个顺序 Celery 任务先执行 Rule、再执行 AI，避免流程锁或重跑造成两种来源互相取消；响应只返回 `processing_runs` 列表。生产异步环境提交后返回 `202`；本地 `CELERY_TASK_ALWAYS_EAGER=True` 会同步完成并返回 `200`。按筛选“处理简历”时由 HR 多选 Rule / AI，服务端为所选模式创建独立运行；「简历分配」仅作为父菜单，规则分配、AI分配子页固定展示各自来源的已有尝试，使用相同表头和操作，不提供处理模式选项或重算入口。两个子页均展示每条尝试的分配原因。页面只在提交请求期间禁用发起按钮，提交成功后可继续筛选、预览、导出和跳转，不得用全屏遮罩冻结网站。
- 上传后的后台编排固定为每个模式各自的 `Step1 → Step2`，不得复用 `all`；`all` 仍只用于显式全流程，顺序为 `Step3 → Step4 → Step1 → Step2`。
- 系统提供全局非阻塞任务中心。HR 和管理员可轮询查看全部处理任务的发起人、类型/策略、当前阶段、进度、范围摘要、结果计数、最近心跳和异常；二级、三级接口人不可见。顶栏「处理任务」按钮以 Badge 提示活跃数量；点击后在不遮罩、不冻结页面的侧边 Drawer 中查看任务、进度、取消和审计，任务详情仅在该 Drawer 中展示。首版以约 2 秒 REST 轮询同步多人视图，不要求 WebSocket。HR/管理员可取消活跃任务：`pending` 立即转为 `cancelled`；`running` 或 `waiting_conflict` 先转为 `cancelling`，在候选人或阶段边界安全停止，已落库结果保留。任务中心需展示并审计取消请求时间、取消完成时间和取消人。
- 院校分类 Step3、需求数据准备/核对 Step4 是可独立维护的前置步骤；显式运行 `all` 时统一按 `Step3 → Step4 → Step1 → Step2` 执行，确保前置数据先就绪。
- 简历库“处理简历”按 `modes` 多选的 Rule / AI，只重算“简历分类、分配与下发”环节，不重跑查重排序、院校分类和需求录入；后端收到包含 AI 但 AI 未启用的请求必须拒绝，不能静默降级为 Rule。规则分配、AI分配子页不承担策略切换或重跑职责。
- 简历库提供“处理简历”按钮：HR/管理员点击后在弹窗中勾选目标系统简历状态及至少一个 Rule / AI 模式，再按当前表格其它筛选条件触发指定范围重新分配；弹窗未选择系统简历状态或模式时前端应提示选择，避免误跑全量。前端通过 `GET /api/ai-availability/` 获取仅含 `enabled` 的 AI 可用性，AI 未启用时禁用 AI 选择；该接口只向具有 `pipeline.run` 权限的用户开放，不泄露连接信息。
- 各步中间结果可查看、表头筛选、分页、导出；所有列表、配置表和详情内嵌表格均支持拖拽调整列宽。可独立查询的分页列表通过表头文本/单选/多选选择器调用后端筛选，详情内嵌表格在当前详情数据内执行本地表头筛选；操作列不提供筛选器，但仍支持列宽调整。
- 列表 API 支持按页加载，前端可通过 `page_size` 控制每页数量，后端限制单页最大 500 条以保护服务。
- Rule 与 AI 结果需要支持对比视图，便于人工核对。
- 3 万条规模下，Rule 与 AI 处理都允许分批产生结果，任务中心按各阶段累计工作量显示连续进度，并可边跑边查看待下发、待复核、失败、建议归档和安全跳过数量；任务状态至少包括排队、运行、等待冲突、取消中、已取消、成功、部分失败和失败。心跳超时的任务必须明确失败原因；安全重试只能处理未开始或等待冲突的候选人，不能重复已完成或已安全跳过的候选人。
- 可配置项集中管理，包括院校标签准入规则、专业大类映射词表、AI 阈值、AI 超时、AI 并发、AI 重试次数、AI 重试退避、任务心跳超时、WeLink 开关等运行参数。院校准入、专业词表等业务规则配置可授权 HR/管理员维护；用户、角色、权限、任务运行保护、认证安全由对应权限码控制。
- AI 模型连接作为系统设置中的独立页面，由 `settings.manage_ai_connection` 权限控制；管理员角色默认拥有该权限，也可在「用户权限」按角色授予。获授权用户可配置 profile、API 风格、模型名、Base URL 和 API Key，并发起最小真实模型测试；未授予该权限的 HR 和接口人菜单、路由和接口均不可见/不可调用。运行时完全不读取任何环境变量或部署文件中的模型连接信息。未保存 API Key 时 AI 未启用。profile 注册表只为配置表单提供模板。API Key 仅允许写入，读取接口永不返回明文或密文；服务端使用由 Django `SECRET_KEY` 派生的 Fernet 密文存入 `Config`。界面只展示稳定错误码与脱敏摘要，不泄露 Key；AI 运行异常只记录稳定错误码和脱敏摘要；第三方 SDK 原始异常绝不进入 AI 决策、API 响应或日志，后端/worker 日志仅记录 profile、model、api_style、错误码和异常类型，运维通过 Docker logs 排查。
- 数据进入同一数据池，不引入批次概念；按 `imported_at` 等时间标签筛选。
- 简历库支持按上传记录的单级撤销：后端先解析本次上传影响的业务键，并只为受影响的候选人/投递范围保存该上传记录的一份快照及本次上传关联处理完成后的流程版本基线；快照覆盖候选人、投递、简历画像、候选人流程、AI 决策、分配尝试和转派历史。HR 只能查询和撤销本人上传记录，管理员可查看和撤销全部上传；同一上传记录只能撤销一次。撤销时锁定全部受影响候选人的流程并比较版本，任一候选人已有后续变更即整体返回 `409`，不做部分回滚。关联处理任务仍在运行时同样返回 `409`；相关 `ProcessingRun` 作为操作审计保留，但标记为已撤销。
- 候选人删除只允许用于尚未产生受保护历史的数据维护。存在任何分配尝试、反馈、AI 决策或转派历史时，后端必须拒绝删除并返回明确原因。
- “清空重导”不得硬删除已有候选人流程、反馈或审计历史；候选人/投递继续按业务键增量并入，主数据 replace 采用停用或更新语义。确需清空测试数据应使用仅限空环境或明确运维授权的独立工具，不作为普通导入模式。
- 工程交付物包括数据库字段表 + UML 类图、前后端接口文档、4+1 架构视图、Docker Compose 部署。
- 数据隐私与合规（手机号等个人信息是否脱敏、留痕）待确认。
