# 智能简历筛选系统 — 需求描述

> 本文是业务需求源头，描述系统要解决什么问题、有哪些角色、输入输出、核心流程和业务规则。后端实现见 `docs/后端设计.md`，数据库模型见 `docs/数据库设计.md`，前端页面与交互见 `docs/前端设计.md`。

## 一、目标与范围

建设网页版校招简历筛选系统，核心流程为：

`查重与志愿排序 → 简历分类、分配与下发`

院校分类和需求录入是分配前置数据准备，可提前独立维护。简历分配与下发策略支持 **Rule / AI（Agent）** 两种模式，由 HR 选择运行。每次处理规模约 **3 万条**简历。

项目采用 vibe coding，不安排固定排期。

系统需要支持：

- 4 张业务表和简历包导入。
- 候选人按人聚合，一名候选人可有多条投递。
- 当前有效志愿展示与按志愿顺序推进分配。
- Rule / AI 策略分配，AI 低置信度进入 HR 复核。
- HR 下发、二级接口人转派、三级接口人反馈。
- 归档候选人查看和 HR 手动强制分配。
- 用户、角色、权限配置。
- 各环节结果查看、筛选、导出。

## 二、输入件

| 文件 | 关键字段 |
| ---- | -------- |
| 简历信息列表（xlsx / xls / csv） | 招聘主体、所属机构、姓名、应聘ID、手机号、性别、对外职位名称、学历、第一学历毕业院校、最高学历毕业院校、最高学历专业、应聘状态、户口所在地、应聘日期 |
| 校招岗位分类及专业要求（xlsx / xls / csv） | 主体、一层/二层部门、岗位类别、对外发布名称、是否对外发布、职位名称、岗位族、工作地点、学历、需求专业、需求数量 |
| 院校分类（xlsx / xls / csv） | 学校、平台/院校标签、所在省份（如有） |
| 部门接口人信息（xlsx / xls / csv） | 序号、招聘主体、一层/二层/三级部门、姓名、工号、接口人层级/权限 |
| 简历包 | 命名格式 `姓名（应聘ID）`，如 `张三（12345）`；简历格式统一为 PDF |

身份口径：

- **规范化姓名 + 规范化手机号** 是候选人归并依据。
- **应聘ID** 是投递维度业务键。
- 手机号缺失的候选人直接舍弃，不入库、不进入分配，并在导入结果中提示。
- 部门接口人文件中的“招聘主体”是外部来源字段，不落为部门或接口人的主体归属；部门主数据只维护组织层级，招聘主体保留在投递、岗位需求等业务记录上。

## 三、业务对象口径

### 候选人与投递

同一位同学可多次投递，单主体最多 2 个岗位，跨两主体最多 4 个岗位。`应聘ID` 按投递唯一，不能标识人，因此业务上区分：

- **Candidate（候选人 / 同学）**：按规范化姓名 + 规范化手机号归并。
- **Resume（投递 / 应聘）**：一条记录对应一个应聘ID，挂在某个候选人下。

展示口径：

- 简历库主列表按 `Candidate` 聚合，一名候选人只显示一行。
- 候选人详情展示该候选人的全部投递、志愿顺序、分配尝试和反馈结果。
- 主列表只展示当前有效志愿：初始展示第一志愿；当前志愿被三级接口人反馈未通过后，再展示下一志愿；已通过候选人展示通过志愿；已归档候选人展示最后处理志愿与归档原因。

招聘主体口径：

- 招聘主体如 GW / YLS 是主数据，不作为自由文本散落在投递和岗位需求中。
- 当前统一使用 `code` 作为主体标识和展示值。
- 部门与招聘主体不建立“属于”关系。

字典口径：

- `JobCategory`（岗位类别）保留 `code + name`，供岗位需求、简历分类、Rule/AI 分配和前端筛选引用。
- `SchoolTag`（院校标签）保留 `code + name`，供学校、候选人打标和院校准入规则引用。
- `School` 只保存学校名称、`province` 和院校标签引用；不保存南北归属，不维护南北省份字典。

## 四、前置数据准备

### 院校分类

用户需求：

- 按第一学历、最高学历对照院校清单打标签。
- 不在清单或学校未配置标签时，可使用默认院校标签。
- 院校分类可在简历分配前提前运行；院校清单更新后也可独立重跑。
- 输出候选人的第一学历标签、最高学历标签，作为分配准入规则输入。

规则边界：

- 院校只存所在省份 `province`。
- 南北归属仅在志愿排序规则运行时判断，不落库、不作为配置项维护。

### 需求录入

用户需求：

- 将校招岗位分类及专业要求整理成结构化岗位需求。
- 维护岗位、部门、岗位类别、需求专业、需求数量等分配前置数据。
- 需求录入可在简历导入前提前维护；岗位需求、专业要求、二级/三级部门接口人更新后可独立重跑或手工维护。

## 五、候选人处理主流程

### Step1 查重与志愿排序

需求：

- 按 `Candidate` 聚合一个人的全部投递。
- 单一主体每人最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各投 2 个时，统一标第一至第四志愿。
- 排序规则：户籍北方优先 GW，南方优先 YLS；户籍缺失时按学校所在地同规则。
- 户籍或学校所在省份的南北判断只在规则运行时计算，不落库。

输出：

- 候选人维度的志愿排序结果。
- 主列表展示当前有效志愿，详情展示完整投递清单。

### Step2 简历分类、分配与下发

需求：

- 以候选人为粒度推进分配，一个候选人一个当前流程。
- 自动分配按志愿顺序依次尝试。第一志愿未反馈前，主列表和流程只暴露第一志愿；反馈未通过后，系统生成下一志愿尝试。
- HR 可选择 **Rule** 或 **AI（Agent）** 策略。两种策略都完成岗位分类、岗位/部门匹配、分配尝试生成，并进入同一套候选人工作流。
- HR 可配置院校标签准入规则。存在启用规则时，Rule 与 AI 策略都必须先命中同一条启用规则，即第一学历标签和最高学历标签同时满足该规则；没有启用规则时，视为不做准入过滤，候选人全部通过该条件。
- AI 只优化简历理解、岗位适配和分流判断，不绕过院校准入、志愿顺序、反馈锁定等硬规则。
- AI 策略读取 PDF 简历，提取项目经历、实习经历、技能栈、专业方向等信息，并结合当前志愿岗位、岗位需求专业和部门信息生成建议。
- AI 推荐版的第一版定位是“受硬规则约束的分流建议器”：AI 只处理候选人的当前有效志愿，不主动跨志愿跳转；系统先做硬规则检查，再调用 AI 生成岗位/部门/接口人建议。
- AI 结果必须可审查，包含推荐动作、推荐岗位/部门/接口人、置信度、分项评分、推荐理由、简历证据和风险点。

AI 阈值：

- `ai_dispatch_threshold` 默认 `0.75`。
- `ai_review_threshold` 默认 `0.5`。
- `recommendation=dispatch` 且 `confidence_score >= 0.75`：生成 `source=ai, pending_dispatch` 的待下发尝试。
- `recommendation != archive` 且 `confidence_score >= 0.5`，但未达到自动下发条件：生成 `source=ai, pending_review` 的 HR 复核项，不自动下发。
- `recommendation=archive`、`confidence_score < 0.5` 或简历缺失/解析失败：只生成 AI 决策记录，建议归档或人工处理，不生成分配尝试。
- AI 失败、超时、解析失败、输出不合法、推荐对象不存在或被硬规则拦截时，不自动回退 Rule，由 HR 选择重试 AI、切换 Rule 或手动强制分配。

分配和反馈：

- HR 将待下发尝试下发至二级部门接口人，支持单条、勾选批量、当前筛选全部下发。
- 二级接口人只能在本二级部门范围内选择下属三级接口人并转派。
- 三级接口人反馈通过/未通过并可填写备注；反馈提交后锁定，不允许二次修改。
- 三级反馈通过后，候选人流程结束，并取消该候选人其他未反馈尝试。
- 三级反馈未通过后，系统自动进入下一志愿；志愿耗尽则归档。
- HR 可从任意投递发起手动强制分配，绕过院校规则、志愿顺序和自动筛选条件；已通过候选人不可再强制分配。
- 手动强制分配可选择二级接口人或三级接口人。选择二级接口人时进入待下发/已下发二级流程；直接选择三级接口人时进入待三级反馈流程，并记录对应转派历史。

归档口径：

- 志愿耗尽、未命中院校规则、找不到岗位、找不到部门、找不到接口人、AI 无有效建议、全部志愿未通过等情况进入归档。
- 归档候选人独立展示，按候选人粒度展示归档原因和志愿概览，并允许 HR 从具体应聘ID发起手动强制分配。

输出：

- 候选人工作流清单。
- 分配尝试清单。
- 归档候选人清单。
- 候选人简历文件导出，支持单条、勾选批量、按筛选全部。

## 六、用户与权限

角色：

- **HR**：全流程操作，包括导入、处理、下发、手动分配、导出和查看反馈。
- **二级部门接口人**：查看 HR 下发给自己的尝试，并转派给本部门下属三级接口人。
- **三级部门接口人**：查看转派给自己的尝试，并提交通过/未通过反馈。
- **管理员**：系统配置、用户、角色、权限管理。

权限要求：

- 权限管理采用 RBAC。
- 用户可绑定一个或多个角色。
- 角色绑定权限点，权限点覆盖菜单入口、页面查看、按钮操作、导出、下发、转派、反馈、系统配置等能力。
- 前端需要支持用户、角色、权限配置。
- 权限点由系统预置为树形清单，前端只允许勾选绑定，不允许随意新增未知权限码。
- 数据范围不单独建表，由角色权限、接口人绑定和部门关系推导。
- 前端权限控制只负责体验和误操作拦截，后端必须做接口级鉴权和数据过滤。
- 导入部门接口人信息时，系统按接口人工号自动创建或更新接口人登录账号：用户名使用工号，新账号默认密码为 `pass1234`，并按接口人层级绑定二级/三级接口人角色及对应 `Contact`。
- 已有同工号账号保留原可用密码和非接口人业务角色，仅替换二级/三级接口人角色；部门接口人 replace 导入时，本次文件中不存在的旧接口人及其账号停用。
- 用户管理不单独维护姓名字段，不展示/编辑/同步 `first_name`、`last_name` 等 Django 姓名类字段；接口人身份展示以绑定的 `Contact.name` 为准。

登录认证：

- 本地正式开发阶段使用系统账号密码登录，后端签发 Token，登录后按 RBAC 权限点和接口人绑定推导数据范围。
- 系统账号已通过用户、角色、权限和接口人绑定映射 HR、管理员、二级接口人、三级接口人等身份。
- 公司 W3 认证仍待外部方案确认；接入后按工号识别登录用户，并只替换外部身份到系统 `User.username` 的适配层，RBAC、Contact 绑定和 `/api/me/` 消费口径保持不变。

## 七、系统需求

- 上传简历后自动触发候选人处理主流程，并展示进度。
- 切换 Rule / AI 策略后，只重算“简历分类、分配与下发”环节，不重跑查重排序、院校分类和需求录入。
- 各步中间结果可查看、筛选、导出。
- Rule 与 AI 结果需要支持对比视图，便于人工核对。
- 3 万条规模下，AI 处理允许分批产生结果，前端可边跑边查看待下发、待复核、失败和建议归档数量。
- 可配置项集中管理，包括院校标签准入规则、AI 阈值、AI 超时、AI 并发、AI 重试次数、AI 重试退避、WeLink 开关等非敏感运行参数。
- 大模型供应商、模型名、API Key 所在环境变量名、Base URL 所在环境变量名、提示词版本和决策版本由后端配置文件抽象并从环境变量读取；API Key 不落库、不进前端、不通过普通配置 API 返回。
- 数据进入同一数据池，不引入批次概念；按 `imported_at` 等时间标签筛选。
- 简历库支持单级撤销：上传含简历数据前保存最近一份快照，撤销后回到上传前状态并清除快照。
- 工程交付物包括数据库字段表 + UML 类图、前后端接口文档、4+1 架构视图、Docker Compose 部署。
- 数据隐私与合规（手机号等个人信息是否脱敏、留痕）待确认。
