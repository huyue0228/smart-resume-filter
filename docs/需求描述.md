# 智能简历筛选系统 — 需求描述

> 本文是业务需求源头，描述系统要解决什么问题、有哪些角色、输入输出、核心流程和业务规则。后端实现见 `docs/后端设计.md`，数据库模型见 `docs/数据库设计.md`，前端页面与交互见 `docs/前端设计.md`。

> 文档分工：本文只定义业务目标、业务规则和验收边界；算法、状态流转和 API 以后端设计为准，字段与删除策略以数据库设计为准，页面与按钮以前端设计为准。四份核心设计文档保持分立，不通过复制整段实现细节互相替代。本文描述目标设计；当前落地状态统一在 `docs/前端设计.md` 的“实现状态速览”和各文档“待实现与风险”段标注。

## 一、目标与范围

建设网页版校招简历筛选系统，核心流程为：

`Step1 查重与志愿排序 → Step2 院校分类及学历/院校准入 → Step3 Rule 前置检查 → Step4 AI 深度筛选（仅 AI 模式）`

岗位需求、部门和接口人维护是分配前置基础数据，不占用编号步骤。Rule 模式执行 Step1–Step3，AI 模式执行 Step1–Step4；简历库人工“处理简历”从 Step2 开始，不重复查重。上传简历和人工“处理简历”都在提交时明确选择 **Rule / AI（Agent）** 中的一种模式；Rule 始终可选，只有当前完整模型连接配置已经真实测试成功时才可选择 AI。系统不设置全局 AI 分配开关。AI 入口只有在真实模型调用、结构化输出、异常处置和禁止 Rule 回退均通过验收后，方可作为生产能力。每次处理规模约 **3 万条**简历，但本轮不包含 3 万条压测。

> **本轮范围边界**：本轮实施 Rule-first 工作流、备份/恢复/灾备和招聘分析。worker heartbeat 超时检测与安全恢复、Prometheus/集中日志/告警、3 万条压测、CI 和浏览器 E2E 均不在本轮实施或验收范围。备份工具只输出可被 Prometheus 读取的文本状态，不代表本轮部署了监控或告警栈。

项目采用 vibe coding，不安排固定排期。

系统需要支持：

- 4 张业务表和简历包导入。
- 候选人按人聚合，一名候选人可有多条投递。
- 当前有效志愿展示与按志愿顺序推进分配。
- Rule-first 分配：先完成学历、院校、当前志愿岗位、二级部门和二级接口人等确定性规则，再把通过者交给 AI 深度判断。AI 不重复判断学历、院校、志愿顺序、岗位存在性、部门归属或接口人选择。
- HR 下发、二级接口人转派、二级转派前或三级转派后按权限反馈。
- 简历库归档筛选和 HR 手动强制分配。
- 用户、角色、权限配置。
- 仅管理员和 HR 默认可见的招聘分析看板，侧栏名称为 `DashBoard`，位于所有业务导航之前并作为登录首页，按导入 cohort 查看转化、耗时、结构与原因分布。
- PostgreSQL 与简历文件的加密增量备份、受保护恢复和隔离灾备演练。
- 各环节结果查看、表头筛选、分页、简历预览和导出；所有数据表格均支持拖拽调整列宽，可筛选业务列在表头提供文本或单选/多选选择器。

## 二、输入件

| 文件 | 关键字段 |
| ---- | -------- |
| 简历信息列表（xlsx / xls / csv） | 招聘主体、所属机构、姓名、应聘ID、手机号、性别、对外职位名称、学历、第一学历毕业院校、最高学历毕业院校、最高学历专业、应聘状态、户口所在地、应聘日期 |
| 校招岗位分类及专业要求（xlsx / xls / csv） | 主体、一层/二层部门、岗位类别、对外发布名称、是否对外发布、职位名称、岗位族、工作地点、学历、工作职责、需求专业、需求数量 |
| 院校分类（xlsx / xls / csv） | 学校、平台/院校标签、所在省份（如有） |
| 部门接口人信息（xlsx / xls / csv） | 序号、招聘主体（仅兼容外部文件识别，导入后丢弃）、一层/二层/三级部门、姓名、工号、接口人层级/权限 |
| 简历包 | 命名格式 `姓名（应聘ID）`，如 `张三（12345）`；简历格式统一为 PDF |

身份口径：

- **规范化姓名 + 规范化手机号** 是候选人归并依据。
- **应聘ID** 是投递维度业务键。
- 手机号缺失的候选人直接舍弃，不入库、不进入分配，并在导入结果中提示。
- 部门接口人文件中的“招聘主体”仅用于兼容外部文件和辅助识别文件类型，导入后丢弃；不落为部门或接口人的主体归属或“主体来源”字段，也不提供相关筛选。部门主数据只维护组织层级，招聘主体保留在投递、岗位需求等业务记录上。

## 三、业务对象口径

### 候选人与投递

同一位同学可多次投递，单主体最多 2 个岗位，跨两主体最多 4 个岗位。`应聘ID` 按投递唯一，不能标识人，因此业务上区分：

- **Candidate（候选人 / 同学）**：按规范化姓名 + 规范化手机号归并。
- **Resume（投递 / 应聘）**：一条记录对应一个应聘ID，挂在某个候选人下。

展示口径：

- 简历库主列表按 `Candidate` 聚合，一名候选人只显示一行，是 HR 查看候选人当前流程、归档信息和主数据缺口的候选人级主入口。
- HR/管理员的候选人详情展示手机号、全部投递、志愿顺序、分配尝试、匹配/手动理由和反馈结果；第一学历标签和最高学历标签以彩色标签显示在各自院校名称旁边。简历库主列表不展示手机号。接口人详情只展示本人可见尝试及其关联投递，不返回手机号、其它志愿、其它尝试或 AI 决策。
- 主列表只展示当前有效志愿：初始展示第一志愿；当前志愿被有权的当前阶段接口人反馈未通过后，再展示下一志愿；已通过候选人展示通过志愿；已归档候选人展示最后处理志愿与归档原因；当前志愿已匹配岗位和二级部门但缺可用二级接口人时，展示当前志愿和阻塞原因，不切换下一志愿。
- 简历库支持按姓名、姓名全拼、姓名拼音首字母、最高学历专业、当前志愿、当前应聘ID、招聘主体、当前岗位、岗位部门、岗位类别、院校标签、简历状态、原因类型等主表字段筛选；简历状态支持表头勾选多选，筛选在后端执行并参与分页和“导出当前筛选全部”。当前应聘ID和三级接口人保留为可选列但默认隐藏，用户可通过列选择器开启；主表不展示流程状态、分配状态或操作列，也不提供对应表头筛选。原因列截断显示，鼠标悬浮时展示完整原因。
- 简历库主列表和候选人详情都必须展示候选人的最高学历专业；该字段来自简历信息列表中的“最高学历专业”，落在 `Candidate.highest_major`，不从当前投递的岗位类别反推。候选人最高学历另取简历信息列表的“学历”列，规范化为 `associate / bachelor / master / doctor`（大专 / 本科 / 硕士 / 博士）；同一文件内同一候选人出现多个已识别值时取最高值，空值或未知值不覆盖已有有效学历。
- 院校标签在简历库、候选人详情、院校清单、院校标签字典和院校准入规则中使用统一彩色标签展示；同名标签颜色保持一致，不同标签使用不同颜色。
- 候选人详情支持预览该候选人的 PDF 简历；预览时必须先通过后端鉴权 API 获取 PDF Blob 和原始文件名，再由前端 PDF.js 渲染到 canvas，不直接暴露静态文件地址。无权限或越权时不可预览且不提供下载入口；PDF 渲染失败或非 PDF 文件时，可下载原文件。候选人删除只作为数据维护能力；仅存在尚未产生历史的空 `CandidateWorkflow` 时允许随候选人一并清理，存在分配尝试/反馈、AI 决策或转派历史中的任一项时必须禁止删除，并返回受保护历史类型。

简历状态是简历库面向 HR 的统一展示态，由投递、分类、分配尝试和反馈记录推导，不覆盖导入文件中的原始“应聘状态”字段；内部状态码保持不变：

- **待处理**：原始导入后尚未完成岗位类别和院校标签分类的候选人/当前投递。
- **已分类**：已完成岗位类别和院校标签分类，但尚未形成有效业务部门推荐。
- **已分配**：已形成业务部门推荐或 HR 待复核/待下发尝试，尚未下发给业务部门筛选。
- **待筛选**：已下发或转派给业务部门，尚未反馈筛选结果。
- **通过**（`screening_passed`）：业务部门反馈通过。
- **不通过**（`screening_rejected`）：业务部门反馈未通过；若仍有下一志愿，系统可继续推进下一志愿。

招聘主体口径：

- 招聘主体如 GW / YLS 是主数据，不作为自由文本散落在投递和岗位需求中。
- 当前统一使用 `code` 作为主体标识和展示值。
- 部门与招聘主体不建立“属于”关系。

字典口径：

- `JobCategory`（岗位类别）保留 `code + name`，供岗位需求、简历分类、Rule/AI 分配和前端筛选引用。
- `SchoolTag`（院校标签）保留 `code + name`，供学校、候选人打标和院校准入规则引用。
- `School` 只保存学校名称、`province` 和院校标签引用；不保存南北归属，不维护南北省份字典。

## 四、前置数据准备

### 院校分类

用户需求：

- 按第一学历、最高学历对照院校清单打标签。
- 系统预置并保证存在编码为 `NON_TARGET` 的“非目标院校”标签。学校不在导入院校清单内时，第一学历和最高学历**始终**使用该标签；只有学校已在清单内但未配置标签时，才使用启用的默认院校标签，若无默认标签则使用“非目标院校”。
- 每次候选人处理都在 Step2 按当时院校清单完整重算并固化第一学历、最高学历标签，同时执行学历和院校准入；Step3/Step4 不得补充、覆盖或重新判断院校标签。
- 院校清单更新后，通过简历库“处理简历”从 Step2 重新处理选定范围；不再保留一个会绕开后续规则的独立院校分类步骤。

规则边界：

- 院校只存所在省份 `province`。
- 南北归属仅在志愿排序规则运行时判断，不落库、不作为配置项维护。

### 需求录入

用户需求：

- 将校招岗位分类及专业要求整理成结构化岗位需求。
- 维护岗位、部门、岗位类别、工作职责、需求专业、需求数量等分配前置数据；工作职责保存完整原文。
- 需求录入可在简历导入前提前维护；岗位需求、专业要求、二级/三级部门接口人更新后可独立重跑或手工维护。
- 岗位需求页面支持新增、编辑和删除岗位；新增或编辑岗位时工作职责必填，并支持在列表展示和文本筛选。“对外名称”和“职位名称”的表头筛选使用支持拼音搜索的多选选择器，并按所选项精确筛选；删除采用失效/停用语义，不破坏历史投递和分配尝试中的岗位引用。
- 岗位表导入按行校验工作职责：缺少工作职责的有效岗位行跳过并在响应中返回数量、Excel 行号和稳定警告码 `job_responsibility_missing`，其余有效行正常导入。清空重导文件若没有任何有效岗位，不得清空现有岗位。
- 系统内置一版专业大类映射词表，并允许 HR/管理员在配置项中维护专业大类、专业别名和关键词。该词表仅用于 Rule 模式 Step3 的确定性专业匹配；AI 模式 Step3 不执行专业词表匹配，Step4 直接根据简历正文中的专业实际方向、项目、实习和技能评估当前固定岗位，避免重复判断。

## 五、候选人处理主流程

### Step1 查重与志愿排序

需求：

- 按 `Candidate` 聚合一个人的全部投递。
- 单一主体每人最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各投 2 个时，统一标第一至第四志愿。
- 排序规则：户籍北方优先 GW，南方优先 YLS；户籍缺失时按学校所在地同规则。
- 户籍或学校所在省份的南北判断只在规则运行时计算，不落库。

输出：

- 候选人维度的志愿排序结果。
- 主列表展示当前有效志愿，详情展示完整投递清单。

### Step2 院校分类与学历/院校准入

需求：

- 院校标签在本阶段按当前院校清单完整重算并固化，同时完成学历准入和院校准入。后续 Rule 和 AI 只能读取，不得补充、修改或重新判断院校标签。
- HR 可配置院校标签准入规则。存在启用规则时，Rule 与 AI 策略都必须先命中同一条启用规则，即“第一学历标签 AND 最高学历标签 AND 允许最高学历”同时满足该规则；多条启用规则之间继续 OR。每条规则的允许最高学历为精确多选集合，未配置表示“不限制并保持旧规则行为”；一旦配置，最高学历为空、无法识别或不在集合内都不通过。没有启用规则时视为不做准入过滤。
- 学历或院校不符合时结束本轮候选人处理并记录 `education_not_eligible` 或 `school_not_eligible`，属于已经得到明确业务结果的 `completed`，不计系统失败。

### Step3 Rule 前置检查

需求：

- 以候选人为粒度推进分配，一个候选人一个当前流程。Step3 只处理 `CandidateWorkflow` 确定的当前有效志愿；该志愿未反馈前不暴露或跳过到后续志愿，反馈未通过后再推进下一志愿。
- 用户在上传或处理简历时选择 **Rule** 或 **AI（Agent）** 策略，单次任务只使用一种策略；AI 选项仅在当前连接配置已通过真实测试时可用，后端仍需在提交时再次校验。
- Rule 策略在院校准入通过后，对当前有效志愿依次执行“岗位匹配 → 专业确定性匹配 → 二级部门检查 → 二级接口人检查”。投递招聘主体与岗位需求主体双方都有值时必须一致；岗位名匹配按同主体优先、精确优先、对外发布名称优先于职位名称、包含匹配兜底的稳定顺序选择岗位。岗位配置需求专业时，先用启用的专业别名将候选人最高学历专业和岗位需求专业映射到专业大类；任一大类相交则专业通过。若大类无交集，或候选人/岗位任一侧未映射到启用大类，则再执行专业名双向包含兜底；词表和兜底都不命中时记录 `major_not_matched`。岗位未配置需求专业，或岗位需求专业为“专业不限 / 不限 / 不限专业”等通配表达时，直接放行。自动分配尝试需记录院校、志愿、岗位、专业大类/专业名、部门和接口人的匹配理由。
- 原因必须区分 `job_not_found`、`major_not_matched`、`secondary_department_missing` 和 `secondary_contact_missing`。这些规则未通过都属于 `completed`，不得记为任务失败。
- AI 模式只按当前有效志愿依次检查岗位、有效二级部门和启用二级接口人，不执行专业确定性匹配；通过后把当前志愿、岗位、二级部门和二级接口人引用固定到运行明细。缺任一前置主数据时不调用模型，并以对应业务原因结束处理。

### Step4 AI 深度筛选与分配

需求：

- AI 只优化规则无法稳定覆盖的专业实际方向、项目、实习、技能与岗位实质匹配、补充优势和风险，不绕过院校准入、志愿顺序、反馈锁定等硬规则。
- Step4 读取 PDF 简历并使用 Step3 固定的岗位、部门和接口人。`current_job` 输入包含当前岗位完整保存职责清洗后的前 12,000 个字符，并要求在既有 `job_requirement` 评分中结合简历项目、实习和技能判断职责覆盖度；工作职责按不可信业务数据处理，提示词必须忽略其中任何改变任务或输出协议的指令。该调整使用 `resume-screening-v2` 提示词版本，继续沿用现有 AI 输出 schema 和五项评分权重，不增加独立“职责评分”字段。模型输入不含岗位、部门或接口人数据库 ID；当前岗位上下文不发送学历要求，当前志愿上下文只发送 `position_name`，不发送 Resume/应聘 ID、志愿序号或招聘主体标识。输出只含推荐结论、置信度、理由、证据、风险和 AI 专项人才判断；`ResumeProfileOutput` 不接受学历字段，不允许模型解析或覆盖 Step2 的学历/院校结论，也不允许模型选择或改荐岗位、部门、接口人。
- 历史岗位允许工作职责为空以保证旧数据可读，Rule 模式不受影响；但 AI Step4 在抽取简历或调用模型之前必须停止该候选人，记录 `needs_attention + job_responsibility_missing`，由 HR 补齐岗位职责后重新处理。
- AI 专项人才判断单独返回 `ai_specialist_match / ai_specialist_confidence / ai_specialist_evidence`，识别智能体、大模型、训练/推理、RAG、微调和模型评测等实质项目、实习或技能。证据必须能在提取正文中定位，专项匹配成立且置信度严格大于配置阈值（默认 0.90）时，才按配置的父级二级接口人和固定三级接口人执行与人工强制分配相同的两段分配链路。功能默认关闭；目标停用、上下级关系失效或配置缺失时进入“需处理”，不得静默回退普通分配。
- AI 正文抽取优先使用 `pypdf`；去除空白后正文不足 50 字符时，才用 PyMuPDF 将 PDF 渲染为图片并交给本地 Tesseract `chi_sim+eng` 做中英文 OCR。OCR 默认最多处理 20 页、200 DPI、总超时 120 秒，且单 worker 最多并发 2 个 OCR，均允许部署环境覆盖。OCR 成功后正文继续写入 `ResumeProfile.raw_text`，解析器版本为 `pypdf-ocr-v2` 并记录 `ocr_fallback` 风险标记；OCR 仍失败时内部抽取错误可记为 `pdf_parse_failed`，但候选人级统一映射为 `needs_attention + resume_text_unavailable`，且绝不回退 Rule。该回退只服务 AI 简历正文抽取，不改变 PDF 预览、下载或原文件保存流程。
- PDF 抽取正文和模型结构化输出中的字符串在写入简历画像或 AI 决策前必须递归移除 NUL（`0x00`）字符；AI 服务产生且可持久化的受控错误消息做相同兜底，避免 PostgreSQL `text/jsonb` 拒绝写入。除 NUL 外不得改写其它业务文本字符，不保存模型完整原始响应，也不为此新增数据库字段或迁移。
- AI 推荐版的第一版定位是“受硬规则约束的分流建议器”：AI 只处理当前有效志愿和预先固定的单一目标岗位，不主动跨志愿或改荐其它岗位。
- AI 结果必须可审查，包含推荐动作、置信度、分项评分、推荐理由、简历证据、风险点和专项人才判断；岗位、部门和接口人来自 Step3 固定引用，不属于模型输出。

AI 阈值：

> AI 能力必须按以下正式口径验收。AI 连接不可用时必须写入明确异常决策并映射为 `needs_attention + ai_connection_error`，不得通过复用 Rule 结果、固定置信度或元数据拼接伪装成可用的 AI 结论。

- `ai_dispatch_threshold` 默认 `0.75`。
- `ai_review_threshold` 默认 `0.5`。
- `recommendation=dispatch` 且 `confidence_score >= ai_dispatch_threshold`：生成 `source=ai, pending_dispatch` 的待下发尝试。
- `recommendation != archive` 且 `confidence_score >= ai_review_threshold`，但未达到自动下发条件：生成 `source=ai, pending_review` 的 HR 复核项，不自动下发。
- `recommendation=archive` 或 `confidence_score < ai_review_threshold`：只生成 AI 决策记录，不生成分配尝试，作为 `completed` 的明确业务建议归档。简历正文不可用、AI 连接/认证、429、输出协议和引用失效按对应 `needs_attention` 原因保留给 HR；`llm_timeout` 单独计入 `failed`。AI 决策保留在简历库详情和 API 中，HR/管理员可重试 AI、改用 Rule、手动强制分配或归档。
- 候选人处理结果统一为 `completed / needs_attention / failed / cancelled`。学历或院校不符合、无匹配岗位、缺二级部门、缺二级接口人、Rule 专业不匹配、Rule/AI 分配成功以及 AI 建议归档/待复核均为 `completed`；岗位缺少工作职责、简历正文不可用、AI 连接/认证、429、输出协议、运行中引用失效和专项分流配置失效为 `needs_attention`；本轮只有 `llm_timeout` 计入 `failed`。所有 AI 异常都不自动回退 Rule，HR 可按权限重试、改用 Rule、人工强制分配或归档。

分配和反馈：

- HR 将待下发尝试下发至二级部门接口人：单条下发在候选人详情中执行；勾选任意候选人后才显示批量操作条，其中支持“下发选中”和“当前筛选全部下发”。
- `pending_dispatch` / `pending_review` 等 HR 待处理尝试不对二级接口人展示；二级接口人只看到 HR 已下发给自己的简历尝试。
- 二级接口人只能在本二级部门范围内选择下属三级接口人并转派。
- 提交反馈由 `attempt.feedback` 权限、当前阶段和接口人绑定共同控制，不由角色名称硬编码：二级接口人仅在本人接收的 `dispatched_l2` 尝试尚未转派时可反馈；转派后该二级接口人不再可提交，避免与三级接口人竞争；三级接口人仅可对本人被转派且状态为 `assigned_l3` 的尝试反馈。
- 反馈结果为通过/未通过并可填写备注；反馈提交后锁定，不允许二次修改。`attempt.feedback` 只授予操作能力，不扩大数据可见范围，用户仍须具备对应的本人接收或本人被转派查看权限。
- 任一允许阶段反馈通过后，候选人流程结束，并取消该候选人其他未反馈尝试；反馈未通过后，系统自动进入下一志愿，志愿耗尽则归档。
- HR 点击简历库“处理简历”后，弹窗固定展示七个选项：`当前选中（N）`、待处理、已分类、已分配、待筛选、通过、不通过。`当前选中`始终由用户手动勾选，不因页面已有选择而默认勾选；`N=0` 时仍显示但禁用。`当前选中`与六种状态互斥，状态之间支持多选。打开弹窗时即冻结当时选中的候选人 ID 和数量，确保展示与最终提交一致。
- 选择 `当前选中` 时，不考虑候选人当前状态，不叠加简历状态、表头筛选或任务结果筛选，仅以 `scope={"candidate_ids":[...],"force_reprocess":true}` 重新执行 Step2。该请求表示 HR 主动重开：清空当前通过指针、归档/阻塞结果和完成时间，取消尚未反馈的自动尝试，保留历史尝试、反馈和 AI 决策，再按本次提交时选择并固化的 Rule / AI 模式处理。提交后发生人工修改时，仍以 workflow revision 保护安全跳过。选中范围提交成功后清空页面勾选。
- 选择一个或多个简历状态时，仍以 `scope.system_statuses + scope.candidate_filters` 与当前表头、任务结果筛选相交，只重跑命中候选人的 Step2；本次请求必须显式提交唯一 `mode`，不得提交 `modes`。Step2 对范围内候选人的院校标签执行完整重算和准入，不把标签补写推迟到后续步骤。普通简历导入使用的 `candidate_ids + source=resume_import` 不表示强制重开，不重开已通过等终态流程。
- 自动处理任务创建时固化候选人范围及当前流程版本；不同候选人可并行处理，同一候选人的自动和人工流程写操作统一串行。后发任务遇到冲突时进入等待并重试；人工下发、转派、反馈、手动分配等操作优先完成，自动任务发现流程版本已变化时安全跳过并记录 `skipped_manual_change`，不覆盖人工结果。
- HR 可从任意投递发起手动强制分配，绕过院校规则、志愿顺序和自动筛选条件；已通过候选人不可再强制分配。手动强制分配与简历库“处理简历”是两个入口：前者不允许重开已通过候选人，后者可通过手动勾选 `当前选中` 对冻结 ID 执行强制重开，或勾选简历状态后按筛选范围重新处理。
- 手动强制分配可选择二级接口人或三级接口人。选择二级接口人时进入待下发/已下发二级流程；直接选择三级接口人时，系统必须校验其所属三级部门存在有效父级二级部门：只有一个有效二级接口人时自动补齐，存在多个时由 HR 明确选择，随后进入待三级反馈流程，并记录“HR 到二级、二级到三级”两段转派历史。没有有效父级二级接口人时禁止直达三级。

归档口径：

- 志愿耗尽、学历/院校不符合、岗位不存在、专业不匹配、缺二级部门、缺二级接口人以及 AI 建议归档均可结束本轮自动处理；在处理中心一律按 `completed` 统计，并保留精确原因码，不得把这些配置或规则结果统计为模型失败。
- `needs_attention` 项保留当前候选人和原因，等待 HR 修复正文、AI 连接/认证/限流/协议、运行中引用或专项分流配置后处置；不得静默回退普通分配。
- 归档候选人不再作为 HR 独立列表入口；归档筛选、归档原因和从具体应聘ID发起手动强制分配统一合并到简历库。
- 简历状态按当前活动流程优先推导：`通过 > 待筛选 > 已分配 > 不通过 > 已分类 > 待处理`。历史志愿的不通过记录不得覆盖下一志愿已生成的待复核、待下发或待筛选状态。

输出：

- 简历库候选人主清单：合并展示当前志愿、当前投递、岗位部门、简历状态和分配/归档/阻塞原因；当前应聘ID和三级接口人作为可选列默认隐藏，原因截断显示并可悬浮查看全文。主表不展示流程状态或分配状态。
- 简历库是候选人分配与下发的唯一页面。主表展示当前有效 `AssignmentAttempt` 的实际来源（`rule` / `ai` / `manual`）、部门、二级/三级接口人和分配原因，但不展示尝试状态和操作列；没有有效尝试时，若 `CandidateWorkflow.started_at` 非空且 `dispatch_strategy` 为 `rule` / `ai`，包括 AI/Rule 的归档、失败和阻塞结果，也展示该自动策略；从未进入处理的待分配流程不展示来源。`allocation_source` 表头筛选必须使用完全相同的派生口径。单击候选人行直接打开详情。未勾选候选人时不展示下发、导出、删除等批量操作，勾选后在表格上方以滑入操作条按权限展示；下发和导出支持处理当前选中候选人或当前筛选全部，删除只处理当前选中候选人。单条下发、确认 AI 建议、转人工、取消、转派、反馈、导出和删除等动作统一进入详情执行。详情保留流程状态、全部投递及其应聘状态、历史尝试及其状态和 AI 决策。二级、三级接口人同样进入简历库，但后端只返回本人接收或被转派的候选人、对应尝试和关联投递，不返回手机号、其它志愿、其它尝试或 AI 决策。
- 任务中心主结果行固定展示处理完成、需处理、失败、跳过和取消，非零数字均可点击。AI 任务的“处理完成”旁可展开“待复核、待下发、建议归档”业务子项；子项合计允许小于处理完成总数，因为 Rule 前置结束项不会产生 AI recommendation。点击结果使用 `processing_run_id + processing_result`，候选人级结果按 ScopeItem 的 `result_type` 精确筛选，业务子项按本运行 AI 决策 recommendation 筛选；原因使用 `reason_code` 精确筛选。筛选参数变化时重新请求第一页并关闭旧详情，但保留页面勾选。
- 候选人简历文件预览和导出支持详情中单条执行、主表勾选批量执行和按当前筛选全部导出；预览时后端通过鉴权 API 返回 PDF Blob 和原始文件名，前端用 PDF.js 渲染到 canvas；详情默认预览当前投递的简历文件，当前投递无文件时回退到同候选人第一条有文件的投递，但不改变当前志愿展示口径；投递志愿表删除预览列，单击志愿行切换到对应简历，单击无文件志愿时显示该投递缺失提示而不保留上一份预览；无权限或越权时不可预览且不提供下载入口，PDF 渲染失败或非 PDF 文件时可下载原文件；仅命中一个可用简历文件且没有缺失清单时直接下载原文件，命中多个文件或存在缺失清单时下载 zip；无文件的候选人进入缺失文件清单，导出完成后前端展示成功导出数量和缺失数量。
- 简历库另为拥有 `resume.view` 的 HR/管理员提供按导入日期导出的结果报表。日期按 Asia/Shanghai 自然日闭区间筛选 `Resume.imported_at`，报表不受当前表头筛选影响；一条应聘ID只统计一次，并依据该投递自己的最新非取消分配尝试计算待处理、已分类、已分配、待筛选、通过、不通过之一，不复制候选人当前志愿状态。Excel 包含“部门汇总”和“简历明细”两张表：汇总按二级部门统计导入、分配及六种状态，包含“未分配”和合计行；明细包含导入时间、姓名、应聘ID、主体、岗位、志愿、最高学历、二三级部门和接口人、分配来源、状态、反馈结果与时间，不包含手机号。部门和接口人优先读取分配快照，关联主数据删除后仍可统计；所有外部文本均做 Excel 公式注入防护。

## 六、用户与权限

角色：

- **HR**：全流程业务操作，包括导入、处理、下发、手动分配、导出、查看反馈、查看招聘分析，以及维护获授权的院校准入、专业词表等业务规则。
- **二级部门接口人**：查看 HR 下发给自己的尝试，并转派给本部门下属三级接口人；获授 `attempt.feedback` 后可在转派前提交反馈。
- **三级部门接口人**：查看转派给自己的尝试；获授 `attempt.feedback` 后提交通过/未通过反馈。
- **管理员**：用户、角色、权限、认证与安全配置管理，也可维护业务规则。

权限要求：

- 权限管理采用 RBAC。
- 用户可绑定一个或多个角色。
- 角色绑定权限点，权限点覆盖菜单入口、页面查看、按钮操作、导出、下发、转派、反馈、系统配置等能力。
- 前端需要支持用户、角色、权限配置。
- 权限点由系统预置为树形清单，前端只允许勾选绑定，不允许随意新增未知权限码。
- 数据范围不单独建表，由角色权限、接口人绑定和部门关系推导。
- 前端权限控制只负责体验和误操作拦截，后端必须做接口级鉴权和数据过滤。
- 招聘分析使用独立权限 `analytics.view`，默认授予管理员和 HR；二级、三级接口人默认不可见且不可调用接口。
- 侧栏独立「处理任务」页面使用 `pipeline.view` 控制查看，默认授予管理员和 HR；创建处理任务和取消活跃任务继续要求 `pipeline.run`。二级、三级接口人默认不授予这两个权限，也不显示该导航项。
- 部门接口人页面的 WeLink 通知开关只对拥有 `department.manage` 的用户显示并允许操作；删除“系统参数”页签后，不在其它页面提供通用 Config 编辑入口。
- 导入部门接口人信息时，系统按接口人工号自动创建或更新接口人登录账号：用户名使用工号，新账号默认密码为 `pass1234`，并按接口人层级绑定二级/三级接口人角色及对应 `Contact`。
- 已有同工号账号保留原可用密码和非接口人业务角色，仅替换二级/三级接口人角色；部门接口人 replace 导入时，本次文件中不存在的旧接口人及其账号停用。用户管理或接口人清单中的单条删除采用清理语义：删除用户时清空该用户的 Token、角色绑定、接口人绑定等账号相关内容；若用户绑定了接口人，则同步删除该接口人。删除接口人时同步删除绑定该接口人的用户信息。历史分配、转派和 AI 决策不级联删除，只保留已有快照文本和审计记录，不再保留对已删除用户/接口人的外键引用。
- 用户管理不单独维护姓名字段，不展示/编辑/同步 `first_name`、`last_name` 等 Django 姓名类字段；接口人身份展示以绑定的 `Contact.name` 为准。
- 用户管理支持删除用户。删除用户采用账号清理语义，不只是停用：删除后该账号不可登录，不再出现在用户管理列表；若后续公司 W3 或接口人导入重新同步同工号账号，按新账号重新创建和绑定。

登录认证：

- 本地正式开发阶段使用系统账号密码登录，后端签发 Token，登录后按 RBAC 权限点和接口人绑定推导数据范围。
- 系统账号已通过用户、角色、权限和接口人绑定映射 HR、管理员、二级接口人、三级接口人等身份。
- 公司 W3 认证仍待外部方案确认；接入后按工号识别登录用户，并只替换外部身份到系统 `User.username` 的适配层，RBAC、Contact 绑定和 `/api/me/` 消费口径保持不变。

## 七、系统需求

- 上传含候选人简历时必须选择 Rule 或 AI，并只创建一条固化该模式的 `ProcessingRun`；上传请求只使用 `processing_mode=rule|ai` 表达模式，人工处理请求只使用 `mode=rule|ai` 且拒绝 `modes`。响应仍返回 `processing_runs` 列表；生产异步环境提交后返回 `202`，本地 `CELERY_TASK_ALWAYS_EAGER=True` 会同步完成并返回 `200`。页面只在提交请求期间禁用发起按钮，提交成功后可继续筛选、预览、下发、导出和跳转，不得用全屏遮罩冻结网站。
- 生产异步环境的 AI Step4 采用有界候选人级任务调度：普通 worker 只消费 `default` 队列，独立 AI worker 以 threads 池消费 `ai` 队列；单个候选人的异常、重试或冲突不阻塞其他候选人。Docker Compose（包括离线包）部署和验收必须同时启动并确认两个消费者；仅运行 `default` worker 不视为 AI 处理能力可用。本地 SQLite + eager 模式仍保持同步串行，不依赖 Redis 或 worker。
- 上传后的后台编排固定为 Rule `Step1 → Step2 → Step3`、AI `Step1 → Step2 → Step3 → Step4`；显式 `all` 使用相同顺序，不再按旧的前置步骤倒序执行。
- 系统提供全局非阻塞任务中心。拥有 `pipeline.view` 的用户可从侧栏独立「处理任务」页面查看全部处理任务的发起人、类型/策略、当前阶段、进度、任务耗时、范围摘要、结果计数、最近心跳和异常；该权限默认授予管理员和 HR，二级、三级接口人默认不可见。任务耗时统一从 `ProcessingRun.created_at`（任务提交/创建时间）起算：存在 `finished_at` 时计算至该时间，否则计算至服务端当前时间。任务页面约每 2 秒轮询，同时提供手工刷新、候选人结果跳转、取消和审计，不再使用顶栏 Badge 或侧边 Drawer。任务中心对排队、运行、取消中、已取消、成功、部分失败、失败和已撤销等状态展示耗时；父运行保留 `waiting_conflict` 兼容状态，但当前 AI 候选人冲突记录在 `ProcessingRunScopeItem.waiting_conflict`，父运行通常保持 `running`。尚无 `finished_at` 的任务耗时随轮询更新，写入 `finished_at` 后耗时保持固定，不要求 WebSocket。取消活跃任务另需 `pipeline.run`：`pending` 立即转为 `cancelled`；`running` 或兼容的 `waiting_conflict` 先转为 `cancelling`，在候选人或阶段边界安全停止，已落库结果保留。任务中心需展示并审计取消请求时间、取消完成时间和取消人。
- AI 任务中心额外展示配置并发上限、当前有效并发、模型重试数和 429 限流数；运行和阶段的主结果计数统一为处理完成、需处理、失败、安全跳过和取消。AI 的待复核、待下发、建议归档作为处理完成的业务子项独立展开，零值禁用，且子项合计可小于处理完成总数。
- 处理中心跳转和简历库表头支持 `result_type + reason_code` 精确组合筛选。至少提供 `education_not_eligible`、`school_not_eligible`、`job_not_found`、`secondary_department_missing`、`secondary_contact_missing`、`major_not_matched`、`job_responsibility_missing`、`llm_timeout`、`resume_text_unavailable`、`ai_connection_error`、`ai_rate_limited`、`ai_invalid_output`、`ai_reference_invalidated`、`ai_special_route_unavailable` 和 `ai_special_route`，不得依靠模糊匹配错误文本。
- 岗位需求、部门和接口人继续独立导入或维护，但它们只是 Step3 的基础数据，不再伪装成流水线编号步骤。
- 简历库“处理简历”从 Step2 开始：完整重算范围内院校标签和准入，再执行 Step3，选择 AI 模式时继续 Step4；不重跑 Step1 查重排序。请求必须提交唯一 `mode` 且不接受 `modes`；AI 未通过当前完整连接配置测试时拒绝提交，不能静默降级为 Rule。
- 拥有 `pipeline.run` 或 `resume.import` 任一权限的用户可读取 `GET /api/allocation-mode/`，供人工处理和上传弹窗共享；接口只返回 `default_mode / available_modes / ai_ready`，不返回模型连接详情。简历库“处理简历”弹窗按 `default_mode=rule` 默认选择 Rule；Rule 始终可选，AI 不可用时禁用并说明原因。弹窗再要求用户选择与状态互斥的`当前选中（N）`或多选六种简历状态；打开时冻结当前选中 ID 和数量，既未选当前选中也未选状态时禁止提交，避免误跑全量。
- 各步中间结果可查看、表头筛选、分页、导出；所有列表、配置表和详情内嵌表格均支持拖拽调整列宽。可独立查询的分页列表通过表头文本/单选/多选选择器调用后端筛选；简历详情内嵌的投递志愿、分配尝试和 AI 筛选决策表不提供筛选器。仍保留操作列的其它页面不为操作列提供筛选器，但支持列宽调整，简历库主表不设置操作列。
- 列表 API 支持按页加载，前端可通过 `page_size` 控制每页数量，后端限制单页最大 500 条以保护服务。
- 历史 Rule 与 AI 结果在简历库详情中按来源保留，便于人工核对；新任务不会同时生成两种来源。
- 当前模型连接未通过与完整配置指纹一致的真实测试时，禁用历史 AI 决策的“重试 AI”，但不影响查看历史决策、确认或取消已有待复核建议、转人工、下发已有待下发尝试及后续转派、反馈。
- 长时间批处理允许分批产生结果，任务中心按各阶段累计工作量显示连续进度，并可边跑边查看待下发、待复核、需处理、模型超时失败、建议归档和安全跳过数量；父任务状态至少包括排队、运行、取消中、已取消、成功、需处理、部分失败和失败，并兼容保留等待冲突，候选人级等待冲突以 ScopeItem 状态记录。现有 heartbeat 时间字段可继续展示，但 heartbeat 超时判定、worker 扫描和安全恢复不属于本轮验收，不得标记为已实现。
- 「配置项」删除“系统参数”页签，只保留院校标签字典、院校准入规则、专业大类映射词表等业务配置。`welink_enabled` 的前端管理入口移动到“部门接口人”页面，由 `department.manage` 控制；后端继续使用白名单配置键保存开关值，不提供任意配置键编辑。AI 阈值、超时、并发、重试、默认关闭的 AI 专项分流开关、严格阈值（默认 0.90）、父级二级接口人和固定三级接口人统一放在“AI 模型连接”页面，并与模型连接共用 `settings.manage_ai_connection` 权限。系统不再提供 `ai_enabled`。`ai_concurrency` 是同一模型资源在所有 worker 和所有运行之间共享的自适应并发上限，默认 8，允许范围 1–20，不是每个 worker 独立的线程数。专项分流启用时必须校验接口人启用状态和部门上下级关系。院校准入、专业词表等业务规则配置可授权 HR/管理员维护；用户、角色、权限、任务运行保护、认证安全由对应权限码控制。
- AI 模型连接作为系统设置中的独立页面，由 `settings.manage_ai_connection` 权限控制；页面分为“模型连接”“AI 运行参数”“AI 专项配置”。管理员角色默认拥有该权限，也可在「用户权限」按角色授予。内网 DeepSeek V4 与 GLM 4.7 共用一个模型服务地址。获授权用户配置 API 风格、模型名称、统一 Base URL 和可选 API Key/访问令牌，并发起最小真实模型测试；API 风格可选 `responses` 或 OpenAI-compatible `chat_json`。后端使用当前 Base URL 和可选访问令牌请求 `GET /models`，前端模型字段以可搜索、可手工输入的下拉框展示返回的模型 ID；模型列表获取失败不阻止手工输入。API 风格始终由管理员显式选择，不从模型列表推断。未授予该权限的 HR 和接口人菜单、路由和接口均不可见/不可调用。运行时完全不读取任何环境变量或部署文件中的模型连接信息；无鉴权的内网服务允许不保存 API Key，只要当前完整配置真实测试成功，上传和处理弹窗就可选择 AI。修改任一连接字段或清除 API Key 会使测试状态失效，此后新提交只能选择 Rule，直至重新测试成功；该变化不取消已有任务，也不改变其提交时固化的模式。API Key 仅允许写入，读取接口永不返回明文或密文；服务端使用由 Django `SECRET_KEY` 派生的 Fernet 密文存入 `Config`。每个 backend/worker 进程按 `api_style + base_url + API Key 指纹 + timeout` 组成的键复用 OpenAI/httpx 客户端，缓存键不包含 `model_name`；上述任一键字段变化时使用新的缓存项，进程退出时关闭客户端，TLS 证书校验仍固定为 `verify=False`。界面只展示稳定错误码与脱敏摘要，不泄露 Key；AI 运行异常只记录稳定错误码和脱敏摘要；第三方 SDK 原始异常绝不进入 AI 决策、API 响应或日志，后端/worker 日志仅记录 model、api_style、错误码和异常类型，运维通过 Docker logs 排查。
- 模型并发额度按 `api_style + base_url + model_name + API Key 指纹` 隔离并由 Redis 在所有 worker/运行间共享：初始有效并发为 2，干净成功窗口按 2→4→8 增长且不超过 `ai_concurrency`；429 时并发乘 0.8 向下取整且遵循 `Retry-After`，超时、网络异常和 5xx 暂停增长但不降低并发。
- 数据进入同一数据池，不引入批次概念；按 `imported_at` 等时间标签筛选。
- 登录后的全站界面采用深色固定侧栏、白色顶部栏、浅灰内容背景、低阴影白卡和靛青主色；侧栏从上到下依次为 `DashBoard`、独立「处理任务」、可动态展开/收起的「数据管理」和「系统设置」，登录页保持原样。`DashBoard` 为管理员和 HR 的登录首页；无 `analytics.view` 权限的接口人按权限进入首个可访问页面。招聘分析默认统计最近 30 个自然日，以 `Resume.imported_at` 形成 cohort；投递数按 Resume 计数，其余阶段按 Candidate 去重。接口支持招聘主体、岗位、二级部门、院校标签、最高学历和分配来源筛选，当前看板界面只保留时间区间和二级部门选择，并内嵌在数据展示区左上角，不设置独立筛选栏。看板固定展示分类、分配、下发、反馈、通过、归档数量，转化率，平均耗时，Rule/AI/Manual 来源，AI 建议/错误码，岗位/部门排行、院校标签/学历分布以及归档/未通过原因；首屏以五张 KPI 卡组织候选人数、分配、下发、反馈和通过，投递/分类并入候选人数卡，归档并入通过卡；招聘概览以分配来源环图、横向流程柱图和 AI 建议环图展示，不展示按日趋势图或候选人明细表；岗位/部门使用横向柱图，来源、建议、标签、学历和原因使用环图；桌面、平板和手机均保持可读。岗位维度使用候选人当前有效投递并在缺失时回退 cohort 内志愿顺序最靠前的投递；部门统计优先使用分配尝试快照，避免部门改名或删除后改变历史展示。统计由后端聚合并缓存 5 分钟，响应统一返回 `data_as_of` 和统计口径，前端不得下载明细后自行计算。
- 生产 Compose 必须包含独立 backup 镜像和每小时备份调度。每个 restic 加密增量快照同时包含 PostgreSQL custom-format dump、`media_data`、版本与 checksum 清单；默认保留 48 个小时版本、30 个每日版本和 12 个每月版本，目标存储应位于异机挂载或外置磁盘。
- 恢复服务不得随正常启动自动执行；任何恢复必须显式确认，覆盖生产库还必须二次确认并先停止应用写入，目标数据库仍有活动连接时一律拒绝恢复。系统提供独立 Compose project、宿主机端口和数据卷的恢复演练，恢复后校验迁移、Django 配置、核心表、外键和简历文件，每次生成演练报告。建议每月隔离恢复、每季度整机恢复演练。本期仍是单机 Compose + 异机/外置备份，不提供 PostgreSQL/Redis 高可用集群。
- `DJANGO_SECRET_KEY`、数据库密码和 restic 密码由备份之外的独立密钥流程保管；缺少原 `DJANGO_SECRET_KEY` 时不得宣称既有 AI 连接密文可完整恢复。
- 扫描件 OCR 属于后端 AI worker 的本地 CPU 密集能力；容器必须安装 Tesseract 及简体中文、英文语言包，运行参数通过 `RESUME_OCR_MAX_PAGES`、`RESUME_OCR_DPI`、`RESUME_OCR_TIMEOUT_SECONDS`、`RESUME_OCR_CONCURRENCY` 覆盖默认限制。
- 简历库支持按上传记录的单级撤销：后端先解析本次上传影响的业务键，并只为受影响的候选人/投递范围保存该上传记录的一份快照及本次上传关联处理完成后的流程版本基线；快照覆盖候选人、投递、简历画像、候选人流程、AI 决策、分配尝试和转派历史。HR 只能查询和撤销本人上传记录，管理员可查看和撤销全部上传；同一上传记录只能撤销一次。撤销时锁定全部受影响候选人的流程并比较版本，任一候选人已有后续变更即整体返回 `409`，不做部分回滚。关联处理任务仍在运行时同样返回 `409`；相关 `ProcessingRun` 作为操作审计保留，但标记为已撤销。
- 候选人删除只允许用于尚未产生受保护历史的数据维护。存在任何分配尝试、反馈、AI 决策或转派历史时，后端必须拒绝删除并返回明确原因。
- “清空重导”不得硬删除已有候选人流程、反馈或审计历史；候选人/投递继续按业务键增量并入，主数据 replace 采用停用或更新语义。确需清空测试数据应使用仅限空环境或明确运维授权的独立工具，不作为普通导入模式。
- 工程交付物包括数据库字段表 + UML 类图、前后端接口文档、4+1 架构视图、Docker Compose 部署。
- 数据隐私与合规（手机号等个人信息是否脱敏、留痕）待确认。
