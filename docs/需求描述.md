# 海纳智聘 — 需求描述

> 本文是业务需求源头，描述系统要解决什么问题、有哪些角色、输入输出、核心流程和业务规则。后端实现见 `docs/后端设计.md`，数据库模型见 `docs/数据库设计.md`，前端页面与交互见 `docs/前端设计.md`。

> 文档分工：本文只定义业务目标、业务规则和验收边界；算法、状态流转和 API 以后端设计为准，字段与删除策略以数据库设计为准，页面与按钮以前端设计为准。四份核心设计文档保持分立，不通过复制整段实现细节互相替代。本文描述目标设计；当前落地状态统一在 `docs/前端设计.md` 的“实现状态速览”和各文档“待实现与风险”段标注。

## 一、目标与范围

建设名为“海纳智聘”的网页版校招简历筛选平台，核心流程为：

`Step1 查重与志愿排序 → Step2 院校分类及学历/院校准入 → Step3 岗位与分配前置检查 → Step4 AI 深度筛选（仅 AI 模式）`

岗位需求、部门和接口人维护是分配前置基础数据，不占用编号步骤。Rule 模式执行 Step1–Step3，AI 模式执行 Step1–Step4；简历库人工“处理简历”从 Step2 开始，不重复查重。上传简历和人工“处理简历”都在提交时明确选择 **Rule / AI（Agent）** 中的一种模式；Rule 始终可选，只有当前完整模型连接配置已经真实测试成功时才可选择 AI。系统不设置全局 AI 分配开关。AI 入口只有在真实模型调用、结构化输出、异常处置和禁止 Rule 回退均通过验收后，方可作为生产能力。每次处理规模约 **3 万条**简历，但本轮不包含 3 万条压测。

> **本轮范围边界**：本轮实施 Rule-first 工作流、备份/恢复/灾备、招聘分析和面向 Grafana 的页面使用频率 JSON 接口。worker heartbeat 超时检测与安全恢复、Prometheus/集中日志/告警、逐条 API 调用频次、访问审计页面、具体用户排行、3 万条压测、CI 和浏览器 E2E 均不在本轮实施或验收范围。备份工具只输出可被 Prometheus 读取的文本状态，使用频率接口只输出 Grafana 可消费的业务 JSON，两者都不代表本轮部署了 Prometheus、监控或告警栈。

项目采用 vibe coding，不安排固定排期。

系统需要支持：

- 4 张业务表和简历包导入。
- 候选人按人聚合，一名候选人可有多条投递。
- 当前有效志愿展示与按志愿顺序推进分配。
- Rule-first 分配：先完成学历、院校、当前志愿岗位、二级部门和二级接口人等确定性规则，再把通过者交给 AI 深度判断。AI 不重复判断学历、院校、志愿顺序、岗位存在性、部门归属或接口人选择。
- HR 下发、二级接口人转派、二级转派前或三级转派后按权限反馈。
- HR 单份强制下发和简历库常驻批量下发；自动分配按任务冻结 `HC × 系数` 容量并在同内部职位的启用岗位间按容量比例分配。
- 简历库归档筛选和 HR 手动强制分配。
- 用户、角色、权限配置。
- 公司 W3 OAuth2 单点登录作为唯一生产登录入口，与现有系统账号、RBAC 和接口人数据范围共用同一用户口径；系统不提供本地密码登录或密码维护，DEBUG 且 W3 未就绪时仅允许使用命令签发的开发令牌。
- 仅管理员和 HR 默认可见的招聘分析看板，侧栏名称为 `DashBoard`，位于所有业务导航之前并作为登录首页，按导入 cohort 查看转化、耗时、结构与原因分布。
- 登录用户的页面浏览量、访问会话数、活跃用户数和页面排行统计；只向 Grafana 或获授权用户提供聚合 JSON，不新增项目内使用频率页面或个人访问名单。
- PostgreSQL 与简历文件的加密增量备份、受保护恢复和隔离灾备演练。
- 各环节结果查看、表头筛选、分页、简历预览和导出；所有数据表格均支持拖拽调整列宽，可筛选业务列在表头提供文本或单选/多选选择器。

## 二、输入件

| 文件 | v1 标准模板字段 |
| ---- | ---------------- |
| 简历信息列表（xlsx / xls / csv） | 招聘主体、所属机构、姓名、应聘ID、手机号、性别、对外职位名称、学历、第一学历毕业院校、最高学历毕业院校、最高学历专业、应聘状态、户口所在地、应聘日期 |
| 校招岗位分类及专业要求（xlsx / xls / csv） | 招聘主体、一层部门、二层部门、三级部门、岗位类别、对外发布名称、是否对外发布、职位名称、岗位族、工作地点、学历、工作职责、需求专业、HC |
| 院校分类（xlsx / xls / csv） | 学校、院校标签、所在省份 |
| 部门接口人信息（xlsx / xls / csv） | 一层部门、二层部门、三级部门、姓名、工号、邮箱、接口人层级、可转派、是否启用 |
| 简历包 | 命名格式 `姓名（应聘ID）`，如 `张三（12345）`；简历格式统一为 PDF |

四类表格均由对应导入弹窗提供 v1 标准 XLSX 模板，文件名依次为“简历信息列表标准模板.xlsx”“岗位标准模板.xlsx”“院校分类标准模板.xlsx”“部门接口人标准模板.xlsx”。模板第一张工作表为冻结并启用筛选的业务数据表，第二张工作表为填写说明；无值字段也必须保留标准列并留空。模板是唯一输入契约，不兼容、猜测或保存客户自定义表头映射；上传列顺序可以不同，但缺失、未知或重复表头必须在创建上传快照、检查业务键或写入数据库前整批拒绝，并返回具体字段清单。

身份口径：

- **规范化姓名 + 规范化手机号** 是候选人归并依据。
- **应聘ID** 是投递维度业务键。
- 手机号缺失的候选人直接舍弃，不入库、不进入分配，并在导入结果中提示。
- 部门接口人标准模板不含“招聘主体”或“序号”；部门主数据只维护组织层级，不落接口人主体归属或“主体来源”字段，也不提供相关筛选。招聘主体保留在投递、岗位需求等业务记录上。

## 三、业务对象口径

### 候选人与投递

同一位同学可多次投递，单主体最多 2 个岗位，跨两主体最多 4 个岗位。`应聘ID` 按投递唯一，不能标识人，因此业务上区分：

- **Candidate（候选人 / 同学）**：按规范化姓名 + 规范化手机号归并。
- **Resume（投递 / 应聘）**：一条记录对应一个应聘ID，挂在某个候选人下。

展示口径：

- 简历库主列表按 `Candidate` 聚合，一名候选人只显示一行，是 HR 查看候选人当前流程、归档信息和主数据缺口的候选人级主入口。
- HR/管理员的候选人详情展示手机号、全部投递、志愿顺序、分配尝试、匹配/手动理由和反馈结果；第一学历标签和最高学历标签以彩色标签显示在各自院校名称旁边。简历库主列表不展示手机号。接口人详情只展示本人可见尝试及其关联投递，不返回手机号、其它志愿、其它尝试或 AI 决策。
- 主列表只展示当前有效志愿：初始展示第一志愿；当前志愿被有权的当前阶段接口人反馈未通过后，再展示下一志愿；已通过候选人展示通过志愿；已归档候选人展示最后处理志愿与归档原因；当前志愿已匹配岗位和二级部门但缺可用二级接口人时，展示当前志愿和阻塞原因，不切换下一志愿。
- 简历库支持按姓名、姓名全拼、姓名拼音首字母、最高学历专业、当前志愿、当前投递时间、当前应聘ID、招聘主体、当前岗位、岗位部门、岗位类别、院校标签、简历状态、原因类型等主表字段筛选。投递时间直接复用现有 `Resume.apply_date`（应聘日期），不新增字段或迁移；主表读取候选人当前投递的 `current_apply_date`，以 `YYYY-MM-DD` 展示，空值显示 `-`，并默认显示在“当前志愿”和默认隐藏的“当前应聘ID”之间。
- `GET /api/candidates/` 使用 `current_apply_date_from / current_apply_date_to` 对页面同一当前投递执行自然日闭区间筛选，允许只传一端；非法日期或开始晚于结束必须返回 400。HR/管理员优先按 `CandidateWorkflow.current_resume` 取当前投递，当前工作流未指定投递（包括无工作流）时按列表既有志愿顺序回退；接口人按本人最新可见尝试关联的投递计算。历史志愿日期不得误命中。日期筛选与其它主表筛选共同参与后端分页、“导出当前筛选全部”和按状态重新处理范围。
- 在拥有 `analytics.view` 的 Dashboard 上，同时拥有 `resume.view` 的用户可从 KPI 主数与辅助投递/分类/归档数、招聘流程、平均耗时、来源/AI/院校/学历/原因环图以及岗位/一二级部门排行点击下钻到简历库。跳转只使用看板最近一次成功查询后已生效的 `data.filters`，不得使用尚未点击查询的草稿条件；简历库显示下钻项和统计范围，可一键返回全部简历。下钻使用独立 `analytics_*` 参数复用 Dashboard 的 `Resume.imported_at` cohort、最新非取消尝试、部门、来源、AI 和原因口径，并与简历库后续表头筛选取交集；“导出当前筛选”和按状态重新处理继续保留该范围。简历库始终按 Candidate 一人一行，因此投递数或跨多个分类合并的“其他”等指标下钻后，列表行数允许小于看板计数。未通过自由文本只在 URL 中传递 SHA-256 稳定键，不传原文。
- 简历状态支持表头勾选多选。当前应聘ID和三级接口人保留为可选列但默认隐藏，用户可通过列选择器开启；主表不展示流程状态、分配状态或操作列，也不提供对应表头筛选。原因列截断显示，鼠标悬浮时展示完整原因。
- 简历库主列表和候选人详情都必须展示候选人的最高学历专业；该字段来自简历信息列表中的“最高学历专业”，落在 `Candidate.highest_major`，不从当前投递的岗位类别反推。候选人最高学历另取简历信息列表的“学历”列，规范化为 `associate / bachelor / master / doctor`（大专 / 本科 / 硕士 / 博士）；同一文件内同一候选人出现多个已识别值时取最高值，空值或未知值不覆盖已有有效学历。
- 院校标签在简历库、候选人详情、院校清单、院校标签字典和院校准入规则中使用统一彩色标签展示；同名标签颜色保持一致，不同标签使用不同颜色。
- 候选人详情支持预览该候选人的 PDF 简历；预览时必须先通过后端鉴权 API 获取 PDF Blob 和原始文件名，再由前端 PDF.js 渲染到 canvas，不直接暴露静态文件地址。无权限或越权时不可预览且不提供下载入口；PDF 渲染失败或非 PDF 文件时，可下载原文件。候选人删除只作为数据维护能力；仅存在尚未产生历史的空 `CandidateWorkflow` 时允许随候选人一并清理，存在分配尝试/反馈、AI 决策或转派历史中的任一项时必须禁止删除，并返回受保护历史类型。

简历状态是简历库面向 HR 的统一展示态，由当前志愿、处理证据、当前有效分配尝试和反馈记录推导，不覆盖导入文件中的原始“应聘状态”字段。统一使用以下八种状态：

- **待处理**（`raw`）：没有完成过 Rule/AI 筛选；仅创建、提交、排队或尚未产出候选人结果的任务不算已经处理。
- **已归档**（`archived`）：已有 Rule/AI 筛选、AI 决策、历史尝试、归档、阻塞或失败/需处理等处理证据，但当前志愿没有有效分配状态。该状态只是统一展示归类，不要求把底层 `CandidateWorkflow.status` 强制改写为 `archived`；原因列继续展示具体原因码和说明。
- **待重新分配**（`pending_reallocation`）：当前志愿已经精确映射到岗位，但本次处理任务的全部候选岗位容量均已用尽；保留当前志愿和岗位分类，不创建分配尝试、不推进下一志愿，等待新任务重新进入分配池。
- **待复核**（`pending_review`）：当前志愿存在有效的 HR 待复核分配尝试。
- **待下发**（`pending_dispatch`）：当前志愿存在有效的 HR 待下发分配尝试。
- **待业务反馈**（`pending_screening`）：当前志愿已下发或转派给业务部门，尚未反馈筛选结果。
- **通过**（`screening_passed`）：当前流程的有效尝试已由业务部门反馈通过。
- **不通过**（`screening_rejected`）：当前志愿的有效尝试已反馈未通过；若工作流已推进到下一志愿，则历史志愿结果不覆盖下一志愿状态。

当前有效尝试必须属于 `CandidateWorkflow.current_resume` 指向的当前志愿；`cancelled` 尝试永远不算有效尝试。`classified`、`allocated` 从本次改造起停止作为简历状态码使用，列表和处理范围收到旧值或任何未知状态必须返回 400，不得忽略非法值后退化为全量查询。

招聘主体口径：

- 招聘主体如 GW / YLS 是主数据，不作为自由文本散落在投递和岗位需求中。
- 当前统一使用 `code` 作为主体标识和展示值。
- 部门与招聘主体不建立“属于”关系。

字典口径：

- `JobCategory`（岗位类别）保留 `code + name`，供岗位需求、简历分类、Rule/AI 分配和前端筛选引用。
- `SchoolTag`（院校标签）保留 `code + name`，供学校、候选人打标和院校准入规则引用。
- `School` 只保存学校名称、`province` 和院校标签引用；不保存南北归属，不维护南北省份字典。

## 四、前置数据准备

### 院校分类

用户需求：

- 按第一学历、最高学历对照院校清单打标签。
- 系统预置并保证存在编码为 `NON_TARGET` 的“非目标院校”标签。学校不在导入院校清单内时，第一学历和最高学历**始终**使用该标签；只有学校已在清单内但未配置标签时，才使用启用的默认院校标签，若无默认标签则使用“非目标院校”。
- 每次候选人处理都在 Step2 按当时院校清单完整重算并固化第一学历、最高学历标签，同时执行学历和院校准入；Step3/Step4 不得补充、覆盖或重新判断院校标签。
- 院校清单更新后，通过简历库“处理简历”从 Step2 重新处理选定范围；不再保留一个会绕开后续规则的独立院校分类步骤。
- 院校清单页面支持按 `school.manage` 新增和编辑学校，维护学校名称、院校标签和所在省份；标签从启用的院校标签字典选择，保存后同步用于 Step2 分类。
- 院校清单导入后，若当前完整 AI 模型连接测试有效，系统对本次导入且所在省份仍为空的院校提交后台补全。文件明确填写的省份优先，空单元格不覆盖已有人工或 AI 值，落库前再次确认记录仍为空。AI 只能返回中国大陆 31 个省级行政区的标准简称；院校名称明确包含校区/分校时按该校区/分校所在地，否则按主校区，不按招生地区猜测，无法可靠判断时保持空值。补全不等待模型结果，AI 不可用、调用/结构化输出失败或任务投递失败均不阻断、不回滚已完成的导入，也不改变 Step2 的纯规则院校标签/准入。

规则边界：

- 院校只存所在省份 `province`。
- 南北归属仅在志愿排序规则运行时判断，不落库、不作为配置项维护。

### 需求录入

用户需求：

- 将校招岗位分类及专业要求整理成结构化岗位需求。
- 维护岗位、部门、岗位类别、工作职责、需求专业、HC（需求人数）等分配前置数据；工作职责保存完整原文。岗位可归属二级或三级部门，`Job.department` 始终指向最深归属节点；列表、筛选、导入、导出和编辑均展示完整的一至三级部门路径。
- 投递的“对外职位名称”必须先通过 Rule / AI 共享的独立确定性服务，在同招聘主体内精确映射到唯一内部 `position_name`，再汇集同招聘主体、同内部职位名称的全部启用岗位作为候选岗位池；该服务不读取候选人专业，也不隶属于 `RuleStrategy`。精确映射行全部缺内部职位名称时记录 `internal_position_name_missing`，存在空值/非空值混合、多个内部职位或主体映射不唯一时记录 `job_mapping_ambiguous`，均结束本轮自动处理并保留具体原因，不按包含关系猜测岗位。
- 系统配置提供正整数 `job_hc_coefficient`，默认 1、允许 1–100。每个处理任务按岗位冻结独立容量 `headcount × job_hc_coefficient`；配置或 HC 后续变化只影响新任务，不回写已有任务容量。
- 需求录入可在简历导入前提前维护；岗位需求、专业要求、二级/三级部门接口人更新后可独立重跑或手工维护。
- 岗位需求页面支持新增、编辑和删除岗位；新增或编辑岗位时工作职责必填，部门选择器显示完整路径并允许选择有效二级或三级节点。列表分别展示一级、二级、三级部门并提供服务端多选筛选；“对外名称”和“职位名称”的表头筛选使用支持拼音搜索的多选选择器，并按所选项精确筛选；删除采用失效/停用语义，不破坏历史投递和分配尝试中的岗位引用。
- 拥有 `job.view` 的用户可通过 `GET /api/jobs/export/` 按岗位表当前筛选下载全部匹配岗位，不受当前页限制；未显式指定启停状态时默认只导出启用岗位。下载 Excel 可直接回导，工作表名为“职位清单”，并与岗位标准模板共享字段定义，列固定为招聘主体、一层部门、二层部门、三级部门、岗位类别、对外发布名称、是否对外发布、职位名称、岗位族、工作地点、学历、工作职责、需求专业、HC；文件须冻结表头、启用筛选并防止公式注入，响应使用 UTF-8 文件名并返回 `X-Export-Count`，无数据时明确返回 400。该数据导出与导入弹窗内的空白“下载标准模板”入口同时保留。
- 部门接口人页面支持按 `department.manage` 新增和编辑接口人；维护姓名、工号、邮箱、所属二级/三级部门、可转派和启用状态，接口人层级由所选部门层级确定。邮箱必填并校验格式，保存时统一转为小写；新增或编辑后同步账号用户名为工号、账号邮箱为接口人邮箱，保持密码不可用，并维护接口人角色和启停状态、保留非接口人业务角色。
- 岗位表只接受标准模板中的“一层部门”“二层部门”“三级部门”等精确表头，不兼容“一级部门”“二级部门”等别名。存在三级部门时岗位绑定三级节点；三级部门缺少有效二级父部门时按 Excel 行号整批报错。缺少工作职责的有效岗位行跳过并在响应中返回数量、Excel 行号和稳定警告码 `job_responsibility_missing`，其余有效行正常导入。清空重导文件若没有任何有效岗位，不得清空现有岗位。
- 岗位清空重导（Replace）是全量同步：岗位业务键固定为“招聘主体 + 一级部门 + 二级部门 + 三级部门 + 对外发布名称 + 内部职位名称 + 岗位类别”，七部分均按统一去空白、忽略大小写的规范化值比较，`是否对外发布` 仍是可更新属性而非业务键。文件或数据库中存在重复完整业务键时整批报错并回滚；完整键唯一命中时原位更新。历史岗位层级不完整且仅对应一个新完整路径时原位补齐；一个旧二级聚合岗位对应多个三级明细时停用旧记录并创建明细岗位，保留历史引用和 HC 快照。其它未命中岗位新增，文件中不存在的岗位仅停用；全量岗位行均无效时不改变现有岗位。导入仍复用 `POST /api/import/`，输入列使用 v1 标准模板中的“招聘主体”和“HC”，不新增数据库字段或迁移。
- 系统内置一版专业大类映射词表，并允许 HR/管理员在配置项中维护专业大类、专业别名和关键词。该词表仅用于 Rule 模式 Step3 的确定性专业匹配；AI 模式 Step3 不执行专业词表匹配，Step4 直接根据简历正文中的专业实际方向、项目、实习和技能评估当前固定岗位，避免重复判断。

## 五、候选人处理主流程

### Step1 查重与志愿排序

需求：

- 按 `Candidate` 聚合一个人的全部投递。
- 单一主体每人最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各投 2 个时，统一标第一至第四志愿。
- 排序规则：户籍北方优先 GW，南方优先 YLS；户籍缺失时按学校所在地同规则。
- 户籍或学校所在省份的南北判断只在规则运行时计算，不落库。

输出：

- 候选人维度的志愿排序结果。
- 主列表展示当前有效志愿，详情展示完整投递清单。

### Step2 院校分类与学历/院校准入

需求：

- 院校标签在本阶段按当前院校清单完整重算并固化，同时完成学历准入和院校准入。后续 Rule 和 AI 只能读取，不得补充、修改或重新判断院校标签。
- HR 可配置院校标签准入规则。存在启用规则时，Rule 与 AI 策略都必须先命中同一条启用规则，即“第一学历标签 AND 最高学历标签 AND 允许最高学历”同时满足该规则；多条启用规则之间继续 OR。每条规则的允许最高学历为精确多选集合，未配置表示“不限制并保持旧规则行为”；一旦配置，最高学历为空、无法识别或不在集合内都不通过。没有启用规则时视为不做准入过滤。
- 学历或院校不符合时结束本轮候选人处理并记录 `education_not_eligible` 或 `school_not_eligible`，属于已经得到明确业务结果的 `completed`，不计系统失败。

### Step3 岗位与分配前置检查

需求：

- 以候选人为粒度推进分配，一个候选人一个当前流程。Step3 只处理 `CandidateWorkflow` 确定的当前有效志愿；该志愿未反馈前不暴露或跳过到后续志愿，反馈未通过后再推进下一志愿。
- 用户在上传或处理简历时选择 **Rule** 或 **AI（Agent）** 策略，单次任务只使用一种策略；AI 选项仅在当前连接配置已通过真实测试时可用，后端仍需在提交时再次校验。
- 当前志愿到内部职位岗位池的精确映射由独立服务统一完成。Rule 和 AI 都先消费同一映射结果，再进入各自后续链路；不得通过 `RuleStrategy` 间接复用该映射。
- Rule 策略在院校准入通过后，对当前有效志愿依次执行“对外职位名称精确映射唯一内部职位 → 同主体内部职位岗位池 → 专业确定性匹配 → 二级部门检查 → 二级接口人检查 → HC 配额选择”。岗位配置需求专业时，先用启用的专业别名将候选人最高学历专业和岗位需求专业映射到专业大类；任一大类相交则专业通过。若大类无交集，或候选人/岗位任一侧未映射到启用大类，则再执行专业名双向包含兜底；词表和兜底都不命中时记录 `major_not_matched`。岗位未配置需求专业，或岗位需求专业为“专业不限 / 不限 / 不限专业”等通配表达时，直接放行。自动分配尝试需记录院校、志愿、内部职位、岗位、专业大类/专业名、部门、接口人和配额选择理由。
- 岗位绑定三级部门时，Rule 与 AI 的分配前置检查统一回溯到其父级二级部门，并只使用该二级部门的启用二级接口人；三级归属不会绕过二级下发链路。
- 同一处理任务内按候选人 ID 升序稳定处理；对仍有容量的候选岗位选择最小 `(已用量 + 1) / 容量`，并以岗位 ID 作为稳定并列决胜，实现等 HC 均分、不同 HC 按比例分配。自动生成 `pending_review` 或 `pending_dispatch` 时立即占用一份容量；下发前取消时幂等释放，已经实际下发后取消或终态处理不释放。手动强制分配绕过任务配额，不占用容量。
- 全部候选岗位容量耗尽时不创建 `AssignmentAttempt`、不推进志愿，保留分类和当前志愿，写入 `job_hc_exhausted` 并展示“待重新分配”；新任务选择该状态后按新任务冻结的容量重新处理。
- 原因必须区分 `job_not_found`、`major_not_matched`、`secondary_department_missing` 和 `secondary_contact_missing`。这些前置检查未通过都属于 `completed`，不得记为任务失败；其中 `major_not_matched` 仅由 Rule 专业审核产生。
- AI 模式对当前有效志愿执行同一“对外职位名称精确映射唯一内部职位 → 同主体内部职位岗位池 → 有效二级部门 → 启用二级接口人 → HC 配额候选岗位选择”，但不执行专业大类词表、专业别名或名称包含审核；通过后把当前志愿、岗位、二级部门、二级接口人和任务容量引用固定到运行明细。正式任务、直接处理、AI 重试和结果落库都必须遵守该边界，不得调用 Rule 专业匹配，不得生成或持久化 `major_not_matched`。映射歧义、内部职位缺失、前置主数据缺失或容量耗尽时不调用模型，并以对应业务原因结束处理。

### Step4 AI 深度筛选与分配

需求：

- AI 只优化规则无法稳定覆盖的专业实际方向、项目、实习、技能与岗位实质匹配、补充优势和风险，不绕过院校准入、志愿顺序、反馈锁定等硬规则。
- Step4 读取 PDF 简历并使用 Step3 固定的岗位、部门和接口人。`current_job` 输入包含当前岗位完整保存职责清洗后的前 12,000 个字符，并要求在既有 `job_requirement` 评分中结合简历项目、实习和技能判断职责覆盖度；工作职责按不可信业务数据处理，提示词必须忽略其中任何改变任务或输出协议的指令。初始激活 Prompt 版本为 `resume-screening-v2`，后续发布形成新版本；现有五项评分权重保持不变，不增加独立“职责评分”字段。模型输入不含岗位、部门或接口人数据库 ID；当前岗位上下文不发送学历要求，当前志愿上下文只发送 `position_name`，不发送 Resume/应聘 ID、志愿序号或招聘主体标识。业务输出只含推荐结论、置信度、理由、证据和风险；`ResumeProfileOutput` 不接受学历字段，不允许模型解析或覆盖 Step2 的学历/院校结论，也不允许模型选择或改荐岗位、部门、接口人。专项识别字段仅作为后台路由输入和内部审计，不通过候选人、分配尝试或 AI 决策公开接口返回。
- 管理员只可编辑五个固定 Prompt 业务模块：筛选角色与任务目标、学历/院校/志愿/当前岗位等业务边界、专业/项目/实习/技能/岗位职责评价口径、AI 专项人才识别口径，以及院校省份/校区/分校判断口径。简历筛选按前四个模块固定顺序组装，院校省份补全使用第五个模块；后端必须追加不可编辑的最小安全底座、动态 JSON 数据载荷、省份白名单和 Pydantic JSON Schema/结构化输出协议，不开放模板变量、字段名或输出 Schema 编辑。简历正文、岗位职责和院校名称中的指令均是不可信数据，不得改变任务、固定岗位或输出协议。
- Prompt 五模块作为整套共享草稿维护，依次经过保存、真实模型测试、原子发布和历史恢复。五个模块均必填；保存时去除 NUL 和首尾空白，单模块最多 8,000 字符、整套最多 24,000 字符，缺失或未知模块、错误类型和超限内容均拒绝。草稿保存、重置、发布和历史恢复使用 `lock_version` 乐观锁，旧版本写入返回 409 且不能覆盖其他管理员的新内容。真实测试只针对已保存草稿，使用内置脱敏简历与普通院校、校区/分校和不确定名称样例，分别走当前 `responses` 或 `chat_json` 正式结构化调用路径；只校验调用与 Schema、简历证据可定位、院校名称不越界和省份白名单，不强制具体推荐结论，不保存模型原始响应。
- 只有草稿测试内容哈希与当前草稿一致、模型连接测试仍有效且测试连接指纹与当前完整连接一致时才能发布。草稿修改、恢复、模型连接修改或连接测试失效都会使 Prompt 测试结论失效；发布本身不使模型连接测试失效。迁移初始化一个激活版本 `resume-screening-v2` 和一份相同内容的未测试共享草稿；后续发布版本使用 `prompt-vNNNNNN-<hash8>`。发布事务将旧激活版本归档、草稿转为激活版本并创建一份同内容的新共享草稿；历史版本只读，“恢复”只将目标内容复制到共享草稿，仍需重新测试和发布，不能直接切换生产版本。
- AI 任务创建时必须把当时的激活版本冻结到 `ProcessingRun.prompt_version`；执行阶段只能读取该激活或已归档版本，成功与失败的 AI 决策都记录实际使用版本。发布新版本只影响新提交的 AI 任务，不取消或改变已创建、排队中的旧任务，不影响 Rule 模式。院校省份补全后台任务同样在投递时携带激活 Prompt 版本，后续批次继续使用该版本并保留名称严格校验和省份白名单。
- 历史岗位允许工作职责为空以保证旧数据可读，Rule 模式不受影响；但 AI Step4 在抽取简历或调用模型之前必须停止该候选人，记录 `needs_attention + job_responsibility_missing`，由 HR 补齐岗位职责后重新处理。
- 后台专项人才判断单独生成 `ai_specialist_match / ai_specialist_confidence / ai_specialist_evidence`，识别智能体、大模型、训练/推理、RAG、微调和模型评测等实质项目、实习或技能。证据必须是可在提取正文中定位且带上下文的片段；证据不足或只有孤立关键词时清除本次专项命中并继续普通 AI 结论，不产生候选人错误。专项匹配成立且置信度严格大于配置阈值（默认 0.90）时，才按后台配置的父级二级接口人和固定三级接口人执行与人工强制分配相同的两段分配链路。功能默认关闭；目标停用、上下级关系失效或配置缺失时记录内部回落审计并继续普通 AI 结论，不进入“需处理”。专项开关、阈值和目标链路只在授权配置页展示；候选人详情、分配尝试、原因筛选和招聘分析不展示专项命中、置信度、证据、审计或专项分流分类，实际分配统一显示为 AI 自动分配。
- AI 正文抽取优先使用 `pypdf`；去除空白后正文不足 50 字符时，才用 PyMuPDF 将 PDF 渲染为图片并交给本地 Tesseract `chi_sim+eng` 做中英文 OCR。OCR 默认最多处理 20 页、200 DPI、总超时 120 秒，且单 worker 最多并发 2 个 OCR，均允许部署环境覆盖。OCR 成功后正文继续写入 `ResumeProfile.raw_text`，解析器版本为 `pypdf-ocr-v2` 并记录 `ocr_fallback` 风险标记；OCR 仍失败时内部抽取错误可记为 `pdf_parse_failed`，但候选人级统一映射为 `needs_attention + resume_text_unavailable`，且绝不回退 Rule。该回退只服务 AI 简历正文抽取，不改变 PDF 预览、下载或原文件保存流程。
- PDF 抽取正文和模型结构化输出中的字符串在写入简历画像或 AI 决策前必须递归移除 NUL（`0x00`）字符；AI 服务产生且可持久化的受控错误消息做相同兜底，避免 PostgreSQL `text/jsonb` 拒绝写入。除 NUL 外不得改写其它业务文本字符，不保存模型完整原始响应，也不为此新增数据库字段或迁移。
- AI 推荐版的第一版定位是“受硬规则约束的分流建议器”：AI 只处理当前有效志愿和预先固定的单一目标岗位，不主动跨志愿或改荐其它岗位。
- 面向 HR 的 AI 结果必须可审查，包含推荐动作、置信度、分项评分、推荐理由、简历证据和风险点；后台专项判断及其路由审计不在业务页面展示。岗位、部门和接口人来自 Step3 固定引用，不属于模型输出。

AI 阈值：

> AI 能力必须按以下正式口径验收。AI 连接不可用时必须写入明确异常决策并映射为 `needs_attention + ai_connection_error`，不得通过复用 Rule 结果、固定置信度或元数据拼接伪装成可用的 AI 结论。

- `ai_dispatch_threshold` 默认 `0.75`。
- `ai_review_threshold` 默认 `0.5`。
- `recommendation=dispatch` 且 `confidence_score >= ai_dispatch_threshold`：生成 `source=ai, pending_dispatch` 的待下发尝试。
- `recommendation != archive` 且 `confidence_score >= ai_review_threshold`，但未达到自动下发条件：生成 `source=ai, pending_review` 的 HR 复核项，不自动下发。
- `recommendation=archive` 或 `confidence_score < ai_review_threshold`：只生成 AI 决策记录，不生成分配尝试，作为 `completed` 的明确业务建议归档。简历正文不可用、AI 连接/认证、429、输出协议和引用失效按对应 `needs_attention` 原因保留给 HR；`llm_timeout` 单独计入 `failed`。AI 决策保留在简历库详情和 API 中，HR/管理员可重试 AI、改用 Rule、手动强制分配或归档。
- 候选人处理结果统一为 `completed / needs_attention / failed / cancelled`。学历或院校不符合、职位映射歧义、内部职位缺失、无匹配岗位、HC 容量耗尽、缺二级部门、缺二级接口人、Rule 专业不匹配、Rule/AI 分配成功以及 AI 建议归档/待复核均为 `completed`；岗位缺少工作职责、简历正文不可用、AI 连接/认证、429、输出协议和运行中引用失效为 `needs_attention`；本轮只有 `llm_timeout` 计入 `failed`。专项证据或后台目标配置不可用只取消专项增强并继续普通 AI，不属于 AI 模型异常，也不回退 Rule。其它 AI 异常由 HR 按权限重试、改用 Rule、人工强制分配或归档。

分配和反馈：

- HR 将待下发尝试下发至二级部门接口人：单条强制下发继续在候选人详情中执行；简历库工具栏常驻“下发”，批量弹窗可选择打开时冻结的已选候选人，或使用字段白名单内的业务枚举多选筛选。该弹窗及候选人级批量接口的独立筛选白名单不加入投递时间；`candidate_filters` 支持 JSON 多选数组，其中 `allocation_source` 和 `reason_code` 也不得按单个字符串限定。批量接口只处理各候选人当前有效的 `pending_dispatch`，并返回成功、跳过和失败的部分成功统计。
- `pending_dispatch` / `pending_review` 等 HR 待处理尝试不对二级接口人展示；二级接口人只看到 HR 已下发给自己的简历尝试。
- 二级接口人只能在本二级部门范围内选择下属三级接口人并转派。
- 提交反馈由 `attempt.feedback` 权限、当前阶段和接口人绑定共同控制，不由角色名称硬编码：二级接口人仅在本人接收的 `dispatched_l2` 尝试尚未转派时可反馈；转派后该二级接口人不再可提交，避免与三级接口人竞争；三级接口人仅可对本人被转派且状态为 `assigned_l3` 的尝试反馈。
- 反馈结果为通过/未通过并可填写备注；反馈提交后锁定，不允许二次修改。`attempt.feedback` 只授予操作能力，不扩大数据可见范围，用户仍须具备对应的本人接收或本人被转派查看权限。
- 任一允许阶段反馈通过后，候选人流程结束，并取消该候选人其他未反馈尝试；反馈未通过后，系统自动进入下一志愿，志愿耗尽则归档。
- HR 点击简历库“处理简历”后，弹窗固定展示九个选项：`当前选中（N）`以及待处理、已归档、待重新分配、待复核、待下发、待业务反馈、通过、不通过八种状态。`当前选中`始终由用户手动勾选，不因页面已有选择而默认勾选；`N=0` 时仍显示但禁用。`当前选中`与八种状态互斥，状态之间支持多选，任一状态都允许重新打开并从 Step2 处理。打开弹窗时即冻结当时选中的候选人 ID 和数量，确保展示与最终提交一致。
- 选择 `当前选中` 时，不考虑候选人当前状态，不叠加简历状态、表头筛选或任务结果筛选，仅以 `scope={"candidate_ids":[...],"force_reprocess":true}` 重新执行 Step2。该请求表示 HR 主动重开：清空当前通过指针、归档/阻塞结果和完成时间，取消尚未反馈的自动尝试，保留历史尝试、反馈和 AI 决策，再按本次提交时选择并固化的 Rule / AI 模式处理。提交后发生人工修改时，仍以 workflow revision 保护安全跳过。选中范围提交成功后清空页面勾选。
- 选择一个或多个简历状态时，仍以 `scope.system_statuses + scope.candidate_filters` 与当前表头、任务结果筛选相交，只重跑命中候选人的 Step2；本次请求必须显式提交唯一 `mode`，不得提交 `modes`。Step2 对范围内候选人的院校标签执行完整重算和准入，不把标签补写推迟到后续步骤。普通简历导入使用的 `candidate_ids + source=resume_import` 不表示强制重开，不重开已通过等终态流程。
- 自动处理任务创建时固化候选人范围及当前流程版本；不同候选人可并行处理，同一候选人的自动和人工流程写操作统一串行。后发任务遇到冲突时进入等待并重试；人工下发、转派、反馈、手动分配等操作优先完成，自动任务发现流程版本已变化时安全跳过并记录 `skipped_manual_change`，不覆盖人工结果。
- HR 可从任意投递发起手动强制分配，绕过院校规则、志愿顺序和自动筛选条件；已通过候选人不可再强制分配。手动强制分配与简历库“处理简历”是两个入口：前者不允许重开已通过候选人，后者可通过手动勾选 `当前选中` 对冻结 ID 执行强制重开，或勾选简历状态后按筛选范围重新处理。
- 手动强制分配可选择二级接口人或三级接口人。选择二级接口人时进入待下发/已下发二级流程；直接选择三级接口人时，系统必须校验其所属三级部门存在有效父级二级部门：只有一个有效二级接口人时自动补齐，存在多个时由 HR 明确选择，随后进入待三级反馈流程，并记录“HR 到二级、二级到三级”两段转派历史。没有有效父级二级接口人时禁止直达三级。

归档口径：

- 志愿耗尽、学历/院校不符合、岗位映射歧义、内部职位缺失、岗位不存在、专业不匹配、缺二级部门、缺二级接口人以及 AI 建议归档均可结束本轮自动处理；在处理中心按各自任务结果统计并保留精确原因码。没有形成当前有效尝试时，简历库业务状态统一展示“已归档”，不得把配置或规则结果统计为模型失败。HC 容量耗尽单独展示“待重新分配”，不归档也不推进志愿。
- `needs_attention` 项保留当前候选人和原因，等待 HR 修复正文、AI 连接/认证/限流/协议或运行中引用后处置；不得静默回退 Rule。后台专项增强自身不可用时继续普通 AI，不产生需人工处置项。
- 归档候选人不再作为 HR 独立列表入口；归档筛选、归档原因和从具体应聘ID发起手动强制分配统一合并到简历库。
- 简历状态按当前志愿的有效尝试和处理证据推导：通过、待业务反馈、待下发、待复核、不通过、待重新分配、已归档、待处理分别对应八种互斥展示态。待复核与待下发不得再合并为“已分配”；历史志愿结果和取消尝试不得覆盖当前志愿状态。

输出：

- 简历库候选人主清单：合并展示当前志愿、当前投递时间、当前投递、岗位部门、简历状态和分配/归档/阻塞原因；投递时间复用当前 `Resume.apply_date`，无日期显示 `-`。当前应聘ID和三级接口人作为可选列默认隐藏，原因截断显示并可悬浮查看全文。主表不展示流程状态或分配状态。
- 简历库是候选人分配与下发的唯一页面。主表展示当前有效 `AssignmentAttempt` 的实际来源（`rule` / `ai` / `manual`）、部门、二级/三级接口人和分配原因，但不展示尝试状态和操作列；没有有效尝试时，若 `CandidateWorkflow.started_at` 非空且 `dispatch_strategy` 为 `rule` / `ai`，包括 AI/Rule 的归档、失败和阻塞结果，也展示该自动策略；从未进入处理的待分配流程不展示来源。`allocation_source` 表头筛选必须使用完全相同的派生口径。单击候选人行直接打开详情。拥有权限时工具栏始终展示批量“下发”，未勾选候选人也可按非空业务枚举筛选处理；弹窗也可处理打开时冻结的当前选中候选人。导出、删除等选中操作仍在勾选后通过表格上方的滑入操作条展示，删除只处理当前选中候选人。单条下发、确认 AI 建议、转人工、取消、转派、反馈、导出和删除等动作统一进入详情执行。详情保留流程状态、全部投递及其应聘状态、历史尝试及其状态和 AI 决策。二级、三级接口人同样进入简历库，但后端只返回本人接收或被转派的候选人、对应尝试和关联投递，不返回手机号、其它志愿、其它尝试或 AI 决策。
- 任务中心主结果行固定展示处理完成、需处理、失败、跳过和取消，非零数字均可点击。AI 任务的“处理完成”旁可展开“待复核、待下发、建议归档”业务子项；子项合计允许小于处理完成总数，因为 Rule 前置结束项不会产生 AI recommendation。点击结果使用 `processing_run_id + processing_result`，该组合仅供任务中心定位某次任务结果；简历库主表不展示“处理结果”列或同名表头筛选。原因仍使用 `reason_code` 精确筛选，列表业务状态始终按八种简历状态统一展示。
- 候选人简历文件预览和导出支持详情中单条执行、主表勾选批量执行和按当前筛选全部导出；预览时后端通过鉴权 API 返回 PDF Blob 和原始文件名，前端用 PDF.js 渲染到 canvas；详情默认预览当前投递的简历文件，当前投递无文件时回退到同候选人第一条有文件的投递，但不改变当前志愿展示口径；投递志愿表删除预览列，单击志愿行切换到对应简历，单击无文件志愿时显示该投递缺失提示而不保留上一份预览；无权限或越权时不可预览且不提供下载入口，PDF 渲染失败或非 PDF 文件时可下载原文件。
- 所有“导出简历”入口先打开同一属性选择弹窗，按候选人、当前投递、岗位需求、分配反馈和“状态与原因”五组提供版本化稳定字段目录，支持全选、清空和恢复默认；目录删除 `processing_result`。未选择任何字段时禁止导出。默认勾选姓名、手机号、当前应聘ID、当前岗位、当前志愿、二级部门、二三级接口人、分配来源和简历状态；浏览器按当前用户记忆最近一次有效字段选择，但“同时下载简历原件”每次打开都默认不勾选且不写入本地偏好。目录升级时自动忽略 `processing_result` 等失效字段，没有有效历史选择时恢复默认。Excel 列始终按字段目录顺序排列，不按点击顺序排列；不开放数据库内部 ID、身份哈希、账号信息、AI 原始正文/画像、后台专项路由和审计配置。
- 候选人选中、当前筛选和详情尝试三个导出入口统一传递 `include_resume_files`。未勾选原件时（`false`）只返回 `简历库清单.xlsx`，不扫描或打包原件，响应标识 Excel 模式、候选人数，原件数和缺失数均为 0；勾选时（`true`）返回既有组合 ZIP，固定包含仅一张“简历库”工作表的 `简历库清单.xlsx` 和显式 `简历文件/` 目录项，存在缺失时另含 `缺失简历文件清单.txt`，同名文件使用应聘ID消歧。为兼容旧客户端，参数缺失时仍按 `true` 返回 ZIP，非法布尔值整个请求失败。Excel 一名候选人一行，候选人级单值投递、岗位和职责取当前有效志愿，尝试级同一候选人选中多条尝试时取 `attempt_no / id` 最大的一条；多值字段以中文顿号连接、时间按 Asia/Shanghai 输出、职责自动换行，所有外部文本执行公式注入防护。手机号对所有拥有简历导出权限的用户开放，但接口人只能导出本人可见分配尝试对应候选人的手机号和简历，不能借此扩大数据范围。
- “导出结果报表”入口位于 `DashBoard` 右上角，不再出现在简历库，也不打开简历属性选择弹窗。按钮继续要求 `resume.view`，页面本身继续要求 `analytics.view`；点击后直接使用看板当前已经查询生效的日期范围、一级部门和二级部门筛选下载 `.xlsx`，分别透传为 `imported_after / imported_before / primary_department_id / department_id`。日期按 Asia/Shanghai 自然日闭区间筛选 `Resume.imported_at`；一条应聘ID只统计一次，并按与列表一致的八种状态生成汇总和明细。一级部门按当前志愿最新非取消分配尝试所关联部门的当前父级一级部门推导，二级部门和接口人继续优先读取该尝试的历史快照。Excel 仍包含“部门汇总”和“简历明细”两张表；关联主数据删除后已有快照仍可统计，所有外部文本均做公式注入防护。Dashboard 的“已生成分配”等独立指标继续使用原有分析口径，不因八状态报表改名或合并。

## 六、用户与权限

角色：

- **HR**：全流程业务操作，包括导入、处理、下发、手动分配、导出、查看反馈、查看招聘分析，以及维护获授权的院校准入、专业词表等业务规则。
- **二级部门接口人**：查看 HR 下发给自己的尝试，并转派给本部门下属三级接口人；获授 `attempt.feedback` 后可在转派前提交反馈。
- **三级部门接口人**：查看转派给自己的尝试；获授 `attempt.feedback` 后提交通过/未通过反馈。
- **管理员**：用户、角色、权限、认证与安全配置管理，也可维护业务规则。

权限要求：

- 权限管理采用 RBAC。
- 用户可绑定一个或多个角色。
- 角色绑定权限点，权限点覆盖菜单入口、页面查看、按钮操作、导出、下发、转派、反馈、系统配置等能力。
- 前端需要支持用户、角色、权限配置。
- 用户权限页只保留“用户管理”和“角色管理”两个页签；角色权限绑定合并到角色管理列表，每个角色通过“配置权限”打开权限树弹窗并保存，不再提供功能重复的独立“权限配置”页签。
- 权限点由系统预置为树形清单，前端只允许勾选绑定，不允许随意新增未知权限码。
- 数据范围不单独建表，由角色权限、接口人绑定和部门关系推导。
- 前端权限控制只负责体验和误操作拦截，后端必须做接口级鉴权和数据过滤。
- 招聘分析使用独立权限 `analytics.view`，默认授予管理员和 HR；二级、三级接口人默认不可见且不可调用接口。
- 使用频率查询接口不新增权限码：普通登录请求必须拥有 `analytics.view`；Grafana 服务请求则必须携带与部署密钥一致的 `X-Usage-Metrics-Key`，且响应只包含聚合统计，不返回个人访问名单或用户排行。
- 侧栏独立「处理任务」页面使用 `pipeline.view` 控制查看，默认授予管理员和 HR；创建处理任务和取消活跃任务继续要求 `pipeline.run`。二级、三级接口人默认不授予这两个权限，也不显示该导航项。
- 部门接口人页面的 WeLink 通知开关只对拥有 `department.manage` 的用户显示并允许操作；删除“系统参数”页签后，不在其它页面提供通用 Config 编辑入口。
- 系统配置新增“分配参数”页签；该页签和 `job_hc_coefficient` 更新只向拥有 `settings.manage_config` 的用户开放，按正整数 1–100 校验，不与 AI 模型连接权限混用。
- 系统设置新增独立「Prompt 管理」菜单和 `/prompt-management` 路由，复用 `settings.manage_ai_connection`；未获该权限时菜单和路由不可见，全部 `/api/ai-prompts/` 接口返回 403。该权限允许读取激活、共享草稿和历史版本的完整 Prompt 文本，但不允许读取内部模型连接指纹或模型原始响应。
- 系统硬编码一个内置受保护管理员：工号/用户名固定为 `012358`，邮箱固定为 `huyue2@ueascend.com`，始终保持 `is_superuser=true`、`is_staff=true`、`is_active=true`，绑定“管理员”角色并拥有全部系统权限。该账号与所有普通账号一样只保留 Django `AbstractUser.password` 兼容列，列值始终为不可用密码标记；账号身份与保护规则属于后端代码常量，不提供配置项或页面开关。
- 导入或在页面新增/编辑部门接口人时，工号和有效邮箱均为必填身份字段，邮箱统一去空白并转为小写。系统同步 `User.username = Contact.employee_no`、`User.email = Contact.email`，新建或更新账号时均设置不可用密码，并按接口人层级绑定二级/三级接口人角色及对应 `Contact`；编辑工号或邮箱时同步更新绑定账号。
- 工号或邮箱已被不同账号占用时拒绝同步；已有目标账号保持密码不可用并保留非接口人业务角色，仅替换二级/三级接口人角色。部门接口人文件缺邮箱、邮箱格式非法、同一邮箱对应多个工号，或邮箱与现有其他接口人冲突时，整批导入以 `ValueError` 失败并回滚。replace 导入时，本次文件中不存在的旧接口人及其账号停用。除内置受保护管理员外，用户管理或接口人清单中的单条删除采用清理语义：删除用户时清空该用户的 Token、角色绑定、接口人绑定等账号相关内容；若用户绑定了接口人，则同步删除该接口人。删除接口人时同步删除绑定该接口人的用户信息。历史分配、转派和 AI 决策不级联删除，只保留已有快照文本和审计记录，不再保留对已删除用户/接口人的外键引用。
- 用户管理新增和编辑时邮箱必填，统一转为小写并按大小写不敏感口径拦截重复；不展示初始密码、重置密码或其它密码控件，不单独维护姓名字段，不展示/编辑/同步 `first_name`、`last_name` 等 Django 姓名类字段，接口人身份展示以绑定的 `Contact.name` 为准。用户 API 不输出密码字段；POST/PATCH 请求只要携带 `password`（包括空值）即返回 400。
- 用户管理支持删除普通用户。删除用户采用账号清理语义，不只是停用：删除后该账号不可登录，不再出现在用户管理列表。内置受保护管理员在用户 API 中只读，任何用户均不得编辑、改绑角色、停用或删除；前端明确标识“内置保护”且不展示编辑、启停和删除操作。W3 登录不自动重建普通已删除账号；只有管理员以未被占用的用户名和邮箱新建用户（用于 W3 时用户名必须为工号），或接口人导入/维护重新同步工号与邮箱时，才按新账号重新创建和绑定。
- 新环境通过账号应用的数据迁移创建内置受保护管理员，并设置不可用密码、管理员角色和超级用户标志；保护账号不依赖 `seed_base` 或人工初始化。

登录认证：

- 公司 W3 已确认为非 OIDC 的 OAuth2 SSO。W3 是可用部署的必要条件；`W3_OAUTH2_ENABLED=False` 只允许作为首次生成环境文件后的安全占位，真正部署前必须改为 `True`。Authorization Code 流程固定回调路径为 `/api/auth/w3/callback/`；流程校验 `state`，默认使用 PKCE S256，并只由服务端请求 W3 Token 和 UserInfo，不依赖 OIDC discovery 或 ID Token。
- W3 UserInfo 已确认在顶层返回 `tenantId`、`uuid`、`globalUserID`、`email`、`employeeNumber`。默认 `W3_OAUTH2_EMPLOYEE_NO_FIELD=employeeNumber`、`W3_OAUTH2_EMAIL_FIELD=email`：后端只用 `employeeNumber` 作为工号精确匹配 `User.username`，用规范化为小写的 `email` 按大小写不敏感口径匹配 `User.email`，且两者必须命中同一个启用账号才允许登录。只匹配一个字段时不做 OR、降级或自动建号；邮箱缺失或格式无效返回稳定码 `email_missing`，双字段无法命中同一账号返回 `account_not_found`。`tenantId`、`uuid`、`globalUserID` 当前不参与账号匹配、不落库；登录成功后继续沿用原用户的 RBAC、Contact 绑定、数据范围和 `/api/me/` 口径。
- W3 回调后，后端通过 Django Session 保存一次性待领取登录结果，由前端再调用 `POST /api/auth/w3/complete/` 一次性领取项目现有 DRF Token。浏览器地址只携带成功/错误状态码，不携带 W3 Access Token 或项目 Token。
- 登录回跳只使用服务端配置且经校验的本站相对地址：路径必须精确为 `/login`，可携带服务端固定查询参数，但不得预置 `oauth2` / `oauth2_error` 保留键，也不得携带 URL params 或 fragment；不允许绝对 URL，也不接受请求传入的任意 `redirect`/`next` 参数，不形成开放重定向。
- W3 是唯一生产登录入口。正常访问 `/login` 时，前端先读取 W3 能力状态；`ready=true` 立即自动跳转后端 W3 授权入口，不显示按钮或用户名/密码表单。只有正在完成回调、回调失败、状态请求失败或 W3 配置未就绪时，页面显示相应状态；`GET /api/auth/w3/status/` 使用 `debug_token_login_enabled` 表示开发令牌入口是否可用，不再返回本地登录开关。
- 删除 `POST /api/auth/login/` 和 Django Admin `/admin/` 路由，访问均返回 404；服务端配置和部署模板不再包含本地登录开关。`POST /api/auth/logout/` 和 `GET /api/me/` 保持不变，W3 登录后继续按同一 RBAC 和接口人绑定推导数据范围。
- W3 未就绪且后端 `DEBUG=True` 时，登录页显示“开发令牌”输入框。开发人员只能通过 `python manage.py issue_dev_token --username <工号>` 为既有且启用的账号重新签发 DRF Token；命令每次废止该账号旧 Token，非 DEBUG、账号不存在或账号停用时拒绝执行。前端先携带输入令牌调用 `/api/me/` 验证，成功后才写入本地登录态；令牌无效或账号不可用时不得保存。该入口不是生产应急登录，生产部署必须强制 `DJANGO_DEBUG=False`。
- W3 开关、提供方地址、客户端凭据、scope、客户端认证方式、工号/邮箱字段路径、redirect URI、PKCE 和超时等配置只来自服务端环境变量；工号和邮箱字段默认分别为顶层 `employeeNumber`、`email`。前端不提供 W3 配置页，后端也不建立 W3 专用身份映射模型或保存其它 UserInfo 标识。接口人主数据为双字段映射新增 `Contact.email`，由 `core.0032_contact_email` 迁移落地；字段以 `blank=True, default=""` 兼容历史数据，迁移会把已有绑定 `User` 的非空邮箱规范化后回填到 `Contact`。旧接口人只有完成该回填或重新导入有效邮箱后，才能满足 W3 工号+邮箱双重映射。
- `User` 模型禁止生成或保存可用密码，新建、编辑、接口人同步和 `seed_base` 均写入不可用密码标记；一次性且不可逆的数据迁移把现有账号密码哈希全部失效。保留 `AbstractUser.password` 数据库列只为 Django 框架兼容，DRF Token 继续作为 W3 登录成功后的项目会话凭据。

## 七、系统需求

- 上传含候选人简历时必须选择 Rule 或 AI，并只创建一条固化该模式的 `ProcessingRun`；上传请求只使用 `processing_mode=rule|ai` 表达模式，人工处理请求只使用 `mode=rule|ai` 且拒绝 `modes`。响应仍返回 `processing_runs` 列表；生产异步环境提交后返回 `202`，本地 `CELERY_TASK_ALWAYS_EAGER=True` 会同步完成并返回 `200`。页面只在提交请求期间禁用发起按钮，提交成功后可继续筛选、预览、下发、导出和跳转，不得用全屏遮罩冻结网站。
- 生产异步环境的 AI Step4 采用有界候选人级任务调度：普通 worker 只消费 `default` 队列，独立 AI worker 以 threads 池消费 `ai` 队列；单个候选人的异常、重试或冲突不阻塞其他候选人。Docker Compose（包括离线包）部署和验收必须同时启动并确认两个消费者；仅运行 `default` worker 不视为 AI 处理能力可用。本地 SQLite + eager 模式仍保持同步串行，不依赖 Redis 或 worker。
- 上传后的后台编排固定为 Rule `Step1 → Step2 → Step3`、AI `Step1 → Step2 → Step3 → Step4`；显式 `all` 使用相同顺序，不再按旧的前置步骤倒序执行。
- 四类标准模板统一通过 `GET /api/import/templates/{template_type}/` 下载，复用 `resume.import` 权限；`template_type` 仅允许 `resume_list / jobs / schools / contacts`，分别返回“简历信息列表标准模板.xlsx”“岗位标准模板.xlsx”“院校分类标准模板.xlsx”“部门接口人标准模板.xlsx”。模板版本固定为 1，第一张工作表为冻结并启用筛选的业务数据表，第二张为填写说明。
- `POST /api/import/` 响应增加 `school_province_enrichment` 元数据，说明本次院校省份后台补全的状态和院校数；生产投递到 `ai` Celery 队列，本地 eager 模式使用单线程后台执行，导入响应均不等待补全结果。
- Prompt 管理页展示当前激活版本、共享草稿是否有未保存修改、Prompt 测试有效性、测试模型和时间；五个模块使用独立长文本编辑器并显示单项/总字符计数，提供保存草稿、真实模型测试、发布、恢复激活值和恢复系统默认值。页面还提供不含真实简历/岗位数据的只读最终组装顺序、分页历史、模块级差异和“恢复到草稿”；未保存、未测试或测试失效时必须禁用发布，发布确认明确说明“只影响新提交的 AI 任务”。
- Prompt 管理接口固定为：`GET /api/ai-prompts/`；`PATCH /api/ai-prompts/draft/`；`POST /api/ai-prompts/draft/reset/`；`POST /api/ai-prompts/draft/test/`；`POST /api/ai-prompts/draft/publish/`；`GET /api/ai-prompts/versions/`；`GET /api/ai-prompts/versions/{version}/`；`POST /api/ai-prompts/versions/{version}/restore/`。全部接口复用 `settings.manage_ai_connection`；校验错误返回 400，乐观锁或测试期间草稿/连接变化返回 409，未授权返回 403。响应和日志不返回内部连接指纹、不保存模型原始响应。
- 系统提供全局非阻塞任务中心。拥有 `pipeline.view` 的用户可从侧栏独立「处理任务」页面查看全部处理任务的发起人、类型/策略、当前阶段、进度、任务耗时、范围摘要、结果计数、最近心跳和异常；该权限默认授予管理员和 HR，二级、三级接口人默认不可见。任务耗时统一从 `ProcessingRun.created_at`（任务提交/创建时间）起算：存在 `finished_at` 时计算至该时间，否则计算至服务端当前时间。任务页面约每 2 秒轮询，同时提供手工刷新、候选人结果跳转、取消和审计，不再使用顶栏 Badge 或侧边 Drawer。任务中心对排队、运行、取消中、已取消、成功、部分失败、失败和已撤销等状态展示耗时；父运行保留 `waiting_conflict` 兼容状态，但当前 AI 候选人冲突记录在 `ProcessingRunScopeItem.waiting_conflict`，父运行通常保持 `running`。尚无 `finished_at` 的任务耗时随轮询更新，写入 `finished_at` 后耗时保持固定，不要求 WebSocket。取消活跃任务另需 `pipeline.run`：`pending` 立即转为 `cancelled`；`running` 或兼容的 `waiting_conflict` 先转为 `cancelling`，在候选人或阶段边界安全停止，已落库结果保留。任务中心需展示并审计取消请求时间、取消完成时间和取消人。
- AI 任务中心额外展示配置并发上限、当前有效并发、模型重试数和 429 限流数；运行和阶段的主结果计数统一为处理完成、需处理、失败、安全跳过和取消。AI 的待复核、待下发、建议归档作为处理完成的业务子项独立展开，零值禁用，且子项合计可小于处理完成总数。
- 处理中心跳转使用 `processing_run_id + processing_result` 定位任务结果；简历库不提供独立 `result_type` 表头筛选，只保留可与任务定位、八种状态组合的 `reason_code` 精确筛选。至少提供 `education_not_eligible`、`school_not_eligible`、`job_mapping_ambiguous`、`internal_position_name_missing`、`job_not_found`、`job_hc_exhausted`、`secondary_department_missing`、`secondary_contact_missing`、`major_not_matched`、`job_responsibility_missing`、`llm_timeout`、`resume_text_unavailable`、`ai_connection_error`、`ai_rate_limited`、`ai_invalid_output` 和 `ai_reference_invalidated`，其中 `major_not_matched` 仅用于 Rule；不得依靠模糊匹配错误文本。后台专项分流不形成公开原因码；历史专项原因通过接口折叠为普通 AI 分配或通用 AI 配置异常。
- 岗位需求、部门和接口人继续独立导入或维护，但它们只是 Step3 的基础数据，不再伪装成流水线编号步骤。
- 简历库“处理简历”从 Step2 开始：完整重算范围内院校标签和准入，再执行 Step3，选择 AI 模式时继续 Step4；不重跑 Step1 查重排序。请求必须提交唯一 `mode` 且不接受 `modes`；AI 未通过当前完整连接配置测试时拒绝提交，不能静默降级为 Rule。
- 拥有 `pipeline.run` 或 `resume.import` 任一权限的用户可读取 `GET /api/allocation-mode/`，供人工处理和上传弹窗共享；接口只返回 `default_mode / available_modes / ai_ready`，不返回模型连接详情。简历库“处理简历”弹窗按 `default_mode=rule` 默认选择 Rule；Rule 始终可选，AI 不可用时禁用并说明原因。弹窗再要求用户选择与状态互斥的`当前选中（N）`或多选八种简历状态；打开时冻结当前选中 ID 和数量，既未选当前选中也未选状态时禁止提交，避免误跑全量。`classified`、`allocated` 或任意未知状态均由后端返回 400。
- 各步中间结果可查看、表头筛选、分页、导出；所有列表、配置表和详情内嵌表格均支持拖拽调整列宽。可独立查询的分页列表通过表头文本/单选/多选选择器调用后端筛选；简历详情内嵌的投递志愿、分配尝试和 AI 筛选决策表不提供筛选器。仍保留操作列的其它页面不为操作列提供筛选器，但支持列宽调整，简历库主表不设置操作列。
- 列表 API 支持按页加载，前端分页主表默认提供每页 `10 / 20 / 50 / 100 / 500` 条选项并通过 `page_size` 提交；后端继续限制单页最大 500 条以保护服务，调用方显式配置的分页选项可覆盖共享默认值。
- 历史 Rule 与 AI 结果在简历库详情中按来源保留，便于人工核对；新任务不会同时生成两种来源。
- 当前模型连接未通过与完整配置指纹一致的真实测试时，禁用历史 AI 决策的“重试 AI”，但不影响查看历史决策、确认或取消已有待复核建议、转人工、下发已有待下发尝试及后续转派、反馈。
- 长时间批处理允许分批产生结果，任务中心按各阶段累计工作量显示连续进度，并可边跑边查看待下发、待复核、需处理、模型超时失败、建议归档和安全跳过数量；父任务状态至少包括排队、运行、取消中、已取消、成功、需处理、部分失败和失败，并兼容保留等待冲突，候选人级等待冲突以 ScopeItem 状态记录。现有 heartbeat 时间字段可继续展示，但 heartbeat 超时判定、worker 扫描和安全恢复不属于本轮验收，不得标记为已实现。
- 「配置项」删除通用“系统参数”页签，保留院校标签字典、院校准入规则、专业大类映射词表等业务配置，并新增受 `settings.manage_config` 保护的“分配参数”页签维护 `job_hc_coefficient`。`welink_enabled` 的前端管理入口移动到“部门接口人”页面，由 `department.manage` 控制；后端继续使用白名单配置键保存开关值，不提供任意配置键编辑。AI 阈值、超时、并发和重试统一放在“AI 模型连接”页面，并与模型连接共用 `settings.manage_ai_connection` 权限；同页“AI 专项”页签维护默认关闭的专项开关、严格阈值（默认 0.90）、父级二级接口人和固定三级接口人。启用时必须校验接口人状态和部门上下级关系，目标三级接口人只能从所选二级接口人下属的启用三级接口人中选择。系统不再提供 `ai_enabled`。`ai_concurrency` 是同一模型资源在所有 worker 和所有运行之间共享的自适应并发上限，默认 8，允许范围 1–20，不是每个 worker 独立的线程数。院校准入、专业词表等业务规则配置可授权 HR/管理员维护；用户、角色、权限、任务运行保护、认证安全由对应权限码控制。
