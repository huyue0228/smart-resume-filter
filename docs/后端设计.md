# 智能简历筛选系统 — 后端设计

> 本文承接 `docs/需求描述.md`，描述后端如何实现业务流程、服务边界、API、任务、权限和异常处理。数据库字段与关系以 `docs/数据库设计.md` 为准；前端页面与交互以 `docs/前端设计.md` 为准。

## 一、技术栈与运行形态

| 层 | 选型 | 说明 |
| -- | ---- | ---- |
| Web 后端 | Django + Django REST Framework | ORM、Admin、认证权限、CRUD API |
| 异步任务 | Celery + Redis | 生产环境处理 3 万条规模批任务，避免请求阻塞 |
| 数据处理 | pandas + openpyxl | 读取 xlsx、字段映射、清洗、错误收集 |
| AI / Agent | OpenAI SDK | 简历正文理解、岗位适配、分流建议 |
| 存储 | PostgreSQL（生产）/ SQLite（本机 demo） | 业务数据、中间结果、配置和任务记录 |
| 文件 | 本地 `media/resumes/`（demo） | 简历 PDF 落盘，供预览和导出 |
| 部署 | Docker Compose | 后端、前端、PostgreSQL、Redis、Celery worker 可组合部署 |

本机 demo 形态：

- SQLite。
- `CELERY_TASK_ALWAYS_EAGER=True`，任务同步执行，免 Redis/PostgreSQL。
- 后端默认 `AllowAny`，方便本机演示。

生产形态：

- PostgreSQL。
- Celery + Redis 异步执行。
- 开启真实登录、RBAC、DRF 权限和接口级数据过滤。

## 二、Django 应用划分

| app | 职责 | 关键模块 |
| --- | ---- | -------- |
| `ingestion` | 数据源适配器，解析输入并写入领域模型 | `sources.py`、`snapshot.py` |
| `core` | 领域模型与基础主数据 | `models.py`、`management/commands/seed_base.py` |
| `pipeline` | 前置处理、候选人处理主流程、Rule/AI 策略、异步任务 | `runner.py`、`strategies.py`、`services/`、`tasks.py` |
| `api` | DRF API、ViewSet、显式动作接口 | `views.py`、`serializers.py`、`urls.py` |
| `accounts` | 用户、RBAC 权限、W3 认证预留 | `models.py`、权限类 |

后端解耦原则：

- 输入层做成数据源适配器，Excel 只是当前来源；业务逻辑不直接依赖 Excel 列名。
- 候选人处理主流程只依赖 Django 模型，不读原始文件字段。
- Rule / AI 分配策略走统一策略接口。
- 业务参数外置为配置或规则表。
- 南北归属只在志愿排序规则运行时判断，不落库、不做可维护省份字典。

## 三、数据流与处理入口

总体数据流：

`ingestion（适配器） → core 模型 → 前置数据准备（院校标签 / 岗位需求 / 接口人） → 候选人处理主流程 → 候选人分配工作流 → 输出（导出 / WeLink 下发 / 接口人反馈）`

处理触发：

- 简历库上传简历后，前端自动触发候选人处理主流程。
- 分配页切换 Rule / AI 策略后，只重算“简历分类、分配与下发”环节。
- 院校分类和需求录入可提前独立运行，也可在主流程前置维护。

任务记录：

- 每次处理写入 `ProcessingRun`。
- `ProcessingRun.step` 支持 `import / all / step1 / step2 / step3 / step4 / step5`。
- `step1` 为查重与志愿排序。
- `step2` 为简历分类、分配与下发。
- `step3` 为院校分类。
- `step4` 为需求录入。
- `step5` 为兼容旧入口的分配步骤别名。
- `all` 按 `step1 → step3 → step2 → step4` 执行；不要按数字顺序推断。`step3` 需在分配前完成，确保院校标签可供分配准入使用。

## 四、导入服务设计

入口：

- `POST /api/import/`
- 支持简历信息列表、岗位需求、院校清单、部门接口人、简历包。
- 各前端数据页可只上传对应文件，后端按字段区分文件类型。

导入流程：

1. 识别上传文件类型。
2. 校验表头和格式。
3. 通过 `ingestion` 适配器解析为领域数据。
4. 规范化姓名、手机号、主体 code、院校名称、岗位类别等业务键。
5. 按应用层查询进行幂等写入。
6. 收集低风险更新、跳过、错误、舍弃数量。
7. 返回导入结果。

身份归并：

- 规范化姓名：去首尾空格、统一全/半角。
- 规范化手机号：去空格、分隔符、`+86` 前缀。
- 手机号缺失时，舍弃该候选人及其投递，不入库、不进入分配。
- 按 `normalized_name + normalized_phone` 查询候选人。
- 命中一条则复用并更新当前字段。
- 命中多条则阻断相关记录并进入导入错误清单。
- 按 `apply_id` 查询投递，存在则更新，不存在则创建并挂到候选人。
- 简历包按 `姓名（应聘ID）` 经应聘ID定位 `Resume`。

招聘主体：

- 导入时按 `RecruitingEntity.code` 匹配主体。
- 查不到时创建或进入人工映射。
- 部门和接口人不保存招聘主体归属。

撤销：

- 上传含简历数据前，写入一份 `ImportSnapshot`。
- 快照覆盖 Candidate / Resume / CandidateWorkflow / AssignmentAttempt。
- 只保留最近一份。
- `POST /api/import/undo/` 还原上传前状态，撤销后删除快照。

## 五、前置处理服务

### 院校分类

模块：`pipeline/services/classify_school.py`

职责：

- 读取 `School` 与 `SchoolTag`。
- 给候选人的第一学历、最高学历写入院校标签。
- 未命中学校或学校未配置标签时，可使用默认院校标签。
- 纯规则处理，不使用 AI。

边界：

- `School` 只保存 `province`，不保存南北归属。
- 户籍缺失时，Step1 可使用学校所在省份作为南北规则兜底。

### 需求录入

模块：`pipeline/services/demand.py`

职责：

- 解析校招岗位分类及专业要求。
- 写入 `Job`、`JobMajor`、`JobCategory`、`Department`。
- 岗位需求必须引用 `RecruitingEntity.code` 与 `JobCategory`。
- 岗位是否参与分配只看 `is_active`。

边界：

- 不引入招聘周期表。
- 不保存 `valid_from / valid_to`。
- 需求专业保留独立 `JobMajor` 明细表。

## 六、候选人处理主流程

入口：

- `POST /api/pipeline/run/`
- 请求包含 `step`、`mode`、`scope` 等参数。
- `mode` 在分配环节记录 Rule / AI。

### Step1 查重与志愿排序

模块：`pipeline/services/dedup.py`

职责：

- 以 `Candidate` 分组。
- 对候选人的 `Resume` 按投递时间、主体、南北规则排序。
- 写入 `volunteer_rank` 和分配主体。
- 维护候选人当前流程的初始当前志愿。

规则：

- 单一主体最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各 2 个岗位时，统一标第一至第四志愿。
- 户籍北方优先 GW，南方优先 YLS。
- 户籍缺失时，按学校所在省份同规则。

### Step2 简历分类、分配与下发

模块：`pipeline/services/allocate.py`

职责：

- 按候选人工作流推进当前志愿。
- 执行院校准入判断。
- 执行岗位分类、岗位匹配、部门和接口人匹配。
- 生成 `AssignmentAttempt`。
- 处理 AI 复核、HR 下发、二级转派、三级反馈、归档和手动强制分配。

共同硬规则：

- 按 `volunteer_rank` 从小到大尝试。
- 存在启用 `SchoolTagRule` 时，候选人的第一学历标签和最高学历标签必须同时命中同一条启用规则。
- 没有启用规则时，院校准入视为全部通过。
- 已通过候选人不可再强制分配。
- 反馈提交后锁定，不允许二次修改。
- 重跑分配环节不清空全部历史；已反馈、已通过、已归档记录保留，只取消并重建未反馈的自动尝试。

Rule 策略：

- 按投递岗位名称/岗位需求映射完成岗位分类。
- 写入 `JobCategory`。
- 匹配岗位二级部门和首个可用二级接口人。
- 创建 `source=rule, pending_dispatch` 尝试。

AI 策略：

- 读取或生成 `ResumeProfile`。
- 结合简历正文、项目经历、当前志愿岗位、岗位需求专业和部门信息生成推荐。
- 写入 `AgentDispatchDecision`。
- `confidence_score >= 0.75` 且建议下发时，创建 `source=ai, pending_dispatch`。
- `0.5 <= confidence_score < 0.75` 或建议复核时，创建 `source=ai, pending_review`。
- `< 0.5`、简历缺失、PDF 解析失败或建议归档时，记录风险点并建议归档或人工处理。
- AI 超时或失败不自动回退 Rule，由 HR 选择重试 AI 或切换 Rule。

## 七、分配状态机

`CandidateWorkflow.status`：

| 状态 | 含义 |
| ---- | ---- |
| `pending` | 待分配 |
| `in_progress` | 进行中 |
| `passed` | 已通过 |
| `archived` | 已归档 |

`AssignmentAttempt.status`：

| 状态 | 含义 | 允许操作 |
| ---- | ---- | -------- |
| `pending_review` | 待 HR 复核 | HR 确认下发、取消或转人工处理 |
| `pending_dispatch` | 待下发 | HR 下发或取消 |
| `dispatched_l2` | 已下发二级 | 二级接口人转派 |
| `assigned_l3` | 已转派三级 | 三级接口人反馈 |
| `passed` | 已通过 | 终态，只读 |
| `rejected` | 未通过 | 终态，系统尝试下一志愿 |
| `cancelled` | 已取消 | 终态，只读 |

核心流转：

- HR 下发：`pending_dispatch → dispatched_l2`。
- 二级转派：`dispatched_l2 → assigned_l3`。
- 三级反馈通过：`assigned_l3 → passed`，候选人流程置 `passed`。
- 三级反馈未通过：`assigned_l3 → rejected`，自动寻找下一志愿；无下一志愿则归档。
- HR 确认 AI 复核项：`pending_review → pending_dispatch`。
- 手动强制分配：取消同流程未反馈尝试后，创建 `source=manual` 尝试；归档流程恢复为 `in_progress`。目标为二级接口人时进入 HR 下发/二级处理链路，目标为三级接口人时直接进入 `assigned_l3`，并写入对应 `AssignmentHandoff` 历史。

快照与历史：

- `AssignmentAttempt` 创建时只写入二级部门、二级接口人、应聘ID、岗位名称快照。
- 三级转派历史通过 `AssignmentHandoff` 记录。
- `AssignmentHandoff` 只记录转交历史，不作为通用审计日志。

## 九、权限与数据范围

正式 RBAC：

- 使用 Django `Group / Permission`。
- 用户通过 `accounts_user_groups` 绑定一个或多个角色。
- 角色通过 `auth_group_permissions` 绑定权限点。
- 权限点由后端预置，并以树形清单返回前端。
- 前端按权限码控制菜单、路由和按钮；后端 DRF 权限类仍按同一权限码做接口级校验。

数据范围：

- 不单独建数据范围表。
- 由角色权限、`User.contact_id`、`Contact.department_id` 推导。
- 二级接口人仅可见 `contact_id` 指向自己的尝试，并只能转派给所属二级部门下的三级接口人。
- 三级接口人仅可见 `sub_contact_id` 指向自己的尝试，并提交反馈。
- HR/管理员默认可看全量。

v1 demo：

- 可继续保留前端演示身份。
- 后端仍 AllowAny。
- 真实登录、RBAC、接口级过滤待后续接入。

## 十、配置与可观测性

`Config` 保存：

- `ai_dispatch_threshold`，默认 `0.75`。
- `ai_review_threshold`，默认 `0.5`。
- `ai_timeout_seconds`。
- `welink_enabled`。

`ProcessingRun` 保存：

- 处理步骤、模式、范围、状态、运行参数、Celery task id、开始/结束时间和错误信息。

日志与错误：

- 导入错误需要返回明确原因和行级上下文。
- AI 失败需要记录失败原因，不自动回退 Rule。
- 批量下发需要返回成功数量、跳过数量和跳过原因。

## 十一、导出与外部集成

简历导出：

- 从 `media/resumes/` 取 PDF 文件。
- 打包 zip 返回。
- 支持单条、勾选批量、按筛选全部导出。
- 无文件的候选人写入压缩包内缺失清单。

WeLink：

- HR 下发后可发送 WeLink 通知。
- demo 可保留占位消息。
- 真实集成后回填 `welink_message_id`。
