# 智能简历筛选系统 — 后端设计

> 本文承接 `docs/需求描述.md`，描述后端如何实现业务流程、服务边界、API、任务、权限和异常处理。数据库字段与关系以 `docs/数据库设计.md` 为准；前端页面与交互以 `docs/前端设计.md` 为准。

> 本文是算法、状态机、API 与任务编排的唯一详细契约。业务目标不在本文重复扩写，字段表不在本文重复维护。未标为“当前实现”的段落描述目标设计；尚未落地的能力必须在“待实现与风险”中明确列出，不能仅凭配置项或占位代码视为已实现。

## 一、技术栈与运行形态

| 层 | 选型 | 说明 |
| -- | ---- | ---- |
| Web 后端 | Django + Django REST Framework | ORM、Admin、认证权限、CRUD API |
| 异步任务 | Celery + Redis | 生产环境处理 3 万条规模批任务，避免请求阻塞 |
| 数据处理 | pandas + openpyxl + xlrd | 读取 xlsx / xls / csv、字段映射、清洗、错误收集 |
| AI / Agent | OpenAI SDK（Responses / OpenAI-compatible Chat Completions） | 简历正文理解、岗位适配、结构化分流建议 |
| 存储 | PostgreSQL（生产）/ SQLite（本地开发） | 业务数据、中间结果、配置和任务记录 |
| 文件 | 本地 `media/resumes/`（本地开发） | 简历 PDF 落盘，供鉴权预览和导出 |
| PDF 预览 | 鉴权文件 API（后端）+ PDF.js 渲染（前端） | 后端返回 PDF Blob 和文件名，前端用鉴权后的 Blob 交给 PDF.js 渲染，不暴露静态文件地址 |
| 部署 | Docker Compose | 后端、前端、PostgreSQL、Redis、Celery worker 可组合部署 |

本机开发形态：

- SQLite。
- `CELERY_TASK_ALWAYS_EAGER=True`，任务同步执行，免 Redis/PostgreSQL。
- 启用 Token 登录、RBAC 权限校验和接口级数据过滤；W3 认证待外部接口方案确认后替换登录适配层。

生产形态：

- PostgreSQL。
- Celery + Redis 异步执行。
- 使用企业认证适配或系统账号登录，继续执行 RBAC、DRF 权限和接口级数据过滤。

## 二、Django 应用划分

| app | 职责 | 关键模块 |
| --- | ---- | -------- |
| `ingestion` | 数据源适配器，解析输入并写入领域模型 | `sources.py`、`snapshot.py` |
| `core` | 领域模型与基础主数据 | `models.py`、`management/commands/seed_base.py` |
| `pipeline` | 前置处理、候选人处理主流程、Rule/AI 策略、异步任务 | `runner.py`、`strategies.py`、`services/`、`tasks.py` |
| `api` | DRF API、ViewSet、显式动作接口 | `views.py`、`serializers.py`、`urls.py` |
| `accounts` | 用户、RBAC 权限、W3 认证预留 | `models.py`、权限类 |

后端解耦原则：

- 输入层做成数据源适配器，Excel 只是当前来源；业务逻辑不直接依赖 Excel 列名。
- 候选人处理主流程只依赖 Django 模型，不读原始文件字段。
- Rule / AI 分配策略走统一策略接口。
- 业务参数外置为配置或规则表。
- 南北归属只在志愿排序规则运行时判断，不落库、不做可维护省份字典。

## 三、数据流与处理入口

总体数据流：

`ingestion（适配器） → core 模型 → 前置数据准备（院校标签 / 岗位需求 / 接口人） → 候选人处理主流程 → 候选人分配工作流 → 输出（导出 / WeLink 下发 / 接口人反馈）`

处理触发：

- 简历库上传含候选人数据后，后端固定创建 Rule `ProcessingRun`；仅 `ai_config.is_ai_enabled` 为真时额外创建 AI `ProcessingRun`。两条记录独立供任务中心轮询，但由一个顺序 Celery 编排先完整执行 Rule、再执行 AI，避免同一候选人流程锁与自动重跑使两种来源尝试互相取消；每条运行各自编排 `step1 → step2`，不得复用 `all`。
- HR 在简历库“处理简历”弹窗多选 Rule、AI 任一或两项后，只为所选模式创建独立运行并重算“简历分类、分配与下发”环节；请求包含 AI 而 `ai_config.is_ai_enabled` 为假时返回校验错误，不得回退 Rule。规则分配、AI分配子页只按来源展示结果，不触发重算。
- 院校分类和需求录入可提前独立运行，也可在主流程前置维护。

任务记录：

- 每次处理写入 `ProcessingRun`。
- `ProcessingRun.step` 支持 `import / all / step1 / step2 / step3 / step4`。
- `step1` 为查重与志愿排序。
- `step2` 为简历分类、分配与下发。
- `step3` 为院校分类。
- `step4` 为需求数据准备核对；岗位需求的解析和幂等写入由 `ingestion` 在导入时完成，Step4 校验分配前置数据并输出汇总。
- `all` 按 `step3 → step4 → step1 → step2` 执行；不要按数字顺序推断。Step3/Step4 先完成院校标签和需求前置数据准备，再进入候选人主流程。普通简历上传不等同于 `all`，默认只执行 Step1/Step2。
- 每个运行记录保存发起人、当前阶段、最近心跳和不含候选人明细的范围摘要；阶段进度由 `ProcessingRunStage` 记录。HR/管理员可轮询查看共享任务，二级、三级接口人不可查看处理任务。前端仅在顶栏「处理任务」Badge 提示活跃数量，点击后以非遮罩侧边 Drawer 读取这些记录。HR/管理员可通过取消动作请求停止活跃运行：排队任务立即取消；运行中或等待冲突任务进入取消中，并在候选人或阶段边界安全停止，已提交的业务结果不回滚。

> **本次实现状态（2026-07-10）**：`ProcessingRunStage`、`ProcessingRunScopeItem`、`workflow_revision_at_submit`、自动分配的 Candidate/Workflow 数据库行锁和前端任务中心已落地。下文的“按上传记录范围恢复并版本冲突 409”、heartbeat 超时监控/恢复、所有人工流程 API 统一加锁，以及 expected revision 推进，均为目标设计，尚未落地；实现前不得按已具备能力对外承诺。本地 `CELERY_TASK_ALWAYS_EAGER=True` 仍会同步完成任务并返回 200；验收非冻结交互必须关闭 eager 并启动 Redis/Celery worker，此时接口才会立即返回 202。

## 四、导入服务设计

入口：

- `POST /api/import/`
- 支持简历信息列表、岗位需求、院校清单、部门接口人、简历包。
- 四张业务表支持 `.xlsx`、`.xls`、`.csv` 表格文件，后端优先按文件内容识别格式，文件后缀仅作为辅助判断。
- 各前端数据页可只上传对应文件，后端按字段区分文件类型。

导入流程：

1. 识别上传文件类型。
2. 校验表头和格式。
3. 通过 `ingestion` 适配器解析为领域数据。
4. 规范化姓名、手机号、主体 code、院校名称、岗位类别等业务键。
5. 按应用层查询进行幂等写入。
6. 收集低风险更新、跳过、错误、舍弃数量。
7. 返回导入结果。

身份归并：

- 规范化姓名：去首尾空格、统一全/半角。
- 规范化手机号：去空格、分隔符、`+86` 前缀。
- 手机号缺失时，舍弃该候选人及其投递，不入库、不进入分配。
- 按 `normalized_name + normalized_phone` 查询候选人。
- 命中一条则复用并更新当前字段。
- 命中多条则阻断相关记录并进入导入错误清单。
- 按 `apply_id` 查询投递，存在则更新，不存在则创建并挂到候选人。
- 简历包按 `姓名（应聘ID）` 经应聘ID定位 `Resume`。

招聘主体：

- 导入时按 `RecruitingEntity.code` 匹配主体。
- 查不到时创建或进入人工映射。
- 部门和接口人不保存招聘主体归属。

部门接口人：

- 导入部门接口人信息时，按 `Contact.employee_no` 幂等写入接口人主数据。
- 每个有效导入的接口人同步一个系统用户：`User.username = Contact.employee_no`，新账号默认密码为 `pass1234`。
- 同步用户时按接口人层级确保拥有 `二级接口人` 或 `三级接口人` 角色，并写入 `User.contact_id`；已有同用户名用户保留原可用密码和非接口人业务角色，仅替换二级/三级接口人角色、启停状态和接口人绑定。
- 接口人导入只确保预置角色存在；默认权限仅在角色首次创建时初始化，不得通过导入重新执行 `permissions.set()` 覆盖管理员已维护的角色权限。
- 部门接口人 replace 导入时，本次文件中不存在的旧接口人置为停用，其绑定账号同步置为停用；本次文件中的接口人账号按 `Contact.is_active` 恢复或停用。replace 导入保留软停用语义，避免批量导入误删历史主数据。
- 部门和接口人不保存招聘主体归属，也不提供“主体来源字段”筛选；导入文件中的招聘主体仅作为外部来源上下文，不写入 `Department` 或 `Contact`。
- 用户管理或接口人清单中的单条删除采用清理语义：`DELETE /api/users/{id}/` 删除账号、Token 和角色绑定；若用户绑定 `Contact`，同步删除该接口人。`DELETE /api/contacts/{id}/` 删除接口人，并同步删除绑定该接口人的用户。删除前后端需先清空历史分配、转派、AI 决策等记录上的用户/接口人外键，仅保留快照字段和审计记录，避免级联删除候选人流程历史。
- 后续 W3 认证按工号识别用户，映射到同一个 `User.username`，不改变 RBAC 和数据范围推导。

撤销：

- 上传含简历数据前先解析业务键，确定本次新增或更新的候选人/投递影响范围，并写入一份 `ImportSnapshot`；不得用全表快照回滚无关候选人的并发操作。
- 快照在该影响范围内覆盖 Candidate / Resume / ResumeProfile / CandidateWorkflow / AgentDispatchDecision / AssignmentAttempt / AssignmentHandoff，并记录关联 `ProcessingRun` id 和上传/关联处理完成后的候选人流程 revision 基线。
- **目标设计（未实现）**：快照按上传记录和创建人保存；HR 只可查询/撤销自己的上传记录，管理员可查询/撤销全部上传记录；同一上传记录只能撤销一次。
- **目标设计（未实现）**：`POST /api/import/undo/` 按上传记录还原上传前业务状态。关联处理任务仍在 `pending`、`running` 或 `waiting_conflict` 时返回 `409`；否则在同一事务内依次锁定范围内 Candidate 和 CandidateWorkflow，并比较每个候选人当前 revision 与上传后基线。任一不一致即整体返回 `409`，不允许部分回滚；全部一致才撤销。撤销后快照标记已撤销，不再作为可撤销对象。对应 `ProcessingRun` 不删除，状态改为 `undone` 并记录撤销时间，保留操作审计。
- 普通导入接口的 `replace` 不得删除候选人、投递、反馈、分配尝试或转派历史。候选人/投递仍按业务键增量并入；岗位、院校、接口人等主数据采用更新或停用语义。测试环境的彻底清空必须走独立运维命令，并显式拒绝存在受保护历史的数据池。

## 五、前置处理服务

### 院校分类

模块：`pipeline/services/classify_school.py`

职责：

- 读取 `School` 与 `SchoolTag`。
- 给候选人的第一学历、最高学历写入院校标签。
- 系统通过 `seed_base` 预置并在分类时自愈启用的 `SchoolTag(code="NON_TARGET", name="非目标院校")`。未命中导入院校清单的学校始终使用该标签；只有命中清单但 `School.school_tag_id` 为空时，才使用启用的默认标签，若无默认标签则回退到“非目标院校”。该标签可用于后续分类、筛选和准入规则。
- 纯规则处理，不使用 AI。

边界：

- `School` 只保存 `province`，不保存南北归属。
- 户籍缺失时，Step1 可使用学校所在省份作为南北规则兜底。

### 需求数据准备核对

模块：`pipeline/services/demand.py`

职责：

- 岗位文件解析、业务键匹配和 `Job` / `JobMajor` / `JobCategory` / `Department` 的幂等写入由 `ingestion` 完成。
- Step4 校验启用岗位是否具备 `RecruitingEntity.code`、`JobCategory`、二级部门、需求专业等分配前置信息，并汇总岗位数、HC 和缺口。
- 专业大类映射主数据 `MajorCategory` / `MajorAlias` 由初始化命令和配置 API 维护，供 Rule 专业匹配和后续 AI 上下文复用。
- 岗位是否参与分配只看 `is_active`。

边界：

- 不引入招聘周期表。
- 不保存 `valid_from / valid_to`。
- 需求专业保留独立 `JobMajor` 明细表；`MajorCategory` / `MajorAlias` 不替代岗位原始需求专业，只作为匹配增强词表。

## 六、候选人处理主流程

入口：

- `POST /api/pipeline/run/`
- 请求包含 `step`、`modes`、`scope` 等参数；`modes` 是 `rule` / `ai` 的非空数组，可选择一项或两项；缺失、空数组或非数组一律返回 400。
- 每个模式创建一条独立 `ProcessingRun`，其 `mode` 记录 Rule / AI；`modes` 含 AI 时服务端必须先校验 `ai_config.is_ai_enabled`。
- `scope` 支持限定处理范围；简历库“处理简历”按钮传入 `scope.system_statuses` 和当前筛选条件时，只重跑命中范围内候选人的 Step2，不重跑全量池。
- 服务端在提交时解析并固化内部 `ProcessingRunScopeItem` 范围及每个候选人的 `workflow_revision_at_submit`；后续执行不再按动态筛选条件重新查询。当前 `resume_process` 的 Step1 不写 CandidateWorkflow，因此 Step2 可继续使用提交版本快照。**目标迁移**为 ScopeItem 增加本任务下一次执行所需的 expected revision，并在本任务成功写入后同一事务内推进，以覆盖未来跨阶段都可能写流程的情形。生产异步环境创建记录并投递顺序 Celery 编排后返回 `202 + processing_runs`；本地 `CELERY_TASK_ALWAYS_EAGER=True` 同步完成后返回 200。前端不逐步调用各 Step。

### Step1 查重与志愿排序

模块：`pipeline/services/dedup.py`

职责：

- 以 `Candidate` 分组。
- 对候选人的 `Resume` 按投递时间、主体、南北规则排序。
- 写入 `volunteer_rank` 和分配主体。
- 维护候选人当前流程的初始当前志愿。

规则：

- 单一主体最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各 2 个岗位时，统一标第一至第四志愿。
- 户籍北方优先 GW，南方优先 YLS。
- 户籍缺失时，按学校所在省份同规则。

### Step2 简历分类、分配与下发

模块：`pipeline/services/allocate.py`

职责：

- 按候选人工作流推进当前志愿。
- 执行院校准入判断。
- 执行岗位分类、岗位匹配、部门和接口人匹配。
- 生成 `AssignmentAttempt`。
- 处理 AI 复核、HR 下发、二级转派、三级反馈、归档和手动强制分配。

共同硬规则：

- 按 `volunteer_rank` 从小到大尝试。
- 存在启用 `SchoolTagRule` 时，候选人的第一学历标签和最高学历标签必须同时命中同一条启用规则。
- 没有启用规则时，院校准入视为全部通过。
- 简历库“处理简历”只重跑带筛选范围的 Step2，不触发全量院校分类 Step3；Step2 必须先锁定本次候选人范围，再仅为范围内缺失 `first_degree_tag` / `highest_degree_tag` 的候选人按当前院校清单、默认院校标签和启用的“非目标院校”兜底标签补齐标签，并且不覆盖已有院校标签，随后再执行院校准入判断。
- 已通过候选人不可再通过“手动强制分配”入口分配；如需重开，必须走简历库“处理简历”入口并显式携带系统简历状态范围。
- 反馈提交后锁定，不允许二次修改。
- 简历库“处理简历”按所选 `modes` 重跑分配环节时不清空全部历史；已反馈、已通过、已归档记录保留。Rule 与 AI 均被选中时，两个来源的自动尝试必须并存，不得在顺序执行或重跑中互相取消；规则分配、AI分配子页只作来源筛选，不触发该重跑。
- 简历库“处理简历”是 HR 主动重新分配入口，必须携带系统简历状态范围及至少一个模式。该入口允许重开已通过、已归档或已不通过候选人流程：保留历史尝试和反馈记录，清空 `passed_attempt_id`、归档原因、阻塞原因和完成时间，将流程恢复为 `in_progress`，再分别按所选 Rule / AI 生成新的自动分配尝试。

Rule 策略：

- 按投递岗位名称/岗位需求映射完成岗位分类。
- 投递招聘主体与岗位需求主体双方都有值时必须一致；岗位命中优先级为同主体、精确匹配、对外发布名称、职位名称、包含匹配兜底，避免多岗位命中时依赖数据库自然顺序。
- 岗位配置需求专业时，先用启用的 `MajorAlias` 将候选人最高学历专业和每个岗位需求专业映射到 `MajorCategory`；任一专业大类相交即视为专业通过。
- 若大类无交集，或候选人/岗位任一侧未映射到启用大类，则再执行专业名双向包含兜底，例如“计算机科学与技术”命中“计算机”；词表和兜底都不命中时继续尝试下一个候选岗位。
- 岗位未配置需求专业，或岗位需求专业为“专业不限 / 不限 / 不限专业”等通配表达时直接放行；候选人最高学历专业缺失且岗位配置了非通配需求专业时不自动放行。
- 写入 `JobCategory`。
- 匹配岗位二级部门和首个可用二级接口人。
- 当前志愿匹配岗位和二级部门但没有可用二级接口人时，保持 `CandidateWorkflow.status=in_progress`、`current_resume/current_rank` 指向当前志愿，写入 `block_reason=contact_not_found` 和 `block_detail`，不创建 `AssignmentAttempt`，不归档，不推进下一志愿。
- 当前志愿匹配到可用二级接口人时，创建 `source=rule, pending_dispatch` 尝试，并写入包含院校、志愿、岗位、专业大类/专业名、部门和接口人的 `match_reason`；生成有效尝试时清空 `block_reason/block_detail`。

AI 策略：

> 当前实现已移除 demo/Rule 回退和固定评分，正式链路位于 `apps.pipeline.ai`，根据当前模型 profile 的 `api_style` 调用模型：`responses` 使用 Pydantic 结构化输出，`chat_json` 使用 JSON Schema 约束并由后端统一校验。未配置密钥、PDF 失败、模型失败或后端护栏失败时写入失败决策并归档当前流程，不自动回退 Rule。

- 系统先执行共同硬规则；硬规则不通过、没有当前志愿、没有岗位需求或院校准入不通过时，不调用 AI。
- `ResumeProfileExtractor` 读取 PDF 抽取正文，生成或更新 `ResumeProfile`，提取教育经历、专业方向、项目经历、实习经历、技能栈、证书奖项和画像风险点。
- `DispatchRecommender` 结合当前有效志愿、岗位需求专业、岗位类别、部门和接口人信息，生成推荐动作、推荐岗位、推荐二级部门、推荐二级接口人、推荐理由和简历证据。
- `DecisionScorer` 根据专业匹配、技能匹配、项目/实习证据强度、岗位需求覆盖度、部门确定性和简历文本质量生成分项评分，并汇总 `confidence_score`。
- `DecisionGuard` 是后端非 AI 裁决器，校验 AI 输出引用的岗位、部门、接口人是否真实存在且可用，并再次校验院校准入、当前志愿和状态机。
- AI 调用必须走结构化输出，后端按 schema 做字段类型、枚举值、引用 ID 和分数区间校验；输出不合法时记录 `invalid_ai_output`，不生成高置信度下发尝试。
- 写入 `AgentDispatchDecision`，只保存业务摘要、证据、风险点、版本和错误信息，不保存 LLM 完整原始响应。
- `recommendation=dispatch` 且 `confidence_score >= ai_dispatch_threshold` 时，创建 `source=ai, pending_dispatch`。
- `recommendation != archive` 且 `confidence_score >= ai_review_threshold`，但未达到自动下发条件时，创建 `source=ai, pending_review`。
- `recommendation=archive`、`confidence_score < ai_review_threshold`、简历缺失、PDF 解析失败、建议归档或后端校验最终失败时，只写入 AI 决策记录，不生成分配尝试，并将 `CandidateWorkflow` 置为 `archived(agent_no_recommendation)`。HR 仍可重试 AI、切换 Rule 后按范围重新处理或手动强制分配。
- AI 超时或失败不自动回退 Rule，由 HR 选择重试 AI、切换 Rule 或手动强制分配。
- 同一 `resume_id + evaluated_job_id + file_checksum + profile_version + prompt_version + decision_version` 已有有效决策时优先复用；其中 `file_checksum/profile_version` 通过 `profile_id` 关联的 `ResumeProfile` 校验。HR 主动重试 AI、简历文件变化、画像版本变化或决策版本变化时才重新调用。

AI 失败分类：

| 错误码 | 含义 | 处理 |
| ------ | ---- | ---- |
| `pdf_missing` | 没有 PDF 文件 | 建议归档或人工处理 |
| `pdf_parse_failed` | PDF 正文抽取失败 | 建议归档或人工处理 |
| `profile_incomplete` | 简历画像不足 | 低置信度或建议复核 |
| `llm_timeout` | AI 调用超时 | 可按配置重试，最终进入人工处理 |
| `llm_error` | AI 接口错误 | 可按配置重试，最终进入人工处理 |
| `invalid_ai_output` | 结构化输出不合法 | 不生成下发尝试，进入人工处理 |
| `reference_not_found` | 推荐岗位/部门/接口人不存在 | 不生成下发尝试，进入人工处理 |
| `guardrail_blocked` | 被后端硬规则拦截 | 不调用或不采纳 AI |
| `ai_not_configured` | 供应商、密钥或服务端依赖未配置 | 不调用 AI，提示管理员在「AI 模型连接」完成配置 |

批处理、进度与并发：

- 每个模式使用独立 `ProcessingRun`，Rule 与 AI 均可每 100 或 200 名候选人切成一个 Celery 子任务；同一次上传或多选处理由外层顺序 Celery 编排先执行全部 Rule 运行、再执行全部 AI 运行，每条运行各自持有 `step1 → step2` 阶段记录。不得并发执行这两种来源而互相取消尝试。
- 每条候选人独立处理当前有效志愿，单条失败不影响同批其他候选人。
- **目标设计（部分未实现）**：子任务按批次或约每秒回写 `ProcessingRunStage` 的工作量、业务结果和心跳；前端连续进度按全部已创建阶段 `Σ processed_count / Σ total_count` 计算，父 `ProcessingRun` 只汇总状态、当前阶段、心跳和最终业务结果，避免切换阶段时进度归零。
- `ProcessingRun` 记录 Celery group id、chunk 大小、chunk 总数、已完成 chunk、失败 chunk 和失败摘要；失败 chunk 可由后端按 chunk 范围重试。
- 前端可以在任务运行中刷新查看已产生的 AI 决策和分配尝试，不等待全量完成。
- 全部成功时 `ProcessingRun.status=success`；部分候选人或部分 chunk 失败但主任务完成时为 `partial_failed`；总任务异常中断时为 `failed`。
- 自动分配当前已在每候选人事务内使用 `select_for_update` 锁定 Candidate 与 CandidateWorkflow 串行执行；锁暂时不可得的条目等待当前事务释放后重试，运行记录在无可执行条目时显示 `waiting_conflict`。
- **目标设计（未实现）**：所有会写入候选人流程、分配尝试或转派状态的自动与人工操作统一使用上述事务锁，并在成功写入时递增 workflow revision。自动任务还锁定 ScopeItem，并比较其 expected revision；不一致时标记 `skipped_manual_change` 并安全跳过。本任务成功写入时同步推进 ScopeItem 的 expected revision，因此同一父任务后续阶段不会误判自身的前序变更。
- **目标设计（未实现）**：worker 每次批量回写同时刷新父/阶段 heartbeat。超过配置的 heartbeat 超时阈值仍未刷新时，监控逻辑将当前阶段和父运行标记为 `failed(worker_heartbeat_timeout)`；安全重试只重新投递仍为 `pending` 或 `waiting_conflict` 的 ScopeItem，已成功、失败或 `skipped_manual_change` 的项不重跑，并继续使用版本校验，避免重复覆盖或重复创建尝试。
- 本地开发可继续使用 eager Celery 同步执行，此时运行接口会在任务结束后返回 200；生产异步环境返回 202，服务字段保持同一响应结构。验收页面非冻结行为时须关闭 eager 并启动 Redis 和 worker。

## 七、分配状态机

系统简历状态：

| 状态码 | 中文 | 推导口径 |
| ------ | ---- | -------- |
| `raw` | 待处理 | 当前候选人/当前投递尚未完成岗位类别和院校标签分类 |
| `classified` | 已分类 | 已完成岗位类别和院校标签分类，但没有有效业务部门推荐或下发尝试 |
| `allocated` | 已分配 | 存在 `pending_review` / `pending_dispatch` 等 HR 待复核或待下发尝试，业务部门尚不可见 |
| `pending_screening` | 待筛选 | 存在 `dispatched_l2` / `assigned_l3` 尝试，已给业务部门但尚未反馈 |
| `screening_passed` | 筛选通过 | 当前流程或最近有效尝试已由业务部门反馈通过 |
| `screening_rejected` | 筛选不通过 | 最近有效尝试已反馈未通过，或全部志愿未通过导致归档 |

> 系统简历状态不落为 `Resume.status`，后者继续保存导入文件中的原始“应聘状态”。列表筛选由后端根据 `CandidateWorkflow`、当前有效 `Resume`、`AssignmentAttempt`、院校标签和岗位类别推导。存在多条历史时按当前活动流程优先：`screening_passed > pending_screening > allocated > screening_rejected > classified > raw`；`screening_passed` 只认当前 `workflow.status=passed` 和 `passed_attempt_id`，待筛选/已分配只认当前未取消活动尝试，筛选不通过只认当前有效志愿的最新反馈或 `all_rejected`，历史志愿的 passed/rejected/cancelled 不覆盖重开后的活动流程。

`CandidateWorkflow.status`：

| 状态 | 含义 |
| ---- | ---- |
| `pending` | 待分配；简历库按流程状态筛选 `pending` 时，也包含尚未创建 `CandidateWorkflow` 的候选人 |
| `in_progress` | 进行中 |
| `passed` | 已通过 |
| `archived` | 已归档 |

`AssignmentAttempt.status`：

| 状态 | 含义 | 允许操作 |
| ---- | ---- | -------- |
| `pending_review` | 待 HR 复核 | HR 确认下发、取消或转人工处理 |
| `pending_dispatch` | 待下发 | HR 下发或取消 |
| `dispatched_l2` | 已下发二级 | 二级接口人转派 |
| `assigned_l3` | 已转派三级 | 三级接口人反馈 |
| `passed` | 已通过 | 终态，只读 |
| `rejected` | 未通过 | 终态，系统尝试下一志愿 |
| `cancelled` | 已取消 | 终态，只读 |

核心流转：

- HR 下发：`pending_dispatch → dispatched_l2`。
- 二级转派：`dispatched_l2 → assigned_l3`。
- 三级反馈通过：`assigned_l3 → passed`，候选人流程置 `passed`。
- 三级反馈未通过：`assigned_l3 → rejected`，自动寻找下一志愿；无下一志愿则归档。
- 当前志愿缺可用二级接口人：流程保持 `in_progress` 并记录阻塞原因，等待 HR 补齐接口人、手动分配或重新处理；该场景不触发下一志愿。
- HR 确认 AI 复核项：`pending_review → pending_dispatch`。
- HR 取消 AI 复核项：`pending_review → cancelled`，写入 `cancel_reason=hr_cancelled`；若流程不存在其它活动尝试，则归档为 `agent_no_recommendation`。
- HR 取消待下发项：`pending_dispatch → cancelled` 并写入取消原因；无其它活动尝试时，Rule 结果归档为 `hr_cancelled`，AI 结果归档为 `agent_no_recommendation`，均可由 HR 重新处理或手动分配。
- HR 转人工处理 AI 复核项：先将原 `pending_review` 置为 `cancelled(manual_replaced)`，再从明确的 `resume_id` 发起手动强制分配。
- 手动强制分配：取消同流程未反馈自动尝试后，创建 `source=manual` 尝试并清空阻塞原因；归档流程恢复为 `in_progress`。目标为二级接口人时进入 HR 下发/二级处理链路。目标为三级接口人时，系统先从三级部门父级确定二级部门；只有一个有效二级接口人时自动补齐，存在多个时要求请求显式传入 `secondary_contact_id`，没有有效二级接口人时拒绝操作。成功后同时填充 `contact/sub_contact`，直接进入 `assigned_l3`，并依次写入 HR→二级、二级→三级两条 `AssignmentHandoff`。

快照与历史：

- `AssignmentAttempt` 创建时写入二级部门、二级接口人姓名/工号、应聘ID、岗位名称和操作者快照；三级转派时补写三级部门、三级接口人姓名/工号快照。
- `AssignmentHandoff` 记录转派历史，同时写入 from/to 接口人姓名/工号、转入部门名称和操作者用户名快照。
- `AgentDispatchDecision` 写入 AI 推荐接口人姓名/工号快照，避免推荐接口人后续删除导致决策详情不可读。
- `AssignmentHandoff` 只记录转交历史，不作为通用审计日志。

## 八、API 设计

通用约定：

- 列表 API 默认分页返回，支持 `page` 和 `page_size` 参数；`page_size` 最大 500，避免一次性拉取过大结果集。
- 候选人、岗位、院校、接口人等列表的表头筛选由后端执行，查询参数直接对应前端可筛选列；候选人姓名搜索同时匹配姓名原文、姓名全拼和姓名拼音首字母。
- 布尔筛选统一接受 `true` / `false` 字符串。
- 文件导出与预览返回 Django `HttpResponse`，不是 DRF `Response`；导出响应通过 `X-Export-Count`、`X-Export-Missing` 返回命中文件数和缺失文件数，预览响应通过 `X-Resume-Filename` 返回原始文件名。预览接口只负责鉴权、数据范围过滤和返回 PDF Blob，不暴露 `media/resumes/` 静态地址，浏览器内预览由前端 PDF.js 将 Blob 渲染到 canvas 完成。导出仅命中单个可用文件且无缺失清单时返回原文件下载，命中多个文件或需要缺失清单时返回 zip。

当前代码落点：

- 标准分页类在 `apps.api.pagination.StandardResultsSetPagination`，由 DRF `DEFAULT_PAGINATION_CLASS` 统一启用；默认 `PAGE_SIZE=20`，允许前端通过 `page_size` 调整，最大 500。
- 文件导出统一走简历导出响应构造器，候选人导出和分配尝试导出复用同一套文件收集、缺失清单和统计响应头；仅一个可用文件且无缺失清单时直接返回原文件，多文件或存在缺失清单时返回 zip。
- 文件预览统一走 `resume_preview_response(resume)`，直接从 `media/resumes/` 读取文件并以 PDF Blob 响应返回，同时通过响应头携带原始文件名；文件缺失或未匹配时返回 404。前端拿到 Blob 后用 PDF.js 渲染 PDF，非 PDF 文件提示下载原文件。
- `bool_query_value` 负责把查询字符串中的 `true` / `false` 规范为布尔值，用于岗位、接口人等表头筛选。
- API 测试需覆盖分页参数、候选人/岗位/院校/接口人表头筛选、候选人拼音搜索、候选人导出单文件/多文件/缺失清单分支、投递预览、候选人 `preview_resume` 当前投递优先和无文件回退、分配尝试数据范围预览，以及接口人 replace 导入不清空简历池。

## 九、权限与数据范围

RBAC：

- 使用 Django `Group / Permission`。
- 用户通过 `accounts_user_groups` 绑定一个或多个角色。
- 角色通过 `auth_group_permissions` 绑定权限点。
- 权限点由后端预置，并以树形清单返回前端。
- 前端按权限码控制菜单、路由和按钮；后端 DRF 权限类仍按同一权限码做接口级校验。

数据范围：

- 不单独建数据范围表。
- 由角色权限、`User.contact_id`、`Contact.department_id` 推导。
- 二级接口人仅可见 `contact_id` 指向自己且已由 HR 下发的尝试，至少排除 `pending_review`、`pending_dispatch`、`cancelled` 等 HR 内部状态；二级接口人只能转派给所属二级部门下的三级接口人。
- 三级接口人仅可见 `sub_contact_id` 指向自己的尝试，并提交反馈。
- HR/管理员默认可看全量。
- AI 分配子页仅向拥有全量分配尝试查看权限的 HR/管理员开放；二级、三级接口人进入规则分配子页，其数据范围仍由上述接口人过滤决定。

本地正式开发：

- W3 方案确认前，使用本地账号密码换取 DRF Token。
- 接口人账号由部门接口人导入自动创建，用户名为工号，新账号默认密码为 `pass1234`；用户管理不维护 `first_name`、`last_name` 等 Django 姓名类字段，姓名展示来自绑定的 `Contact`。
- 用户管理删除采用清理语义：删除 `User` 账号、Token 和角色绑定；若用户绑定 `Contact`，同步删除该接口人。后端删除流程必须先将历史分配、转派、AI 决策等记录中的 `contact/sub_contact/recommended_contact/from_contact/to_contact/created_by` 等外键置空，历史页面通过 `AssignmentAttempt`、`AssignmentHandoff`、`AgentDispatchDecision` 的快照字段继续展示当时的接口人、工号、部门和操作者信息，管理员不能通过删除用户破坏候选人流程历史。
- `seed_base` 初始化管理员、HR、多个二级接口人、多个三级接口人账号，以及专业大类映射词表第一版，供权限链路和 Rule 专业匹配功能测试；其中 `OTHER_GENERAL` 泛称大类默认停用，需由 HR 按招聘口径主动启用或拆分。
- 后端接口默认要求认证；业务接口按稳定权限码做 DRF 权限校验，并按接口人绑定过滤分配数据范围。

## 十、配置与可观测性

`Config` 保存：

- `ai_dispatch_threshold`，默认 `0.75`。
- `ai_review_threshold`，默认 `0.5`。
- `ai_timeout_seconds`。
- `ai_concurrency`。
- `ai_retry_count`。
- `ai_retry_backoff_seconds`。
- `processing_run_heartbeat_timeout_seconds`。
- `welink_enabled`。

AI 配置分层：

- `backend/config/ai_models.json` 维护模型 profile 注册表，声明配置表单可选的默认模板、`api_style`、默认模型和 Base URL；`apps.pipeline.ai_config` 负责加载、校验并只读取管理员保存的连接配置。
- 管理员通过受 `settings.manage_permissions` 保护的 `/api/ai-connection/` 管理 profile、`api_style`、`model_name`、`base_url` 与 API Key；HR、二级和三级接口人无查看、修改或测试权限。连接信息不混入普通 `/api/configs/` 的可编辑项。
- API Key 只接受写入：GET 响应只给出是否已配置等安全摘要，永不返回明文或密文。服务端使用 Django `SECRET_KEY` 派生 Fernet 密钥加密后保存到 `Config`，运行时解密供调用使用；API、前端状态、任务记录和错误响应均不得回显 Key。
- 模型连接只从管理员保存的 Config 记录读取；调用时完全不读取环境变量或部署文件中的 profile、模型名、Base URL 与 API Key。清除已保存 Key 后 AI 未配置并返回 `ai_not_configured`；profile 注册表只提供配置表单模板。
- `POST /api/ai-connection/test/` 以当前保存配置发起最小真实模型请求，返回可读成功信息或稳定错误码与脱敏摘要。连接失败、超时和调用异常只按统一映射写入 `AgentDispatchDecision.error_code/error_message`；第三方 SDK 原始异常绝不写入 AI 决策、API 响应或日志。后端与 worker 标准输出仅记录 profile、model、api_style、稳定错误码和异常类型，供 Docker logs 排查。

`ProcessingRun` 保存：

- 处理步骤、模式、内部固化范围及对外范围摘要、发起人、当前阶段、状态、运行参数、Celery task id、最近心跳、开始/结束时间、最终业务结果和错误信息。
- 取消审计：`cancel_requested_at`、`cancelled_at`、`cancelled_by` 及取消人用户名快照。运行状态包含 `cancelling` / `cancelled`；任务中心的活跃集应包含 `pending`、`running`、`waiting_conflict` 和 `cancelling`。
- `ProcessingRunStage` 保存父运行内各阶段的状态、累计工作量和 heartbeat；普通上传的两个阶段为 Step1、Step2，连续进度只由阶段累计工作量计算。
- 批处理最终结果统计：成功、失败、安全跳过、待复核、待下发、建议归档；Rule 与 AI 使用同一口径，阶段工作量不由父运行保存。
- Celery chunk 追踪：group id、chunk 大小、chunk 总数、已完成 chunk、失败 chunk、失败摘要。
- AI 策略版本信息：模型名称、prompt 版本、decision 版本。
- 上传撤销时，相关运行记录保留并更新为 `status=undone`，写入撤销时间和操作者；关联任务未结束时拒绝撤销，快照改为已撤销状态而非删除。

日志与错误：

- 导入错误需要返回明确原因和行级上下文。
- AI 失败需要记录失败原因，不自动回退 Rule。
- AI 重试只针对超时、限流、网络错误等临时错误；PDF 解析失败、输出结构不合法、引用不存在等确定性错误不做无限重试。
- 批量下发需要返回成功数量、跳过数量和跳过原因。
- 取消不会回滚已经落库的候选人处理或分配尝试；执行器在开始阶段、处理候选人循环及结束阶段检查取消请求，取消后把未完成阶段标记为 `cancelled` 并结束父运行。

## 十一、导出与外部集成

简历导出：

- 从 `media/resumes/` 取 PDF 文件。
- 仅命中一个可用文件且没有缺失清单时，直接返回该原始文件，保留原文件名和内容类型；命中多个文件或存在缺失清单时，打包 zip 返回。
- 支持从候选人列表按候选人 ID、候选人当前筛选条件导出，也支持从分配尝试列表单条、勾选批量、按筛选全部导出。
- 无文件的候选人写入压缩包内缺失清单。

简历预览：

- 候选人详情从 `Resume` 维度预览 PDF；默认预览对象由 Candidate API 的 `preview_resume` 提供，当前投递有文件时优先预览当前投递，当前投递无文件时回退同候选人第一条有文件投递。
- 分配尝试详情从 `AssignmentAttempt` 维度预览 PDF，并复用分配尝试的数据范围控制，确保二级/三级接口人只能预览自己可见尝试的简历。
- 后端预览接口不生成图片、不转换 PDF，也不返回静态文件路径；鉴权和数据范围校验通过后，接口返回 PDF Blob，并通过响应头返回原始文件名。PDF.js 渲染、Blob URL 新窗口打开和下载入口由前端负责；无权限或越权时前端不得提供预览或下载入口，PDF 渲染失败或非 PDF 文件时保留下载原文件入口。
- 生产 Nginx/前端容器不得挂载或公开 `media/resumes/`，不得配置 `/media/` 静态 alias；预览和下载必须全部经过上述鉴权 API。

WeLink：

- HR 下发后可发送 WeLink 通知。
- demo 可保留占位消息。
- 真实集成后回填 `welink_message_id`。
