# 海纳智聘 — 后端设计

> 本文承接 `docs/需求描述.md`，描述后端如何实现业务流程、服务边界、API、任务、权限和异常处理。数据库字段与关系以 `docs/数据库设计.md` 为准；前端页面与交互以 `docs/前端设计.md` 为准。

> 本文是算法、状态机、API 与任务编排的唯一详细契约。业务目标不在本文重复扩写，字段表不在本文重复维护。未标为“当前实现”的段落描述目标设计；尚未落地的能力必须在“待实现与风险”中明确列出，不能仅凭配置项或占位代码视为已实现。

## 一、技术栈与运行形态

| 层 | 选型 | 说明 |
| -- | ---- | ---- |
| Web 后端 | Django + Django REST Framework | ORM、Admin、认证权限、CRUD API |
| 身份认证 | DRF Token + W3 OAuth2 Authorization Code | W3 是唯一生产入口；无本地密码 API，DEBUG 且 W3 未就绪时可用命令重新签发开发 Token。两种 Token 取得路径共用 User / RBAC；W3 使用 state、默认 PKCE S256 和服务端 Token/UserInfo 请求 |
| 异步任务 | Celery + Redis | 生产环境处理 3 万条规模批任务，避免请求阻塞 |
| 数据处理 | pandas + openpyxl + xlrd | 读取 xlsx / xls / csv、标准字段解析、清洗、错误收集 |
| AI / Agent | OpenAI SDK（Responses / OpenAI-compatible Chat Completions） | 简历正文理解、岗位适配、结构化分流建议 |
| 存储 | PostgreSQL（生产）/ SQLite（本地开发） | 业务数据、中间结果、配置和任务记录 |
| 文件 | 本地 `media/resumes/`（本地开发） | 简历 PDF 落盘，供鉴权预览和导出 |
| PDF 预览 | 鉴权文件 API（后端）+ PDF.js 渲染（前端） | 后端返回 PDF Blob 和文件名，前端用鉴权后的 Blob 交给 PDF.js 渲染，不暴露静态文件地址 |
| 部署 | 外层 HTTPS 反向代理 + Docker Compose | 企业网关/WAF/Nginx/Caddy 终止 TLS 并统一转发 frontend；Compose 包含后端、前端、PostgreSQL、Redis、`default` worker、threads `ai` worker 与每小时 backup scheduler |

本机开发形态：

- SQLite。
- `CELERY_TASK_ALWAYS_EAGER=True`，任务同步执行，免 Redis/PostgreSQL。
- 启用 DRF Token 会话、RBAC 权限校验和接口级数据过滤；生产前端只走 W3 OAuth2，不提供本地密码登录或密码维护。

生产形态：

- PostgreSQL。
- Celery + Redis 异步执行。
- W3 OAuth2 SSO 是唯一生产登录入口；部署未完成 W3 配置时不得回退到密码表单。仅当后端 `DEBUG=True` 且 W3 未就绪时，`/login` 显示开发令牌输入框；令牌必须先通过 `/api/me/` 验证，再复用同一 RBAC、DRF 权限和接口级数据过滤。
- Compose frontend 前默认部署企业网关、WAF、Nginx 或 Caddy 等 HTTPS 反向代理。外层代理只把全部路径转发到 frontend 暴露端口，frontend 内置 Nginx 再代理 `/api` 到 `backend:8000`；不得让外层代理或客户端绕过 frontend 直接访问 backend。

## 二、Django 应用划分

| app | 职责 | 关键模块 |
| --- | ---- | -------- |
| `ingestion` | 数据源适配器，解析输入并写入领域模型 | `sources.py`、`snapshot.py` |
| `core` | 领域模型与基础主数据 | `models.py`、`management/commands/seed_base.py` |
| `pipeline` | 前置处理、候选人处理主流程、Rule/AI 策略、异步任务 | `runner.py`、`strategies.py`、`services/`、`tasks.py` |
| `api` | DRF API、ViewSet、显式动作接口 | `views.py`、`serializers.py`、`urls.py` |
| `accounts` | 用户、RBAC 权限、W3 OAuth2 协议适配 | `models.py`、`oauth2.py`、权限类 |

`api/analytics.py` 负责招聘分析参数校验、数据库聚合、统一统计口径和 5 分钟缓存；前端只消费聚合结果。

后端解耦原则：

- 输入层做成数据源适配器，Excel 只是当前来源；业务逻辑不直接依赖 Excel 列名。
- 候选人处理主流程只依赖 Django 模型，不读原始文件字段。
- 当前志愿到内部职位岗位池的精确映射位于独立 `pipeline/services/job_mapping.py`，不属于 `RuleStrategy`；Rule / AI 共用映射结果后分别进入专业审核或 AI 目标准备。
- Rule 专业审核只由 Rule 链路调用；AI 正式任务、直接处理、重试及结果落库不得调用 `RuleStrategy` 的专业匹配。
- 业务参数外置为配置或规则表。
- 南北归属只在志愿排序规则运行时判断，不落库、不做可维护省份字典。

## 三、数据流与处理入口

总体数据流：

`ingestion（适配器） → core 模型 → 前置数据准备（院校标签 / 岗位需求 / 接口人） → 候选人处理主流程 → 候选人分配工作流 → 输出（导出 / WeLink 下发 / 接口人反馈）`

处理触发：

- 简历库上传含候选人数据时必须提交唯一 `processing_mode=rule|ai`，并只创建一条 `ProcessingRun`：Rule 编排 `step1 → step2 → step3`，AI 编排 `step1 → step2 → step3 → step4`。
- HR 在简历库“处理简历”弹窗中选择冻结的当前选中候选人，或选择目标简历状态后，从 Step2 开始按本次请求唯一 `mode=rule|ai` 创建运行，不重复 Step1；两种范围互斥。Rule 始终允许提交，AI 模式必须在提交时验证当前完整连接配置已经真实测试成功，不得回退 Rule。
- 岗位需求、部门和接口人通过导入和主数据页面提前维护，是 Step3 的基础数据，不再占用编号步骤。

任务记录：

- 每次处理写入 `ProcessingRun`。
- `ProcessingRun.step` 支持 `import / all / step1 / step2 / step3 / step4`。
- `step1` 为查重与志愿排序。
- `step2` 为院校分类及学历/院校准入，完整固化院校标签和准入结论。
- `step3` 为岗位与分配前置检查：Rule 模式在独立岗位映射后完成确定性专业审核与分配，AI 模式在同一独立映射后跳过 Rule 专业审核，只固定当前志愿、岗位、二级部门和二级接口人。
- `step4` 仅用于 AI 模式的深度筛选与分配；AI 不重复 Step2/Step3 已确定的规则。
- `all` 与正常处理都按数字顺序执行；Rule 为 Step1–Step3，AI 为 Step1–Step4。
- 每个运行记录保存发起人、当前阶段、最近心跳和不含候选人明细的范围摘要；阶段进度由 `ProcessingRunStage` 记录。拥有 `pipeline.view` 的用户可在侧栏独立「处理任务」页面轮询查看全部共享任务；该权限默认授予 HR/管理员，二级、三级接口人默认不授予，前端不再使用顶栏 Badge 或侧边 Drawer。取消活跃运行另需 `pipeline.run`：排队任务立即取消；运行中或等待冲突任务进入取消中，并在候选人或阶段边界安全停止，已提交的业务结果不回滚。

> **本次实现状态（2026-07-20）**：Rule-first Step1–Step4、统一候选人结果口径、精确原因码和后台专项路由已落地；专项匹配及其证据、配置和路由码只保留内部审计，不通过业务 API、页面或招聘分析显式展示。`ProcessingRunStage`、`ProcessingRunScopeItem`、候选人 AI 任务、专用 `ai` 队列、短事务处理租约和人工操作版本防覆盖继续沿用。本地 `CELERY_TASK_ALWAYS_EAGER=True` 串行同步完成并返回 200；生产 AI Step4 由 `default` worker 调度、threads `ai` worker 消费候选人任务并返回 202。heartbeat 超时监控/恢复不在本轮实现范围。

## 四、导入服务设计

入口：

- `POST /api/import/`
- `GET /api/import/templates/{template_type}/`
- 支持简历信息列表、岗位需求、院校清单、部门接口人、简历包。
- 四张业务表支持 `.xlsx`、`.xls`、`.csv` 表格文件，后端优先按文件内容识别格式，文件后缀仅作为辅助判断。
- 各前端数据页可只上传对应文件；`POST /api/import/` 继续按上传字段识别 `resume_list / jobs / schools / contacts` 表类型，不通过非标准表头猜测类型或字段映射。
- 模板下载复用 `resume.import` 权限，`template_type` 仅允许 `resume_list / jobs / schools / contacts`。四个响应均为版本 1 的 XLSX，文件名依次为“简历信息列表标准模板.xlsx”“岗位标准模板.xlsx”“院校分类标准模板.xlsx”“部门接口人标准模板.xlsx”；第一张工作表为冻结并启用筛选的业务数据表，第二张为填写说明。

v1 标准表头：

| `template_type` | 标准字段 |
| --------------- | -------- |
| `resume_list` | 招聘主体、所属机构、姓名、应聘ID、手机号、性别、对外职位名称、学历、第一学历毕业院校、最高学历毕业院校、最高学历专业、应聘状态、户口所在地、应聘日期 |
| `jobs` | 招聘主体、一层部门、二层部门、三级部门、岗位类别、对外发布名称、是否对外发布、职位名称、岗位族、工作地点、学历、工作职责、需求专业、HC |
| `schools` | 学校、院校标签、所在省份 |
| `contacts` | 一层部门、二层部门、三级部门、姓名、工号、邮箱、接口人层级、可转派、是否启用 |

模板字段定义是表格导入与模板生成的唯一代码级来源。岗位职位清单导出复用 `jobs` 的同一字段定义，保证下载数据仍可直接回导；系统不维护客户表头别名、猜测规则或可配置字段映射。

导入流程：

1. 按 `POST /api/import/` 上传字段识别表类型，并按文件内容校验实际格式。
2. 按该类型的 v1 标准字段校验表头；列顺序不强制，无值字段仍须保留空列。缺失、未知或重复表头时在快照创建、业务键检查和任何写库之前整批失败，并返回各类具体字段清单。
3. 通过 `ingestion` 适配器解析为领域数据。
4. 规范化姓名、手机号、主体 code、院校名称、岗位类别等业务键。
5. 按应用层查询进行幂等写入。
6. 收集低风险更新、跳过、错误、舍弃数量。
7. 返回导入结果。

岗位 Replace 全量同步：

- 继续使用 `POST /api/import/`，标准输入列使用“招聘主体”和“HC”；不拆分现有 POST 导入接口，也不增加数据库字段或迁移。
- 固定完整业务键为“招聘主体、一级部门、二级部门、三级部门、对外发布名称、内部职位名称、岗位类别”；七部分统一去空白并忽略大小写后比较，`是否对外发布` 仍是属性而非业务键。匹配范围包含启用和停用岗位。
- 写入前同时校验文件全部候选岗位行和数据库全部岗位；任一侧存在重复业务键时整批报错，外层事务回滚本次全部更新、专业替换和停用操作，不选择其中一条猜测匹配。
- 完整键唯一命中时覆盖岗位全部可导入属性、`headcount`（标准输入列为“HC”）和完整 `JobMajor` 明细，并写 `is_active=true` 以重新启用。旧岗位层级不完整且只对应一个新完整路径时原位补齐；一个旧二级聚合岗位拆为多个三级岗位时，旧记录仅写 `is_active=false`，新建各明细岗位，历史引用和 `ProcessingRunJobCapacity` 快照保持指向旧记录。其它未命中岗位新建；Replace 文件中不存在的岗位停用，不硬删除。
- 全部岗位行均无效时跳过同步和停用，现有岗位保持不变。停用岗位已有的 `ProcessingRunJobCapacity` 不删除、不重算，历史任务 HC 继续使用创建时冻结值。

院校省份 AI 后台补全（当前实现）：院校清单导入只收集本次写入后 `province` 仍为空的 `School.id`；文件明确省份时优先写入，空单元格不覆盖已有人工/AI 值。仅当当前完整模型连接指纹的真实测试仍有效时，`submit_school_province_enrichment()` 才在生产将任务投递到 `ai` Celery 队列，本地 eager 则交给 `max_workers=1` 的后台线程池；两者都立即返回导入响应。投递时读取并随任务参数携带当前激活 Prompt 版本，后续批次按该激活或已归档版本读取不可变模块，不受后来发布影响。任务分批调用当前 AI 连接，只接受中国大陆 31 个省级行政区标准简称；名称明确包含校区/分校时按该校区/分校，否则按主校区，不按招生地区猜测，无法可靠判断时留空。每条落库仍使用 `WHERE province=''` 条件更新，不覆盖排队后的人工修改。AI 不可用时通过响应状态说明未投递；调用失败、结构化输出失败或队列投递失败只保留空值并记录脱敏后台日志，均不回滚或阻断导入。该增强只维护 `School.province`，不进入 `ProcessingRun`，不改变 Step2 纯规则的院校标签和准入。

身份归并：

- 规范化姓名：去首尾空格、统一全/半角。
- 规范化手机号：去空格、分隔符、`+86` 前缀。
- 手机号缺失时，舍弃该候选人及其投递，不入库、不进入分配。
- 按 `normalized_name + normalized_phone` 查询候选人。
- 命中一条则复用并更新当前字段。
- 命中多条则阻断相关记录并进入导入错误清单。
- 按 `apply_id` 查询投递，存在则更新，不存在则创建并挂到候选人。
- 简历包按 `姓名（应聘ID）` 经应聘ID定位 `Resume`。
- 简历信息列表的“学历”列规范化为 `associate / bachelor / master / doctor`。兼容专科/高职、学士、研究生等常见写法；同一文件内同一候选人出现多个已识别学历时按大专 < 本科 < 硕士 < 博士取最高值。空值或未知值不覆盖已有有效 `Candidate.highest_education`，新候选人保持空；历史数据需通过重导原简历信息列表补齐。

招聘主体：

- 导入时按 `RecruitingEntity.code` 匹配主体。
- 查不到时创建或进入人工映射。
- 部门和接口人不保存招聘主体归属。

部门接口人：

- 导入部门接口人信息时，按 `Contact.employee_no` 幂等写入接口人主数据；标准模板包含“邮箱”，不包含“招聘主体”或“序号”。工号和邮箱必填，邮箱经 Django 邮箱格式校验并统一去空白、转为小写。
- 解析完整文件后再写入：缺邮箱、格式非法、同一规范化邮箱对应多个工号，或邮箱与现有其他接口人冲突时抛出 `ValueError`，由导入外层事务整批回滚，不停用或部分更新任何接口人。
- 每个有效导入的接口人同步一个系统用户：`User.username = Contact.employee_no`、`User.email = Contact.email`，新建或更新账号均调用 `set_unusable_password()`。工号或邮箱已被不同账号占用时拒绝同步，不猜测账号归属。
- 同步用户时按接口人层级确保拥有 `二级接口人` 或 `三级接口人` 角色，并写入 `User.contact_id`；已有目标用户保持密码不可用并保留非接口人业务角色，仅同步用户名、邮箱、二级/三级接口人角色、启停状态和接口人绑定。
- 接口人导入只确保预置角色存在；默认权限仅在角色首次创建时初始化，不得通过导入重新执行 `permissions.set()` 覆盖管理员已维护的角色权限。
- 部门接口人 replace 导入时，本次文件中不存在的旧接口人置为停用，其绑定账号同步置为停用；本次文件中的接口人账号按 `Contact.is_active` 恢复或停用。replace 导入保留软停用语义，避免批量导入误删历史主数据。
- 部门和接口人不保存招聘主体归属，也不提供“主体来源字段”筛选；部门接口人标准模板不包含招聘主体，不写入 `Department` 或 `Contact`。
- 除内置受保护管理员外，用户管理或接口人清单中的单条删除采用清理语义：`DELETE /api/users/{id}/` 删除账号、Token 和角色绑定；若用户绑定 `Contact`，同步删除该接口人。`DELETE /api/contacts/{id}/` 删除接口人，并同步删除绑定该接口人的普通用户。删除前后端需先清空历史分配、转派、AI 决策等记录上的用户/接口人外键，仅保留快照字段和审计记录，避免级联删除候选人流程历史。
- W3 UserInfo 顶层字段已确认为 `tenantId / uuid / globalUserID / email / employeeNumber`。认证只读取 `employeeNumber` 作为工号匹配 `User.username`，读取 `email` 按大小写不敏感口径匹配 `User.email`，两者必须严格映射同一个已存在且启用的账号；任一字段不匹配均拒绝登录，不做 OR、降级、自动建号或账号启用。`tenantId`、`uuid`、`globalUserID` 不参与账号匹配、不落库，也不改变 RBAC 和数据范围推导。

撤销：

- 上传含简历数据前先解析业务键，确定本次新增或更新的候选人/投递影响范围，并写入一份 `ImportSnapshot`；不得用全表快照回滚无关候选人的并发操作。
- 快照在该影响范围内覆盖 Candidate / Resume / ResumeProfile / CandidateWorkflow / AgentDispatchDecision / AssignmentAttempt / AssignmentHandoff，并记录关联 `ProcessingRun` id 和上传/关联处理完成后的候选人流程 revision 基线。
- **目标设计（未实现）**：快照按上传记录和创建人保存；HR 只可查询/撤销自己的上传记录，管理员可查询/撤销全部上传记录；同一上传记录只能撤销一次。
- **目标设计（未实现）**：`POST /api/import/undo/` 按上传记录还原上传前业务状态。关联处理任务仍在 `pending`、`running` 或 `waiting_conflict` 时返回 `409`；否则在同一事务内依次锁定范围内 Candidate 和 CandidateWorkflow，并比较每个候选人当前 revision 与上传后基线。任一不一致即整体返回 `409`，不允许部分回滚；全部一致才撤销。撤销后快照标记已撤销，不再作为可撤销对象。对应 `ProcessingRun` 不删除，状态改为 `undone` 并记录撤销时间，保留操作审计。
- 普通导入接口的 `replace` 不得删除候选人、投递、反馈、分配尝试或转派历史。候选人/投递仍按业务键增量并入；岗位、院校、接口人等主数据采用更新或停用语义。测试环境的彻底清空必须走独立运维命令，并显式拒绝存在受保护历史的数据池。

## 五、前置处理服务

### 院校分类

模块：`pipeline/services/classify_school.py`

职责：

- 读取 `School` 与 `SchoolTag`。
- 给候选人的第一学历、最高学历写入院校标签。
- 系统通过 `seed_base` 预置并在分类时自愈启用的 `SchoolTag(code="NON_TARGET", name="非目标院校")`。未命中导入院校清单的学校始终使用该标签；只有命中清单但 `School.school_tag_id` 为空时，才使用启用的默认标签，若无默认标签则回退到“非目标院校”。该标签可用于后续分类、筛选和准入规则。
- 纯规则处理，不使用 AI。

边界：

- `School` 只保存 `province`，不保存南北归属。
- 户籍缺失时，Step1 可使用学校所在省份作为南北规则兜底。

### 岗位需求基础数据维护

模块：`ingestion/sources.py`、`pipeline/services/demand.py`

职责：

- 岗位文件解析、业务键匹配和 `Job` / `JobMajor` / `JobCategory` / `Department` 的幂等写入由 `ingestion` 完成。导入只接受“招聘主体”“一层部门”“二层部门”“三级部门”等 v1 标准表头，不兼容“主体”“一级部门”“二级部门”“需求数量”等别名；三级名称存在但缺有效二级父部门时按 Excel 行号报错。`Job.department` 始终保存二级或三级的最深归属节点，统一层级解析器负责还原一级/二级/三级。Replace 按“招聘主体 + 一级部门 + 二级部门 + 三级部门 + 对外发布名称 + 内部职位名称 + 岗位类别”的规范化完整键执行事务内全量同步，并按唯一补齐/一拆多规则兼容历史二级聚合岗位；文件或数据库重复完整键使整批回滚。
- 岗位需求导入时逐行读取并完整保存 `Job.responsibilities`。职位名称或对外名称有效但“工作职责”为空的行跳过，累计 `jobs_skipped`，并在 `_warnings` 中返回 `job_responsibility_missing`、数量和从 2 开始的 Excel 行号；其它有效行继续导入。Replace 模式只有至少一条有效岗位时才执行同步和停用，防止全无效文件改变现有岗位。
- 岗位需求导入还校验启用岗位是否具备 `RecruitingEntity.code`、`JobCategory`、有效二级归属和需求专业等分配前置信息，并汇总岗位数、HC 和缺口。三级岗位通过统一层级解析器回溯父级二级部门及二级接口人；这些维护动作不再占用候选人处理的编号步骤。
- 专业大类映射主数据 `MajorCategory` / `MajorAlias` 由初始化命令和配置 API 维护，仅供 Rule 专业匹配；AI 可以读取当前固定岗位原始需求专业作为模型上下文，但不使用该词表做确定性筛选。
- 岗位是否参与分配只看 `is_active`。

边界：

- 不引入招聘周期表。
- 不保存 `valid_from / valid_to`。
- 需求专业保留独立 `JobMajor` 明细表；`MajorCategory` / `MajorAlias` 不替代岗位原始需求专业，只作为匹配增强词表。

## 六、候选人处理主流程

入口：

- `POST /api/pipeline/run/`
- 请求包含 `step`、唯一 `mode` 和 `scope` 等参数；`mode` 只能是 `rule|ai`，缺失或提交 `modes` 时返回 400。
- 服务端按请求的唯一 `mode` 创建一条 `ProcessingRun` 并固化本次 Rule / AI；AI 模式提交前必须校验当前完整连接配置已经真实测试成功。
- `scope` 支持两种互斥的 Step2 起始处理范围：状态范围传入 `system_statuses + candidate_filters`，与当前表头及任务结果筛选相交；当前选中范围只传入打开弹窗时冻结的 `candidate_ids + force_reprocess=true`，忽略候选人当前状态，不叠加任何状态或筛选范围。两者都从 Step2 重跑命中候选人，并按模式继续 Step3/Step4。
- `system_statuses` 只接受 `raw / archived / pending_reallocation / pending_review / pending_dispatch / pending_screening / screening_passed / screening_rejected`。旧 `classified / allocated` 和任何未知值均返回 400；不得丢弃非法值后继续创建全量任务。
- 公开运行接口仅允许在 `step=step2` 时使用 `force_reprocess=true`，必须搭配非空的正数整型 `candidate_ids` 数组，且不得同时提交 `system_statuses` 或 `candidate_filters`；`force_reprocess` 非布尔值、步骤错误、ID 为空/非正整数或范围混用都返回 400。
- 服务端在提交时解析并固化内部 `ProcessingRunScopeItem` 范围及每个候选人的 `workflow_revision_at_submit`；后续执行不再按动态筛选条件重新查询。Step2 固化院校准入，Step3 再固定 AI 所需业务引用和 `workflow_revision_at_prepare`；生产异步环境中只有 AI Step4 由调度任务有界投递候选人级任务到 `ai` 队列。创建运行后返回 `202 + processing_runs`，本地 eager 串行同步完成后返回 200。前端不逐步调用各 Step。

### Step1 查重与志愿排序

模块：`pipeline/services/dedup.py`

职责：

- 以 `Candidate` 分组。
- 对候选人的 `Resume` 按投递时间、主体、南北规则排序。
- 写入 `volunteer_rank` 和分配主体。
- 维护候选人当前流程的初始当前志愿。

规则：

- 单一主体最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各 2 个岗位时，统一标第一至第四志愿。
- 户籍北方优先 GW，南方优先 YLS。
- 户籍缺失时，按学校所在省份同规则。

### Step2 院校分类及学历/院校准入

模块：`pipeline/services/classify_school.py`、`pipeline/services/school_admission.py`、`pipeline/services/allocate.py`

职责：

- 对本次冻结范围按当前院校清单完整重算 `first_degree_tag / highest_degree_tag` 及平台展示字段；正式流程固定使用覆盖模式。
- 在同一步执行最高学历与院校标签准入，保存命中的 `SchoolTagRule` 引用供 Step3 审计使用。
- 不符合学历或院校规则时归档当前流程，但 ScopeItem 记为 `completed`，原因分别为 `education_not_eligible / school_not_eligible`，不得算系统失败。
- Step3/Step4 不再调用院校分类或重新执行院校准入，也不得改写固化标签。

准入规则：

- Step2 以候选人为粒度评估学历与院校准入，不选择志愿、岗位或接口人。
- 存在启用 `SchoolTagRule` 时，候选人的第一学历标签、最高学历标签和 `highest_education` 必须同时命中同一条启用规则；多条启用规则之间 OR。规则未配置 `SchoolTagRuleEducation` 表示不限制最高学历；一旦配置，候选人学历为空、无法识别或不在允许集合中都不通过，并分别输出“最高学历缺失”或“最高学历不在允许范围”的归档说明。
- 没有启用规则时，院校准入视为全部通过。
- 简历库“处理简历”从 Step2 开始，按当前院校清单覆盖生成本次范围的院校标签和准入结果；院校主数据变化必须通过新运行产生新结果，不在运行中途补标签。
- 已通过候选人不可再通过“手动强制分配”入口分配；如需重开，必须走简历库“处理简历”入口，手动勾选 `当前选中` 或勾选包含“通过”的状态范围。
- 反馈提交后锁定，不允许二次修改。
- 简历库“处理简历”重跑时不清空全部历史；历史尝试、已提交反馈和 `AgentDispatchDecision` 都保留，只取消尚未反馈的 Rule / AI 自动尝试，手动尝试不因重开自动取消。模型连接后续变化不主动取消已有任务或重算已有结果。
- `force_reprocess=true` 是 HR 对冻结 `candidate_ids` 发起的主动重开信号。执行前清空 `passed_attempt_id`、归档原因/说明、阻塞原因/说明和 `completed_at`，将流程恢复为 `in_progress`，再按本次提交时选择并固化的唯一 Rule / AI 模式生成新的自动尝试。提交后 workflow revision 发生人工变化时，本次范围项记为 `skipped_manual_change` 并不覆盖人工结果。
- 普通简历导入的 `candidate_ids + source=resume_import` 不设置 `force_reprocess`，不按 HR 主动重开处理；候选人已处于通过等终态时保持原流程和尝试。

### Step3 岗位与分配前置检查

模块：`pipeline/services/job_mapping.py`、`pipeline/services/allocate.py`、`pipeline/strategies.py`

两种模式都从 `CandidateWorkflow` 已确定的当前有效志愿开始，不在本步跳过该志愿选择后续志愿。当前志愿反馈未通过后，候选人工作流再推进到下一志愿。

岗位映射与任务容量（两种模式共用）：

- `resolve_job_pool()` 是独立确定性岗位映射服务，只读取当前投递、招聘主体和启用岗位，不读取候选人专业，也不依赖 `RuleStrategy`。Rule / AI 都先取得这份映射结果；Rule 随后执行专业审核，AI 随后直接执行部门、接口人和 HC 选择。
- 当前投递的对外职位名称先在同招聘主体的启用岗位中做精确映射，必须得到唯一非空内部 `position_name`；全部精确映射行都缺内部职位名称时写 `completed + internal_position_name_missing`，存在空值与非空值混合、多个不同内部职位或无法确定唯一主体时写 `completed + job_mapping_ambiguous`，均不使用包含匹配猜测。
- 映射成功后只汇集同招聘主体、同内部 `position_name` 的全部启用 `Job`。任务创建时读取 `job_hc_coefficient`（默认 1，1–100），在 `ProcessingRun.job_hc_coefficient_snapshot` 固化本次系数，并为当时全部启用岗位创建独立 `ProcessingRunJobCapacity` 快照：`headcount_snapshot`、`coefficient_snapshot`、`capacity=headcount × coefficient`、`used_count=0`；候选人只在精确映射后的岗位池中选用对应容量行。后续修改 HC 或系数不影响已创建任务。
- 同一运行按候选人 ID 升序稳定处理；在仍有容量且通过本模式其它前置检查的岗位中，按最小 `(used_count + 1) / capacity` 选择，岗位 ID 作为并列决胜。容量行必须在短事务中 `select_for_update` 并原子校验、占用，防止并发超配。
- 自动生成 `pending_review` 或 `pending_dispatch` 尝试时写入 `capacity_reservation_id` 并把 `used_count` 加一。下发前取消时通过 `capacity_released_at` 做幂等释放并减一；已经进入 `dispatched_l2 / assigned_l3 / passed / rejected` 的占用不释放。手动强制分配绕过配额，不关联容量行。
- 所有候选岗位容量耗尽时，不创建尝试、不推进当前志愿，保留投递分类和当前志愿，ScopeItem 写 `completed + job_hc_exhausted`；该证据派生为 `pending_reallocation`，供后续新任务直接重新处理。

Rule 模式：

- 顺序固定为：当前志愿 → 唯一内部职位映射 → 同主体内部职位岗位池 → 专业确定性匹配 → 有效二级部门 → 启用二级接口人 → HC 配额选择 → 创建 Rule 分配。
- 岗位分类和候选岗位池复用上述精确映射，不再按对外名称/职位名称包含关系兜底。
- 岗位配置需求专业时，先用启用的 `MajorAlias` 将候选人最高学历专业和每个岗位需求专业映射到 `MajorCategory`；任一专业大类相交即视为专业通过。
- 若大类无交集，或候选人/岗位任一侧未映射到启用大类，则再执行专业名双向包含兜底，例如“计算机科学与技术”命中“计算机”；词表和兜底都不命中时继续尝试下一个候选岗位。
- 岗位未配置需求专业，或岗位需求专业为“专业不限 / 不限 / 不限专业”等通配表达时直接放行；候选人最高学历专业缺失且岗位配置了非通配需求专业时不自动放行。
- Rule 模式执行专业大类/别名与专业名兜底匹配并写入 `JobCategory`；不命中时本轮停止并写 `completed + major_not_matched`。
- 当前志愿未匹配到启用岗位需求时，ScopeItem 写 `completed + job_not_found`；已匹配岗位但没有有效二级部门时写 `completed + secondary_department_missing`。`archive_detail` 分别明确岗位需求缺口或部门缺口，不得使用模糊的“未匹配”文案。
- 当前志愿匹配岗位和二级部门但该部门没有启用二级接口人时，保持 `CandidateWorkflow.status=in_progress`、`current_resume/current_rank` 指向当前志愿，写入 `block_reason=contact_not_found` 和包含岗位、部门及“该部门没有启用的二级接口人”的 `block_detail`，不创建 `AssignmentAttempt`，不归档，不推进下一志愿。
- 当前志愿匹配到可用二级接口人时，创建 `source=rule, pending_dispatch` 尝试，并写入包含院校、志愿、岗位、专业大类/专业名、部门和接口人的 `match_reason`；生成有效尝试时清空 `block_reason/block_detail`。

AI 模式：

- 顺序固定为：当前有效志愿 → 唯一内部职位映射 → 同主体内部职位岗位池 → 有效二级部门 → 启用二级接口人 → HC 配额候选岗位选择。本步不调用专业大类、专业别名或专业名兜底匹配。
- 上述边界覆盖正式 ProcessingRun、直接 AI 处理、AgentDecision 重试和模型结果落库前的引用重取；这些入口只能复用独立岗位映射与 AI 目标准备，不得调用 `RuleStrategy.filter_major_eligible_jobs()`，也不得生成、传播或持久化 `major_not_matched`。该原因码仅属于 Rule 专业审核结果。
- 通过后把 `prepared_resume/job/department/contact/capacity`、Step2 的 `matched_rule` 和工作流版本固定到 `ProcessingRunScopeItem`。普通 AI 分配只能消费这些引用，不得自行改选；真正形成待复核/待下发尝试时再原子占用容量。
- `job_mapping_ambiguous / internal_position_name_missing / job_not_found / secondary_department_missing / secondary_contact_missing / job_hc_exhausted` 都是 `completed` 业务结果，不投递 Step4；缺接口人或容量耗尽时工作流仍停留当前志愿等待补数据或新任务。

> `CandidateWorkflow.archive_reason/block_reason` 中的 `job_not_matched / department_not_found / contact_not_found` 等历史内部枚举仍保持可读；处理中心和简历库以 ScopeItem 的上述稳定 `reason_code` 统计与筛选，不反向改写历史记录。

### Step4 AI 深度筛选与分配

> 正式链路位于 `apps.pipeline.ai`，根据系统设置保存的 `api_style` 调用内网模型：`responses` 使用 Pydantic 结构化输出，`chat_json` 使用 JSON Schema 约束并由后端统一校验。只消费 Step3 固定引用，不选择数据库对象，不回退 Rule。

- 只有通过 Step2/Step3 且 ScopeItem 仍为待处理的候选人进入 Step4。模型调用前重新校验固定 Resume、Job、二级 Department、二级 Contact 是否仍存在、启用且关系一致；失效时记 `needs_attention + ai_reference_invalidated`，不调用模型。
- `ResumeProfileExtractor` 先用 `pypdf` 读取 PDF 正文；去空白后不足 50 字符时才启用本地 OCR 回退：PyMuPDF 按页渲染图像，Tesseract 使用 `chi_sim+eng` 识别中英文。默认最多 20 页、200 DPI、总超时 120 秒，单 worker 通过有界信号量最多并发 2 个 OCR；`RESUME_OCR_MAX_PAGES`、`RESUME_OCR_DPI`、`RESUME_OCR_TIMEOUT_SECONDS`、`RESUME_OCR_CONCURRENCY` 可覆盖默认值。正文足够的文本 PDF 不触发 OCR；OCR 文本与原有少量文本合并后仍不足 50 字符、依赖/工具缺失、超时或识别失败统一抛出 `pdf_parse_failed`。
- 抽取成功后将正文写入 `ResumeProfile.raw_text`，解析器版本固定为 `pypdf-ocr-v2`，使用 OCR 时在 `profile_risk_flags` 记录 `ocr_fallback`；解析器版本参与缓存校验，使旧画像重新抽取。正文写入前移除 NUL（`0x00`）字符，不改写其它字符。OCR 只属于 AI 正文抽取链路，不改变预览、下载和原 PDF 保存；任何 OCR 失败都不得回退 Rule。
- `_current_job_context` 只提供当前固定岗位的名称、类别、需求专业和工作职责，不提供学历要求或岗位/部门/接口人 ID；工作职责先移除 NUL、去除首尾空白，再截取最多 12,000 字符，提示词声明其只是业务数据并忽略其中任何改变任务或输出协议的指令。`current_volunteer` 只发送 `position_name`，不发送 Resume ID、应聘 ID、志愿序号或招聘主体标识。不得查询或发送其它岗位、院校标签、学历/院校准入、志愿选择、部门选择或接口人选择任务。`ResumeProfileOutput` 不接受学历字段，Step2 固定的学历/院校结论不由 AI 解析、补写或覆盖。
- 新增或通过 API 编辑岗位时 `responsibilities` 必填；历史空值保留可读且不影响 Rule。AI 服务在 PDF 抽取和模型调用前检查工作职责，空值抛出稳定 `job_responsibility_missing`，候选人映射为 `needs_attention`。初始激活 Prompt 为 `resume-screening-v2`，后续使用任务创建时冻结的已发布版本；继续使用既有 `job_requirement` 分项表达简历对岗位职责的覆盖度，不修改输出 schema 或评分权重。
- `DispatchRecommender` 只判断专业实际方向、项目/实习证据、技能和当前固定岗位实质适配性，输出推荐动作、理由、证据、风险以及仅供后台使用的专项人才字段。普通分配一律使用 Step3 固定的岗位、部门和接口人。
- `DecisionScorer` 根据专业实际方向、技能、项目/实习证据、岗位需求覆盖和简历文本质量汇总 `confidence_score`，不包含部门确定性评分。
- AI 调用必须走结构化输出；后端 schema 明确禁止岗位、部门和接口人 ID，并校验枚举和分数区间。输出不合法时记录 `ai_invalid_output`。
- 模型返回 `ResumeScreeningOutput` 后，先对其全部字符串递归移除 NUL（`0x00`）字符并重新执行 schema 校验，再将同一份已清洗结构化输出写入 `ResumeProfile` 和 `AgentDispatchDecision`；该范围包含 JSONField 内任意层级的字符串。`AIServiceError` 在构造时对其受控错误消息执行同类清洗，供 AI 异常决策持久化。清理只删除 NUL，不改变其它业务文本字符；决策仍只保存业务摘要、证据、风险点、版本和错误信息，不保存 LLM 完整原始响应。
- `recommendation=dispatch` 且 `confidence_score >= ai_dispatch_threshold` 时，创建 `source=ai, pending_dispatch`。
- `recommendation != archive` 且 `confidence_score >= ai_review_threshold`，但未达到自动下发条件时，创建 `source=ai, pending_review`。
- 上述两类 AI 尝试落库前必须锁定 Step3 固定的 `ProcessingRunJobCapacity` 并再次校验剩余容量；占用成功后在同一事务创建尝试并回写 `capacity_reservation`。若并发导致容量已满，则不创建尝试，ScopeItem 改写 `completed + job_hc_exhausted`，当前志愿保持不变。
- `recommendation=archive` 或低于复核阈值时只写 AI 决策并归档，是 `completed + ai_archived`；待复核和成功分配同样属于 completed。
- 后台专项字段为 `ai_specialist_match / ai_specialist_confidence / ai_specialist_evidence`。证据必须是可在 `ResumeProfile.raw_text` 中定位且至少包含有效上下文的片段；没有可定位证据或只有孤立关键词时，服务将 match 置 false、置信度置 0、证据置空，保留普通 AI 推荐且不抛 `ai_invalid_output`。专项开关启用且置信度严格大于阈值时，调用与 `manual_assign` 共用的 `_force_assign_locked` 领域服务，以 `source=ai, route_code=ai_special_route` 创建 `assigned_l3` 尝试，并写系统→二级、二级→三级两段 `AssignmentHandoff`。尝试和决策保存置信度、证据、目标快照、配置指纹版本、处理运行和触发时间，但普通序列化不返回这些内部字段。
- 专项分流配置默认关闭，包含阈值、父级二级接口人、固定三级接口人；启用保存和运行提交都校验接口人启用状态及部门父子关系。配置在运行期间失效时，将 `target_unavailable` 与异常类型写入内部配置快照并继续执行原普通 AI 推荐，不写候选人错误码、不进入 `needs_attention`。
- AI 超时或其它技术失败不自动回退 Rule，也不允许执行过程中改变本次已固化模式；只有 `llm_timeout` 计入 failed。
- 同一 `resume_id + evaluated_job_id + file_checksum + profile_version + prompt_version + decision_version` 已有有效决策时优先复用；其中 `file_checksum/profile_version` 通过 `profile_id` 关联的 `ResumeProfile` 校验。HR 主动重试 AI、简历文件变化、画像版本变化或决策版本变化时才重新调用。

#### AI Prompt 管理与固定 harness

- `apps.pipeline.ai.prompt_harness` 是 Prompt 组装的唯一边界。管理员只能维护五个固定模块：`screening_role_goal`、`screening_rule_guardrails`、`screening_job_evaluation`、`screening_ai_specialist`、`school_province_inference`。简历筛选按前四个键的固定顺序组装，院校补全只使用第五个键；不开放模板变量、动态字段名或输出 Schema 编辑。
- harness 为两类任务分别追加不可编辑的最小安全底座，把简历正文、当前志愿、当前岗位/岗位职责、候选人引用和院校名称视为不可信业务数据，忽略其中改变任务、规则、固定岗位或输出格式的指令。动态输入由后端构造成 JSON；院校任务固定追加中国大陆 31 个省级行政区标准简称白名单和名称逐字返回约束；调用前再由 Pydantic 模型生成 JSON Schema，追加“只输出结构化 JSON、不得包含额外字段”的协议。模型连接测试使用的 `Reply with OK.` 仍是连接层固定探针，不属于可编辑 Prompt。
- `normalize_modules()` 要求请求恰好包含五个字符串模块，移除 NUL 和首尾空白后仍必须非空；单模块最多 8,000 字符，整套最多 24,000 字符，缺失、未知、类型错误或超限均抛出可安全返回的 400 校验错误。规范化模块按键排序序列化后计算 SHA-256 内容哈希。
- `AIPromptVersion` 只允许一个 `draft` 和一个 `active`。数据迁移把旧内嵌语义拆成五模块，创建 `release_sequence=0` 的激活版本 `resume-screening-v2` 和同内容、未测试的 `draft-resume-screening-v2`。后续发布版本为 `prompt-vNNNNNN-<hash8>`；版本标识字段最大 32 字符。
- 共享草稿保存、重置、发布和历史恢复均在事务内锁行，并通过 `lock_version` 做乐观锁；旧锁版本返回 409，不覆盖其他管理员的新草稿。保存、重置或恢复会清除草稿测试字段。恢复来源可为当前激活版本、系统默认模块或某个激活/归档历史；历史恢复只复制模块到草稿，不能直接切换生产版本。
- Prompt 真实测试要求当前模型连接测试有效，并对已保存草稿分别调用简历筛选与院校省份的正式 Responses API 或 Chat JSON 路径。合成简历覆盖岗位职责、项目、实习、技能和 AI 专项证据；院校样例覆盖普通院校、校区和不确定名称。测试只验结构化调用成功、简历证据可在合成正文定位、院校名称不越界和省份白名单，不要求固定 recommendation；数据库只保存内容哈希、模型名、内部连接指纹、操作者/时间，以及推荐动作、证据数量和院校请求/返回数量等脱敏摘要，不保存模型原始响应，序列化也不返回连接指纹。
- 原子发布要求草稿测试内容哈希仍等于当前内容哈希、当前连接测试有效且连接指纹未变化。事务内将旧 active 归档、草稿改为 active 并分配下一发布序号，再从新激活版本复制出一份同内容的新共享草稿。发布不清除模型连接测试；草稿修改、连接保存或连接测试失效会使 Prompt 测试失效。
- `runner.create_runs()` 创建 AI `ProcessingRun` 时读取当前激活版本并写入 `prompt_version`，执行时将该值传入模型服务；harness 只按指定的 active/archived 版本读取模块，不读取后来发布的 active。成功和失败 `AgentDispatchDecision` 均从运行记录写入实际版本。发布因此只影响新提交的 AI 任务，不取消旧任务、不影响 Rule 模式；院校补全则在投递 Celery/本地线程时直接携带版本字符串。

AI 异常与结果分类：

| 错误码 | 含义 | 处理 |
| ------ | ---- | ---- |
| `resume_text_unavailable` | PDF 缺失或正文无法提取 | `needs_attention`，补文件或人工处理 |
| `job_responsibility_missing` | 当前固定岗位缺少工作职责 | `needs_attention`，补齐岗位后重跑，不调用模型 |
| `llm_timeout` | AI 调用超时 | `failed`，可按配置重试 |
| `ai_connection_error` | 连接、认证、服务端依赖或基础设施异常 | `needs_attention` |
| `ai_rate_limited` | 模型 429 限流 | `needs_attention`，稍后重试 |
| `ai_invalid_output` | 普通 AI 结构化输出不合法 | `needs_attention`；后台专项证据无法定位不使用此错误码 |
| `ai_reference_invalidated` | Step3 固定引用在 AI 提交前失效 | `needs_attention` |
| 后台专项证据或目标不可用 | 内部增强条件不成立 | 清除或跳过专项命中，继续普通 AI，不形成公开错误码 |

批处理、进度与并发：

- 每次上传或处理请求使用一条独立 `ProcessingRun`，上传 Rule 持有 Step1–Step3，上传 AI 持有 Step1–Step4；人工处理从 Step2 开始。模式在提交时固化；之后修改模型连接只使当前连接测试状态失效并影响新请求的 AI 可选性，不取消排队中或运行中的任务，也不改变其已固化模式。
- AI Step4 调度任务以有界活动窗口向 `ai` 队列投递仍为 pending 的 `ProcessingRunScopeItem`；Step2/Step3 已形成业务结果的候选人不会调用模型。普通 worker 只消费 `default`，threads AI worker 只消费 `ai`。
- 模型请求共享并发与本地 OCR 并发分别限流：`ai_concurrency` 管理模型额度；OCR 的单 worker 上限默认 2，避免 threads AI worker 被 CPU 密集的渲染/识别任务占满。后端镜像必须安装 Tesseract、简体中文和英文语言包，Python 依赖包含 PyMuPDF 与 pytesseract。
- `ai_concurrency` 是所有 worker 与所有运行共享的模型请求上限，默认 8，取值 1–20。Redis 以 `api_style + base_url + model_name + API Key SHA-256 指纹` 的摘要命名租约和状态资源，不在键中暴露密钥。有效并发从 `min(2, 上限)` 开始，干净成功窗口按 2→4→8 增长；429 将并发乘 0.8 向下取整并遵循 `Retry-After`，超时、网络异常和 5xx 只暂停增长，不降低并发。
- 候选人 AI 处理分为“短事务领取—事务外模型调用—短事务校验提交”：领取时锁定 ScopeItem/Candidate/Workflow 并写入有期限的处理令牌；提交时同时校验令牌和 workflow revision。人工分配、下发、转派、反馈等写操作优先，会使租约失效并推进 revision；在途 AI 结果因此标记 `skipped_manual_change` 而不覆盖人工结果。
- ScopeItem 执行状态继续使用 `pending / queued / processing / waiting_conflict / success / needs_attention / failed / skipped_manual_change / cancelled`，业务结果另用 `result_type=completed / needs_attention / failed / cancelled` 和稳定 `reason_code` 保存；执行状态和业务原因不得混用错误文案推断。
- `ProcessingRun` 与 `ProcessingRunStage` 同步累计 completed、needs_attention、failed、安全跳过和取消数；`success_count` 作为历史兼容字段等于 completed。全部 ScopeItem 进入终态后才收口运行；有 timeout 为 `partial_failed`，只有需处理项为 `needs_attention`。Run 额外记录并发、重试和 429 指标。
- `last_heartbeat_at` 继续作为历史兼容和任务中心展示字段。heartbeat 超时判定、独立扫描 worker、自动或人工安全恢复均不在本轮实现与验收范围，不得从该字段推断已具备超时恢复能力。
- 本地 SQLite + eager Celery 继续同步串行执行，不使用 Redis 共享额度，运行接口在任务结束后返回 200。生产异步环境返回 202；验收并发时须关闭 eager，并启动 Redis、`default` worker 和 threads `ai` worker。

## 七、分配状态机

简历状态（推导态）：

| 状态码 | 中文 | 推导口径 |
| ------ | ---- | -------- |
| `raw` | 待处理 | 没有完成过 Rule/AI 筛选；仅有任务提交、排队或未产出候选人结果不算处理证据 |
| `archived` | 已归档 | 已有筛选、AI 决策、历史尝试、工作流归档/阻塞或 ScopeItem 失败/需处理等证据，但当前志愿没有下列有效尝试且最新原因不是容量耗尽；这是展示归类，不强制改写 `CandidateWorkflow.status` |
| `pending_reallocation` | 待重新分配 | 当前志愿最新相关处理结果为 `job_hc_exhausted`，且没有当前有效尝试；保留当前志愿等待新任务 |
| `pending_review` | 待复核 | 当前志愿存在未取消的 `AssignmentAttempt.status=pending_review` |
| `pending_dispatch` | 待下发 | 当前志愿存在未取消的 `AssignmentAttempt.status=pending_dispatch` |
| `pending_screening` | 待业务反馈 | 当前志愿存在 `dispatched_l2 / assigned_l3` 尝试，已给业务部门但尚未反馈 |
| `screening_passed` | 通过 | 当前志愿按 `attempt_no / id` 最新的非取消尝试状态为 `passed` |
| `screening_rejected` | 不通过 | 当前志愿按 `attempt_no / id` 最新的非取消尝试状态为 `rejected` |

> 简历状态不落为 `Resume.status`，后者继续保存导入文件中的原始“应聘状态”。“当前有效尝试”必须同时满足 `attempt.resume_id = workflow.current_resume_id` 且 `status != cancelled`；历史志愿的 passed/rejected/cancelled 只在详情保留，不参与当前状态推导。应用层先取得当前志愿按 `attempt_no / id` 最新的非取消尝试，再依次映射 `screening_passed / screening_rejected / pending_screening / pending_review / pending_dispatch`；没有有效尝试时再判断 `pending_reallocation → archived → raw`。`classified`、`allocated` 立即停止支持，任何列表或处理范围接口收到旧值或未知状态均返回 400，不得静默忽略。

`CandidateWorkflow.status`：

| 状态 | 含义 |
| ---- | ---- |
| `pending` | 待分配；候选人尚未生成有效分配尝试 |
| `in_progress` | 进行中 |
| `passed` | 已通过 |
| `archived` | 已归档 |

`AssignmentAttempt.status`：

| 状态 | 含义 | 允许操作 |
| ---- | ---- | -------- |
| `pending_review` | 待 HR 复核 | HR 确认下发、取消或转人工处理 |
| `pending_dispatch` | 待下发 | HR 下发或取消 |
| `dispatched_l2` | 已下发二级 | 绑定二级接口人转派；拥有 `attempt.feedback` 时也可在转派前反馈 |
| `assigned_l3` | 已转派三级 | 绑定三级接口人在拥有 `attempt.feedback` 时反馈；原二级接口人不可再反馈 |
| `passed` | 已通过 | 终态，只读 |
| `rejected` | 未通过 | 终态，系统尝试下一志愿 |
| `cancelled` | 已取消 | 终态，只读 |

> `CandidateWorkflow.status` 和 `AssignmentAttempt.status` 均继续作为领域状态及详情数据保留；八种简历状态是业务展示层，不强制迁移既有工作流枚举。简历库主表继续隐藏流程状态和分配状态，详情接口保留底层状态。

核心流转：

- HR 下发：`pending_dispatch → dispatched_l2`。
- 二级转派：`dispatched_l2 → assigned_l3`。
- 二级转派前反馈：绑定二级接口人在同时拥有 `attempt.view_received` 与 `attempt.feedback` 时，可将 `dispatched_l2 → passed/rejected`；一旦转派为 `assigned_l3` 即失去本次反馈入口。
- 三级反馈：绑定三级接口人在同时拥有 `attempt.view_assigned` 与 `attempt.feedback` 时，将 `assigned_l3 → passed/rejected`。
- 任一允许阶段反馈通过时，候选人流程置 `passed`；反馈未通过时自动寻找下一志愿，无下一志愿则归档。事务锁、重复提交保护及取消其它未反馈尝试逻辑共用同一状态机。
- 当前志愿缺可用二级接口人：流程保持 `in_progress` 并记录阻塞原因，等待 HR 补齐接口人、手动分配或重新处理；该场景不触发下一志愿。
- HR 确认 AI 复核项：`pending_review → pending_dispatch`。
- HR 取消 AI 复核项：`pending_review → cancelled`，写入 `cancel_reason=hr_cancelled`；若流程不存在其它活动尝试，则归档为 `agent_no_recommendation`。
- HR 取消待下发项：`pending_dispatch → cancelled` 并写入取消原因；无其它活动尝试时，Rule 结果归档为 `hr_cancelled`，AI 结果归档为 `agent_no_recommendation`，均可由 HR 重新处理或手动分配。
- 取消 `pending_review / pending_dispatch` 自动尝试时，若 `capacity_reservation` 非空且尚无 `dispatched_at`，在同一事务锁定容量行、将 `used_count` 幂等减一并写 `capacity_released_at`；重复取消不得重复释放。已经实际下发的尝试及手动强制分配不释放任务容量。
- HR 转人工处理 AI 复核项：先将原 `pending_review` 置为 `cancelled(manual_replaced)`，再从明确的 `resume_id` 发起手动强制分配。
- 强制分配领域服务：`manual_assign` 与后台专项分流共用 `_force_assign_locked`，统一取消同流程未反馈尝试、校验二/三级接口人关系、创建 `assigned_l3` 和两段 `AssignmentHandoff`。人工入口使用 `source=manual` 并使在途自动令牌失效；后台路由使用 `source=ai + route_code=ai_special_route`，复用当前任务令牌但保留内部审计字段。对外序列化折叠为普通 AI 自动分配，`AssignmentAttemptSerializer` 和 `AgentDispatchDecisionSerializer` 不返回 `route_code`、专项置信度、专项证据、配置快照或是否命中/已路由字段。

快照与历史：

- `AssignmentAttempt` 创建时写入二级部门、二级接口人姓名/工号、应聘ID、岗位名称和操作者快照；三级转派时补写三级部门、三级接口人姓名/工号快照。
- `AssignmentHandoff` 记录转派历史，同时写入 from/to 接口人姓名/工号、转入部门名称和操作者用户名快照。
- `AgentDispatchDecision` 写入 AI 推荐接口人姓名/工号快照，避免推荐接口人后续删除导致决策详情不可读。
- `AssignmentHandoff` 只记录转交历史，不作为通用审计日志。

## 八、API 设计

通用约定：

- 列表 API 默认分页返回，支持 `page` 和 `page_size` 参数；共享前端分页主表默认提供每页 `10 / 20 / 50 / 100 / 500` 条选项，并按当前选项提交 `page_size`。后端最大接受 500，避免一次性拉取过大结果集。
- 候选人、岗位、院校、接口人、候选人工作流、分配尝试、用户/角色和配置字典等分页列表的表头筛选由后端执行，查询参数直接对应前端可筛选列；候选人姓名搜索同时匹配姓名原文、姓名全拼和姓名拼音首字母。分配尝试筛选同时覆盖当前关联对象和历史快照文本，保证关联对象删除后仍可按可见内容查询。
- 布尔筛选统一接受 `true` / `false` 字符串。
- 简历业务状态参数统一使用八值白名单 `raw / archived / pending_reallocation / pending_review / pending_dispatch / pending_screening / screening_passed / screening_rejected`；多值参数先过滤空字符串，再校验每个非空项，出现旧值或未知值即整体返回 400。
- 文件导出与预览返回 Django `HttpResponse`，不是 DRF `Response`；两个简历导出接口始终返回 ZIP，并通过 `X-Export-Count`、`X-Export-Missing`、`X-Export-Candidate-Count` 分别返回命中文件数、缺失文件数和候选人数。职位清单导出返回独立 XLSX 和 `X-Export-Count`。预览响应继续通过 `X-Resume-Filename` 返回原始文件名；预览接口只负责鉴权、数据范围过滤和返回 PDF Blob，不暴露 `media/resumes/` 静态地址，浏览器内预览由前端 PDF.js 将 Blob 渲染到 canvas 完成。

当前代码落点：

- 标准分页类在 `apps.api.pagination.StandardResultsSetPagination`，由 DRF `DEFAULT_PAGINATION_CLASS` 统一启用；默认 `PAGE_SIZE=20`，允许前端通过 `page_size` 调整，最大 500。
- 文件导出统一走简历组合导出响应构造器，候选人导出和分配尝试导出复用字段白名单、候选人级 Excel、文件收集、缺失清单、同名消歧和统计响应头；单份简历也返回包含 Excel 和 `简历文件/` 的 ZIP。
- 文件预览统一走 `resume_preview_response(resume)`，直接从 `media/resumes/` 读取文件并以 PDF Blob 响应返回，同时通过响应头携带原始文件名；文件缺失或未匹配时返回 404。前端拿到 Blob 后用 PDF.js 渲染 PDF，非 PDF 文件提示下载原文件。
- `bool_query_value` 负责把查询字符串中的 `true` / `false` 规范为布尔值，用于岗位、接口人等表头筛选。
- 职位清单由 `apps.api.job_export` 基于完整的岗位列表筛选查询集即时生成，不使用分页结果；未显式指定启停状态时只包含启用岗位。工作表固定名为“职位清单”，复用岗位模板字段定义，按招聘主体、一层部门、二层部门、三级部门、岗位类别、对外发布名称、是否对外发布、职位名称、岗位族、工作地点、学历、工作职责、需求专业、HC 的固定顺序写列；表头冻结且启用筛选，按内容限制列宽，所有字符串写入前防护 `= / + / - / @` 公式前缀。
- API 测试需覆盖四个模板类型的 `resume.import` 权限、XLSX 文件名、版本 1、两张工作表、字段顺序、冻结/筛选表头，以及四类导入缺失、未知、重复表头均在快照和写库前整批失败并返回具体清单；同时覆盖分页参数、岗位一至三级序列化与新旧筛选参数、二级/三级编辑校验、职位清单权限/筛选/启用口径/跨页全量/响应头/与岗位模板共享列顺序/公式防护，以及其它候选人/院校/接口人、工作流、分配尝试、用户/角色和配置字典表头筛选。Ingestion 聚焦测试另覆盖七字段完整业务键、大小写/空白归一化、三级缺父级行号、旧二级岗位唯一补齐与一拆多、完整专业替换、已有 HC 快照保留和事务回滚；Pipeline 聚焦测试覆盖三级岗位回溯父级二级接口人、AI 专业不匹配仍调用模型且所有入口不落 `major_not_matched`，以及 Rule 仍正常产出该原因。

## 九、权限与数据范围

RBAC：

- 使用 Django `Group / Permission`。
- 用户通过 `accounts_user_groups` 绑定一个或多个角色。
- 角色通过 `auth_group_permissions` 绑定权限点。
- 权限点由后端预置，并以树形清单返回前端。
- 前端按权限码控制菜单、路由和按钮；后端 DRF 权限类仍按同一权限码做接口级校验。
- `pipeline.view` 控制共享 ProcessingRun 列表/详情和侧栏独立处理任务页，`pipeline.run` 控制创建流程及取消活跃运行；两者默认授予管理员和 HR，二级、三级接口人默认不授予。
- `analytics.view` 默认授予管理员和 HR；二级、三级接口人默认不授予，招聘分析接口不复用接口人的分配数据范围。
- 部门接口人页只按 `department.manage` 展示和操作 WeLink 开关；分配参数页只按 `settings.manage_config` 展示和操作 `job_hc_coefficient`。ConfigViewSet 的注册表读取兼容两类既有权限，但更新 HC 系数时额外强制校验 `settings.manage_config`；`department.manage` 不得更新 HC 系数。该边界也不恢复通用“系统参数”页签或开放任意 Config 键。
- `accounts.0005_add_analytics_permission` 以增量数据迁移创建权限并只向既有“管理员”“HR”组追加绑定，升级时不运行全量 `seed_base`，也不覆盖管理员维护的其它角色权限。
- 账号应用的数据迁移硬编码创建内置受保护管理员：`username="012358"`、`email="huyue2@ueascend.com"`、`is_superuser=True`、`is_staff=True`、`is_active=True`，执行 `set_unusable_password()` 并绑定“管理员”组。该迁移是新环境的创建来源，不依赖 `seed_base`。

数据范围：

- 不单独建数据范围表。
- 由角色权限、`User.contact_id`、`Contact.department_id` 推导。
- 二级接口人仅可见 `contact_id` 指向自己且已由 HR 下发的尝试，至少排除 `pending_review`、`pending_dispatch`、`cancelled` 等 HR 内部状态；二级接口人只能转派给所属二级部门下的三级接口人。若另获授 `attempt.feedback`，只可对本人接收且仍为 `dispatched_l2` 的尝试反馈。

- HR/管理员默认可看全量。
- HR/管理员通过简历库查看全部候选人和分配历史；二级、三级接口人也进入简历库，但候选人查询、筛选选项、详情、导出和预览都必须按上述接口人数据范围过滤。普通接口人列表和详情响应仍只保留本人可见尝试及其关联投递，不返回手机号、其它志愿、其它尝试或 AI 决策；简历组合导出是明确例外：拥有 `attempt.export` 的接口人可在 Excel 中选择手机号字段，但只能得到本人可见尝试对应候选人的手机号，不能扩展候选人或投递范围。

W3 OAuth2 认证（当前实现）：

- W3 是非 OIDC 的 OAuth2 SSO。`apps.accounts.oauth2` 实现提供方无关的 Authorization Code 流程，不使用 discovery、ID Token 或前端直连 Token 端点。回调路径固定为 `/api/auth/w3/callback/`；生产 `W3_OAUTH2_REDIRECT_URI` 必须是 W3 平台精确登记的完整 HTTPS URL，与外层 TLS 代理使用的生产域名及 `https://<生产域名>/api/auth/w3/callback/` 逐字一致，且自身不得携带 params、query 或 fragment。`DJANGO_ALLOWED_HOSTS` 必须包含同一生产域名。
- 发起授权时生成高强度 `state`，默认生成 PKCE verifier 并发送 S256 challenge；二者和创建时间保存在 Django Session。回调首先一次性取出事务并用恒定时间比较校验 `state` 及 TTL，失败时不请求提供方 Token/UserInfo。
- 后端根据 `client_secret_basic / client_secret_post / none` 之一请求 Token 端点，再以 UserInfo 查询参数 `access_token + scope + client_id` 请求用户信息，HTTP 头只声明 `Accept: application/json`。提供方响应顶层包含 `tenantId`、`uuid`、`globalUserID`、`email`、`employeeNumber`；默认 `W3_OAUTH2_EMPLOYEE_NO_FIELD=employeeNumber`、`W3_OAUTH2_EMAIL_FIELD=email`。后端只从这两个配置路径提取字符串/整数工号和有效邮箱，邮箱统一转为小写；工号精确匹配 `User.username`、邮箱按大小写不敏感口径匹配 `User.email`，并同时命中同一个账号。只匹配一个字段不做 OR 或降级。邮箱缺失、非字符串或格式无效返回 `email_missing`，双字段未命中同一账号返回 `account_not_found`，停用账号返回 `account_inactive`；全程不自动创建、启用或修改用户、角色与 Contact 绑定，不读取或持久化 `tenantId`、`uuid`、`globalUserID`。
- 回调成功后复用项目现有 DRF Token，但只将 `token + user_id + created_at` 存入轮换过 session key 的 Django Session。前端回跳 URL 只携带 `oauth2=success` 或稳定 `oauth2_error`；同一 Session 再调用 `POST /api/auth/w3/complete/` 后才一次性返回 DRF Token，返回前即从 Session 取出，不在 URL、日志或提供方回跳参数中暴露 W3 或项目 Token。
- 授权入口不接受业务请求传入的 `redirect`/`next` 参数。授权、Token、UserInfo 和 redirect URI 必须为 HTTPS（仅 DEBUG 允许 localhost HTTP）；前端回跳只使用服务端 `W3_OAUTH2_FRONTEND_CALLBACK_URL`，该值必须是单斜杠开头、不含 scheme/netloc、反斜杠或换行符的本站相对地址，解析后的路径必须精确为 `/login`，仅允许携带服务端固定查询参数且不得预置 `oauth2` / `oauth2_error` 保留键，不得携带 URL params 或 fragment，也不允许绝对 URL，因此不形成开放重定向。W3 授权与前端回跳响应统一设置 `Cache-Control: no-store` 和 `Referrer-Policy: no-referrer`；W3 在非 DEBUG 环境启用时，Session Cookie 设置 `Secure + HttpOnly + SameSite=Lax`。
- 全部配置只来自服务端环境变量：`W3_OAUTH2_ENABLED`、`W3_OAUTH2_CLIENT_ID`、`W3_OAUTH2_CLIENT_SECRET`、`W3_OAUTH2_AUTHORIZE_URL`、`W3_OAUTH2_TOKEN_URL`、`W3_OAUTH2_USERINFO_URL`、`W3_OAUTH2_REDIRECT_URI`、`W3_OAUTH2_FRONTEND_CALLBACK_URL`、`W3_OAUTH2_SCOPE`、`W3_OAUTH2_EMPLOYEE_NO_FIELD`、`W3_OAUTH2_EMAIL_FIELD`、`W3_OAUTH2_CLIENT_AUTH_METHOD`、`W3_OAUTH2_USE_PKCE`、`W3_OAUTH2_TIMEOUT_SECONDS`、`W3_OAUTH2_TRANSACTION_TTL_SECONDS`。可用部署必须显式设置 `W3_OAUTH2_ENABLED=True`；`.env.example` 的 false 仅是首次生成 `.env` 后退出的安全占位。默认值包括 `W3_OAUTH2_EMPLOYEE_NO_FIELD=employeeNumber`、`W3_OAUTH2_EMAIL_FIELD=email`、`W3_OAUTH2_FRONTEND_CALLBACK_URL=/login`、`W3_OAUTH2_USE_PKCE=True`；不再存在本地登录开关。W3 未启用或配置未就绪时生产部署校验直接失败；开发环境则由状态接口决定是否显示 DEBUG 开发令牌入口。该功能不读取 `Config`，也不建立 W3 专用身份映射模型。接口人邮箱字段由 `core.0032_contact_email` schema migration 新增，并将已有绑定用户的非空 `User.email` 规范化回填到 `Contact.email`。
- 待 W3 外部确认的生产信息为 authorize/token/userinfo 地址、client id/secret、scope、client auth method 和最终生产 redirect URI；UserInfo 顶层字段及 `employeeNumber / email` 双字段账号映射已确认。

账号密码与本地开发：

- `User` 继续继承 Django `AbstractUser` 并保留 `password` 数据库列，但模型层的 `set_password()` 和 `save()` 都会强制写入不可用密码标记，禁止产生或直接保存可用密码哈希。`accounts.0007_invalidate_user_passwords` 以不可逆数据迁移一次性使现有账号密码全部失效；迁移回滚不会恢复旧哈希。
- 删除本地用户名/密码 `AuthLoginView` 及 `/api/auth/login/` 路由，并从项目 URLConf 删除 Django Admin `/admin/`。两条路径均返回 404。DRF Token 认证仍保留，作为 W3 回调完成后的项目会话协议。
- 接口人账号由部门接口人导入或页面 POST/PATCH 自动创建、更新，用户名为工号、邮箱为规范化后的接口人邮箱；每次同步都调用 `set_unusable_password()`，同时按接口人所属部门层级维护二级/三级接口人角色，并使账号启停状态与 `Contact.is_active` 一致。编辑工号或邮箱时同步修改绑定账号，工号或邮箱被不同账号占用时拒绝，非接口人业务角色不变。用户管理新增/编辑同样要求有效且大小写不敏感唯一的邮箱，不序列化密码并拒绝请求中的 `password` 字段；不维护 `first_name`、`last_name` 等 Django 姓名类字段，姓名展示来自绑定的 `Contact`。历史接口人若未由 `core.0032_contact_email` 从已有 `User.email` 回填，必须重新导入或维护邮箱后才能满足 W3 双字段映射。
- 普通用户管理删除采用清理语义：删除 `User` 账号、Token 和角色绑定；若用户绑定 `Contact`，同步删除该接口人。后端删除流程必须先将历史分配、转派、AI 决策等记录中的 `contact/sub_contact/recommended_contact/from_contact/to_contact/created_by` 等外键置空，历史页面通过 `AssignmentAttempt`、`AssignmentHandoff`、`AgentDispatchDecision` 的快照字段继续展示当时的接口人、工号、部门和操作者信息，管理员不能通过删除用户破坏候选人流程历史。内置受保护管理员不进入该流程，所有写入和删除请求在清理前即返回拒绝。
- 内置受保护管理员固定为工号/用户名 `012358`、邮箱 `huyue2@ueascend.com`，无本地可用密码，始终启用并具备 staff、superuser、管理员角色和全部权限。账号由数据迁移创建，`seed_base` 不负责创建、覆盖或重置它。

## 十、配置与可观测性

### 招聘分析聚合

- `GET /api/analytics/recruitment-overview/` 默认使用最近 30 天，可显式传入 `date_from` / `date_to`，最大 366 天；筛选项为 `entity`、`job_id`、`department_id`、`school_tag_id`、`education`、`source`。
- cohort 以 `Resume.imported_at` 的 Asia/Shanghai 自然日闭区间确定。投递记录按 Resume 计数，候选人及分类、分配、下发、反馈、通过、归档阶段按 Candidate 去重；各转化率统一使用 cohort 去重候选人数作为分母。Dashboard 对每条投递按 `attempt_no / id` 取最新非取消 `AssignmentAttempt`，`department_id` 与 `source` 筛选及部门排行使用这一有效尝试，取消记录不能覆盖当前归属；结果报表另按候选人当前志愿的有效尝试取归属和八状态。
- 岗位排行优先使用 `CandidateWorkflow.current_resume`，无当前投递时回退 cohort 内志愿顺序最靠前投递；部门排行在上述最新非取消尝试中优先读取 `department_name_snapshot`，避免主数据改名或删除影响展示。
- 平均耗时分别按候选人参与对应事件统计的 cohort 投递中最早 `Resume.imported_at`，到最早分配创建、下发和反馈时间计算。Rule/AI/Manual、AI recommendation 和错误码按各分组内去重候选人数统计；同一候选人落入不同分组时可分别计入。自由文本未通过原因只返回前 10 项并限制显示长度。
- 返回统一 `data_as_of`、生效 `filters` 和 `methodology`；统计结果分为 `summary`、`conversion`、`average_hours`、`trend`、`source_distribution`、`ai_recommendation_distribution`、`ai_error_distribution`、`job_ranking`、`department_ranking`、`school_tag_ranking`、`education_distribution`、`archive_reason_distribution`、`rejection_reason_distribution`，并返回 `filter_options`。同一规范化筛选参数缓存 300 秒，缓存命中时 `data_as_of` 保持该份统计结果的生成时点；前端不得拉取候选人明细重新统计。
- Dashboard 的“已生成分配”、分类、下发、反馈等分析指标继续按独立事件口径聚合，不改名为八种简历状态，也不因 `classified / allocated` 查询状态码下线而删除。

### 备份、恢复与灾备

- `smart-resume-filter-backup` 自包含 PostgreSQL client、restic 和校验脚本。`backup-scheduler` 正常启动后立即执行一次，之后默认每小时执行；`backup`、`backup-verify`、`restore` 通过 Compose profile 手工运行，其中 restore 正常启动时绝不执行。
- 每个 restic 快照包含 PostgreSQL custom-format dump、完整 `media_data`、应用/数据库版本、时间、文件数、大小和 SHA-256 清单；仓库默认保留 48 hourly、30 daily、12 monthly。状态目录输出最后尝试/成功信息及 Prometheus 文本格式状态文件，但不包含简历明细或凭据；本轮不因此部署 Prometheus 或告警服务。
- restic 仓库通过 `BACKUP_TARGET_PATH` 挂载，默认值为 `/mnt/smart-resume-filter-backups`；生产必须使用已经存在、可写并指向异机挂载或外置磁盘的绝对路径。镜像、端口、worker/OCR、数据库标识和备份保留参数等静态运行参数在部署模板中预置。首次运行部署脚本只创建权限为 `600` 的 `.env`，从 `/dev/urandom` 分别生成相互独立的 `RESTIC_PASSWORD`、`POSTGRES_PASSWORD`、`DJANGO_SECRET_KEY` 且不回显；`W3_OAUTH2_ENABLED=False` 作为 `.env.example` 安全占位保留，然后脚本在任何 Docker 变更前退出。运维补齐 W3 参数并把开关改为 true 后，第二次运行才执行真正部署。检测到已有容器或任何项目数据卷时禁止用占位值生成新密钥，必须先恢复原 `.env`；该保护同样适用于升级、迁移和灾后重建。三项密钥不进入快照；缺少原 `DJANGO_SECRET_KEY` 时既有 AI 连接密文不能保证解密。
- 部署入口 `skills/smart-resume-offline-deploy/scripts/deploy.sh` 在 `docker load`、Compose build、init、`up` 等任何 Docker 变更前执行 `validate-w3-env.sh`。校验器首先强制 `DJANGO_DEBUG=False`，再要求 `W3_OAUTH2_ENABLED=True`；缺失或非法值均立即失败，不再跳过提供方参数校验。必填变量为 `W3_OAUTH2_CLIENT_ID`、`W3_OAUTH2_AUTHORIZE_URL`、`W3_OAUTH2_TOKEN_URL`、`W3_OAUTH2_USERINFO_URL`、`W3_OAUTH2_REDIRECT_URI`、`W3_OAUTH2_EMPLOYEE_NO_FIELD`、`W3_OAUTH2_EMAIL_FIELD`、`W3_OAUTH2_CLIENT_AUTH_METHOD`、`W3_OAUTH2_TIMEOUT_SECONDS`、`W3_OAUTH2_TRANSACTION_TTL_SECONDS`，其中字段路径默认固定为 `employeeNumber / email`。客户端认证方式只允许 `client_secret_basic / client_secret_post / none`；前两者要求 `W3_OAUTH2_CLIENT_SECRET`，`none` 允许为空；`W3_OAUTH2_SCOPE` 按提供方要求填写。`W3_OAUTH2_FRONTEND_CALLBACK_URL=/login`、`W3_OAUTH2_USE_PKCE=True` 使用安全默认；部署模板不含本地登录开关。
- 部署校验要求 authorize/token/userinfo/redirect URI 均为 HTTPS；redirect URI 必须精确指向 `/api/auth/w3/callback/`，不得携带 params、query 或 fragment。`W3_OAUTH2_FRONTEND_CALLBACK_URL` 必须指向本站 `/login`，可带不包含保留键的固定 query，但不得预置 `oauth2` / `oauth2_error`。布尔配置必须可解析，请求超时必须为正数，事务 TTL 必须为正整数。校验失败会在任何 Docker 变更前退出，错误只包含配置键名和稳定说明，不输出 secret；部署后的 `verify.sh` 在执行 Compose 和应用检查前再次运行同一校验。
- 生产流量拓扑固定为 `客户端 HTTPS → 外层企业网关/WAF/Nginx/Caddy → frontend 暴露端口 → frontend 内置 Nginx`；静态页面由 frontend 返回，`/api` 再由 frontend 内置 Nginx 转发到 Compose 内网 `backend:8000`。外层代理不得按 `/api` 分流直连 backend，backend 暴露端口不得作为正式入口。
- 外层代理保留客户端请求 `Host`，设置 `X-Real-IP`、追加 `X-Forwarded-For` 并设置 `X-Forwarded-Proto=https`。这些头目前只作为边缘入口和代理链的标准约束；frontend 内置 Nginx 会重写相关转发头，Django 也未配置 `SECURE_PROXY_SSL_HEADER`，所以后端当前不把它们作为可信的原始协议或客户端地址来源。同机反代建议设置 `FRONTEND_BIND=127.0.0.1`、`BACKEND_BIND=127.0.0.1`；异机网关只通过受控内网/防火墙访问 frontend，不能访问 backend。`DJANGO_ALLOWED_HOSTS` 使用生产域名，不用服务器 IP 代替。
- 生产验收必须从实际客户端网络验证生产 HTTPS 域名、证书链和有效期、HTTP→HTTPS 跳转、`GET /api/auth/w3/status/` 就绪状态及完整 W3 回调。只验证容器健康检查、服务器本机端口或直接访问 `IP:5173` 均不能判定正式部署完成。
- 恢复要求 `CONFIRM_RESTORE=YES_I_UNDERSTAND`；目标等于生产库时还要求 `ALLOW_PRODUCTION_OVERWRITE=YES`，且发现目标库仍有活动连接时拒绝。恢复顺序固定为数据库、media、迁移/约束/文件完整性检查、应用启动和业务冒烟。
- `ops/backup/drill.sh` 使用独立 Compose project、宿主机端口和命名卷恢复最新或指定快照，不复用生产数据库或 media 卷；演练执行 `migrate --check --plan`、`manage.py check`、核心表计数、数据库约束与缺失简历文件检查，并将开始/完成时间、快照、统计和失败原因写入 JSON 报告。建议每月隔离恢复、每季度整机恢复演练。
- 当前灾备等级为单机 Compose + 异机/外置加密备份，不承诺 PostgreSQL/Redis 高可用或自动故障切换。

`Config` 保存：

- `job_hc_coefficient`，默认 `1`，正整数范围 `1–100`；只影响新建处理任务的岗位容量快照。
- `ai_dispatch_threshold`，默认 `0.75`。
- `ai_review_threshold`，默认 `0.5`。
- `ai_timeout_seconds`。
- `ai_concurrency`。
- `ai_retry_count`。
- `ai_retry_backoff_seconds`。
- `ai_special_route_enabled`，默认 `false`。
- `ai_special_route_threshold`，默认 `0.90`，运行时严格大于才触发。
- `ai_special_route_secondary_contact_id / ai_special_route_tertiary_contact_id`。
- `welink_enabled`。

系统不再保存或读取 `ai_enabled`；数据迁移删除历史遗留键。Rule / AI 由每次上传或处理请求显式选择，并固化在 `ProcessingRun.mode`。

AI 配置分层：

- `apps.pipeline.ai_config` 只读取并校验系统设置保存的统一内网地址、API 风格、手动模型名称和可选 API Key，不预设模型名称。
- 模型列表查询使用当前统一 Base URL 和可选 API Key 调用 `GET {base_url}/models`，只返回规范化的模型 ID 候选项，不持久化列表，也不根据列表推断 `api_style`。列表查询失败不影响管理员手工输入模型名称。
- `/api/ai-connection/`、`/api/ai-connection/settings/`、连接测试以及全部 `/api/ai-prompts/` 接口统一受 `settings.manage_ai_connection` 保护；管理员角色默认拥有该权限，管理员也可通过角色权限绑定授予其他角色。未获授权的 HR、二级和三级接口人无查看、修改或测试权限，DRF 返回 403。模型连接、AI 运行参数和专项配置都不混入普通 `/api/configs/` 的可编辑项；前端分别提供「AI 模型连接」和「Prompt 管理」独立页面。
- 系统不提供全局 AI 分配开关。连接测试成功且其指纹与当前 API 风格、模型名、Base URL 和可选 API Key 完整一致时，`/api/allocation-mode/` 才返回 AI 可选；这不是持续健康探针。每次请求显式选择并固化模式，连接状态后续变化不取消已有任务或改变历史尝试。
- API Key 只接受写入：GET 响应只给出是否已配置等安全摘要，永不返回明文或密文。服务端使用 Django `SECRET_KEY` 派生 Fernet 密钥加密后保存到 `Config`，运行时解密供调用使用；API、前端状态、任务记录和错误响应均不得回显 Key。
- 模型连接只从系统设置保存的 Config 记录读取；调用时完全不读取环境变量或部署文件中的 API 风格、模型名、Base URL 与 API Key。API Key 可为空；清除已保存 Key 后会使连接测试失效，新提交只可选择 Rule，重新测试无鉴权内网服务成功后恢复 AI 选项。
- backend Web 进程和 Celery worker 进程分别维护进程内客户端缓存，按 `(api_style, base_url, API Key SHA-256 指纹, timeout_seconds)` 精确组成的缓存键复用 OpenAI SDK 客户端及其底层 httpx 客户端，以复用 HTTP 连接；缓存键不包含 `model_name`。任一缓存键字段变化时创建并使用新的缓存项，不复用旧连接。进程退出时通过退出钩子关闭缓存中的客户端；底层 httpx 客户端继续使用 `verify=False`。缓存只存在于进程内，不写入 `Config`，不改变连接测试指纹契约。
- `ai_concurrency` 已启用为跨 worker/跨运行的 Redis 共享自适应并发上限，默认 8，范围 1–20。专用 AI worker 线程数只提供本机执行容量，不绕过模型资源的共享上限。
- `ai_special_route_enabled` 默认关闭；`ai_special_route_threshold` 默认 0.90 且使用严格大于语义；`ai_special_route_secondary_contact_id / ai_special_route_tertiary_contact_id` 指定固定链路。这四个 `section=special_route` 键在“AI 专项”页签展示；接口返回全部启用接口人的层级、部门和父部门信息，页面先选父级二级接口人，再只列其下属三级接口人。配置写入时后端逐键校验启用链路；已启用状态切换目标时，页面按“关闭 → 更新阈值/目标变化项 → 按最终状态恢复开关”顺序保存，失败后重新读取服务端真实状态。运行时目标失效则记录内部回落快照并继续普通 AI。专项命中、证据、路由码和配置审计仍不进入候选人详情、公开原因或招聘分析。
- `POST /api/ai-connection/test/` 以当前保存配置发起最小真实模型请求，成功后保存不含密钥的连接指纹和测试时间。连接保存或清除 Key 时删除该状态；连接失败、超时和调用异常只按统一映射写入 `AgentDispatchDecision.error_code/error_message`，不自动切换正在使用的模式。第三方 SDK 原始异常绝不写入 AI 决策、API 响应或日志。
- Prompt 全文、版本和测试/发布审计保存在独立 `AIPromptVersion`，不写入 `Config`。模型连接保存或清除 Key 时，除了删除连接测试状态，还立即清除共享草稿的 Prompt 测试字段；发布 Prompt 不修改模型连接配置或连接测试状态。

`ProcessingRun` 持久化与 API 派生：

- 处理步骤、模式、内部固化范围及对外范围摘要、发起人、当前阶段、状态、运行参数、Celery task id、最近心跳、开始/结束时间、最终业务结果和错误信息。
- 运行列表和详情序列化时返回派生字段 `elapsed_seconds`，统一按 `(finished_at 或服务端当前时间) - created_at` 计算并取非负整数秒：存在 `finished_at` 时使用该时间固定结果，否则使用序列化时的服务端当前时间。该字段不写入 `ProcessingRun`，不新增数据库迁移；任务提交后的排队时间计入总耗时。
- 取消审计：`cancel_requested_at`、`cancelled_at`、`cancelled_by` 及取消人用户名快照。运行状态包含 `cancelling` / `cancelled`；任务中心的活跃集应包含 `pending`、`running`、`waiting_conflict` 和 `cancelling`。
- `ProcessingRunStage` 保存父运行内 Step1–Step4 的状态和累计工作量；上传 Rule 为三阶段、AI 为四阶段，人工处理从 Step2 开始。
- 批处理最终结果统计：处理完成、需处理、失败、安全跳过、取消，以及 AI 待复核、待下发、建议归档子项；Run 和 Stage 均保存 completed/needs_attention/failed/skipped/cancelled 计数。
- Rule / AI 主结果按 `ProcessingRunScopeItem.result_type` 跳转简历库；AI `review / dispatch / archive` 以同一运行 `AgentDispatchDecision.recommendation` 为 completed 业务细分。跳转只构造任务定位参数 `processing_run_id + processing_result`；主表不暴露独立 `result_type`/“处理结果”筛选，`reason_code` 仍可与任务定位及八种业务状态组合。
- AI 运行可观测指标：`ai_concurrency_limit`、`ai_effective_concurrency`、`ai_retry_count`、`ai_rate_limit_count`；候选人级完成度继续复用 chunk 计数字段，AI 模式下 `chunk_size=1`。
- AI 策略版本信息：模型名称、提交时冻结的 prompt 版本、decision 版本；执行和成功/失败决策只读取该 prompt 版本，后来发布的新版本不回写既有运行。
- 上传撤销时，相关运行记录保留并更新为 `status=undone`，写入撤销时间和操作者；关联任务未结束时拒绝撤销，快照改为已撤销状态而非删除。

日志与错误：

- 导入错误需要返回明确原因和行级上下文。
- AI 异常需要记录稳定原因，不自动回退 Rule；AI 服务通过 `AIServiceError` 传递的受控错误消息在构造时移除 NUL（`0x00`）字符，避免其写入异常决策时触发 PostgreSQL `DataError`。候选人级只有 `llm_timeout` 映射为 failed，其它受控 AI 异常映射为 needs_attention；该口径不表示对系统内所有数据库文本字段做全局清洗。
- AI 重试只针对超时、限流、网络错误等临时错误；PDF 解析失败、输出结构不合法、引用不存在等确定性错误不做无限重试。
- 候选人级批量下发返回 `total / eligible / dispatched / skipped / failed / errors` 统计；`errors` 只记录实际下发失败详情，不为每条状态不符合的跳过项生成原因。
- 取消不会回滚已经落库的候选人处理或分配尝试；执行器在开始阶段、处理候选人循环及结束阶段检查取消请求，取消后把未完成阶段标记为 `cancelled` 并结束父运行。

- 两个接口始终返回 `application/zip` 的组合包，单份简历也不直接返回原文件。ZIP 固定写入 `简历库清单.xlsx` 和显式 `简历文件/` 目录项，即使没有可用简历也保留空目录；Excel 只有一个名为“简历库”的工作表，并按候选人一人一行。存在缺失文件时额外写入 `缺失简历文件清单.txt`；简历文件同名时先附加应聘ID，仍重名时再追加序号消歧。
- 候选人导出对 HR/管理员取当前有效志愿及其最新有效尝试生成单值投递、岗位、职责、部门和反馈字段，同时把候选人现有范围内全部投递简历加入文件目录；尝试级导出按当前用户可见尝试收集文件，同一候选人命中多条所选尝试时以 `attempt_no / id` 最大的一条生成该候选人 Excel 行。
- Excel 多值字段以中文顿号连接；时间统一转换为 Asia/Shanghai 的 `YYYY-MM-DD HH:mm:ss`，工作职责列自动换行，所有字符串在写入前防护 `= / + / - / @` 公式前缀。手机号对所有拥有简历导出权限的用户开放；接口人虽然可选手机号，但候选人、当前投递、尝试和文件仍严格限定在本人接收或本人被转派的数据范围。
- 响应保留 `X-Export-Count`、`X-Export-Missing`，并增加 `X-Export-Candidate-Count`；三者依次表示 ZIP 内可用简历文件数、缺失文件数和去重候选人数。

结果报表：

- `GET /api/resumes/result-report/` 以投递为粒度，一条 `Resume.apply_id` 只计一次；必须显式传入导入日期范围，并可传入当前 Dashboard 已生效的二级部门 `department_id`。该接口仍独立返回 `.xlsx`，不接受简历属性选择，也不并入组合 ZIP。
- 查询批量 `select_related` 候选人并预取处理证据和全部非 `cancelled` 分配尝试，复用候选人列表的八状态推导器，避免报表另立状态口径。有效尝试必须属于当前志愿，历史志愿结果不得覆盖当前志愿；`pending_review`、`pending_dispatch` 分开统计，容量耗尽映射 `pending_reallocation`，其它已有处理证据但无当前有效分配状态映射 `archived`。二级部门过滤使用当前志愿最新有效尝试的 `department_id`。
- `.xlsx` 的“部门汇总”包含二级部门、导入简历数、分配简历数和八种状态计数，并生成“未分配”和合计行；“简历明细”包含导入时间、姓名、应聘ID、招聘主体、岗位、志愿、最高学历、二三级部门/接口人、分配来源、简历状态、反馈结果与时间，不包含手机号。
- 部门和接口人字段优先读取 `AssignmentAttempt` 快照，关联对象删除后再无外键也能统计；所有写入单元格的外部字符串需对 `= / + / - / @` 公式前缀做转义，防止 Excel 公式注入。

简历预览：

- 候选人详情从 `Resume` 维度预览 PDF；默认预览对象由 Candidate API 的 `preview_resume` 提供，当前投递有文件时优先预览当前投递，当前投递无文件时回退同候选人第一条有文件投递。
- 分配尝试详情从 `AssignmentAttempt` 维度预览 PDF，并复用分配尝试的数据范围控制，确保二级/三级接口人只能预览自己可见尝试的简历。
- 后端预览接口不生成图片、不转换 PDF，也不返回静态文件路径；鉴权和数据范围校验通过后，接口返回 PDF Blob，并通过响应头返回原始文件名。PDF.js 渲染、Blob URL 新窗口打开和下载入口由前端负责；无权限或越权时前端不得提供预览或下载入口，PDF 渲染失败或非 PDF 文件时保留下载原文件入口。
- 生产 Nginx/前端容器不得挂载或公开 `media/resumes/`，不得配置 `/media/` 静态 alias；预览和下载必须全部经过上述鉴权 API。
