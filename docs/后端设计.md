# 智能简历筛选系统 — 后端设计

> 本文承接 `docs/需求描述.md`，描述后端如何实现业务流程、服务边界、API、任务、权限和异常处理。数据库字段与关系以 `docs/数据库设计.md` 为准；前端页面与交互以 `docs/前端设计.md` 为准。

## 一、技术栈与运行形态

| 层 | 选型 | 说明 |
| -- | ---- | ---- |
| Web 后端 | Django + Django REST Framework | ORM、Admin、认证权限、CRUD API |
| 异步任务 | Celery + Redis | 生产环境处理 3 万条规模批任务，避免请求阻塞 |
| 数据处理 | pandas + openpyxl + xlrd | 读取 xlsx / xls / csv、字段映射、清洗、错误收集 |
| AI / Agent | OpenAI SDK | 简历正文理解、岗位适配、结构化分流建议 |
| 存储 | PostgreSQL（生产）/ SQLite（本地开发） | 业务数据、中间结果、配置和任务记录 |
| 文件 | 本地 `media/resumes/`（本地开发） | 简历 PDF 落盘，供鉴权预览和导出 |
| PDF 预览 | PDF.js（前端）+ 鉴权文件 API（后端） | 后端返回 PDF Blob 和文件名，前端自行渲染，避免依赖浏览器原生 PDF 插件 |
| 部署 | Docker Compose | 后端、前端、PostgreSQL、Redis、Celery worker 可组合部署 |

本机开发形态：

- SQLite。
- `CELERY_TASK_ALWAYS_EAGER=True`，任务同步执行，免 Redis/PostgreSQL。
- 启用 Token 登录、RBAC 权限校验和接口级数据过滤；W3 认证待外部接口方案确认后替换登录适配层。

生产形态：

- PostgreSQL。
- Celery + Redis 异步执行。
- 使用企业认证适配或系统账号登录，继续执行 RBAC、DRF 权限和接口级数据过滤。

## 二、Django 应用划分

| app | 职责 | 关键模块 |
| --- | ---- | -------- |
| `ingestion` | 数据源适配器，解析输入并写入领域模型 | `sources.py`、`snapshot.py` |
| `core` | 领域模型与基础主数据 | `models.py`、`management/commands/seed_base.py` |
| `pipeline` | 前置处理、候选人处理主流程、Rule/AI 策略、异步任务 | `runner.py`、`strategies.py`、`services/`、`tasks.py` |
| `api` | DRF API、ViewSet、显式动作接口 | `views.py`、`serializers.py`、`urls.py` |
| `accounts` | 用户、RBAC 权限、W3 认证预留 | `models.py`、权限类 |

后端解耦原则：

- 输入层做成数据源适配器，Excel 只是当前来源；业务逻辑不直接依赖 Excel 列名。
- 候选人处理主流程只依赖 Django 模型，不读原始文件字段。
- Rule / AI 分配策略走统一策略接口。
- 业务参数外置为配置或规则表。
- 南北归属只在志愿排序规则运行时判断，不落库、不做可维护省份字典。

## 三、数据流与处理入口

总体数据流：

`ingestion（适配器） → core 模型 → 前置数据准备（院校标签 / 岗位需求 / 接口人） → 候选人处理主流程 → 候选人分配工作流 → 输出（导出 / WeLink 下发 / 接口人反馈）`

处理触发：

- 简历库上传简历后，前端自动触发候选人处理主流程。
- 分配页切换 Rule / AI 策略后，只重算“简历分类、分配与下发”环节。
- 院校分类和需求录入可提前独立运行，也可在主流程前置维护。

任务记录：

- 每次处理写入 `ProcessingRun`。
- `ProcessingRun.step` 支持 `import / all / step1 / step2 / step3 / step4 / step5`。
- `step1` 为查重与志愿排序。
- `step2` 为简历分类、分配与下发。
- `step3` 为院校分类。
- `step4` 为需求录入。
- `step5` 为兼容旧入口的分配步骤别名。
- `all` 按 `step1 → step3 → step2 → step4` 执行；不要按数字顺序推断。`step3` 需在分配前完成，确保院校标签可供分配准入使用。

## 四、导入服务设计

入口：

- `POST /api/import/`
- 支持简历信息列表、岗位需求、院校清单、部门接口人、简历包。
- 四张业务表支持 `.xlsx`、`.xls`、`.csv` 表格文件，后端优先按文件内容识别格式，文件后缀仅作为辅助判断。
- 各前端数据页可只上传对应文件，后端按字段区分文件类型。

导入流程：

1. 识别上传文件类型。
2. 校验表头和格式。
3. 通过 `ingestion` 适配器解析为领域数据。
4. 规范化姓名、手机号、主体 code、院校名称、岗位类别等业务键。
5. 按应用层查询进行幂等写入。
6. 收集低风险更新、跳过、错误、舍弃数量。
7. 返回导入结果。

身份归并：

- 规范化姓名：去首尾空格、统一全/半角。
- 规范化手机号：去空格、分隔符、`+86` 前缀。
- 手机号缺失时，舍弃该候选人及其投递，不入库、不进入分配。
- 按 `normalized_name + normalized_phone` 查询候选人。
- 命中一条则复用并更新当前字段。
- 命中多条则阻断相关记录并进入导入错误清单。
- 按 `apply_id` 查询投递，存在则更新，不存在则创建并挂到候选人。
- 简历包按 `姓名（应聘ID）` 经应聘ID定位 `Resume`。

招聘主体：

- 导入时按 `RecruitingEntity.code` 匹配主体。
- 查不到时创建或进入人工映射。
- 部门和接口人不保存招聘主体归属。

部门接口人：

- 导入部门接口人信息时，按 `Contact.employee_no` 幂等写入接口人主数据。
- 每个有效导入的接口人同步一个系统用户：`User.username = Contact.employee_no`，新账号默认密码为 `pass1234`。
- 同步用户时按接口人层级确保拥有 `二级接口人` 或 `三级接口人` 角色，并写入 `User.contact_id`；已有同用户名用户保留原可用密码和非接口人业务角色，仅替换二级/三级接口人角色、启停状态和接口人绑定。
- 部门接口人 replace 导入时，本次文件中不存在的旧接口人置为停用，其绑定账号同步置为停用；本次文件中的接口人账号按 `Contact.is_active` 恢复或停用。replace 导入保留软停用语义，避免批量导入误删历史主数据。
- 用户管理或接口人清单中的单条删除采用清理语义：`DELETE /api/users/{id}/` 删除账号、Token 和角色绑定；若用户绑定 `Contact`，同步删除该接口人。`DELETE /api/contacts/{id}/` 删除接口人，并同步删除绑定该接口人的用户。删除前后端需先清空历史分配、转派、AI 决策等记录上的用户/接口人外键，仅保留快照字段和审计记录，避免级联删除候选人流程历史。
- 后续 W3 认证按工号识别用户，映射到同一个 `User.username`，不改变 RBAC 和数据范围推导。

撤销：

- 上传含简历数据前，写入一份 `ImportSnapshot`。
- 快照覆盖 Candidate / Resume / CandidateWorkflow / AssignmentAttempt。
- 只保留最近一份。
- `POST /api/import/undo/` 还原上传前状态，撤销后删除快照。

## 五、前置处理服务

### 院校分类

模块：`pipeline/services/classify_school.py`

职责：

- 读取 `School` 与 `SchoolTag`。
- 给候选人的第一学历、最高学历写入院校标签。
- 未命中学校或学校未配置标签时，可使用默认院校标签。
- 纯规则处理，不使用 AI。

边界：

- `School` 只保存 `province`，不保存南北归属。
- 户籍缺失时，Step1 可使用学校所在省份作为南北规则兜底。

### 需求录入

模块：`pipeline/services/demand.py`

职责：

- 解析校招岗位分类及专业要求。
- 写入 `Job`、`JobMajor`、`JobCategory`、`Department`。
- 岗位需求必须引用 `RecruitingEntity.code` 与 `JobCategory`。
- 岗位是否参与分配只看 `is_active`。

边界：

- 不引入招聘周期表。
- 不保存 `valid_from / valid_to`。
- 需求专业保留独立 `JobMajor` 明细表。

## 六、候选人处理主流程

入口：

- `POST /api/pipeline/run/`
- 请求包含 `step`、`mode`、`scope` 等参数。
- `mode` 在分配环节记录 Rule / AI。
- `scope` 支持限定处理范围；简历库“处理简历”按钮传入 `scope.system_statuses` 和当前筛选条件时，只重跑命中范围内候选人的 Step2，不重跑全量池。

### Step1 查重与志愿排序

模块：`pipeline/services/dedup.py`

职责：

- 以 `Candidate` 分组。
- 对候选人的 `Resume` 按投递时间、主体、南北规则排序。
- 写入 `volunteer_rank` 和分配主体。
- 维护候选人当前流程的初始当前志愿。

规则：

- 单一主体最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各 2 个岗位时，统一标第一至第四志愿。
- 户籍北方优先 GW，南方优先 YLS。
- 户籍缺失时，按学校所在省份同规则。

### Step2 简历分类、分配与下发

模块：`pipeline/services/allocate.py`

职责：

- 按候选人工作流推进当前志愿。
- 执行院校准入判断。
- 执行岗位分类、岗位匹配、部门和接口人匹配。
- 生成 `AssignmentAttempt`。
- 处理 AI 复核、HR 下发、二级转派、三级反馈、归档和手动强制分配。

共同硬规则：

- 按 `volunteer_rank` 从小到大尝试。
- 存在启用 `SchoolTagRule` 时，候选人的第一学历标签和最高学历标签必须同时命中同一条启用规则。
- 没有启用规则时，院校准入视为全部通过。
- 已通过候选人不可再通过“手动强制分配”入口分配；如需重开，必须走简历库“处理简历”入口并显式携带系统简历状态范围。
- 反馈提交后锁定，不允许二次修改。
- 普通重跑分配环节或切换 Rule / AI 策略不清空全部历史；已反馈、已通过、已归档记录保留，只取消并重建未反馈的自动尝试。
- 简历库“处理简历”是 HR 主动重新分配入口，必须携带系统简历状态范围。该入口允许重开已通过、已归档或已不通过候选人流程：保留历史尝试和反馈记录，取消未反馈自动尝试，清空 `passed_attempt_id`、归档原因和完成时间，将流程恢复为 `in_progress`，再按当前 Rule / AI 策略重新生成自动分配尝试。

Rule 策略：

- 按投递岗位名称/岗位需求映射完成岗位分类。
- 写入 `JobCategory`。
- 匹配岗位二级部门和首个可用二级接口人。
- 创建 `source=rule, pending_dispatch` 尝试。

AI 策略：

- 系统先执行共同硬规则；硬规则不通过、没有当前志愿、没有岗位需求或院校准入不通过时，不调用 AI。
- `ResumeProfileExtractor` 读取 PDF 抽取正文，生成或更新 `ResumeProfile`，提取教育经历、专业方向、项目经历、实习经历、技能栈、证书奖项和画像风险点。
- `DispatchRecommender` 结合当前有效志愿、岗位需求专业、岗位类别、部门和接口人信息，生成推荐动作、推荐岗位、推荐二级部门、推荐二级接口人、推荐理由和简历证据。
- `DecisionScorer` 根据专业匹配、技能匹配、项目/实习证据强度、岗位需求覆盖度、部门确定性和简历文本质量生成分项评分，并汇总 `confidence_score`。
- `DecisionGuard` 是后端非 AI 裁决器，校验 AI 输出引用的岗位、部门、接口人是否真实存在且可用，并再次校验院校准入、当前志愿和状态机。
- AI 调用必须走结构化输出，后端按 schema 做字段类型、枚举值、引用 ID 和分数区间校验；输出不合法时记录 `invalid_ai_output`，不生成高置信度下发尝试。
- 写入 `AgentDispatchDecision`，只保存业务摘要、证据、风险点、版本和错误信息，不保存 LLM 完整原始响应。
- `recommendation=dispatch` 且 `confidence_score >= 0.75` 时，创建 `source=ai, pending_dispatch`。
- `recommendation != archive` 且 `confidence_score >= 0.5`，但未达到自动下发条件时，创建 `source=ai, pending_review`。
- `recommendation=archive`、`confidence_score < 0.5`、简历缺失、PDF 解析失败、建议归档或后端校验失败时，只写入 AI 决策记录，记录风险点并建议归档或人工处理，不生成分配尝试。
- AI 超时或失败不自动回退 Rule，由 HR 选择重试 AI、切换 Rule 或手动强制分配。
- 同一 `resume_id + evaluated_job_id + file_checksum + profile_version + prompt_version + decision_version` 已有有效决策时优先复用；其中 `file_checksum/profile_version` 通过 `resume_profile_id` 关联的 `ResumeProfile` 校验。HR 主动重试 AI、简历文件变化、画像版本变化或决策版本变化时才重新调用。

AI 失败分类：

| 错误码 | 含义 | 处理 |
| ------ | ---- | ---- |
| `pdf_missing` | 没有 PDF 文件 | 建议归档或人工处理 |
| `pdf_parse_failed` | PDF 正文抽取失败 | 建议归档或人工处理 |
| `profile_incomplete` | 简历画像不足 | 低置信度或建议复核 |
| `llm_timeout` | AI 调用超时 | 可按配置重试，最终进入人工处理 |
| `llm_error` | AI 接口错误 | 可按配置重试，最终进入人工处理 |
| `invalid_ai_output` | 结构化输出不合法 | 不生成下发尝试，进入人工处理 |
| `reference_not_found` | 推荐岗位/部门/接口人不存在 | 不生成下发尝试，进入人工处理 |
| `guardrail_blocked` | 被后端硬规则拦截 | 不调用或不采纳 AI |

AI 批处理：

- 生产环境以一个 `ProcessingRun` 作为总任务，每 100 或 200 名候选人切成一个 Celery 子任务。
- 每条候选人独立处理当前有效志愿，单条失败不影响同批其他候选人。
- 子任务持续回写 `ProcessingRun` 统计：总数、已处理、成功、失败、待下发、待复核、建议归档。
- `ProcessingRun` 记录 Celery group id、chunk 大小、chunk 总数、已完成 chunk、失败 chunk 和失败摘要；失败 chunk 可由后端按 chunk 范围重试。
- 前端可以在任务运行中刷新查看已产生的 AI 决策和分配尝试，不等待全量完成。
- 全部成功时 `ProcessingRun.status=success`；部分候选人或部分 chunk 失败但主任务完成时为 `partial_failed`；总任务异常中断时为 `failed`。
- 本地开发可继续使用 eager Celery 同步执行，但服务接口和状态字段保持与生产一致。

## 七、分配状态机

系统简历状态：

| 状态码 | 中文 | 推导口径 |
| ------ | ---- | -------- |
| `raw` | 待处理 | 当前候选人/当前投递尚未完成岗位类别和院校标签分类 |
| `classified` | 已分类 | 已完成岗位类别和院校标签分类，但没有有效业务部门推荐或下发尝试 |
| `allocated` | 已分配 | 存在 `pending_review` / `pending_dispatch` 等 HR 待复核或待下发尝试，业务部门尚不可见 |
| `pending_screening` | 待筛选 | 存在 `dispatched_l2` / `assigned_l3` 尝试，已给业务部门但尚未反馈 |
| `screening_passed` | 筛选通过 | 当前流程或最近有效尝试已由业务部门反馈通过 |
| `screening_rejected` | 筛选不通过 | 最近有效尝试已反馈未通过，或全部志愿未通过导致归档 |

> 系统简历状态不落为 `Resume.status`，后者继续保存导入文件中的原始“应聘状态”。列表筛选由后端根据 `CandidateWorkflow`、当前有效 `Resume`、`AssignmentAttempt`、院校标签和岗位类别推导。

`CandidateWorkflow.status`：

| 状态 | 含义 |
| ---- | ---- |
| `pending` | 待分配 |
| `in_progress` | 进行中 |
| `passed` | 已通过 |
| `archived` | 已归档 |

`AssignmentAttempt.status`：

| 状态 | 含义 | 允许操作 |
| ---- | ---- | -------- |
| `pending_review` | 待 HR 复核 | HR 确认下发、取消或转人工处理 |
| `pending_dispatch` | 待下发 | HR 下发或取消 |
| `dispatched_l2` | 已下发二级 | 二级接口人转派 |
| `assigned_l3` | 已转派三级 | 三级接口人反馈 |
| `passed` | 已通过 | 终态，只读 |
| `rejected` | 未通过 | 终态，系统尝试下一志愿 |
| `cancelled` | 已取消 | 终态，只读 |

核心流转：

- HR 下发：`pending_dispatch → dispatched_l2`。
- 二级转派：`dispatched_l2 → assigned_l3`。
- 三级反馈通过：`assigned_l3 → passed`，候选人流程置 `passed`。
- 三级反馈未通过：`assigned_l3 → rejected`，自动寻找下一志愿；无下一志愿则归档。
- HR 确认 AI 复核项：`pending_review → pending_dispatch`。
- 手动强制分配：取消同流程未反馈尝试后，创建 `source=manual` 尝试；归档流程恢复为 `in_progress`。目标为二级接口人时进入 HR 下发/二级处理链路，目标为三级接口人时直接进入 `assigned_l3`，并写入对应 `AssignmentHandoff` 历史。

快照与历史：

- `AssignmentAttempt` 创建时写入二级部门、二级接口人姓名/工号、应聘ID、岗位名称和操作者快照；三级转派时补写三级部门、三级接口人姓名/工号快照。
- `AssignmentHandoff` 记录转派历史，同时写入 from/to 接口人姓名/工号、转入部门名称和操作者用户名快照。
- `AgentDispatchDecision` 写入 AI 推荐接口人姓名/工号快照，避免推荐接口人后续删除导致决策详情不可读。
- `AssignmentHandoff` 只记录转交历史，不作为通用审计日志。

## 八、API 设计

通用约定：

- 列表 API 默认分页返回，支持 `page` 和 `page_size` 参数；`page_size` 最大 500，避免一次性拉取过大结果集。
- 候选人、岗位、院校、接口人等列表的表头筛选由后端执行，查询参数直接对应前端可筛选列；候选人姓名搜索同时匹配姓名原文、姓名全拼和姓名拼音首字母。
- 布尔筛选统一接受 `true` / `false` 字符串。
- 文件导出与预览返回 Django `HttpResponse`，不是 DRF `Response`；导出响应通过 `X-Export-Count`、`X-Export-Missing` 返回命中文件数和缺失文件数，预览响应通过 `X-Resume-Filename` 返回原始文件名。预览接口只负责鉴权、数据范围过滤和返回 PDF Blob，不暴露 `media/resumes/` 静态地址，浏览器内渲染由前端 PDF.js 完成。导出仅命中单个可用文件且无缺失清单时返回原文件下载，命中多个文件或需要缺失清单时返回 zip。

当前代码落点：

- 标准分页类在 `apps.api.pagination.StandardResultsSetPagination`，由 DRF `DEFAULT_PAGINATION_CLASS` 统一启用；默认 `PAGE_SIZE=20`，允许前端通过 `page_size` 调整，最大 500。
- 文件导出统一走简历导出响应构造器，候选人导出和分配尝试导出复用同一套文件收集、缺失清单和统计响应头；仅一个可用文件且无缺失清单时直接返回原文件，多文件或存在缺失清单时返回 zip。
- 文件预览统一走 `resume_preview_response(resume)`，直接从 `media/resumes/` 读取文件并以 PDF Blob 响应返回，同时通过响应头携带原始文件名；文件缺失或未匹配时返回 404。前端拿到 Blob 后交给 PDF.js 渲染，不依赖 `<object>` / `<iframe>` 的浏览器原生 PDF 预览能力。
- `bool_query_value` 负责把查询字符串中的 `true` / `false` 规范为布尔值，用于岗位、接口人等表头筛选。
- API 测试需覆盖分页参数、候选人/岗位/院校/接口人表头筛选、候选人拼音搜索、候选人导出单文件/多文件/缺失清单分支、投递预览、分配尝试数据范围预览，以及接口人 replace 导入不清空简历池。

## 九、权限与数据范围

RBAC：

- 使用 Django `Group / Permission`。
- 用户通过 `accounts_user_groups` 绑定一个或多个角色。
- 角色通过 `auth_group_permissions` 绑定权限点。
- 权限点由后端预置，并以树形清单返回前端。
- 前端按权限码控制菜单、路由和按钮；后端 DRF 权限类仍按同一权限码做接口级校验。

数据范围：

- 不单独建数据范围表。
- 由角色权限、`User.contact_id`、`Contact.department_id` 推导。
- 二级接口人仅可见 `contact_id` 指向自己且已由 HR 下发的尝试，至少排除 `pending_review`、`pending_dispatch`、`cancelled` 等 HR 内部状态；二级接口人只能转派给所属二级部门下的三级接口人。
- 三级接口人仅可见 `sub_contact_id` 指向自己的尝试，并提交反馈。
- HR/管理员默认可看全量。

本地正式开发：

- W3 方案确认前，使用本地账号密码换取 DRF Token。
- 接口人账号由部门接口人导入自动创建，用户名为工号，新账号默认密码为 `pass1234`；用户管理不维护 `first_name`、`last_name` 等 Django 姓名类字段，姓名展示来自绑定的 `Contact`。
- 用户管理删除采用清理语义：删除 `User` 账号、Token 和角色绑定；若用户绑定 `Contact`，同步删除该接口人。后端删除流程必须先将历史分配、转派、AI 决策等记录中的 `contact/sub_contact/recommended_contact/from_contact/to_contact/created_by` 等外键置空，历史页面通过 `AssignmentAttempt`、`AssignmentHandoff`、`AgentDispatchDecision` 的快照字段继续展示当时的接口人、工号、部门和操作者信息，管理员不能通过删除用户破坏候选人流程历史。
- `seed_base` 初始化管理员、HR、多个二级接口人和多个三级接口人账号，供权限链路功能测试。
- 后端接口默认要求认证；业务接口按稳定权限码做 DRF 权限校验，并按接口人绑定过滤分配数据范围。

## 十、配置与可观测性

`Config` 保存：

- `ai_dispatch_threshold`，默认 `0.75`。
- `ai_review_threshold`，默认 `0.5`。
- `ai_timeout_seconds`。
- `ai_concurrency`。
- `ai_retry_count`。
- `ai_retry_backoff_seconds`。
- `welink_enabled`。

AI 配置分层：

- 后端代码集中在 `apps.pipeline.ai_config` 抽象 AI 配置。
- 可由 HR 页面维护的运行参数放入 `Config`，包括阈值、超时、并发、重试次数和退避。
- 大模型连接信息不进入前端和普通配置表，只从环境变量读取：`AI_PROVIDER`、`AI_MODEL_NAME`、`AI_API_KEY_ENV`、`AI_BASE_URL_ENV`、`AI_PROMPT_VERSION`、`AI_DECISION_VERSION`。
- `AI_API_KEY_ENV` 默认指向 `OPENAI_API_KEY`，避免把真实密钥落库或返回给前端。

`ProcessingRun` 保存：

- 处理步骤、模式、范围、状态、运行参数、Celery task id、开始/结束时间和错误信息。
- AI 批处理统计：总数、已处理、成功、失败、待复核、待下发、建议归档。
- Celery chunk 追踪：group id、chunk 大小、chunk 总数、已完成 chunk、失败 chunk、失败摘要。
- AI 策略版本信息：模型名称、prompt 版本、decision 版本。

日志与错误：

- 导入错误需要返回明确原因和行级上下文。
- AI 失败需要记录失败原因，不自动回退 Rule。
- AI 重试只针对超时、限流、网络错误等临时错误；PDF 解析失败、输出结构不合法、引用不存在等确定性错误不做无限重试。
- 批量下发需要返回成功数量、跳过数量和跳过原因。

## 十一、导出与外部集成

简历导出：

- 从 `media/resumes/` 取 PDF 文件。
- 仅命中一个可用文件且没有缺失清单时，直接返回该原始文件，保留原文件名和内容类型；命中多个文件或存在缺失清单时，打包 zip 返回。
- 支持从候选人列表按候选人 ID、候选人当前筛选条件导出，也支持从分配尝试列表单条、勾选批量、按筛选全部导出。
- 无文件的候选人写入压缩包内缺失清单。

简历预览：

- 候选人详情从 `Resume` 维度预览 PDF。
- 分配尝试详情从 `AssignmentAttempt` 维度预览 PDF，并复用分配尝试的数据范围控制，确保二级/三级接口人只能预览自己可见尝试的简历。
- 后端预览接口不生成图片、不转换 PDF，也不返回静态文件路径；鉴权和数据范围校验通过后，接口返回 PDF Blob，并通过响应头返回原始文件名。PDF.js 渲染、分页、缩放、适配宽度和 PDF.js 预览窗口由前端负责；无权限或越权时前端不得提供预览或下载入口，只有已授权但 PDF.js 加载失败时才保留下载原文件入口。

WeLink：

- HR 下发后可发送 WeLink 通知。
- demo 可保留占位消息。
- 真实集成后回填 `welink_message_id`。
