# 智能简历筛选系统 — 需求与技术方案

> 网页版校招简历筛选系统，以「查重与志愿排序 → 简历分类、分配与下发」为候选人处理主流程；院校分类和需求录入作为前置数据准备，可提前独立维护。简历分配+下发策略支持 **Rule / AI（Agent）** 配置，由用户选择运行。每次处理约 **3 万条**简历。
> 本文聚焦**每个环节的用户需求与技术栈选择**；采用 vibe coding，不安排固定排期。

---

## 一、总体技术栈

| 层 | 选型 | 理由 |
|----|------|------|
| 后端 | Django + Django REST Framework | 自带 ORM / Admin / 认证权限，契合 CRUD + RBAC 权限管理 |
| 任务调度 | Celery + Redis | 3 万条批处理异步化，避免请求阻塞，可查询进度/重试 |
| 数据处理 | pandas + openpyxl | 读写 xlsx、字段映射、清洗 |
| AI / Agent | OpenAI SDK | 岗位语义分类、简历正文与项目经历解析、AI 分流建议，封装为可切换策略 |
| 存储 | PostgreSQL（生产）/ SQLite（本机 demo） | 保存简历数据、中间结果、配置；简历文件落盘 `media/resumes/` |
| 前端 | Vite + React 18 + Ant Design + @ant-design/pro-components（ProLayout/ProTable） | 上传/表格/开关组件齐全；仅做交互，不含业务计算 |
| 部署 | Docker Compose | 后端 + 前端 + 库一体 |
| 登录 | 待定：是否接入公司 W3 认证 | 见待确认 |

> **异步处理**：候选人处理主流程（尤其 3 万条规模）以 Celery 任务运行，前端触发后查询进度，结果落库后可导出。
> **本机 demo 形态**：SQLite + `CELERY_TASK_ALWAYS_EAGER`（同步执行，免 Redis/Postgres）；后端默认关闭鉴权（AllowAny）便于本机演示。生产经环境变量切 PostgreSQL + Celery/Redis 异步 + RBAC。

**架构原则（解耦）**：输入来源未来可能变化（不一定是 HR 的 Excel），因此——

- **输入层做成数据源适配器**，Excel 解析只是一种实现，换数据源不动业务逻辑。
- **候选人处理主流程只依赖 Django 模型**（Candidate / Resume / Job / School / Contact / CandidateWorkflow / AssignmentAttempt / SchoolTagRule），不直接读 Excel 字段。
- **Rule / AI 分配策略走统一策略接口**（`pipeline/strategies.py`），互不耦合。
- **业务参数外置为配置**（院校标签准入规则、南北省份字典、AI 置信度阈值、AI 超时等）。

**Django 应用划分**

| app | 职责 | 关键模块 |
|-----|------|----------|
| `ingestion` | 数据源适配器，解析输入并写入模型 | `sources.py`（`ExcelSource` 等） |
| `core` | 领域模型 | `models.py`（Candidate/Resume/ResumeProfile/Job/School/Contact/CandidateWorkflow/AssignmentAttempt/SchoolTagRule/AgentDispatchDecision） |
| `pipeline` | 前置处理 + 候选人处理主流程 + 双策略 + 异步 | `services/`（dedup/classify_school/demand/allocate）、`strategies.py`（Rule/AI）、`tasks.py`（Celery 任务） |
| `accounts` | 用户、RBAC 权限、W3 认证 | `models.py` / `permissions.py` |

数据流向：`ingestion（适配器）→ core 模型 → 前置数据准备（院校标签 / 岗位需求）→ 候选人处理主流程 → 候选人分配工作流 → 输出（导出 / WeLink 下发 / 接口人反馈）`

> 说明：核心逻辑**全在后端**。院校分类、需求录入可提前运行并作为分配依据；候选人处理主流程中，查重与志愿排序为确定性规则，简历分类、分配与下发由同一个策略执行，支持 Rule / AI（Agent）切换。各环节输出均可独立导出 xlsx。

## 二、输入件

| 文件 | 关键字段 |
|------|----------|
| 简历信息列表.xlsx | 招聘主体、所属机构、姓名、应聘ID、手机号、性别、对外职位名称、学历、第一学历毕业院校、最高学历毕业院校、最高学历专业、应聘状态、户口所在地、应聘日期 |
| 校招岗位分类及专业要求.xlsx | 主体、一层/二层部门、岗位类别、对外发布名称、是否对外发布、职位名称、岗位族、工作地点、学历、需求专业、需求数量 |
| 院校分类.xlsx | 学校、平台 |
| 部门接口人信息.xlsx | 序号、一层/二层/三级部门、姓名、工号、接口人层级/权限 |
| 简历包 | 命名格式 `姓名（应聘ID）`，如 `张三（12345）` |

> 身份口径：**姓名 + 手机号 → 同学身份（`identity_hash`）；应聘ID → 投递唯一键**。

## 三、逐环节：用户需求 + 技术实现

### 数据模型 · 身份与投递

同一位同学可多次投递（单主体 ≤2、跨两主体 ≤4），而 **应聘ID 按投递唯一**，不能标识人。因此拆为两个实体：

- **`Candidate`（同学 / 人）** —— 唯一键 `identity_hash = hash(规范化姓名 + 规范化手机号)`。
  - 承载**人维度**字段：姓名、手机号（原文，仅存储）、性别、户口所在地、第一/最高学历毕业院校、最高学历专业等。
  - 规范化规则（保证哈希稳定）：姓名去首尾空格、统一全/半角；手机号去空格与分隔符、去 `+86` 前缀；推荐 `SHA-256` 十六进制。
- **`Resume`（投递 / 应聘）** —— 唯一键 `应聘ID`（按投递唯一），外键 `candidate → Candidate`。
  - 承载**投递维度**字段：招聘主体、所属机构、对外职位名称、应聘状态、应聘日期、志愿排序结果（第一~第四志愿、所属主体）等。
- **关系**：`Candidate 1—N Resume`，一位同学对应多条投递。
- **简历库展示口径**：简历库主列表按 `Candidate` 聚合展示，一名候选人只显示一行；候选人详情中展示该候选人的全部 `Resume` 投递、志愿顺序、分配尝试和反馈结果。
- **当前显示志愿口径**：主列表只展示候选人的当前有效志愿。初始展示第一志愿；当前志愿被三级接口人反馈未通过后，主列表再切换展示下一志愿；已通过候选人展示通过的志愿；已归档候选人展示最后处理志愿与归档原因。
- **已知边界**：姓名或手机号写法不一致 → 哈希不同 → 视为不同人（接受的限制）；**手机号缺失**时哈希不稳定，回退为「以该条 `应聘ID` 单独成人」。
- 说明：哈希仅作身份/查重键，手机号原文照常存储用于业务，**不用于脱敏**（不解决数据隐私待确认项）。

### 数据模型 · 分配工作流

分配以**候选人级工作流**为核心：一个候选人一个流程，流程内按志愿顺序生成多次分配尝试。

- **`CandidateWorkflow`（候选人分配流程）** —— 唯一绑定一个 `Candidate`，记录流程状态。
  - 状态包括：待分配、进行中、已通过、已归档。
  - 承载当前处理到哪条志愿、归档原因、完成时间等流程级信息。
  - v1 不引入批次/周期表，同一候选人只维护一个当前分配流程；历史招聘周期隔离暂不设计。
- **`AssignmentAttempt`（分配尝试）** —— 一次具体分配动作，绑定 `CandidateWorkflow` 与某条 `Resume`。
  - 来源包括：Rule 自动分配、AI 自动分配、HR 手动强制分配。
  - 状态包括：待下发、已下发、已通过、未通过、已取消。
  - 承载分配部门、二级接口人、三级接口人、命中规则、AI 决策、下发时间、转派时间、反馈结果、反馈备注、手动分配原因和历史快照等信息。
- **`SchoolTagRule`（院校标签准入规则）** —— HR 在配置项中维护，供简历分类、分配与下发环节判断候选人是否允许进入自动分配。
  - 每条规则分别配置「第一学历允许标签」和「最高学历允许标签」。
  - 候选人的两个标签都命中同一条启用规则，才算通过该规则；多条规则之间是 OR。
  - 「非目标院校」只是普通标签，HR 可以把它加入规则；系统只按 HR 启用的规则判断准入。

### 数据模型 · 简历解析与 AI 决策

AI 策略必须读取候选人简历正文，尤其是项目经历、实习经历、技能栈和专业方向。为避免每次运行重复解析简历，解析结果与 AI 决策单独落库。

- **`ResumeProfile`（简历结构化画像）** —— 唯一绑定一条 `Resume`，保存从简历文件中解析出的正文与结构化信息。
  - 包括：解析状态、正文摘要、项目经历列表、实习/工作经历、技能关键词、证书/竞赛、解析版本、文件哈希、解析错误等。
  - 简历文件未上传、解析失败或正文质量不足时，AI 策略应进入低置信度或需人工复核，不得静默下发。
- **`AgentDispatchDecision`（AI 策略决策）** —— 记录 AI Agent 对某候选人某次志愿尝试的建议。
  - 包括：推荐动作（建议下发 / 需人工复核 / 建议归档）、推荐部门/接口人、置信度、理由、引用证据、风险点、模型版本、提示词版本、原始响应摘要等。
  - AI 决策只生成待 HR 确认的分配尝试或复核结论；最终是否下发仍由 HR 执行。

### 前置 · 数据导入

**用户需求**

数据有两种维护方式并存：

1. **表格批量导入**：上传 4 张表 + 简历包，按 `姓名（应聘ID）` 解析对应关系；导入时校验表头/格式，不一致则拦截并明确报错。空数据库时整表导入，已有数据时增量更新（不覆盖历史）。
2. **系统内增删改查**：对已存储的数据（简历、岗位、院校清单、接口人等）支持在页面上单条增 / 删 / 改 / 查，用于日常维护，无需重新导表。

**技术实现**
- `ingestion/sources.py` 的 `ExcelSource` → pandas/openpyxl 解析 → `core` 模型 → PostgreSQL。
- **身份归并流程**：① 由 姓名+手机号 算 `identity_hash`，对 `Candidate` 按 hash 幂等 `get_or_create`；② 按 `应聘ID` 创建/更新 `Resume` 并挂到对应 `Candidate`；③ 简历包 `姓名（应聘ID）` 经 `应聘ID` 定位 `Resume` 再关联其 `Candidate`。
- 增量更新语义不变（不覆盖历史），以 `identity_hash` 与 `应聘ID` 作幂等键。
- 所有数据进入**同一数据池**，不分批次；按 `imported_at` 等时间标签筛选。
- 解耦关键：Excel 仅是一种数据源实现，后续可加 DB/API 适配器。
- **简历包**：解压后文件**落盘 `media/resumes/`**，`Resume.resume_file` 记文件名，供分配页导出。
- CRUD 借助 Django ORM / DRF ViewSet 实现；接口人按「部门 + 人员」**树形结构**管理，支持一层/二层/三级部门；二级部门接口人可配置“允许转派给下级三级部门接口人”权限，列表/检索经 `/api/contacts/`。
- **前端导入入口分散**：不设独立导入页，各数据页（简历库/岗位/院校/接口人）各放一个导入按钮，后端复用同一 `/api/import/`（按字段区分文件类型，可只传其一）。
- **上传即处理**：在简历库上传简历后，前端自动触发候选人处理主流程（`/api/pipeline/run/`）：先查重与志愿排序，再按当前 Rule / AI 策略执行简历分类、分配与下发，用进度条呈现。
- **单级撤销**：上传含简历的数据前，后端将 Candidate/Resume/CandidateWorkflow/AssignmentAttempt 序列化存入 `ImportSnapshot`（仅留最近一份）；`/api/import/undo/` 可一键还原到上传前状态（删本次新增 + 还原被覆盖旧值），撤销后快照清除。

### 前置处理 · 院校分类

**用户需求**
- 按第一学历、最高学历对照院校清单（平台字段）打标签。
- 不在清单 → 标「非目标院校」。
- 院校分类可在简历分类、分配与下发之前提前运行；院校清单更新后也可独立重跑。
- 输出：候选人的「第一学历标签 / 最高学历标签」两字段，作为分配准入规则的输入。

**技术实现**
- `pipeline/services/classify_school.py`，**纯规则**：Python + pandas 对照院校清单查表；**不用 AI**。

### 前置处理 · 需求录入

**用户需求**
- 把校招需求汇总表整理成结构化需求表（部门/岗位/学历/专业/数量）。
- 需求录入是分配前置主数据，可在简历导入前提前维护；岗位需求、专业要求、二级/三级部门接口人更新后可独立重跑或手工维护。

**技术实现**
- `pipeline/services/demand.py`，**纯规则**：pandas/openpyxl 解析重组；**不用 AI**。

### Step1 查重与志愿排序

**用户需求**
- **查重**：按 `Candidate`（`identity_hash`）聚合一个人的全部投递。
- 单一主体每人最多 2 个岗位，按投递时间标第一/第二志愿。
- 跨两主体各投 2 个 → 统一标第一至第四志愿。
- 排序规则：户籍北方 → 优先 GW；南方 → 优先 YLS；户籍缺失 → 按学校所在地同规则。
- 输出：候选人维度的志愿排序结果；主列表展示当前有效志愿，候选人详情展示完整投递清单。

**技术实现**
- `pipeline/services/dedup.py`，**纯规则**：按 `Candidate` 分组、组内按投递时间 + 南北规则排序；南北省份字典外置为配置；**不用 AI**。

### Step2 简历分类、分配与下发

**用户需求**
- 以候选人为粒度推进分配：一个候选人一个分配流程，按志愿顺序依次尝试。
- 自动分配与简历库当前志愿保持一致：第一志愿未反馈前，主列表和流程只暴露第一志愿；三级接口人反馈未通过后，系统生成下一志愿尝试，主列表再展示该下一志愿。
- HR 可配置简历分配+下发策略：**Rule** 或 **AI（Agent）**。两种策略都完成岗位分类、岗位/部门匹配、分配尝试生成，并进入同一套候选人工作流与分配尝试列表。
- HR 可在配置项维护院校标签准入规则；Rule 与 AI 策略都必须先命中任一启用规则。AI 只优化简历理解、岗位适配和分流判断，不绕过 HR 配置的硬性准入条件。
- AI 策略必须读取候选人简历文件，提取项目经历、实习经历、技能栈、专业方向等信息，并结合当前志愿岗位、岗位需求专业和部门信息生成建议。
- 三级接口人反馈「通过」后，该候选人流程结束；反馈「未通过」后，系统自动进入下一志愿。
- 志愿耗尽、未命中院校规则、找不到岗位/部门/接口人时，候选人进入归档。
- HR 可从任意投递发起手动强制分配，绕过院校规则、志愿顺序和自动筛选条件；已通过候选人不可再强制分配。
- 分配执行采用两级接口人链路：HR 将分配尝试下发至二级部门接口人（**WeLink 通知**）；支持单条下发、勾选批量下发、按当前筛选条件一键全部下发；二级部门接口人有权限在本二级部门范围内选择下属三级部门接口人并转派简历；三级部门接口人反馈通过/未通过并可填写备注。
- 输出：候选人工作流清单、分配尝试清单、归档候选人清单 + **候选人简历文件可导出**（单条 / 勾选批量 / 按筛选全部）。

**技术实现**
- `pipeline/services/allocate.py` 负责简历分类、自动分配、续分配、归档与手动分配；岗位分类不再作为独立步骤暴露，而是分配策略内部的一个动作。
- **Rule 策略**：按 `volunteer_rank` 从小到大尝试候选人的 `Resume`；候选人院校标签命中任一启用 `SchoolTagRule` 后，按投递岗位名称/岗位需求映射表完成岗位分类与岗位匹配，再按岗位二级部门和部门首个二级接口人生成待下发尝试。
- **AI（Agent）策略**：沿用同一工作流状态机和志愿顺序，先读取/生成 `ResumeProfile`，再由 Agent 对候选人当前志愿进行岗位分类、岗位适配和二级部门/二级接口人推荐，输出置信度、引用证据和风险点，形成 `AgentDispatchDecision`。达到阈值时创建 `source=ai` 的待下发尝试；低置信度或关键信息缺失时标记为需人工复核，不自动下发给接口人。
- **HR 下发**：HR 可对 `pending_dispatch` 尝试执行单条、勾选批量或按当前筛选全部下发；系统只处理待下发尝试，已下发、已转派、已反馈、已取消记录自动跳过，并返回成功/跳过数量。下发后 `AssignmentAttempt` 进入二级待转派状态。
- **二级转派**：HR 下发后，二级部门接口人只能选择自己所属二级部门下的启用三级部门接口人，不可跨二级部门转派；转派动作写入审计记录并通知三级接口人。
- **用户选择策略**：上传后自动处理、手动运行分配、Rule/AI 切换都必须显式携带 `dispatch_strategy`。切换策略时重算「简历分类、分配与下发」环节，不重跑查重排序、院校分类和需求录入。
- **失败回退边界**：AI 超时或调用失败时，不静默改用 Rule；系统应提示失败原因，由 HR 选择重试 AI 或改用 Rule，避免用户误以为 AI 已完成判断。
- **无规则保护**：没有任何启用的 `SchoolTagRule` 时，简历分类、分配与下发环节失败并提示 HR 先配置院校标签准入规则，避免系统在无准入口径时产生分配结果。
- **重跑语义**：重跑分配环节不清空全部历史；已反馈、已通过、已归档记录保留，只取消并重建未反馈的自动分配尝试。
- **归档口径**：归档原因使用枚举记录，包括无启用规则、未命中院校规则、志愿耗尽、未匹配岗位、无部门、无接口人、AI 无有效建议、全部志愿未通过等；补充说明写入归档详情。
- **反馈状态机**：
  - 三级接口人反馈「通过」：当前 `AssignmentAttempt` 记为已通过，`CandidateWorkflow` 记为已通过，并取消该候选人其他未反馈尝试。
  - 三级接口人反馈「未通过」：当前 `AssignmentAttempt` 记为未通过，系统自动寻找下一志愿；若无下一志愿或后续志愿均不可分配，则候选人归档。
  - 反馈提交后锁定，不允许二次修改。
- **手动强制分配**：`POST /api/resumes/{id}/manual-assign/`，HR 选择目标二级接口人或直接选择三级接口人并建议填写原因；系统取消该候选人未反馈尝试，创建 `source=manual` 的分配尝试。若目标是二级接口人，则仍需二级转派；若目标是三级接口人，则直接进入待反馈。归档候选人也可手动分配，流程回到进行中。
- **历史可追溯**：分配尝试创建时保存二级部门、二级接口人、三级部门、三级接口人、应聘ID、岗位名称快照；后续主数据改名不影响历史列表与导出。
- **AI 可追溯**：AI 策略产生的尝试必须关联 `AgentDispatchDecision`，HR 可查看置信度、推荐理由、项目经历证据和风险点；接口人页面只展示必要的简历与岗位信息，不暴露完整提示词或模型调试信息。
- **接口边界**：
  - `/api/school-tag-rules/`：院校标签准入规则 CRUD。
  - `/api/workflows/`：候选人工作流列表，支持按状态筛选归档候选人。
  - `/api/workflow-attempts/`：分配尝试列表、单条下发、反馈、导出。
  - `/api/workflow-attempts/bulk-dispatch/`：HR 批量下发；传 `ids` 表示勾选批量，不传或空数组表示按当前筛选全部下发；仅处理 `pending_dispatch`。
  - `/api/workflow-attempts/{id}/assign-sub-contact/`：二级部门接口人转派给三级部门接口人。
  - `/api/agent-decisions/`：AI 策略决策列表与详情。
  - `/api/resumes/{id}/manual-assign/`：HR 手动强制分配。
- **简历导出**：`/api/workflow-attempts/export/?ids=` 从 `media/resumes/` 取文件打包 zip；无文件的候选人写入压缩包内缺失清单。

## 四、用户与权限

- **角色**：HR（全流程操作）/ 二级部门接口人（查看 HR 下发给自己的尝试，并转派给本部门下属三级接口人）/ 三级部门接口人（查看转派给自己的尝试，并提交反馈）/ 管理员（系统配置与用户管理）。
- **RBAC 权限分割**：按角色控制可见数据与可执行操作。
- **接口人管理**：「部门 + 人员」树形结构；二级部门接口人可配置转派权限，三级部门接口人负责最终反馈；接口人为非必要文件，权限可单独开通。
- **登录认证**：待定是否接入公司 W3 认证。
- 技术：`accounts` app（自定义 `User`，角色 HR/二级接口人/三级接口人/管理员），基于 Django 认证/权限体系 + DRF 权限类实现。
- **v1 现状**：角色隔离先做**前端演示版**（顶部「演示身份」切换）；二级接口人演示身份临时绑定数据库第一个二级接口人，只显示下发给自己的尝试并可转派；三级接口人演示身份临时绑定数据库第一个三级接口人，只显示转派给自己的尝试并可反馈。后端仍 AllowAny；真实 RBAC + 登录、接口级数据过滤待 M6。

## 五、通用 / 系统需求

- 各步中间结果可查看、筛选、导出（流水线每步可追溯）。
- **v1 交互**：处理对用户透明——上传简历即自动跑候选人处理主流程（进度条）；简历分配+下发策略在「简历分配」页选择；切换 Rule / AI 策略后只重算「简历分类、分配与下发」环节；简历库支持单级撤销。
- 规则 vs AI 结果对比视图，便于人工核对。
- AI 策略失败/超时不自动回退 Rule，需由 HR 明确选择重试或切换 Rule。
- 可配置项集中管理（院校标签准入规则、南北省份字典、AI 置信度阈值、AI 超时等）。
- 新增独立「归档候选人」视图，按候选人粒度展示归档原因和志愿概览，并允许 HR 从具体应聘ID发起手动强制分配。
- **工程交付物**：数据库 UML / ER 图、前后端接口文档、4+1 架构视图、Docker Compose 部署。
