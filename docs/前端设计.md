## 一、全局框架（ProLayout）

```
┌───────────────────────────────────────────────────────────┐
│ ▣ 智能简历筛选系统                    [演示身份: HR ▾] │ 顶栏
├──────────────┬────────────────────────────────────────────┤
│ 数据管理 ▾    │                                            │
│   · 简历库    │            内容区                          │
│   · 岗位需求  │      (ProTable / Modal 导入)              │
│   · 院校清单  │                                            │
│   · 部门接口人│                                            │
│ 简历分配 ▾    │                                            │
│   · 候选人工作流│                                          │
│   · 分配尝试  │                                            │
│   · 归档候选人│                                            │
│ 系统设置 ▾    │  ← 接口人身份时，左侧仅保留「简历分配」      │
│   · 配置项    │                                            │
│   · 用户权限  │                                            │
└──────────────┴────────────────────────────────────────────┘
```

> 当前结构：
> 1. **数据导入入口在各数据页内**：简历→简历库、岗位→岗位需求、院校→院校清单、接口人→部门接口人。
> 2. **处理由上传和策略切换触发**：上传简历后自动触发候选人处理主流程；分配页切换 Rule / AI 分配策略时，只重算「简历分类、分配与下发」环节。
> 左侧菜单**按角色显示**：HR/管理员见全部；二级/三级接口人仅见「分配尝试」。**分配策略**位于分配工作流区域，分配页是其结果落点。

## 二、关键页面

### 1) 简历库（候选人列表 + 投递详情 + 上传即处理 + 撤销）
```
简历库                    [↥ 上传简历] [↺ 撤销上次上传] [导出]
┌ 筛选: 导入时间[范围] 状态[▾] 🔍姓名/手机
├──────────────────────────────────────────────────────────
│ 姓名 │手机│当前志愿│当前投递岗位│岗位类别│院校标签│流程状态│操作
│ 张三 │138│1       │后端        │技术类  │平台A   │进行中  │详情 手动分配
│ 李四 │139│1       │产品        │产品类  │平台B   │待分配  │详情
└ 分页 / 共 N 名候选人

详情抽屉 / 详情页：
┌ 候选人：张三  13800000000  院校标签：第一学历=平台A / 最高学历=平台A
├ 投递志愿
│ 志愿│应聘ID│主体│投递岗位│岗位类别│应聘状态│分配状态│反馈
│ 1  │A001 │GW │后端    │技术类  │待处理  │已转派三级│未通过
│ 2  │A002 │YLS│产品    │产品类  │待处理  │待下发  │-
├ 分配尝试
│ 次序│来源│投递岗位│二级接口人│三级接口人│状态│反馈备注│时间
└ 操作：从选中应聘ID发起手动强制分配

上传后自动弹出进度条：
┌ 正在处理简历（分配策略：Rule） ───────────────  ┐
│ [■■■■■■□□□□] 60%   正在：简历分类、分配与下发   │
└────────────────────────────────────────────────┘
```
> **上传**：「上传简历」弹窗含两类文件 **① 简历信息列表 .xlsx + ② 简历包 .zip** + 导入模式（增量/清空重导）。
> **上传即处理**：上传成功后自动按当前分配策略跑候选人处理主流程（查重与志愿排序 → 简历分类、分配与下发），前端按环节驱动进度条。院校分类和需求录入是前置数据准备，可在对应主数据页提前维护或独立重跑。
> **增量 + 冲突以新为准**：按 `identity_hash`/`应聘ID` 幂等 `update_or_create`，重复数据以新上传覆盖旧值；同一人多投通过 identity_hash 归并。
> **候选人聚合展示**：主列表以 `Candidate` 为行粒度，一名候选人只显示一行；所有投递岗位、应聘ID、志愿顺序、分配尝试和反馈记录进入详情抽屉/详情页。
> **当前志愿展示**：主列表仅展示当前有效志愿。初始只展示第一志愿；第一志愿反馈未通过后，系统生成并展示下一志愿；通过后固定展示通过志愿；归档后展示最后处理志愿和归档原因。
> **单级撤销**：上传前后端存一份快照（Candidate/Resume/CandidateWorkflow/AssignmentAttempt）；「撤销上次上传」一键回到上传前状态（删本次新增 + 还原被覆盖旧值），撤销后快照清除。仅保留最近一次（单级）。

### 3) 候选人处理主流程（随上传/换策略自动触发）
处理由两个动作触发，均以**进度条**呈现：
- **上传简历**（简历库）→ 自动跑候选人处理主流程；
- **切换 Rule / AI 分配策略**（简历分配页）→ 只重算「简历分类、分配与下发」环节。

```
前置数据准备：
  院校分类、需求录入、部门接口人维护

候选人处理主流程：
  Step1 查重与志愿排序 → Step2 简历分类、分配与下发
```
> 院校分类和需求录入提前完成，保证分配时院校标签、岗位需求、专业要求和接口人已就绪。
> demo 同步执行（Celery eager）；前端逐步调用 `/api/pipeline/run/` 推进进度条。每次执行写一条 `ProcessingRun`（审计用，暂无展示页）。

### 5) 分配工作流 / 分配尝试 / 归档候选人
```
候选人工作流                    分配策略: ( Rule ) ( AI )
                              [运行分配]
┌ 筛选: 状态[▾] 候选人 投递岗位
├──────────────────────────────────────────────────────────
│候选人│当前志愿│当前投递│策略│流程状态│归档原因│更新时间│操作       │
│张三  │1       │后端    │AI  │进行中  │        │09:30   │查看尝试   │
└ 已归档候选人可从具体应聘ID发起手动强制分配
```
> **分配策略**：页头提供一个分段器「Rule / AI」。切换前先弹确认；确认后只重算「简历分类、分配与下发」环节。选择存于前端（localStorage），上传简历时也读取当前选择。
> **Rule 策略**：按志愿顺序、院校标签准入规则、岗位需求映射、岗位二级部门和二级接口人生成待下发尝试。
> **AI 策略**：Agent 读取候选人简历正文和项目经历，结合当前志愿、岗位需求专业与部门信息完成岗位分类、适配判断和二级部门/二级接口人推荐。高置信度形成待下发尝试；低置信度展示为 HR 复核项，不直接下发给接口人。
> **分配尝试**：展示 `AssignmentAttempt`，支持状态筛选、导出、下发、查看反馈。接口：`/api/workflow-attempts/`。
> **AI 决策详情**：HR 可在尝试详情查看 AI 置信度、推荐理由、项目经历证据和风险点。接口人只看到已下发给自己的尝试和必要简历信息。
> **导出**：把候选人**简历文件**打包成 zip 下载（`/api/workflow-attempts/export/`）；支持单条、勾选批量、按筛选「导出全部」。无文件的候选人写入压缩包内「缺失简历文件清单.txt」。
> **HR 下发操作**：HR 可单条下发，也可勾选多条后「下发选中」，或按当前筛选条件「一键全部下发」。批量下发只处理 `pending_dispatch`，其他状态自动跳过并提示成功/跳过数量。接口：`POST /api/workflow-attempts/bulk-dispatch/`。
> **下发、转派与反馈**：HR 将待下发尝试下发至二级部门接口人；二级接口人在本二级部门范围内选择三级部门接口人并转派；三级接口人对已转派尝试提交通过/未通过 + 可选备注，提交后锁定。
> **转派操作**：二级接口人的分配尝试列表展示「转派」按钮，弹窗只列出当前二级部门下启用的三级接口人；转派后状态变为「已转派三级」，并记录转派历史。
> **归档候选人**：独立页面展示归档原因、志愿概览，并允许 HR 从具体应聘ID发起手动强制分配。
> **角色差异**：二级接口人仅看到下发给自己的尝试，可导出、查看反馈和转派给本部门三级接口人；三级接口人仅看到转派给自己的尝试，可导出并提交反馈；接口人均无 HR 下发、手动分配和模式开关。

### 6) 系统设置（占位 · M4/M6）
- **配置项**：院校标签准入规则、南北省份字典（省份→南/北）、AI 置信度阈值、AI 超时、W3 认证开关。
- **用户权限**：用户列表 + 角色（HR / 二级接口人 / 三级接口人 / 管理员），RBAC。

## 三、角色与可见性

v1 用**前端演示角色**实现（`RoleContext` + localStorage，顶部「演示身份」下拉切换，无真实登录）：

| 区域 | HR / 管理员 | 二级接口人 | 三级接口人 |
|------|-------------|------------|------------|
| 简历库（上传 / 撤销）/ 岗位 / 院校 / 部门接口人 | ✓ | ✗ | ✗ |
| 分配尝试 — 导出 / 反馈查看 | ✓ | ✓ | ✓ |
| 分配尝试 — 单条/批量/全部下发 / 分配策略切换 / 手动强制分配 | ✓ | ✗ | ✗ |
| 分配尝试 — 转派给三级接口人 | ✗ | ✓ | ✗ |
| 分配尝试 — 提交通过/未通过反馈 | ✗ | ✗ | ✓ |
| 系统设置 | ✓（管理员）| ✗ | ✗ |

> 二级/三级接口人登录后默认落到「分配尝试」，访问其它路径自动重定向回该页。
> **重要边界**：v1 的隔离只是**前端遮挡**，后端仍 AllowAny；真正的接口级隔离（含“二级只能看自己接收的尝试并只能转派本部门三级接口人”“三级只能看自己被转派的尝试”）需 M6 接入 RBAC + 登录后在后端按身份过滤。

## 四、当前页面清单
1. 简历库：上传、撤销、筛选；按候选人一人一行展示当前志愿；详情查看全部投递、分配尝试和反馈结果。
2. 岗位需求、院校清单、部门接口人：主数据维护与导入。
3. 候选人工作流：查看流程状态、当前志愿、归档原因。
4. 分配尝试：HR 单条/批量/全部下发、二级接口人转派、三级接口人反馈、导出、反馈查看。
5. 归档候选人：查看归档原因和志愿概览，发起手动强制分配。
6. 配置项：维护院校标签准入规则、南北省份字典、AI 置信度阈值和系统参数。
