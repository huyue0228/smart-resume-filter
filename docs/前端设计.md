│ ▣ 海纳智选      ├──────────────────────────────────────────┤
│ DashBoard       │                                          │
│ 处理任务        │                                          │
│ 数据管理 ▾      │                                          │
│   · 简历库      │            浅灰内容区                    │
│   · 岗位需求    │      (PageContainer / ProTable)          │
│   · 院校清单    │                                          │
│   · 部门接口人  │                                          │
│ 系统设置 ▾      │  ← 接口人身份时仅显示有权访问的菜单         │
│   · 配置项      │                                          │
│   · AI 模型连接 │                                          │

> 当前结构：
> 1. **数据导入入口在各数据页内**：简历→简历库、岗位→岗位需求、院校→院校清单、接口人→部门接口人。
> 2. **处理由上传和处理简历触发**：两种入口都要求用户选择本次 Rule / AI 模式并只创建一条任务；上传从 Step1 开始，“处理简历”从 Step2 院校分类/准入开始，Rule 止于 Step3，AI 继续 Step4。Rule 始终可选，AI 仅在当前模型连接测试有效时可选。
> 3. **所有数据表格支持列宽拖拽，可筛选业务列支持表头筛选**：可独立查询的列表采用后端分页，表头文本/单选/多选筛选参数进入接口查询，`page_size` 最大 500，导出全部按当前筛选条件执行；简历详情内嵌表格不提供筛选器。简历库主表不设操作列；其它页面保留的操作列可调整宽度，但不提供筛选器。
> 4. **`DashBoard` 是置顶首页**：路由仍为 `/analytics`，不属于“数据管理”子菜单；管理员和 HR 登录后默认进入该页，未获 `analytics.view` 权限时整个导航项隐藏并进入首个有权页面。
> 5. **侧栏分组可独立展开或收起**：「数据管理」和「系统设置」分别维护展开状态；点击某个子页面只更新当前选中路由，不应自动收起其它已展开分组。
> 6. **处理任务是独立导航与页面**：路由 `/processing-tasks` 由 `pipeline.view` 控制，位于 `DashBoard` 之后，不再占用顶部栏或以 Drawer 展示；取消活跃任务仍要求 `pipeline.run`。
> 左侧菜单**按权限码和数据范围显示**：简历库是候选人查看、分配下发、二级转派和分阶段反馈的统一入口。HR/管理员查看全量；二级/三级接口人也进入 `/resumes`，但只看到本人接收或被转派的候选人和对应尝试。

当前共享实现：

- `SmartDataTable.jsx` 统一提供列宽拖拽、列设置、服务端/本地筛选和行点击隔离能力；简历库主表及岗位、院校、接口人、用户权限和配置表按列启用筛选，简历详情的投递志愿、分配尝试和 AI 筛选决策表不配置筛选器。
- `ResizableHeaderCell.jsx` 负责表头拖拽手柄和 pointer 事件；样式类 `.srf-column-resize-handle` 定义在全局 CSS。
- `SchoolTagBadge.jsx` 统一渲染院校标签，根据完整标签名称生成稳定区分色；同名标签同色，不同标签使用不同颜色，简历库、候选人详情、院校清单、院校标签字典和准入规则保持一致。
- `ResumePreview.jsx` 负责 PDF/文件预览，PDF 通过鉴权 API 取得 Blob 后交给 PDF.js 渲染到 canvas，不依赖浏览器原生 PDF 内嵌能力；组件支持未选择、加载中、失败提示、分页、新窗口打开和“下载原文件”；可按 `resume` 直接预览，也可按 `attemptId` 走分配尝试数据范围预览。无权限或越权时不展示下载入口；PDF 渲染失败或非 PDF 文件时可下载原文件。
- 前端 API 封装位于 `src/api/services.js`：`previewResume`、`previewAllocationResume`、`exportCandidates`、`deleteCandidate` 分别对应预览、按筛选导出和候选人维护能力。
- 全站登录后界面统一使用浅灰背景、低阴影白卡、靛青主色、深色固定侧栏和白色顶部栏；`ConfigProvider`、ProLayout token 与全局 CSS 统一 Card、Table、Tabs、表单、Drawer 和 Modal 的视觉，登录页保持原样。
- `AnalyticsPage.jsx` 通过 `fetchRecruitmentOverview` 只读取后端聚合数据，使用 Ant Design 卡片和 Chart.js 环图/横向柱图展示，不下载候选人明细自行统计。
- 主布局为拥有 `pipeline.view` 的用户提供独立“处理任务”页面，该权限默认授予 HR/管理员；页面约每 2 秒轮询并支持手工刷新。任务卡按 Step1–Step4 展示阶段和耗时，主结果固定为处理完成、需处理、失败、跳过、取消；AI 的待复核、待下发、建议归档是处理完成子项。非零结果跳转 `processing_result=<completed|needs_attention|failed|skipped|cancelled>`，旧 success 链接仅兼容；取消按钮另按 `pipeline.run` 控制，并保留并发审计交互。

- AI 任务卡额外展示 `ai_effective_concurrency / ai_concurrency_limit`、模型重试数和 429 限流数；所有任务统一展示 completed、needs_attention、failed、skipped 和 cancelled 计数。

> **上传**：「上传简历」弹窗含两类文件 **① 简历信息列表 .xlsx / .xls / .csv + ② 简历包 .zip**。普通用户入口只提供安全的增量更新；主数据 replace 使用更新/停用语义，不得删除候选人流程、反馈或审计历史。测试环境彻底清空不放在普通上传弹窗中。
> **上传即处理**：上传 Rule 运行 `Step1 查重/排序 → Step2 院校分类/准入 → Step3 Rule 分配`；上传 AI 再继续 `Step4 AI 深度筛选`。人工“处理简历”从 Step2 开始。岗位、部门和接口人独立维护，是 Step3 的基础数据，不再显示为编号步骤。异步 202 / eager 200、范围固化和页面非阻塞契约保持不变。
> **增量 + 冲突处理**：按 `normalized_name + normalized_phone` 归并候选人，按 `应聘ID` 幂等更新投递；低风险重复更新当前主记录，但不删除已反馈流程、分配尝试和历史快照；高风险重复进入导入错误清单。手机号缺失的候选人直接舍弃，不入库、不进入分配，并在导入结果中提示。“学历”列在后端规范化为大专/本科/硕士/博士，同文件同候选人取最高已识别值，空值或未知值不覆盖已有有效学历。
> **候选人聚合展示**：主列表以 `Candidate` 为行粒度，一名候选人只显示一行。单击候选人行直接打开详情，勾选框、表头筛选、列宽拖拽等控件点击不得误触发详情。HR/管理员详情展示手机号、最高学历及中文标签、最高学历专业、全部投递、志愿顺序、分配尝试、匹配/手动理由和反馈记录；接口人详情仅展示本人可见尝试及其关联投递，不返回手机号、其它志愿、其它尝试或 AI 决策。
> **当前志愿展示**：主列表仅展示当前有效志愿。Rule 原因文案清楚区分缺岗位、专业不匹配、缺二级部门、缺二级接口人；AI 模式 Step3 也展示岗位/部门/接口人缺口，但这些均为“处理完成”的业务结果，不标红为模型失败，且不调用 AI。只有模型超时显示失败。
> **简历状态**：简历库展示后端推导的统一状态，不覆盖导入文件中的原始“应聘状态”。状态选项为：待处理、已分类、已分配、待筛选、通过、不通过；内部状态码保持不变。存在历史不通过和下一志愿活动尝试时，按 `通过 > 待筛选 > 已分配 > 不通过 > 已分类 > 待处理` 展示，但只读取当前 workflow、当前通过指针和未取消活动尝试，历史 passed/rejected/cancelled 只在详情中展示，不覆盖重开后的当前状态。
> **主表列与筛选**：新增“处理结果”和“原因”列，分别按 `result_type` 与精确 `reason_code` 下拉筛选，可与任务、状态及其它表头条件组合。稳定原因码至少包含 `education_not_eligible / school_not_eligible / job_not_found / secondary_department_missing / secondary_contact_missing / major_not_matched / job_responsibility_missing / llm_timeout / resume_text_unavailable / ai_connection_error / ai_rate_limited / ai_invalid_output / ai_reference_invalidated / ai_special_route_unavailable / ai_special_route`。原因列继续截断并用 Tooltip 展示说明，不用错误文本模糊匹配。其它当前投递、来源、详情和默认隐藏列契约保持不变。
> **筛选、处理、下发与导出**：主列表支持现有候选人字段以及按上述 `allocation_source` 派生口径的分配来源、部门、二三级接口人和分配原因的表头筛选，不提供流程状态或分配状态筛选。任务中心跳转时，`processing_run_id + processing_result` 作为 ProTable 稳定外部参数与其它筛选相交；同页新增、切换或清除任务筛选都重新请求第一页，并关闭旧详情但保留页面勾选。常驻工具栏提供上传、处理、导出结果报表和撤销等页面级动作；未选择候选人时隐藏批量业务操作，勾选后在表格上方以滑入操作条按权限展示「下发选中/当前筛选、导出选中/当前筛选、删除选中、取消选择」。批量下发、导出和删除继续沿用候选人数据范围与历史保护规则。
>
> 「处理简历」始终打开同一个弹窗：先选择本次 Rule / AI 模式，再选择`当前选中（N）`或六种简历状态；`当前选中`始终手动勾选、`N=0` 时禁用，并与六种可多选状态互斥；打开时冻结候选人 ID 和数量。当前选中提交的 scope 只含 `candidate_ids + force_reprocess=true`，成功后清空勾选；状态范围提交 `system_statuses + candidate_filters` 并继承当前表头和任务结果筛选。用户取消选择或当前选中处理成功之外的任务筛选切换均不清空勾选。弹窗通过 `GET /api/allocation-mode/` 读取 `default_mode / available_modes / ai_ready`，按 `default_mode=rule` 默认选择 Rule；AI 不可用时禁用并说明原因，提交时发送唯一 `mode` 且不发送 `modes`。
> **结果报表**：仅拥有 `resume.view` 的 HR/管理员显示「导出结果报表」。点击后弹窗要求选择导入日期范围，未选择完整范围时禁用导出；前端以 `imported_after / imported_before` 调用 `GET /api/resumes/result-report/` 并下载 `.xlsx`。弹窗明确提示报表按应聘记录首次导入日期导出、独立于当前表头筛选。文件含“部门汇总”和“简历明细”，逐应聘ID统计六种状态、部门快照和反馈；无手机号字段，现有 ZIP 简历导出按钮与接口保持不变。
> **简历预览与删除**：详情抽屉默认选中当前投递中有文件的简历；当前投递无文件时，自动回退到同候选人第一条有文件的投递，不改变当前志愿展示口径。投递志愿表不设预览列，用户单击志愿行即切换到该投递的简历；单击未关联简历文件的志愿时，预览区切换为该志愿的缺失提示，不保留上一份简历。前端通过鉴权 API 获取 PDF Blob 后用 PDF.js 渲染到 canvas，并读取预览响应头 `X-Resume-Filename` 展示原始文件名。无权限或越权时不展示预览和下载入口；PDF 渲染失败或非 PDF 文件时可下载原文件。详情删除不依赖前端预先判断是否存在受保护历史；用户点击后由后端统一校验，返回 409 时前端展示原始错误说明。批量删除逐条执行同一后端保护，并汇总成功与失败结果。
> **按上传记录撤销（目标设计，后端未实现）**：后端先解析每次上传影响的业务键，只为该候选人/投递范围保存覆盖 Candidate / Resume / ResumeProfile / CandidateWorkflow / AgentDispatchDecision / AssignmentAttempt / AssignmentHandoff 的独立快照及本次上传关联处理完成后的流程版本基线；“上传撤销记录”只展示当前 HR 自己的上传，管理员可查看全部。用户按选定上传记录执行撤销，同一记录仅可撤销一次；撤销时后端锁定该记录的全部候选人并校验版本，任一候选人存在后续变更即整体返回 `409`，前端不显示部分撤销成功。关联 ProcessingRun 未结束时同样禁用该记录的撤销并展示原因；已撤销的运行保留审计展示。

### 2) 岗位需求 / 院校清单 / 部门接口人（结构同构）
```
岗位需求                                       [↥ 导入岗位] [新增岗位]
│ 对外名称│职位名称│岗位类别│工作职责│岗位族│部门│工作地│学历│HC│对外发布│操作
│ ...    │...   │...   │...    │... │...│...│...│...│...    │编辑 删除

院校清单                                       [↥ 导入院校]
│ 学校 │ 院校标签 │

部门接口人                                     [↥ 导入接口人]
│ 姓名 │ 工号 │ 所属部门 │ 部门层级 │ 接口人层级 │ 可转派
```
> 三页各自只导入对应的一张表格文件（.xlsx / .xls / .csv）；后端复用同一 `/api/import/`（按字段区分），无需分别建接口。
> 岗位、院校、部门接口人列表均使用表头筛选和列宽拖拽；筛选条件进入后端查询并与分页共同生效。岗位新增“工作职责”列和文本表头筛选；新增/编辑弹窗使用必填多行文本框展示并保存完整职责。岗位还支持主体、对外名称、职位名称、岗位族、部门、地点、学历、HC、是否发布等筛选，其中对外名称和职位名称使用支持拼音搜索的多选选择器，前端分别通过 `public_name_in`、`position_name_in` 提交所选值；页面并提供编辑和删除操作。导入响应含 `job_responsibility_missing` 时以 warning 展示跳过数量和 Excel 行号；replace 文件没有任何有效岗位（包括全部因缺职责被跳过）时，提示未更新且保留原岗位列表。删除岗位采用停用/失效语义，历史投递和分配尝试仍可追溯。院校清单前端只展示学校和院校标签，不展示所在地/所在省份；省份字段可作为导入和排序规则后台数据保留。接口人支持姓名、工号、部门、层级、是否可转派、是否启用筛选；不展示或筛选招聘主体归属/主体来源。
> 部门接口人 replace/清空重导时，本次文件中不存在的旧接口人及其绑定账号会同步停用；列表默认只展示启用接口人，可通过状态筛选查看停用接口人。单条“删除”操作采用清理语义：删除接口人并同步删除绑定用户，历史分配记录不删除，只通过快照字段展示原接口人信息。
> **字典化口径**：岗位类别来自 `JobCategory` 字典，院校标签来自 `SchoolTag` 字典，专业大类词表来自 `MajorCategory` + `MajorAlias`；字典项保留 `code + name` 或规范化名称，前端展示业务名称，导入/匹配优先使用 `code` 或规范化名称。
> **非目标院校预置**：院校标签字典预置启用 `NON_TARGET / 非目标院校`。院校清单外的学校在分类时始终写入该标签；清单内学校未配置标签时才使用启用默认标签，无默认标签时回退到该预置标签。院校列表可显示/维护清单内学校的标签，但不能把清单外学校误展示为默认标签。
> **院校标签准入规则**：配置项中维护 `SchoolTagRule`，规则允许标签通过 `SchoolTagRuleTag` 关联到 `SchoolTag`，并区分第一学历/最高学历两个作用域；另以 `SchoolTagRuleEducation` 保存允许最高学历多选集合。
> **招聘主体**：岗位和投递引用 `RecruitingEntity.code`，前端直接展示 GW / YLS 等主体编码；部门和部门接口人不建立“属于招聘主体”的关系。
> **省份口径**：`School` 只保存所在省份 `province`；系统不维护南北省份分区字典，南北归属仅在志愿排序规则运行时计算，不落库、不作为配置页维护项。

### 3) 候选人处理主流程（随上传/处理简历提交后台任务）
处理由两个动作触发，均创建**可共享的后台任务**：
- **上传简历**（简历库）→ 导入弹窗凭 `resume.import` 读取 `default_mode / available_modes / ai_ready`，默认选择 Rule；用户确认本次唯一 Rule / AI 模式后，上传请求以 `processing_mode` 创建一条运行；
- **处理简历**（简历库）→ 在处理弹窗选择本次 Rule / AI 模式，以唯一 `mode` 创建运行，从 Step2 院校分类/准入开始，不重复 Step1。

> AI 模式通过真实模型链路处理；未配置可用连接或调用异常时展示后端“需处理”原因和处置入口，只有 `llm_timeout` 展示为“失败”；不得展示 Rule 结果、固定置信度或元数据拼接结论。

```
候选人处理主流程：
  Step1 查重与志愿排序
    → Step2 院校分类及学历/院校准入
    → Step3 Rule 前置检查
    → Step4 AI 深度筛选与分配（仅 AI）

基础数据：岗位需求、部门、二/三级接口人独立维护
```
> Step2 完整生成并固化院校标签；Step3/Step4 不再修改。岗位需求和接口人应在处理前维护就绪。
> 前端提交 `/api/pipeline/run/` 或上传请求后，生产异步环境收到 `202 + processing_runs` 即恢复页面操作；本地 eager 模式同步完成后返回相同字段的 200。每次只创建本次选择模式的一条运行。拥有 `pipeline.view` 的用户通过侧栏独立「处理任务」页约每 2 秒轮询；管理员和 HR 默认拥有该权限，二级、三级接口人默认不展示该导航项。连接配置后续变化不改变已按提交时模式固化的任务。
> 多个 HR 可同时提交任务。提交范围与版本快照已由后端固化；同一候选人的自动任务会等待当前候选人处理租约释放。人工下发、转派、反馈或手动分配会推进流程版本并使在途自动任务令牌失效；版本或令牌不一致时任务显示 `skipped_manual_change`，安全跳过结果且不覆盖人工操作。

### 4) 简历库中的分配尝试
```
简历库                                [处理简历]
┌ 表头筛选: 来源、部门、接口人、候选人、投递岗位、分配原因
├──────────────────────────────────────────────────────────
│候选人│岗位│来源│二级接口人│三级接口人│分配原因（截断）│
│张三  │后端│规则│技术部接口人│平台组接口人│岗位与专业匹配… │
├ 勾选后滑入: 已选 N 项｜下发选中/当前筛选｜导出选中/当前筛选｜删除选中｜取消选择
└ 详情展示全部投递、历史尝试、AI 决策、反馈和简历预览
```
> **统一操作台**：简历库主表展示当前有效 `AssignmentAttempt` 的业务结果和实际来源；没有有效尝试但已自动处理过的 Rule/AI 业务归档、需处理、模型超时失败或规则阻塞结果按工作流策略展示来源；从未处理的待分配流程不展示来源。详情展示完整历史及每次尝试状态。HR 进行待复核确认、取消、转人工、单条/选中/筛选全部下发；二级接口人转派，并可在获授反馈权限时于转派前反馈；三级接口人在转派后反馈。分配原因统一读取 `match_reason`，主表截断显示并支持悬浮查看全文，Rule 和 AI 来源都保留审计。
> **AI 决策边界**：AI 只处理 Step2/Step3 已通过的候选人，不判断学历、院校、志愿、岗位存在性、部门归属或接口人选择。历史决策仍可查看；已有待复核/待下发结果继续按原权限处置，重试入口还要求当前模型连接测试有效。
> **Rule 策略**：只处理当前有效志愿，按“岗位 → 专业确定性匹配 → 二级部门 → 二级接口人”生成待下发尝试；反馈未通过后才由工作流推进下一志愿。岗位未配置需求专业，或岗位需求专业为“专业不限 / 不限 / 不限专业”等通配表达时，不阻断自动分配。岗位配置非通配需求专业时，后端先用专业大类词表判断候选人最高学历专业与岗位需求专业是否同属大类；若大类无交集，或候选人/岗位任一侧未映射到启用大类，则再用专业名双向包含兜底。当前投递岗位未配置匹配启用岗位需求、已匹配岗位但专业不符合、已匹配岗位未配置有效二级部门时展示各自业务原因；当前志愿匹配岗位和二级部门但该部门没有启用二级接口人时，前端不展示下一志愿，而是在简历库显示阻塞原因。多岗位命中时后端按同主体、精确匹配、对外发布名称、职位名称和包含匹配的固定顺序选择岗位，并在尝试详情展示岗位、专业大类/专业名、部门和接口人等匹配理由。
> **AI 策略（当前实现）**：Agent 读取当前固定岗位名称、需求专业、工作职责和简历正文，评估专业实际方向、项目、实习、技能、职责覆盖度、补充优势与风险；工作职责最多发送清洗后的前 12,000 字符，按不可信业务数据处理并忽略其中的模型指令，只纳入既有 `job_requirement` 分项。新调用使用 `resume-screening-v2`，AI 输出 schema 与五项评分权重不变，不增加独立职责评分。当前岗位上下文不发送学历要求，当前志愿只发送 `position_name`，不发送 Resume/应聘 ID、志愿序号或招聘主体标识。模型协议不含任何岗位/部门/接口人 ID，也不接受学历输出；普通 AI 分配使用 Step3 固定对象，Step2 学历/院校结论不由 AI 补写或覆盖。历史岗位缺少工作职责时仍允许 Rule 处理；选择 AI 时显示“需处理 / 岗位缺少工作职责”，并在 PDF 抽取和模型调用前结束本候选人。专项人才字段在详情展示“专项匹配/置信度/证据/是否已分流”；开关启用且置信度严格大于 90% 时，页面显示来源为 AI、分流码为 `ai_special_route` 的已转派三级尝试及两段历史。目标配置失效显示“需处理”，不显示普通分配成功。OCR、阈值和不回退 Rule 的既有交互保持不变。
> **AI 并发执行**：生产环境的 Step4 按候选人投递到独立 `ai` 队列并发处理；本地 SQLite + eager 模式仍串行同步执行。
> **分配尝试**：简历库主表支持来源、部门、接口人、候选人、投递岗位和分配原因筛选，不展示或筛选分配状态；详情保留尝试状态展示，但详情内嵌表不提供筛选器，并支持导出、下发、转派、反馈、查看详情和简历预览。接口人只看到本人数据范围内已下发或已转派的尝试，不展示 HR 待处理状态。
> **AI 复核操作**：HR 可在 `pending_review` 尝试详情中确认下发、取消或转人工处理；当前完整模型连接配置测试有效时还可重试 AI。分别调用 `confirm-review`、`cancel-review`、`transfer-to-manual` 和 AgentDecision `retry` 接口。取消后若没有其它活动尝试，简历库显示 `agent_no_recommendation` 归档；转人工时必须从该尝试的具体投递进入手动分配，不允许隐式换志愿。
> **待下发取消**：HR 可取消 `pending_dispatch` 尝试，调用 `POST /api/workflow-attempts/{id}/cancel/`；取消后刷新候选人当前状态和可执行操作。
> **AI 结果边界**：只有 `llm_timeout` 使用“失败”；岗位缺少工作职责、正文不可用、连接/认证、429、输出协议、固定引用和专项配置失效显示“需处理”；学历/院校/岗位/部门/接口人等规则结果显示“处理完成”。所有异常均不自动回退 Rule。
> **详情与预览**：分配尝试详情抽屉展示候选人、应聘ID、岗位、二级/三级接口人、状态、反馈备注等信息，并通过 `/api/workflow-attempts/{id}/resume-preview/` 在当前用户数据范围内获取 PDF Blob，再用 PDF.js 渲染到 canvas。接口人账号只能预览自己可见分配尝试的简历；越权尝试由后端返回 404/403 类错误，前端展示为不可预览且不提供下载入口。PDF 渲染失败或非 PDF 文件时，保留下载原文件入口。
> **导出**：主表勾选批量和当前筛选导出走 `/api/candidates/export/`，详情中的接口人单条导出可走 `/api/workflow-attempts/export/`；两者都只返回当前用户数据范围内的候选人简历文件。单条且命中一个可用文件、没有缺失清单时直接下载原文件；批量、多文件或存在缺失清单时下载 zip，缺失候选人写入压缩包内「缺失简历文件清单.txt」。前端读取 `X-Export-Count` / `X-Export-Missing` 展示导出统计。
> **HR 下发操作**：HR 可在详情中单条下发；勾选任意候选人后，滑入操作条提供「下发选中」和「下发当前筛选」。候选人维度批量接口只处理当前有效 `pending_dispatch` 尝试，其他状态自动跳过并提示成功/跳过数量。
> **下发、转派与反馈**：HR 将待下发尝试下发至二级部门接口人。详情抽屉的「提交反馈」按 `attempt.feedback`、当前接口人绑定和尝试状态计算，不写死角色：二级接口人在本人接收的 `dispatched_l2` 阶段可于转派前提交通过/未通过 + 可选备注；转派为 `assigned_l3` 后二级不再显示提交按钮，改由本人被转派的三级接口人提交。已反馈结果和备注继续只读展示，提交后锁定；无操作条件时不显示可提交按钮。
> **转派操作**：二级接口人在简历库本人可见候选人详情中使用「转派」，弹窗只列出当前二级部门下启用的三级接口人；转派后状态变为「已转派三级」，并记录转派历史。
> **手动强制分配**：HR 从具体应聘ID打开弹窗，先选择目标类型（二级接口人 / 三级接口人），再选择对应接口人。选择二级接口人时走普通下发与二级转派链路；直接选择三级接口人时，前端展示其父级二级部门：若只有一个有效二级接口人则自动补齐，若有多个则要求 HR 明确选择，确认后进入「已转派三级 / 待反馈」并展示两段转派历史。没有有效父级二级接口人时阻止提交并提示改选二级接口人。已通过候选人不可通过该入口再次强制分配；如需重开已通过候选人，使用简历库「处理简历」入口。
> **AI 专项配置**：「AI 模型连接 → AI 专项配置」页签提供默认关闭的专项开关、严格阈值、父级二级接口人和固定三级接口人选择器，并与模型连接、AI 运行参数统一受 `settings.manage_ai_connection` 控制；选项只显示启用接口人。后端仍是上下级关系的最终校验者，前端原样展示配置保存错误。
> **归档候选人**：归档原因、志愿概览和从具体应聘ID发起手动强制分配统一合并到简历库；不再作为 HR 独立菜单入口。
> **角色差异**：二级接口人仅看到已下发给自己的尝试，可导出、查看反馈和转派给本部门三级接口人；获授 `attempt.feedback` 时可在转派前反馈。三级接口人仅看到转派给自己的尝试，获授 `attempt.feedback` 时可提交反馈。反馈权限不扩大本人接收/本人被转派的数据范围；接口人均无 HR 下发、手动分配、二级接口人筛选和模式开关。

### 5) DashBoard（招聘分析）

- 路由 `/analytics` 和侧栏置顶「DashBoard」导航项由 `analytics.view` 控制；管理员和 HR 默认可见并以该路由作为登录首页，二级/三级接口人默认不可见且按权限进入首个可访问页面；越权路由跳回有权默认页，接口仍以后端 403 为准。
- 页面采用与全站一致的浅灰背景、低阴影白卡和靛青主色。页面不设置独立筛选栏，只在数据展示区左上角内嵌时间区间和二级部门两个筛选器；首屏展示候选人数、分配、下发、反馈、通过五张 KPI 卡，图标固定在卡片右上角，不展示按日趋势图或候选人明细表。
- 看板界面只开放时间区间和二级部门筛选；未指定日期时后端默认最近 30 天，页面显示当前实际 cohort 和 `data_as_of`。接口为兼容既有调用仍可接受招聘主体、岗位、院校标签、最高学历和分配来源参数，但当前页面不展示这些选择器。
- 五张核心卡依次展示候选人数、已生成分配、已下发、已反馈和已通过；投递记录/已分类收入候选人数卡辅助信息，已归档收入已通过卡辅助信息。招聘概览使用“分配来源环图 + 候选人/分配/下发/反馈/通过横向流程柱图 + AI 建议环图”的三列布局。
- 页面继续展示导入到分配/下发/反馈的平均耗时、岗位/二级部门排行、院校标签/学历以及 AI 错误、归档原因和未通过原因。岗位和部门使用横向柱图；来源、建议、标签、学历和原因使用带数量、占比和 HTML 图例的环图，类别过多时合并为“其他”。AI 错误为空时只说明当前范围未记录错误，不宣称模型服务整体健康。
- 所有数字来自 `GET /api/analytics/recruitment-overview/` 的后端聚合结果；前端不请求候选人明细、不自行合并状态。图表使用 `chart.js` + `react-chartjs-2`，只注册环图、横向柱图、坐标轴、Tooltip 和 Legend 所需模块。后端响应中的 `trend` 字段暂保留供旧客户端兼容，当前页面不渲染该字段。空数据、接口失败和重新加载均提供明确状态。
- 岗位和部门排行直接展示接口返回的当前有效投递/历史部门快照口径；前端不再用当前岗位、部门主数据重算或覆盖历史标签。接口结果缓存 5 分钟，页面必须展示 `data_as_of`，不得把页面刷新时间伪装为数据统计时点。

> **备份与恢复边界**：备份调度、restic 保留、显式确认恢复（覆盖生产库时二次确认）和隔离演练属于部署运维能力，不在前端新增菜单或恢复按钮；浏览器端不得接收或保存数据库、restic、`DJANGO_SECRET_KEY` 等凭据。

### 6) 业务配置与系统设置（设计 · M4/M6）
- **配置项**：删除“系统参数”页签，只保留院校标签字典、院校准入规则、专业大类词表等业务配置页签。
- **部门接口人**：列表上方提供紧凑的 WeLink 通知开关，只有拥有 `department.manage` 的用户可见和操作；开关读取、更新 `welink_enabled`，不提供任意系统参数编辑入口。
- **AI 模型连接**：系统设置提供独立的「AI 模型连接」子页（路由 `/ai-connection`），页内分为“模型连接”“AI 运行参数”“AI 专项配置”三个页签，全部由 `settings.manage_ai_connection` 控制。模型连接页使用 `GET/PATCH /api/ai-connection/` 配置共享内网地址、API 风格（Responses API / OpenAI-compatible Chat JSON）、模型名称和可选 API Key/访问令牌，并提供真实连接测试；模型名称使用可搜索、可手工输入的下拉框，页面通过后端读取当前 Base URL 的 `GET /models` 结果作为选项，获取失败时提示但不禁用手工输入。API 风格仍由管理员单独选择，不根据模型列表自动推断。AI 运行参数和专项配置使用 `/api/ai-connection/settings/` 及其单项 PATCH 接口维护阈值、超时、并发、重试、专项分流开关、严格阈值和目标接口人。连接状态展示当前配置是否测试通过和测试时间；保存或清除任何连接配置会使测试状态失效，上传和处理弹窗随即只允许 Rule，重新测试成功后恢复 AI 选项。Key 绝不回显；无鉴权服务可留空并直接测试。系统不再提供全局 AI 分配开关。
- **准入规则配置**：规则表单从 `SchoolTag` 字典勾选标签，保存为 `SchoolTagRule` + `SchoolTagRuleTag`；另提供“允许最高学历”多选器（大专/本科/硕士/博士），保存为 `allowed_highest_educations` 并在规则列表展示。候选人必须在同一条启用规则内同时命中第一学历标签、最高学历标签和允许最高学历；学历多选留空表示不限，多条启用规则之间 OR，没有启用规则时视为不做院校准入过滤。
- **专业大类词表配置**：配置项新增「专业大类词表」页签。页面展示专业大类列表和当前大类下的专业别名/关键词，支持新增、编辑、停用、删除；字段包括大类编码、大类名称、大类说明、排序、专业别名、匹配方式（精确 / 包含）、来源、备注和启用状态。内置词表可编辑和停用；专业大类存在任何别名时不允许直接删除，确需删除需先删除或迁移别名，后端返回明确错误时前端以消息提示。
- **用户权限**：RBAC 配置页，管理员维护用户、角色、权限绑定和接口人绑定关系；接口人账号由部门接口人导入自动创建，用户管理不单独维护 `first_name`、`last_name` 等 Django 姓名类字段，并支持删除用户。

> 权限分区：岗位类别、院校标签、院校准入规则和专业大类词表属于业务配置，可分别授权 HR/管理员；模型连接、全部 AI 运行参数和 AI 专项配置统一归入「AI 模型连接」，使用 `settings.manage_ai_connection` 权限，默认授予管理员角色并可按角色委派；用户、角色、其它认证和安全开关属于系统设置。前端按具体权限码控制菜单、路由和页面，不以“是否管理员”硬编码整个配置页。
> “配置项”页面不再调用普通系统参数列表。部门接口人页面通过 `GET /api/configs/welink_enabled/` 读取并通过 `PATCH /api/configs/welink_enabled/` 更新 WeLink 通知开关；未知配置、类型错误或越权由后端拒绝。AI 连接使用独立且受 `settings.manage_ai_connection` 保护的接口，不在普通配置列表混入或回显 Key；前端不提供任意新增/删除配置键。

用户权限页建议拆成三个页签：

| 页签 | 主要能力 | 说明 |
| ---- | -------- | ---- |
| 用户管理 | 用户列表、新增/编辑/启停/删除用户、绑定角色、绑定接口人 | 接口人用户由导入自动创建，用户名为工号；用户管理不展示/编辑 `first_name`、`last_name` 等姓名类字段，接口人姓名来自绑定 `Contact`；导入同步接口人角色时保留其它业务角色；删除用户采用账号清理语义，删除账号、Token 和角色绑定，若用户绑定接口人则同步删除接口人；历史审计和分配记录不删除，只保留快照展示；二级/三级数据范围由绑定接口人和部门关系决定 |
| 角色管理 | 角色列表、新增、编辑角色 | 预置 HR、二级接口人、三级接口人、管理员；管理员可按需新增业务角色；Django Group 暂不提供独立启停状态 |
| 权限配置 | 以树形权限点为角色勾选授权 | 权限点由后端预置，只允许勾选绑定，不允许前端随意新增未知权限码 |

权限树按模块组织：

| 模块 | 权限示例 |
| ---- | -------- |
| 简历库 | 查看、上传、撤销、导出、手动分配 |
| 主数据 | 岗位需求、院校清单、部门接口人的查看/导入/编辑/删除；部门接口人页 WeLink 开关（`department.manage`） |
| 分配工作流 | 查看工作流、查看尝试、详情单条下发、下发选中、下发当前筛选、导出 |
| 接口人处理 | 二级转派、提交反馈、反馈查看（提交阶段仍受绑定和状态限制） |
| 业务配置 | 岗位/院校字典、准入规则、专业词表 |
| AI 模型连接 | 模型连接、全部 AI 运行参数和 AI 专项配置（`settings.manage_ai_connection`） |
| 招聘分析 | 查看招聘总览（`analytics.view`） |
| 处理任务 | 查看共享处理记录（`pipeline.view`）；创建流程和取消活跃任务（`pipeline.run`） |
| 系统设置 | 用户权限、认证与安全配置、AI 模型连接（`settings.manage_ai_connection`） |

前端权限生效：
- 登录后调用 `/api/me/`，获得 `permissions`、`roles`、`contact`、`data_scope`。
- ProLayout 菜单按权限码过滤；页面按钮按权限码控制显示和禁用态。菜单的展开分组由前端显式维护，路由跳转和子页选择只影响选中态，不清空其它已展开分组。
- 无权限路由展示「无权限」页面；接口请求失败仍以后端 403 为准。
- 本地开发阶段使用系统账号密码登录并保存 Token；接口人账号用户名为工号，新账号默认密码为 `pass1234`；W3 认证接入后按工号识别用户并替换登录适配层，页面仍消费 `/api/me/`。

## 三、角色与可见性

权限体系采用 RBAC。前端不再写死角色能力，而是基于 `/api/me/` 返回的权限码、角色、接口人绑定和数据范围动态控制菜单、路由和按钮：

| 区域 | 默认角色权限 | 二级接口人 | 三级接口人 |
|------|-------------|------------|------------|
| 简历库 — 候选人列表和本人分配数据 | 全量 | 仅本人接收 | 仅本人被转派 |
| 简历库 — 上传 / 撤销 / 删除 / 处理简历 | ✓ | ✗ | ✗ |
| 简历库 — 导出 / 反馈查看 | ✓ | ✓（本人范围） | ✓（本人范围） |
| 简历库 — 单条/批量/全部下发 / 手动强制分配 | ✓ | ✗ | ✗ |
| 简历库 — 二级转派给三级接口人 | ✗ | ✓ | ✗ |
| 简历库 — 提交通过/未通过反馈 | ✗ | 获授 `attempt.feedback` 后仅转派前 | 获授 `attempt.feedback` 后仅本人被转派 |
| AI 模型连接 — 模型连接、运行参数、专项配置与测试 | 拥有 `settings.manage_ai_connection` 的角色（管理员默认拥有） | 未授予时 ✗ | 未授予时 ✗ |
| 部门接口人 — WeLink 通知开关 | 拥有 `department.manage` 的角色（管理员 / HR 默认拥有） | 默认 ✗ | 默认 ✗ |
| 处理任务 — 页面与共享记录 | ✓（管理员 / HR，`pipeline.view`） | 默认 ✗ | 默认 ✗ |
| 招聘分析 | ✓（管理员 / HR，`analytics.view`） | ✗ | ✗ |
| 业务规则配置 | 按权限码授权 HR / 管理员 | ✗ | ✗ |
| 用户权限与安全设置 | ✓（管理员）| ✗ | ✗ |

> 二级/三级接口人默认没有 `analytics.view`，登录后按权限顺序进入首个可访问页面，通常为「简历库」，不得硬编码固定首页。接口人响应不包含手机号、其它志愿、其它尝试或 AI 决策，简历预览和导出使用尝试级数据范围。
> **重要边界**：前端权限配置只负责体验和误操作拦截，不能替代后端鉴权。后端接口必须同步按权限码鉴权，并保证“二级只能看自己接收且已下发的尝试并只能转派本部门三级接口人”“三级只能看自己被转派的尝试”。

## 四、目标页面清单与当前状态
1. `DashBoard`：路由 `/analytics`，按导入 cohort 查看总览、转化、耗时、来源、AI、岗位/部门和原因分布；页面只在数据区左上角提供时间区间和二级部门筛选，构成分布采用环图、岗位/部门采用横向柱图，管理员和 HR 默认可见并作为首页。
2. 处理任务：路由 `/processing-tasks`，独立展示共享任务、阶段、耗时、结果、手工刷新、候选人跳转与取消审计；`pipeline.view` 控制页面和记录查看，`pipeline.run` 控制取消。
3. 简历库：统一承载候选人列表、当前分配结果、分配原因、AI 复核、HR 单条/批量/筛选全部下发、二级转派、二级转派前/三级转派后反馈、结果报表、详情、历史尝试、AI 决策和简历预览。主表不展示流程状态或分配状态，当前应聘ID和三级接口人默认隐藏，原因截断并支持悬浮查看全文；上传和处理弹窗都选择本次 Rule / AI 模式，Rule 始终可选，连接测试有效时才启用 AI。每次只生成所选模式的一条任务。HR/管理员看全量，接口人只看本人范围。
4. 岗位需求、院校清单、部门接口人：主数据维护、导入、表头筛选和列宽拖拽；岗位需求支持编辑和删除；院校清单前端不展示所在地；部门接口人页承载 WeLink 通知开关，只有 `department.manage` 可操作。
5. 配置项与 AI 模型连接：配置项只维护院校标签、院校准入和专业词表等业务规则，不再提供“系统参数”页签；拥有 `settings.manage_ai_connection` 的角色在独立「AI 模型连接」页维护模型连接、AI 运行参数和 AI 专项配置。连接测试成功后，上传和处理简历时才可选择 AI 模式。
6. 用户权限：维护用户、角色、权限绑定和接口人绑定关系，支撑 RBAC 前端配置。
