```
┌───────────────────────────────────────────────────────────┐
│ ▣ 智能简历筛选系统  [处理任务 Badge]  [当前用户 / 角色 ▾] │ 顶栏
├──────────────┬────────────────────────────────────────────┤
│ 数据管理 ▾    │                                            │
│   · 简历库    │            内容区                          │
│   · 岗位需求  │      (ProTable / Modal 导入)              │
│   · 院校清单  │                                            │
│   · 部门接口人│                                            │
│ 简历分配 ▾    │                                            │
│   · 规则分配  │                                            │
│   · AI分配    │                                            │
│ 系统设置 ▾    │  ← 接口人身份时，左侧仅保留「简历分配」      │
│   · 配置项    │                                            │
│   · 用户权限  │                                            │
└──────────────┴────────────────────────────────────────────┘
```

> 当前结构：
> 1. **数据导入入口在各数据页内**：简历→简历库、岗位→岗位需求、院校→院校清单、接口人→部门接口人。
> 2. **处理由上传和处理简历触发**：上传含候选人简历后固定触发 Rule、AI 可用时追加 AI；HR 在处理简历时多选 Rule / AI 任一或两项，只重算「简历分类、分配与下发」环节。
> 3. **主要数据表格采用后端分页、表头筛选和列宽拖拽**：筛选参数进入接口查询，`page_size` 最大 500，导出全部按当前筛选条件执行。
> 4. **左侧菜单展开状态保持独立**：用户手动展开的一级菜单分组应保持展开；点击某个子页面只更新当前选中路由，不应自动收起其它已展开分组。
> 左侧菜单**按权限码和数据范围显示**：简历分配是父级菜单，HR/管理员进入两个真实子路由「规则分配」(`/allocations/rule`) 与「AI分配」(`/allocations/ai`)；二级/三级接口人仅见「规则分配」并直接进入该操作台。两个子页复用同一分配尝试页面，区别只在请求 `source=rule` 或 `source=ai`。

当前共享实现：

- `DataTableControls.jsx` 提供文本筛选、单选/多选筛选、筛选参数规范化和可拖拽列宽 Hook；筛选浮层统一提供确认、重置和取消操作；简历库、岗位、院校、接口人页面统一复用。
- `ResizableHeaderCell.jsx` 负责表头拖拽手柄和 pointer 事件；样式类 `.srf-column-resize-handle` 定义在全局 CSS。
- `ResumePreview.jsx` 负责 PDF/文件预览，PDF 通过鉴权 API 取得 Blob 后交给 PDF.js 渲染到 canvas，不依赖浏览器原生 PDF 内嵌能力；组件支持未选择、加载中、失败提示、分页、新窗口打开和“下载原文件”；可按 `resume` 直接预览，也可按 `attemptId` 走分配尝试数据范围预览。无权限或越权时不展示下载入口；PDF 渲染失败或非 PDF 文件时可下载原文件。
- 前端 API 封装位于 `src/api/services.js`：`previewResume`、`previewAllocationResume`、`exportCandidates`、`deleteCandidate` 分别对应预览、按筛选导出和候选人维护能力。
- 主布局提供非阻塞的“处理任务”顶栏按钮；仅 HR/管理员可见，Badge 约每 2 秒轮询并提示活跃数量。点击后打开非遮罩侧边 Drawer 任务中心，在其中查看每条运行的进度、范围摘要、结果、异常和取消审计，并提供「取消任务」：排队任务直接显示已取消；运行中/等待冲突任务显示取消中，完成安全停止后显示已取消，不回滚已生成结果。任务详情仅在 Drawer 中呈现。**目标设计（部分后端未实现）**：按各阶段累计工作量展示连续进度，并展示范围摘要、安全跳过、最近心跳和异常；心跳超时失败时明确展示原因，且仅未开始/等待冲突的范围项可由后端安全重试。不展示候选人 ID 范围明细。

### 1) 简历库（候选人列表 + 投递详情 + 上传即处理 + 撤销）

> **上传**：「上传简历」弹窗含两类文件 **① 简历信息列表 .xlsx / .xls / .csv + ② 简历包 .zip**。普通用户入口只提供安全的增量更新；主数据 replace 使用更新/停用语义，不得删除候选人流程、反馈或审计历史。测试环境彻底清空不放在普通上传弹窗中。
> **上传即处理**：上传含候选人数据时，后端固定创建 Rule 运行，并仅在 `ai_config.is_ai_enabled` 时额外创建 AI 运行；响应只以 `processing_runs` 返回两条或一条独立任务。生产异步环境提交后返回 202，本地 `CELERY_TASK_ALWAYS_EAGER=True` 同步完成后返回 200；两者使用同一响应字段。后台由同一顺序任务先执行 Rule、后执行 AI；各自编排 `Step1 查重与志愿排序 → Step2 简历分类、分配与下发`，不得复用 `all`，也不得让两种来源尝试互相取消。院校分类 Step3 和需求数据准备核对 Step4 是前置数据准备，可在对应主数据页提前维护或独立运行；显式“全流程”操作才按 `Step3 → Step4 → Step1 → Step2` 执行。「处理简历」按钮只提交带筛选范围的 Step2，不重跑查重排序、全量院校分类和需求核对；后端会在提交时锁定当前筛选范围，为范围内缺失院校标签的候选人补齐标签，不覆盖已有标签。发起按钮仅在提交请求期间禁用，拿到任务记录后页面仍可筛选、预览、导出和跳转。
> **增量 + 冲突处理**：按 `normalized_name + normalized_phone` 归并候选人，按 `应聘ID` 幂等更新投递；低风险重复更新当前主记录，但不删除已反馈流程、分配尝试和历史快照；高风险重复进入导入错误清单。手机号缺失的候选人直接舍弃，不入库、不进入分配，并在导入结果中提示。
> **候选人聚合展示**：主列表以 `Candidate` 为行粒度，一名候选人只显示一行；主列表不展示候选人手机号，手机号只在详情抽屉/详情页展示；主列表和详情都展示 `Candidate.highest_major` 最高学历专业；所有投递岗位、应聘ID、志愿顺序、分配尝试、匹配/手动理由和反馈记录进入详情抽屉/详情页。
> **当前志愿展示**：主列表仅展示当前有效志愿。初始只展示第一志愿；第一志愿反馈未通过后，系统生成并展示下一志愿；通过后固定展示通过志愿；归档后展示最后处理志愿和归档原因；当前志愿匹配岗位和二级部门但缺可用二级接口人时，固定展示当前志愿和阻塞原因。
> **系统简历状态**：简历库展示后端推导的统一状态，不覆盖导入文件中的原始“应聘状态”。状态选项为：待处理、已分类、已分配、待筛选、筛选通过、筛选不通过；存在历史未通过和下一志愿活动尝试时，按 `筛选通过 > 待筛选 > 已分配 > 筛选不通过 > 已分类 > 待处理` 展示，但只读取当前 workflow、当前通过指针和未取消活动尝试，历史 passed/rejected/cancelled 只在详情中展示，不覆盖重开后的当前状态。
> **筛选、处理与导出**：主列表筛选在表头内完成，支持姓名/全拼/拼音首字母、最高学历专业、当前志愿、当前应聘ID、招聘主体、当前岗位、岗位部门、岗位类别、院校标签、系统简历状态、流程状态、原因类型等字段；系统简历状态和流程状态都使用表头勾选多选筛选。工具栏提供「处理简历」按钮，HR/管理员在弹窗中勾选一个或多个目标系统简历状态，并多选规则 / AI（至少一项，可同时选两项）；前端通过 `GET /api/ai-availability/` 仅读取 `enabled`，AI 未启用时禁用 AI 选项。提交 `POST /api/pipeline/run/` 时必须传非空 `modes` 数组和当前筛选条件；未选择状态或模式时提示选择，AI 未启用时即使绕过前端传入 `ai` 后端也必须拒绝。该入口可按筛选范围重开已通过、已归档或已不通过候选人流程，前端需提示会保留历史尝试/反馈并分别生成所选来源的自动尝试，两种来源不会互相取消；「导出当前筛选」按后端筛选结果导出，单个可用文件且没有缺失清单时直接下载原文件，多个文件或存在缺失清单时下载 zip；前端读取导出响应头 `X-Export-Count` / `X-Export-Missing` 展示命中和缺失数量。
> **简历预览与删除**：详情抽屉默认选中当前投递中有文件的简历；当前投递无文件时，自动回退到同候选人第一条有文件的投递，不改变当前志愿展示口径。候选人多条投递间可手动切换预览，未关联简历文件的投递预览入口置灰并提示原因；前端通过鉴权 API 获取 PDF Blob 后用 PDF.js 渲染到 canvas，并读取预览响应头 `X-Resume-Filename` 展示原始文件名。无权限或越权时不展示预览和下载入口；PDF 渲染失败或非 PDF 文件时可下载原文件。候选人存在分配尝试、反馈、AI 决策或转派历史时不显示可执行删除，或保持禁用并解释原因；后端返回 409 时展示原始错误说明。
> **按上传记录撤销（目标设计，后端未实现）**：后端先解析每次上传影响的业务键，只为该候选人/投递范围保存覆盖 Candidate / Resume / ResumeProfile / CandidateWorkflow / AgentDispatchDecision / AssignmentAttempt / AssignmentHandoff 的独立快照及本次上传关联处理完成后的流程版本基线；“上传撤销记录”只展示当前 HR 自己的上传，管理员可查看全部。用户按选定上传记录执行撤销，同一记录仅可撤销一次；撤销时后端锁定该记录的全部候选人并校验版本，任一候选人存在后续变更即整体返回 `409`，前端不显示部分撤销成功。关联 ProcessingRun 未结束时同样禁用该记录的撤销并展示原因；已撤销的运行保留审计展示。

### 2) 岗位需求 / 院校清单 / 部门接口人（结构同构）
```
岗位需求                                       [↥ 导入岗位] [新增岗位]
│ 对外名称│职位名称│岗位类别│岗位族│部门│工作地│学历│HC│对外发布│操作
│ ...    │...   │...   │... │...│...│...│...│...    │编辑 删除

院校清单                                       [↥ 导入院校]
│ 学校 │ 院校标签 │

部门接口人                                     [↥ 导入接口人]
│ 姓名 │ 工号 │ 所属部门 │ 部门层级 │ 接口人层级 │ 可转派
```
> 三页各自只导入对应的一张表格文件（.xlsx / .xls / .csv）；后端复用同一 `/api/import/`（按字段区分），无需分别建接口。
> 岗位、院校、部门接口人列表均使用表头筛选和列宽拖拽；筛选条件进入后端查询并与分页共同生效。岗位支持主体、发布名称、岗位族、部门、地点、学历、HC、是否发布等筛选，并提供编辑和删除操作；删除岗位采用停用/失效语义，历史投递和分配尝试仍可追溯。院校清单前端只展示学校和院校标签，不展示所在地/所在省份；省份字段可作为导入和排序规则后台数据保留。接口人支持姓名、工号、部门、层级、是否可转派、是否启用筛选；不展示或筛选招聘主体归属/主体来源。
> 部门接口人 replace/清空重导时，本次文件中不存在的旧接口人及其绑定账号会同步停用；列表默认只展示启用接口人，可通过状态筛选查看停用接口人。单条“删除”操作采用清理语义：删除接口人并同步删除绑定用户，历史分配记录不删除，只通过快照字段展示原接口人信息。
> **字典化口径**：岗位类别来自 `JobCategory` 字典，院校标签来自 `SchoolTag` 字典，专业大类词表来自 `MajorCategory` + `MajorAlias`；字典项保留 `code + name` 或规范化名称，前端展示业务名称，导入/匹配优先使用 `code` 或规范化名称。
> **非目标院校预置**：院校标签字典预置启用 `NON_TARGET / 非目标院校`。院校清单外的学校在分类时始终写入该标签；清单内学校未配置标签时才使用启用默认标签，无默认标签时回退到该预置标签。院校列表可显示/维护清单内学校的标签，但不能把清单外学校误展示为默认标签。
> **院校标签准入规则**：配置项中维护 `SchoolTagRule`，规则允许标签通过 `SchoolTagRuleTag` 关联到 `SchoolTag`，并区分第一学历/最高学历两个作用域。
> **招聘主体**：岗位和投递引用 `RecruitingEntity.code`，前端直接展示 GW / YLS 等主体编码；部门和部门接口人不建立“属于招聘主体”的关系。
> **省份口径**：`School` 只保存所在省份 `province`；系统不维护南北省份分区字典，南北归属仅在志愿排序规则运行时计算，不落库、不作为配置页维护项。

### 3) 候选人处理主流程（随上传/处理简历提交后台任务）
处理由两个动作触发，均创建**可共享的后台任务**：
- **上传简历**（简历库）→ 固定创建 Rule 运行；AI 可用时同时创建 AI 运行，按 Rule 后 AI 顺序执行；
- **以 Rule / AI 多选发起处理简历**（简历库）→ 为所选模式分别创建运行，只重算「简历分类、分配与下发」环节。

> AI 模式通过真实模型链路处理；未配置密钥或调用失败时展示后端失败原因和处置入口，不得展示 Rule 结果、固定置信度或元数据拼接结论。

```
前置数据准备：
  院校分类、需求录入、部门接口人维护

候选人处理主流程：
  Step1 查重与志愿排序 → Step2 简历分类、分配与下发
```
> 院校分类和需求录入提前完成，保证分配时院校标签、岗位需求、专业要求和接口人已就绪。
> 前端提交 `/api/pipeline/run/` 或上传请求后，生产异步环境收到 `202 + processing_runs` 即恢复页面操作；本地 `CELERY_TASK_ALWAYS_EAGER=True` 同步完成后返回相同字段的 200。普通上传的 Rule 与可用 AI 运行均由后端完成 Step1→Step2，并依次执行。HR/管理员通过顶栏「处理任务」Badge 与点击后的非遮罩侧边 Drawer 按约 2 秒轮询每条独立任务数据；二级、三级接口人不展示任务中心。任务状态为排队中、处理中、等待冲突、取消中、已取消、成功、部分失败或失败；活跃任务在 Drawer 内可调用 `POST /api/pipeline/runs/{id}/cancel/` 取消。任务结束时只提示“结果已更新，点击刷新”，不强制改写其他 HR 当前表格的筛选条件。
> 多个 HR 可同时提交任务。提交范围与版本快照已由后端固化；同一候选人的自动任务会等待当前候选人事务完成。**目标设计（后端未实现）**：人工下发、转派、反馈或手动分配与自动任务使用统一流程锁，版本不一致时任务显示 `skipped_manual_change` 安全跳过结果，不覆盖人工操作。

### 5) 分配尝试
```
简历分配 ▾
  规则分配 `/allocations/rule`  或  AI分配 `/allocations/ai`
┌ 筛选: 状态[▾] 候选人 投递岗位
├──────────────────────────────────────────────────────────
│候选人│应聘ID│岗位│二级接口人│三级接口人│状态│反馈│更新时间│操作       │
│张三  │A001 │后端│技术部接口人│平台组接口人│已转派三级│待反馈│09:30│查看   │
└ 候选人级流程状态、归档原因和阻塞原因在简历库展示和筛选
```
> **两个子页，同一操作台**：「规则分配」和「AI分配」是可直达、可刷新的真实子路由，均渲染同一个 `AssignmentAttempt` 表格和操作集合：状态/表头筛选、详情、PDF 预览、导出、HR 单条/选中/当前筛选全部下发至二级接口人、二级转派三级、三级反馈。前端将当前子页的 `source` 参数带入列表、导出和批量操作，避免跨模式误操作。
> **AI 决策边界**：AI 子页不是独立的 AI 决策列表。仅已生成 `AssignmentAttempt` 的 AI 结果进入 `source=ai` 表格；失败、低置信度和建议归档而未生成尝试的 AI 决策继续保存在后端决策记录中，HR/管理员从简历库详情或 `/api/agent-decisions/`、`/retry/` 处置，不能伪造成可下发的表格行。
> **Rule 策略**：按志愿顺序、院校标签准入规则、招聘主体一致性、岗位需求映射、岗位需求专业、岗位二级部门和二级接口人生成待下发尝试；岗位未配置需求专业，或岗位需求专业为“专业不限 / 不限 / 不限专业”等通配表达时，不阻断自动分配。岗位配置非通配需求专业时，后端先用专业大类词表判断候选人最高学历专业与岗位需求专业是否同属大类；若大类无交集，或候选人/岗位任一侧未映射到启用大类，则再用专业名双向包含兜底。当前志愿匹配岗位和二级部门但缺可用二级接口人时，前端不展示下一志愿，而是在简历库显示阻塞原因。多岗位命中时后端按同主体、精确匹配、对外发布名称、职位名称和包含匹配的固定顺序选择岗位，并在尝试详情展示岗位、专业大类/专业名、部门和接口人等匹配理由。
> **AI 策略（当前实现）**：Agent 只处理候选人的当前有效志愿，硬规则先行，不跨志愿跳转。Agent 读取 `ResumeProfile.raw_text` 及结构化画像字段，结合当前志愿、岗位需求专业与部门信息生成建议。达到 `ai_dispatch_threshold` 形成 `pending_dispatch`；达到 `ai_review_threshold` 但未达到自动下发条件时形成 `pending_review`；建议归档、低于复核阈值、简历缺失、解析失败或最终失败时只展示 AI 决策，不生成分配尝试，候选人流程显示为“已归档 / AI 无有效建议”。前端轮询 `ProcessingRun` 展示进度；`partial_failed` 显示警告，不提示完全成功。
> **分配尝试**：两个子页均展示 `AssignmentAttempt`，支持同一组状态筛选、导出、下发、转派、反馈、查看详情和简历预览。HR/管理员在规则页/AI页分别查看各自来源的待复核、待下发、已下发等状态；二级接口人只在规则页看到已由 HR 下发给自己的尝试，不展示 `pending_dispatch` / `pending_review` 等 HR 待处理状态，也不提供“二级接口人”筛选项。接口：`/api/workflow-attempts/?source=rule|ai`。
> **AI 复核操作**：HR 可在 `pending_review` 尝试详情中确认下发、取消、转人工处理或重试 AI；分别调用 `confirm-review`、`cancel-review`、`transfer-to-manual` 和 AgentDecision `retry` 接口。取消后若没有其它活动尝试，简历库显示 `agent_no_recommendation` 归档；转人工时必须从该尝试的具体投递进入手动分配，不允许隐式换志愿。
> **待下发取消**：HR 可取消 `pending_dispatch` 尝试，调用 `POST /api/workflow-attempts/{id}/cancel/`；取消后刷新候选人当前状态和可执行操作。
> **AI 失败边界**：AI 超时、调用失败、PDF 解析失败、输出不合法、推荐对象不存在或被硬规则拦截时，不自动回退 Rule；前端提示失败原因，由 HR 明确选择重试 AI、切换 Rule 或手动强制分配。
> **详情与预览**：分配尝试详情抽屉展示候选人、应聘ID、岗位、二级/三级接口人、状态、反馈备注等信息，并通过 `/api/workflow-attempts/{id}/resume-preview/` 在当前用户数据范围内获取 PDF Blob，再用 PDF.js 渲染到 canvas。接口人账号只能预览自己可见分配尝试的简历；越权尝试由后端返回 404/403 类错误，前端展示为不可预览且不提供下载入口。PDF 渲染失败或非 PDF 文件时，保留下载原文件入口。
> **导出**：导出候选人**简历文件**（`/api/workflow-attempts/export/`）；支持单条、勾选批量、按筛选「导出全部」。单条且命中一个可用文件、没有缺失清单时直接下载原文件；批量、多文件或存在缺失清单时下载 zip，缺失候选人写入压缩包内「缺失简历文件清单.txt」。前端读取 `X-Export-Count` / `X-Export-Missing` 展示导出统计。
> **HR 下发操作**：HR 可单条下发，也可勾选多条后「下发选中」，或按当前筛选条件「一键全部下发」。批量下发只处理 `pending_dispatch`，其他状态自动跳过并提示成功/跳过数量。接口：`POST /api/workflow-attempts/bulk-dispatch/`。
> **下发、转派与反馈**：HR 将待下发尝试下发至二级部门接口人；二级接口人在本二级部门范围内选择三级部门接口人并转派；三级接口人对已转派尝试提交通过/未通过 + 可选备注，提交后锁定。
> **转派操作**：二级接口人的分配尝试列表展示「转派」按钮，弹窗只列出当前二级部门下启用的三级接口人；转派后状态变为「已转派三级」，并记录转派历史。
> **手动强制分配**：HR 从具体应聘ID打开弹窗，先选择目标类型（二级接口人 / 三级接口人），再选择对应接口人。选择二级接口人时走普通下发与二级转派链路；直接选择三级接口人时，前端展示其父级二级部门：若只有一个有效二级接口人则自动补齐，若有多个则要求 HR 明确选择，确认后进入「已转派三级 / 待反馈」并展示两段转派历史。没有有效父级二级接口人时阻止提交并提示改选二级接口人。已通过候选人不可通过该入口再次强制分配；如需重开已通过候选人，使用简历库「处理简历」入口。
> **归档候选人**：归档原因、志愿概览和从具体应聘ID发起手动强制分配统一合并到简历库；不再作为 HR 独立菜单入口。
> **角色差异**：二级接口人仅看到已下发给自己的尝试，可导出、查看反馈和转派给本部门三级接口人；三级接口人仅看到转派给自己的尝试，可导出并提交反馈；接口人均无 HR 下发、手动分配、二级接口人筛选和模式开关。

### 6) 业务配置与系统设置（设计 · M4/M6）
- **配置项**：岗位类别字典、院校标签字典、院校标签准入规则、专业大类映射词表、`ai_dispatch_threshold`（默认 0.75）、`ai_review_threshold`（默认 0.5）、AI 超时、AI 并发、AI 重试次数、AI 重试退避、任务心跳超时；任务心跳超时仅管理员可维护。不维护南北省份字典。W3 认证属于待实现的安全适配，不作为通用业务配置项。
- **AI 模型连接（仅管理员）**：系统设置提供「AI 模型连接」页，使用 `GET/PATCH /api/ai-connection/` 配置 profile、`api_style`、模型名、Base URL 和 API Key，并提供 `POST /api/ai-connection/test/` 的最小真实模型测试。Key 可输入和更新，但页面重新加载时只展示“已配置/未配置”安全摘要，绝不展示明文或密文；清除已保存 Key 后应明确提示 AI 未配置。测试结果只展示可读成功信息或稳定错误码、脱敏摘要，不展示第三方 SDK 原始异常。该页由 `settings.manage_permissions` 控制，HR 和接口人菜单、路由、接口均不可见/不可调用；运行时只读取该页保存的数据库连接，profile 注册表只提供表单默认模板。
- **准入规则配置**：规则表单从 `SchoolTag` 字典勾选标签，保存为 `SchoolTagRule` + `SchoolTagRuleTag`；第一学历允许标签和最高学历允许标签分开配置，但候选人必须在同一条启用规则内同时命中第一学历和最高学历标签才算通过；多条启用规则之间 OR，没有启用规则时视为不做院校准入过滤。
- **专业大类词表配置**：配置项新增「专业大类词表」页签。页面展示专业大类列表和当前大类下的专业别名/关键词，支持新增、编辑、停用、删除；字段包括大类编码、大类名称、大类说明、排序、专业别名、匹配方式（精确 / 包含）、来源、备注和启用状态。内置词表可编辑和停用；专业大类存在任何别名时不允许直接删除，确需删除需先删除或迁移别名，后端返回明确错误时前端以消息提示。
- **用户权限**：RBAC 配置页，管理员维护用户、角色、权限绑定和接口人绑定关系；接口人账号由部门接口人导入自动创建，用户管理不单独维护 `first_name`、`last_name` 等 Django 姓名类字段，并支持删除用户。

> 权限分区：岗位类别、院校标签、院校准入规则、专业大类词表和 AI 非敏感运行参数属于业务配置，可分别授权 HR/管理员；用户、角色、权限、认证、安全开关和 AI 模型连接属于系统设置，仅管理员可见。前端按具体权限码控制页签，不以“是否管理员”硬编码整个配置页。
> 普通配置页通过 `GET /api/configs/` 获取白名单项，通过 `PATCH /api/configs/{key}/` 更新；未知配置、类型错误或越权由后端拒绝。AI 连接使用独立管理员接口，不在普通配置列表混入或回显 Key；前端不提供任意新增/删除配置键。

用户权限页建议拆成三个页签：

| 页签 | 主要能力 | 说明 |
| ---- | -------- | ---- |
| 用户管理 | 用户列表、新增/编辑/启停/删除用户、绑定角色、绑定接口人 | 接口人用户由导入自动创建，用户名为工号；用户管理不展示/编辑 `first_name`、`last_name` 等姓名类字段，接口人姓名来自绑定 `Contact`；导入同步接口人角色时保留其它业务角色；删除用户采用账号清理语义，删除账号、Token 和角色绑定，若用户绑定接口人则同步删除接口人；历史审计和分配记录不删除，只保留快照展示；二级/三级数据范围由绑定接口人和部门关系决定 |
| 角色管理 | 角色列表、新增、编辑角色 | 预置 HR、二级接口人、三级接口人、管理员；管理员可按需新增业务角色；Django Group 暂不提供独立启停状态 |
| 权限配置 | 以树形权限点为角色勾选授权 | 权限点由后端预置，只允许勾选绑定，不允许前端随意新增未知权限码 |

| 模块 | 权限示例 |
| ---- | -------- |
| 简历库 | 查看、上传、撤销、导出、手动分配 |
| 主数据 | 岗位需求、院校清单、部门接口人的查看/导入/编辑/删除 |
| 分配工作流 | 查看工作流、查看尝试、单条下发、批量下发、一键全部下发、导出 |

前端权限生效：
- 登录后调用 `/api/me/`，获得 `permissions`、`roles`、`contact`、`data_scope`。
- ProLayout 菜单按权限码过滤；页面按钮按权限码控制显示和禁用态。菜单的展开分组由前端显式维护，路由跳转和子页选择只影响选中态，不清空其它已展开分组。

## 三、角色与可见性

权限体系采用 RBAC。前端不再写死角色能力，而是基于 `/api/me/` 返回的权限码、角色、接口人绑定和数据范围动态控制菜单、路由和按钮：

| 区域 | HR / 管理员 | 二级接口人 | 三级接口人 |
|------|-------------|------------|------------|
| 简历库（上传 / 撤销）/ 岗位 / 院校 / 部门接口人 | ✓ | ✗ | ✗ |
| 分配尝试 — 导出 / 反馈查看 | ✓ | ✓ | ✓ |
| 分配尝试 — 单条/批量/全部下发 / 手动强制分配 | ✓ | ✗ | ✗ |
| 简历分配路由 | 规则分配、AI分配 | 仅规则分配 | 仅规则分配 |
| 分配尝试 — 转派给三级接口人 | ✗ | ✓ | ✗ |
| 分配尝试 — 提交通过/未通过反馈 | ✗ | ✗ | ✓ |
| AI 模型连接 — 查看/保存/测试 | ✓（仅 `settings.manage_permissions`） | ✗ | ✗ |
| 业务规则配置 | 按权限码授权 HR / 管理员 | ✗ | ✗ |
| 用户权限与安全设置 | ✓（管理员）| ✗ | ✗ |

> 二级/三级接口人登录后默认落到「简历分配」，访问其它路径自动重定向回分配尝试操作台。
> **重要边界**：前端权限配置只负责体验和误操作拦截，不能替代后端鉴权。后端接口必须同步按权限码鉴权，并保证“二级只能看自己接收且已下发的尝试并只能转派本部门三级接口人”“三级只能看自己被转派的尝试”。

## 四、目标页面清单与当前状态
1. 简历库：上传、按上传记录撤销、表头筛选、拼音搜索、列宽拖拽、删除、按候选人一人一行展示最高学历专业、当前志愿、当前应聘ID、当前投递、岗位部门、系统简历状态、流程状态和分配/归档/阻塞原因；主表不展示手机号，详情查看候选人手机号、最高学历专业、全部投递、分配尝试、匹配/手动理由、反馈结果和 PDF 预览；支持点击“处理简历”后在弹窗勾选系统简历状态和规则/AI 多选模式，并处理当前表格其它筛选范围内简历；上传固定生成 Rule 任务、AI 可用时追加 AI 任务，处理提交后通过顶栏「处理任务」Badge 和非遮罩侧边 Drawer 查看每条运行进度，支持按当前筛选导出候选人简历，单个可用文件且无缺失清单时下载原文件，多文件或有缺失清单时下载 zip。
2. 岗位需求、院校清单、部门接口人：主数据维护、导入、表头筛选和列宽拖拽；岗位需求支持编辑和删除；院校清单前端不展示所在地。
3. 简历分配已作为父菜单拆为真实「规则分配」和「AI分配」子路由；两页复用同一分配尝试表和下发、转派、反馈、导出、详情、PDF 预览功能，仅以 `source=rule/ai` 筛选。二级、三级接口人仅可见规则分配。未生成分配尝试的 AI 决策不进入 AI 分配表，仍由简历库详情和 AI 决策 API 处置；待复核尝试支持确认、取消和转人工，简历库支持对当前志愿发起手动分配。HR/管理员可从全局任务中心查看共享的基础运行状态和当前已实现统计，接口人不可见；完整的阶段累计、心跳超时和安全重试语义以本章“实现状态速览”中的待实现说明为准。

5. 用户权限：维护用户、角色、权限绑定和接口人绑定关系，支撑 RBAC 前端配置。
