> 当前结构：
> 1. **数据导入入口在各数据页内**：简历→简历库、岗位→岗位需求、院校→院校清单、接口人→部门接口人。
> 2. **处理由上传和处理简历触发**：两种入口都要求用户选择本次 Rule / AI 模式并只创建一条任务；上传从 Step1 开始，“处理简历”从 Step2 院校分类/准入开始，Rule 止于 Step3，AI 继续 Step4。Rule 始终可选，AI 仅在当前模型连接测试有效时可选。
> 3. **所有数据表格支持列宽拖拽，可筛选业务列支持表头筛选**：可独立查询的列表采用后端分页，表头文本/单选/多选筛选参数进入接口查询，`page_size` 最大 500，导出全部按当前筛选条件执行；简历详情内嵌表格不提供筛选器。简历库主表不设操作列；其它页面保留的操作列可调整宽度，但不提供筛选器。
> 4. **`DashBoard` 是置顶首页**：路由仍为 `/analytics`，不属于“数据管理”子菜单；管理员和 HR 登录后默认进入该页，未获 `analytics.view` 权限时整个导航项隐藏并进入首个有权页面。
> 5. **侧栏分组可独立展开或收起**：「数据管理」和「系统设置」分别维护展开状态；点击某个子页面只更新当前选中路由，不应自动收起其它已展开分组。
> 6. **处理任务是独立导航与页面**：路由 `/processing-tasks` 由 `pipeline.view` 控制，位于 `DashBoard` 之后，不再占用顶部栏或以 Drawer 展示；取消活跃任务仍要求 `pipeline.run`。
> 7. **Prompt 管理是独立系统设置页面**：路由 `/prompt-management` 与全部操作复用 `settings.manage_ai_connection`；无权限时菜单被过滤，直接访问也跳回首个有权页面，接口仍由后端返回 403。
> 左侧菜单**按权限码和数据范围显示**：简历库是候选人查看、分配下发、二级转派和分阶段反馈的统一入口。HR/管理员查看全量；二级/三级接口人也进入 `/resumes`，但只看到本人接收或被转派的候选人和对应尝试。

当前共享实现：

- `SmartDataTable.jsx` 统一提供列宽拖拽、列设置、服务端/本地筛选和行点击隔离能力；简历库主表及岗位、院校、接口人、用户权限和配置表按列启用筛选，简历详情的投递志愿、分配尝试和 AI 筛选决策表不配置筛选器。
- `ResizableHeaderCell.jsx` 负责表头拖拽手柄和 pointer 事件；样式类 `.srf-column-resize-handle` 定义在全局 CSS。
- `SchoolTagBadge.jsx` 统一渲染院校标签，根据完整标签名称生成稳定区分色；同名标签同色，不同标签使用不同颜色，简历库、候选人详情、院校清单、院校标签字典和准入规则保持一致。
- `ResumePreview.jsx` 负责 PDF/文件预览，PDF 通过鉴权 API 取得 Blob 后交给 PDF.js 渲染到 canvas，不依赖浏览器原生 PDF 内嵌能力；组件支持未选择、加载中、失败提示、分页、新窗口打开和“下载原文件”；可按 `resume` 直接预览，也可按 `attemptId` 走分配尝试数据范围预览。无权限或越权时不展示下载入口；PDF 渲染失败或非 PDF 文件时可下载原文件。
- `ResumeExportModal.jsx` 统一承载候选人级和尝试级简历导出的属性选择。弹窗从 `/api/candidates/export-fields/` 获取版本 2 的候选人、当前投递、岗位需求、分配反馈、状态与原因五组字段目录；目录不含 `processing_result`。弹窗提供全选、清空、恢复默认和已选数量；未选字段、目录加载失败或正在加载时禁用“导出 ZIP”。用户确认后按 `srf.resume-export-fields:<user id/username>` 将目录版本和稳定字段键保存到 `localStorage`；重新打开时过滤 `processing_result` 等失效字段，剩余有效选择为空、JSON 无效或存储不可用时使用后端默认字段。勾选顺序不影响提交和 Excel 列顺序。
- 前端 API 封装位于 `src/api/services.js`：`fetchW3OAuth2Status`、`completeW3OAuth2Login`、`previewResume`、`previewAllocationResume`、`fetchCandidateExportFields`、`exportCandidates`、`exportAllocations`、`exportResumeResultReport`、`deleteCandidate` 分别对应 W3 登录能力/一次性完成、预览、字段目录、两类组合导出、Dashboard 结果报表和候选人维护能力；Prompt 管理使用 `fetchAIPrompts / saveAIPromptDraft / resetAIPromptDraft / testAIPromptDraft / publishAIPromptDraft / fetchAIPromptVersions / fetchAIPromptVersion / restoreAIPromptVersion` 对应初始化、共享草稿、真实测试、发布、历史详情和恢复接口。
- 全站登录后界面统一使用浅灰背景、低阴影白卡、靛青主色、深色固定侧栏和白色顶部栏；`ConfigProvider`、ProLayout token 与全局 CSS 统一 Card、Table、Tabs、表单、Drawer 和 Modal 的视觉。`/login` 不再承载用户名密码表单或普通登录按钮，正常状态只短暂显示跳转状态并自动进入 W3。
- `AnalyticsPage.jsx` 通过 `fetchRecruitmentOverview` 只读取后端聚合数据，使用 Ant Design 卡片和 Chart.js 环图/横向柱图展示，不下载候选人明细自行统计。
- 主布局为拥有 `pipeline.view` 的用户提供独立“处理任务”页面，该权限默认授予 HR/管理员；页面约每 2 秒轮询并支持手工刷新。任务卡按 Step1–Step4 展示阶段和耗时，主结果固定为处理完成、需处理、失败、跳过、取消；AI 的待复核、待下发、建议归档是处理完成子项。非零结果跳转 `processing_result=<completed|needs_attention|failed|skipped|cancelled>`，旧 success 链接仅兼容；取消按钮另按 `pipeline.run` 控制，并保留并发审计交互。

- AI 任务卡额外展示 `ai_effective_concurrency / ai_concurrency_limit`、模型重试数和 429 限流数；所有任务统一展示 completed、needs_attention、failed、skipped 和 cancelled 计数。

W3 唯一入口交互：

- `/login` 没有正常登录表单。无 W3 回调参数时，`LoginPage.jsx` 请求 `GET /api/auth/w3/status/`；`ready=true` 且 `start_url` 有效时立即自动导航到后端 W3 授权入口，不要求用户再次点击。加载期间只显示“正在跳转 W3”，不得闪现用户名、密码、测试账号或本地登录入口。
- 状态请求失败、`ready=false`、W3 未启用或配置不完整时，不降级到本地密码登录，只显示最小配置异常说明和“重试”操作；重试重新读取 status。前端可读取 `local_login_enabled` 用于诊断兼容，但不得据此渲染本地表单或调用 `POST /api/auth/login/`。
- 自动跳转只使用后端返回的固定 `start_url`，前端不构造 authorize URL，不接受或转发用户传入的 `redirect`/`next`。后端回跳只返回服务端配置且校验过的本站相对地址，路径必须精确为 `/login`，可携带服务端固定查询参数，但不得预置 `oauth2` / `oauth2_error` 保留键，也不得携带 URL params 或 fragment；绝对 URL 不允许，因此前端不形成开放重定向。
- 回跳登录页仅识别 `oauth2=success` 和 `oauth2_error=<stable_code>`。成功时 `RoleContext` 调用 `POST /api/auth/w3/complete/` 一次性领取后端经 Django Session 保存的项目 DRF Token，再沿用现有 `localStorage` 和 `/api/me/` 初始化逻辑。URL 不携带 W3 Access Token 或项目 Token；重复/过期领取显示后端错误并要求重新登录。
- `state_invalid / provider_denied / authorization_code_missing / token_exchange_failed / userinfo_failed / employee_no_missing / email_missing / account_not_found / account_inactive` 在登录页映射为明确中文错误，未知码显示通用“W3 登录失败”。`email_missing` 提示 W3 用户信息缺少有效邮箱；工号和邮箱未同时映射到同一个启用账号，或账号停用时只提示联系管理员，前端不做单字段降级、不自动建号或切换其他账号。
- W3 UserInfo 顶层字段已确认为 `tenantId`、`uuid`、`globalUserID`、`email`、`employeeNumber`；服务端默认用 `employeeNumber` 严格匹配 `User.username`、用 `email` 匹配 `User.email`，`tenantId / uuid / globalUserID` 不参与匹配、不落库，前端也不消费或展示。W3 提供方地址、client 凭据、scope、工号/邮箱字段路径、PKCE 和 redirect URI 等均为服务端环境变量，默认 `W3_OAUTH2_EMPLOYEE_NO_FIELD=employeeNumber`、`W3_OAUTH2_EMAIL_FIELD=email`；前端不提供 W3 配置页、不保存 provider token 或客户端 secret。服务端保留且默认关闭的 `POST /api/auth/login/` 只供受控兼容/应急，前端永不展示或调用；`POST /api/auth/logout/` 和 `GET /api/me/` 交互保持不变。

> **上传**：「上传简历」弹窗含两类文件 **① 简历信息列表 .xlsx / .xls / .csv + ② 简历包 .zip**。普通用户入口只提供安全的增量更新；主数据 replace 使用更新/停用语义，不得删除候选人流程、反馈或审计历史。测试环境彻底清空不放在普通上传弹窗中。
> **上传即处理**：上传 Rule 运行 `Step1 查重/排序 → Step2 院校分类/准入 → Step3 岗位与分配前置检查`，其中 Rule 分支在独立岗位映射后完成专业审核与分配；上传 AI 同样运行 Step1–Step3，但 Step3 跳过 Rule 专业审核并冻结目标，再继续 `Step4 AI 深度筛选`。人工“处理简历”从 Step2 开始。岗位、部门和接口人独立维护，是 Step3 的基础数据，不再显示为编号步骤。异步 202 / eager 200、范围固化和页面非阻塞契约保持不变。
> **增量 + 冲突处理**：按 `normalized_name + normalized_phone` 归并候选人，按 `应聘ID` 幂等更新投递；低风险重复更新当前主记录，但不删除已反馈流程、分配尝试和历史快照；高风险重复进入导入错误清单。手机号缺失的候选人直接舍弃，不入库、不进入分配，并在导入结果中提示。“学历”列在后端规范化为大专/本科/硕士/博士，同文件同候选人取最高已识别值，空值或未知值不覆盖已有有效学历。
> **候选人聚合展示**：主列表以 `Candidate` 为行粒度，一名候选人只显示一行。单击候选人行直接打开详情，勾选框、表头筛选、列宽拖拽等控件点击不得误触发详情。HR/管理员详情展示手机号、最高学历及中文标签、最高学历专业、全部投递、志愿顺序、分配尝试、匹配/手动理由和反馈记录；接口人详情仅展示本人可见尝试及其关联投递，不返回手机号、其它志愿、其它尝试或 AI 决策。
> **当前志愿展示**：主列表仅展示当前有效志愿。Rule 原因文案清楚区分缺岗位、专业不匹配、缺二级部门、缺二级接口人；AI 模式 Step3 也展示岗位/部门/接口人缺口，但这些均为“处理完成”的业务结果，不标红为模型失败，且不调用 AI。只有模型超时显示失败。
> **简历状态**：简历库展示后端推导的八种统一状态，不覆盖导入文件中的原始“应聘状态”：待处理 `raw`、已归档 `archived`、待重新分配 `pending_reallocation`、待复核 `pending_review`、待下发 `pending_dispatch`、待业务反馈 `pending_screening`、通过 `screening_passed`、不通过 `screening_rejected`。当前有效尝试必须属于当前志愿且未取消；历史志愿 passed/rejected/cancelled 只在详情展示。只有任务提交或排队时仍为待处理；已有失败、需处理、AI 决策、历史尝试、归档或阻塞证据但无当前有效尝试时展示已归档，同时原因列保留具体问题。`classified / allocated` 不再兼容。
> **主表列与筛选**：主表删除“处理结果”列和同名表头筛选，只保留八种“简历状态”和精确“原因”筛选。稳定原因码除原有规则/AI 原因外增加 `job_mapping_ambiguous / internal_position_name_missing / job_hc_exhausted`；其中容量耗尽展示待重新分配，其它未形成有效尝试的结果展示已归档。原因列继续截断并用 Tooltip 展示说明，不用错误文本模糊匹配。任务中心仍可用 `processing_run_id + processing_result` 定位某次任务结果，但列表业务状态始终按八状态显示。
> **筛选、处理、下发与导出**：主列表支持现有候选人字段以及按上述 `allocation_source` 派生口径的分配来源、部门、二三级接口人和分配原因的表头筛选，不提供流程状态或分配状态筛选。任务中心跳转时，`processing_run_id + processing_result` 作为 ProTable 稳定外部参数与其它筛选相交；同页新增、切换或清除任务筛选都重新请求第一页，并关闭旧详情但保留页面勾选。常驻工具栏提供上传、处理、下发和撤销，结果报表入口已迁至 Dashboard；未选择候选人时仍显示“下发”，导出/删除等选中操作按现有滑入操作条展示。
>
> 「处理简历」始终打开同一个弹窗：先选择本次 Rule / AI 模式，再选择`当前选中（N）`或上述八种简历状态；`当前选中`始终手动勾选、`N=0` 时禁用，并与八种可多选状态互斥；任意状态都可重开。打开时冻结候选人 ID 和数量。当前选中提交的 scope 只含 `candidate_ids + force_reprocess=true`，成功后清空勾选；状态范围提交 `system_statuses + candidate_filters` 并继承当前表头和任务结果筛选。用户取消选择或当前选中处理成功之外的任务筛选切换均不清空勾选。弹窗通过 `GET /api/allocation-mode/` 读取 `default_mode / available_modes / ai_ready`，按 `default_mode=rule` 默认选择 Rule；AI 不可用时禁用并说明原因，提交时发送唯一 `mode` 且不发送 `modes`。旧状态或未知状态返回 400 时原样提示，绝不按全量任务继续。
> **结果报表**：简历库不再显示「导出结果报表」或日期弹窗；该动作迁到 Dashboard 右上角，详见 DashBoard 章节。简历组合导出与结果报表是两个独立能力，结果报表不打开属性选择弹窗。
> **简历预览与删除**：详情抽屉默认选中当前投递中有文件的简历；当前投递无文件时，自动回退到同候选人第一条有文件的投递，不改变当前志愿展示口径。投递志愿表不设预览列，用户单击志愿行即切换到该投递的简历；单击未关联简历文件的志愿时，预览区切换为该志愿的缺失提示，不保留上一份简历。前端通过鉴权 API 获取 PDF Blob 后用 PDF.js 渲染到 canvas，并读取预览响应头 `X-Resume-Filename` 展示原始文件名。无权限或越权时不展示预览和下载入口；PDF 渲染失败或非 PDF 文件时可下载原文件。详情删除不依赖前端预先判断是否存在受保护历史；用户点击后由后端统一校验，返回 409 时前端展示原始错误说明。批量删除逐条执行同一后端保护，并汇总成功与失败结果。
> **按上传记录撤销（目标设计，后端未实现）**：后端先解析每次上传影响的业务键，只为该候选人/投递范围保存覆盖 Candidate / Resume / ResumeProfile / CandidateWorkflow / AgentDispatchDecision / AssignmentAttempt / AssignmentHandoff 的独立快照及本次上传关联处理完成后的流程版本基线；“上传撤销记录”只展示当前 HR 自己的上传，管理员可查看全部。用户按选定上传记录执行撤销，同一记录仅可撤销一次；撤销时后端锁定该记录的全部候选人并校验版本，任一候选人存在后续变更即整体返回 `409`，前端不显示部分撤销成功。关联 ProcessingRun 未结束时同样禁用该记录的撤销并展示原因；已撤销的运行保留审计展示。

> 岗位、院校、部门接口人列表均使用表头筛选和列宽拖拽；筛选条件进入后端查询并与分页共同生效。岗位新增“工作职责”列和文本表头筛选；新增/编辑弹窗使用必填多行文本框展示并保存完整职责。岗位还支持主体、对外名称、职位名称、岗位族、部门、地点、学历、HC、是否发布等筛选，其中对外名称和职位名称使用支持拼音搜索的多选选择器，前端分别通过 `public_name_in`、`position_name_in` 提交所选值；页面并提供编辑和删除操作。岗位 Replace 继续复用现有导入弹窗、`POST /api/import/` 和“需求数量”列，不新增前端字段或数据库迁移：后端按招聘主体、二级部门、对外发布名称、内部职位名称、岗位类别的规范化业务键执行原子全量同步；唯一命中更新全部属性、HC 和完整专业明细并重新启用，未命中新建，文件外岗位停用。文件或数据库有重复键时前端展示整批失败且不得显示部分成功；已有 HC 快照不受停用影响。导入响应含 `job_responsibility_missing` 时以 warning 展示跳过数量和 Excel 行号；Replace 文件没有任何有效岗位（包括全部因缺职责被跳过）时，提示未更新且保留原岗位列表。删除岗位采用停用/失效语义，历史投递、分配尝试和任务容量快照仍可追溯。院校清单展示学校、院校标签和所在省份，拥有 `school.manage` 时显示新增按钮和行内编辑；弹窗从启用标签字典选择标签。接口人列表新增邮箱列和文本表头筛选，同时支持姓名、工号、部门、层级、是否可转派、是否启用筛选；拥有 `department.manage` 时显示新增、编辑和删除，新增/编辑弹窗要求有效邮箱并在提交前去空白、转为小写，只允许选择二级或三级部门并由部门层级确定接口人层级。保存后由后端同步账号用户名为工号、账号邮箱为接口人邮箱，并维护二级/三级接口人角色和启停状态；编辑工号或邮箱时同步绑定账号，不展示或筛选招聘主体归属/主体来源。
> 部门接口人样例文件包含“邮箱”列。导入缺邮箱、邮箱格式非法、同一邮箱对应多个工号，或与现有其他接口人冲突时，前端展示整批失败，不显示部分成功；邮箱由后端按小写规范化并与工号共同同步到账号。
> 升级时后端迁移会把已有绑定用户的非空邮箱回填到接口人；仍为空的历史接口人需在页面补录或重新导入有效邮箱，之后才能满足 W3 工号+邮箱双字段映射。
> **分页主表视口布局**：全站通过 `SmartDataTable` 承载的分页主表统一固定顶部功能栏和表头，页面滚动只发生在表格数据区域；分页栏固定在当前表格可视宽度的右下角并始终右对齐。分页栏保持透明，不增加白色底条、顶边框或阴影；组件按窗口、侧栏宽度、页头、页签和批量操作条动态计算表体高度。详情抽屉内 `pagination=false` 的投递、尝试和 AI 决策等内嵌表继续自然展开，不启用视口固定布局。
> 部门接口人 replace/清空重导时，本次文件中不存在的旧接口人及其绑定账号会同步停用；列表默认只展示启用接口人，可通过状态筛选查看停用接口人。单条“删除”操作采用清理语义：删除接口人并同步删除绑定用户，历史分配记录不删除，只通过快照字段展示原接口人信息。
> **字典化口径**：岗位类别来自 `JobCategory` 字典，院校标签来自 `SchoolTag` 字典，专业大类词表来自 `MajorCategory` + `MajorAlias`；字典项保留 `code + name` 或规范化名称，前端展示业务名称，导入/匹配优先使用 `code` 或规范化名称。
> **非目标院校预置**：院校标签字典预置启用 `NON_TARGET / 非目标院校`。院校清单外的学校在分类时始终写入该标签；清单内学校未配置标签时才使用启用默认标签，无默认标签时回退到该预置标签。院校列表可显示/维护清单内学校的标签，但不能把清单外学校误展示为默认标签。
> **院校标签准入规则**：配置项中维护 `SchoolTagRule`，规则允许标签通过 `SchoolTagRuleTag` 关联到 `SchoolTag`，并区分第一学历/最高学历两个作用域；另以 `SchoolTagRuleEducation` 保存允许最高学历多选集合。
> **招聘主体**：岗位和投递引用 `RecruitingEntity.code`，前端直接展示 GW / YLS 等主体编码；部门和部门接口人不建立“属于招聘主体”的关系。
> **省份口径**：`School` 只保存所在省份 `province`；系统不维护南北省份分区字典，南北归属仅在志愿排序规则运行时计算，不落库、不作为配置页维护项。
> **院校省份后台补全**：`/api/import/` 响应携带 `school_province_enrichment` 的 `not_requested / ai_unavailable / queued / queue_failed` 状态，其中 `queued` 时导入成功文案提示已提交后台补全。导入弹窗按导入响应立即结束并恢复页面操作，当前页面不轮询、不等待 AI 补全结果；失败不将已导入数据显示为导入失败，用户后续刷新院校列表时查看已落库的标准省份简称。

### 3) 候选人处理主流程（随上传/处理简历提交后台任务）
处理由两个动作触发，均创建**可共享的后台任务**：
- **上传简历**（简历库）→ 导入弹窗凭 `resume.import` 读取 `default_mode / available_modes / ai_ready`，默认选择 Rule；用户确认本次唯一 Rule / AI 模式后，上传请求以 `processing_mode` 创建一条运行；
- **处理简历**（简历库）→ 在处理弹窗选择本次 Rule / AI 模式，以唯一 `mode` 创建运行，从 Step2 院校分类/准入开始，不重复 Step1。

> AI 模式通过真实模型链路处理；未配置可用连接或调用异常时展示后端“需处理”原因和处置入口，只有 `llm_timeout` 展示为“失败”；不得展示 Rule 结果、固定置信度或元数据拼接结论。

```
候选人处理主流程：
  Step1 查重与志愿排序
    → Step2 院校分类及学历/院校准入
    → Step3 岗位与分配前置检查
    → Step4 AI 深度筛选与分配（仅 AI）

基础数据：岗位需求、部门、二/三级接口人独立维护
```
> Step2 完整生成并固化院校标签；Step3/Step4 不再修改。岗位需求和接口人应在处理前维护就绪。
> 前端提交 `/api/pipeline/run/` 或上传请求后，生产异步环境收到 `202 + processing_runs` 即恢复页面操作；本地 eager 模式同步完成后返回相同字段的 200。每次只创建本次选择模式的一条运行。拥有 `pipeline.view` 的用户通过侧栏独立「处理任务」页约每 2 秒轮询；管理员和 HR 默认拥有该权限，二级、三级接口人默认不展示该导航项。连接配置后续变化不改变已按提交时模式固化的任务。
> 多个 HR 可同时提交任务。提交范围与版本快照已由后端固化；同一候选人的自动任务会等待当前候选人处理租约释放。人工下发、转派、反馈或手动分配会推进流程版本并使在途自动任务令牌失效；版本或令牌不一致时任务显示 `skipped_manual_change`，安全跳过结果且不覆盖人工操作。

### 4) 简历库中的分配尝试
```
简历库                                [处理简历] [下发]
┌ 表头筛选: 来源、部门、接口人、候选人、投递岗位、分配原因
├──────────────────────────────────────────────────────────
│候选人│岗位│来源│二级接口人│三级接口人│分配原因（截断）│
│张三  │后端│规则│技术部接口人│平台组接口人│岗位与专业匹配… │
├ 勾选后滑入: 已选 N 项｜导出选中/当前筛选｜删除选中｜取消选择
└ 详情展示全部投递、历史尝试、AI 决策、反馈和简历预览
```
> **统一操作台**：简历库主表展示当前有效 `AssignmentAttempt` 的业务结果和实际来源；没有有效尝试但已自动处理过的 Rule/AI 业务归档、需处理、模型超时失败或规则阻塞结果按工作流策略展示来源；从未处理的待分配流程不展示来源。详情展示完整历史及每次尝试状态。HR 进行待复核确认、取消、转人工、单条/选中/筛选全部下发；二级接口人转派，并可在获授反馈权限时于转派前反馈；三级接口人在转派后反馈。分配原因统一读取 `match_reason`，主表截断显示并支持悬浮查看全文，Rule 和 AI 来源都保留审计。
> **AI 决策边界**：岗位精确映射是 Rule / AI 共享的独立确定性服务，不属于 Rule 专业策略。Rule 在映射后才执行专业大类词表和名称包含审核；AI 在映射后直接选择部门、接口人和 HC，不执行上述专业审核。该边界覆盖正式任务、直接处理、AI 重试和结果落库，因此 AI 页面、任务结果和原因筛选都不得出现新产生的 `major_not_matched`。AI 只处理 Step2/Step3 已通过的候选人，不判断学历、院校、志愿、岗位存在性、部门归属或接口人选择。历史决策仍可查看；已有待复核/待下发结果继续按原权限处置，重试入口还要求当前模型连接测试有效。
> **Rule 策略**：只处理当前有效志愿，按“同主体对外职位名称精确映射唯一内部职位 → 同主体内部职位岗位池 → 专业确定性匹配 → 二级部门 → 二级接口人 → HC 配额”生成待下发尝试；反馈未通过后才由工作流推进下一志愿。岗位未配置需求专业，或岗位需求专业为“专业不限 / 不限 / 不限专业”等通配表达时，不阻断自动分配。岗位配置非通配需求专业时，后端先用专业大类词表判断候选人最高学历专业与岗位需求专业是否同属大类；若大类无交集，或候选人/岗位任一侧未映射到启用大类，则再用专业名双向包含兜底。对外名称映射歧义、内部职位缺失、岗位/部门/接口人缺口分别展示稳定原因，不用包含关系猜测内部职位。每个任务冻结 `HC × 系数` 容量，并按候选人 ID 和最小 `(已用量 + 1) / 容量` 稳定选择岗位；容量耗尽时不生成尝试、不推进志愿，状态展示“待重新分配”。
> **AI 策略（当前实现）**：AI Step3 使用与 Rule 相同的内部职位精确映射、同主体岗位池和 HC 配额选择，但不做专业词表筛选。Agent 读取当前固定岗位名称、需求专业、工作职责和简历正文，评估专业实际方向、项目、实习、技能、职责覆盖度、补充优势与风险；工作职责最多发送清洗后的前 12,000 字符，按不可信业务数据处理并忽略其中的模型指令，只纳入既有 `job_requirement` 分项。初始激活 Prompt 为 `resume-screening-v2`，后续调用使用任务提交时冻结的已发布版本；五项评分权重不变，不增加独立职责评分。当前岗位上下文不发送学历要求，当前志愿只发送 `position_name`，不发送 Resume/应聘 ID、志愿序号或招聘主体标识。模型协议不含任何岗位/部门/接口人 ID，也不接受学历输出；普通 AI 分配使用 Step3 固定对象，形成待复核/待下发尝试时占用任务容量。Step2 学历/院校结论不由 AI 补写或覆盖。历史岗位缺少工作职责时仍允许 Rule 处理；选择 AI 时显示“需处理 / 岗位缺少工作职责”，并在 PDF 抽取和模型调用前结束本候选人。后台专项判断及其置信度、证据、配置和路由状态不在 AI 决策表格、详情、分配尝试、原因筛选或处理任务中展示；实际路由成功统一显示为普通 AI 自动分配，证据或目标不可用时后台继续普通 AI 结论。OCR、阈值和不回退 Rule 的既有交互保持不变。
> **AI 并发执行**：生产环境的 Step4 按候选人投递到独立 `ai` 队列并发处理；本地 SQLite + eager 模式仍串行同步执行。
> **分配尝试**：简历库主表支持来源、部门、接口人、候选人、投递岗位和分配原因筛选，不展示或筛选分配状态；详情保留尝试状态展示，但详情内嵌表不提供筛选器，并支持导出、下发、转派、反馈、查看详情和简历预览。接口人只看到本人数据范围内已下发或已转派的尝试，不展示 HR 待处理状态。
> **AI 复核操作**：HR 可在 `pending_review` 尝试详情中确认下发、取消或转人工处理；当前完整模型连接配置测试有效时还可重试 AI。分别调用 `confirm-review`、`cancel-review`、`transfer-to-manual` 和 AgentDecision `retry` 接口。取消后若没有其它活动尝试，简历库显示 `agent_no_recommendation` 归档；转人工时必须从该尝试的具体投递进入手动分配，不允许隐式换志愿。
> **待下发取消**：HR 可取消 `pending_dispatch` 尝试，调用 `POST /api/workflow-attempts/{id}/cancel/`；取消后刷新候选人当前状态和可执行操作。
> **AI 结果边界**：只有 `llm_timeout` 使用“失败”；岗位缺少工作职责、正文不可用、连接/认证、429、输出协议和固定引用失效显示“需处理”；学历/院校/岗位/部门/接口人等规则结果显示“处理完成”。后台专项证据或目标配置不可用时继续普通 AI，不形成可见错误。其它异常均不自动回退 Rule。
> **详情与预览**：分配尝试详情抽屉展示候选人、应聘ID、岗位、二级/三级接口人、状态、反馈备注等信息，并通过 `/api/workflow-attempts/{id}/resume-preview/` 在当前用户数据范围内获取 PDF Blob，再用 PDF.js 渲染到 canvas。接口人账号只能预览自己可见分配尝试的简历；越权尝试由后端返回 404/403 类错误，前端展示为不可预览且不提供下载入口。PDF 渲染失败或非 PDF 文件时，保留下载原文件入口。
> **导出**：主表勾选和当前筛选导出走 `/api/candidates/export/`，详情中的接口人单条导出走 `/api/workflow-attempts/export/`；所有入口先打开同一个 `ResumeExportModal`，从候选人、当前投递、岗位需求、分配反馈、状态与原因五组字段中勾选属性，支持全选、清空和恢复默认，未选任何字段时禁止提交。目录版本升级后删除 `processing_result`，读取浏览器历史时自动忽略该失效键；常用字段默认勾选，最近一次有效选择按用户写入 `localStorage`。前端以逗号分隔 `fields` 提交，后端按固定目录顺序生成列。
>
> 两个接口始终下载组合 ZIP，单条简历也不再直返原文件。ZIP 含 `简历库清单.xlsx` 和显式 `简历文件/` 目录项，即使没有可用简历也保留该空目录；仅有缺失时再含 `缺失简历文件清单.txt`。Excel 一名候选人一行。前端读取 `X-Export-Candidate-Count`、`X-Export-Count`、`X-Export-Missing`，提示候选人数、简历文件数和缺失数。手机号在字段目录中对 `resume.view` 或 `attempt.export` 用户均可选；接口人导出仍只基于本人可见尝试，不因选择手机号扩大数据范围。
> **HR 下发操作**：HR 可在详情中保留单条强制下发；拥有 `attempt.dispatch` 时，简历库工具栏常驻「下发」，不依赖是否已经勾选候选人。点击后在“当前选中”和“业务筛选”两种互斥范围中选择：当前选中在打开弹窗时冻结候选人 ID 和数量，`N=0` 时禁用；业务筛选只提供后端白名单允许的枚举多选项，不允许空范围。候选人维度批量接口只处理当前志愿的有效 `pending_dispatch`，其它状态跳过；前端按接口 `detail` 汇总展示下发、跳过和失败数量，单项失败不隐藏已经成功的下发。
> **下发、转派与反馈**：HR 将待下发尝试下发至二级部门接口人。详情抽屉的「提交反馈」按 `attempt.feedback`、当前接口人绑定和尝试状态计算，不写死角色：二级接口人在本人接收的 `dispatched_l2` 阶段可于转派前提交通过/未通过 + 可选备注；转派为 `assigned_l3` 后二级不再显示提交按钮，改由本人被转派的三级接口人提交。已反馈结果和备注继续只读展示，提交后锁定；无操作条件时不显示可提交按钮。
> **转派操作**：二级接口人在简历库本人可见候选人详情中使用「转派」，弹窗只列出当前二级部门下启用的三级接口人；转派后状态变为「已转派三级」，并记录转派历史。
> **手动强制分配**：HR 从具体应聘ID打开弹窗，先选择目标类型（二级接口人 / 三级接口人），再选择对应接口人。选择二级接口人时走普通下发与二级转派链路；直接选择三级接口人时，前端展示其父级二级部门：若只有一个有效二级接口人则自动补齐，若有多个则要求 HR 明确选择，确认后进入「已转派三级 / 待反馈」并展示两段转派历史。没有有效父级二级接口人时阻止提交并提示改选二级接口人。已通过候选人不可通过该入口再次强制分配；如需重开已通过候选人，使用简历库「处理简历」入口。
> **AI 专项配置与业务展示边界**：专项开关、阈值和目标接口人由「AI 模型连接 → AI 专项」页签配置；专项命中、置信度、证据、路由码和审计快照仍只在后端保留，不得出现在候选人列表/详情、分配尝试、处理原因、招聘分析或图表图例中。专项实际分配继续统一展示为 AI 自动分配。
> **归档候选人**：归档原因、志愿概览和从具体应聘ID发起手动强制分配统一合并到简历库；不再作为 HR 独立菜单入口。
> **角色差异**：二级接口人仅看到已下发给自己的尝试，可导出、查看反馈和转派给本部门三级接口人；获授 `attempt.feedback` 时可在转派前反馈。三级接口人仅看到转派给自己的尝试，获授 `attempt.feedback` 时可提交反馈。反馈权限不扩大本人接收/本人被转派的数据范围；接口人均无 HR 下发、手动分配、二级接口人筛选和模式开关。

### 5) DashBoard（招聘分析）

- 路由 `/analytics` 和侧栏置顶「DashBoard」导航项由 `analytics.view` 控制；管理员和 HR 默认可见并以该路由作为登录首页，二级/三级接口人默认不可见且按权限进入首个可访问页面；越权路由跳回有权默认页，接口仍以后端 403 为准。
- 页面采用与全站一致的浅灰背景、低阴影白卡和靛青主色。页面不设置独立筛选栏，只在数据展示区左上角内嵌时间区间和二级部门两个筛选器；右上角在用户同时拥有 `resume.view` 时显示「导出结果报表」，否则只保留数据截至时间。首屏展示候选人数、分配、下发、反馈、通过五张 KPI 卡，图标固定在卡片右上角，不展示按日趋势图或候选人明细表。
- 看板界面只开放时间区间和二级部门筛选；未指定日期时后端默认最近 30 天，页面显示当前实际 cohort 和 `data_as_of`。接口为兼容既有调用仍可接受招聘主体、岗位、院校标签、最高学历和分配来源参数，但当前页面不展示这些选择器。
- 「导出结果报表」不打开日期或属性选择弹窗，直接读取后端最近一次成功加载并已生效的 `data.filters.date_from / date_to / department_id`，分别映射为 `imported_after / imported_before / department_id` 调用 `/api/resumes/result-report/`；用户在筛选控件修改但尚未点击查询的草稿值不能提前影响导出。日期未生效时按钮禁用，下载仍为独立 `.xlsx`，不并入简历组合 ZIP。
- 结果报表的“部门汇总”和“简历明细”统一按八种新简历状态输出；Dashboard 卡片中的“已生成分配”、分类、下发、反馈等仍是独立分析指标，名称和统计口径保持不变。
- 五张核心卡依次展示候选人数、已生成分配、已下发、已反馈和已通过；投递记录/已分类收入候选人数卡辅助信息，已归档收入已通过卡辅助信息。招聘概览使用“分配来源环图 + 候选人/分配/下发/反馈/通过横向流程柱图 + AI 建议环图”的三列布局。
- 页面继续展示导入到分配/下发/反馈的平均耗时、岗位/二级部门排行、院校标签/学历以及 AI 错误、归档原因和未通过原因。岗位和部门使用横向柱图；来源、建议、标签、学历和原因使用带数量、占比和 HTML 图例的环图，类别过多时合并为“其他”。AI 错误为空时只说明当前范围未记录错误，不宣称模型服务整体健康。
- 所有数字来自 `GET /api/analytics/recruitment-overview/` 的后端聚合结果；前端不请求候选人明细、不自行合并状态。图表使用 `chart.js` + `react-chartjs-2`，只注册环图、横向柱图、坐标轴、Tooltip 和 Legend 所需模块。后端响应中的 `trend` 字段暂保留供旧客户端兼容，当前页面不渲染该字段。空数据、接口失败和重新加载均提供明确状态。
- 岗位和部门排行直接展示接口返回的当前有效投递/最新非取消分配尝试部门快照口径；前端不再用当前岗位、部门主数据重算或覆盖历史标签。Dashboard 部门筛选按 cohort 中每条投递的最新非取消尝试生效；结果报表接收同一已生效部门 ID，但由报表接口按候选人当前志愿的最新非取消尝试重新过滤和输出。接口结果缓存 5 分钟，页面必须展示 `data_as_of`，不得把页面刷新时间伪装为数据统计时点。

> **部署、备份与恢复边界**：静态运行参数由部署模板预置，浏览器端不提供 `.env` 初始化、备份路径、密钥或 W3 配置页面。首次运行部署脚本只生成三项独立密钥和权限为 `600` 的 `.env`，保留 `.env.example` 的 `W3_OAUTH2_ENABLED=False` 安全占位，然后在任何 Docker 变更前退出；运维必须补齐 W3 参数、把开关改为 true，再第二次运行真正部署。W3 是可用部署的必要条件，`validate-w3-env.sh` 对 disabled、缺失或非法开关直接失败，不再跳过。必填变量为 client id、authorize/token/userinfo/redirect 地址、工号/邮箱字段路径、客户端认证方式、请求超时和事务 TTL；字段路径默认 `employeeNumber / email`，basic/post 要求 secret，none 可空，scope 按提供方要求；本地登录关闭、前端回跳 `/login` 和 PKCE 开启使用安全默认。redirect URI 必须为 HTTPS、精确指向 `/api/auth/w3/callback/` 且不带 params/query/fragment；前端回跳必须指向本站 `/login`，可带非保留固定 query，但不得预置 `oauth2` / `oauth2_error`。错误只在终端输出键名和稳定说明，不显示 secret；`verify.sh` 会重复同一校验。`BACKUP_TARGET_PATH` 默认 `/mnt/smart-resume-filter-backups`，必须是已存在、可写的绝对路径。检测到已有容器或数据卷时必须恢复原 `.env`，不得重新生成。备份调度、restic 保留、显式确认恢复（覆盖生产库时二次确认）和隔离演练属于部署运维能力，不在前端新增菜单或恢复按钮；浏览器端不得接收或保存数据库、restic、`DJANGO_SECRET_KEY` 等凭据。
>
> **正式 HTTPS 入口**：生产默认在 Compose frontend 前使用企业网关、WAF、Nginx 或 Caddy 终止 TLS。外层代理把所有路径统一转发到 frontend 暴露端口；frontend 容器内置 Nginx 返回静态页面，并把 `/api` 转发到 `backend:8000`。外层代理不得把 `/api` 直接转发 backend，也不得暴露可绕过 frontend 的 backend 端口。代理必须保留 `Host`，设置 `X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto=https`；同机反代建议 `FRONTEND_BIND=127.0.0.1`、`BACKEND_BIND=127.0.0.1`，异机网关只通过受控内网/防火墙访问 frontend。
>
> `DJANGO_ALLOWED_HOSTS` 填生产域名，`W3_OAUTH2_REDIRECT_URI` 必须与 `https://<生产域名>/api/auth/w3/callback/` 逐字一致。生产验收从真实客户端网络检查 HTTPS 域名、证书、HTTP→HTTPS 跳转、`/api/auth/w3/status/` 和完整 W3 回调；仅访问服务器 IP、`IP:5173` 或容器健康检查不算完成。

前端权限生效：
- 登录后调用 `/api/me/`，获得 `permissions`、`roles`、`contact`、`data_scope`。
- ProLayout 菜单按权限码过滤；页面按钮按权限码控制显示和禁用态。菜单的展开分组由前端显式维护，路由跳转和子页选择只影响选中态，不清空其它已展开分组。
- 无权限路由展示「无权限」页面；接口请求失败仍以后端 403 为准。
- W3 OAuth2 是唯一前端登录入口，只有 UserInfo 顶层 `employeeNumber` 和 `email` 同时命中同一个启用账号才完成登录；`tenantId`、`uuid`、`globalUserID` 不参与前端或后端账号匹配。完成一次性 Token 领取后复用同一 `RoleContext`、`localStorage` 和 `/api/me/` 消费口径。服务端本地密码 API 默认关闭，前端不展示、不调用，即使运维临时开启也不改变页面入口。

## 三、角色与可见性

权限体系采用 RBAC。前端不再写死角色能力，而是基于 `/api/me/` 返回的权限码、角色、接口人绑定和数据范围动态控制菜单、路由和按钮：

| 区域 | 默认角色权限 | 二级接口人 | 三级接口人 |
|------|-------------|------------|------------|
| 简历库 — 候选人列表和本人分配数据 | 全量 | 仅本人接收 | 仅本人被转派 |
| 简历库 — 上传 / 撤销 / 删除 / 处理简历 | ✓ | ✗ | ✗ |
| 简历库 — 导出 / 反馈查看 | ✓ | ✓（本人范围） | ✓（本人范围） |
| 简历库 — 单条/批量/全部下发 / 手动强制分配 | ✓ | ✗ | ✗ |
| 简历库 — 二级转派给三级接口人 | ✗ | ✓ | ✗ |
| 简历库 — 提交通过/未通过反馈 | ✗ | 获授 `attempt.feedback` 后仅转派前 | 获授 `attempt.feedback` 后仅本人被转派 |
| AI 模型连接 — 模型连接、AI 运行参数、AI 专项与测试 | 拥有 `settings.manage_ai_connection` 的角色（管理员默认拥有） | 未授予时 ✗ | 未授予时 ✗ |
| Prompt 管理 — 五模块草稿、真实测试、发布、历史恢复 | 拥有 `settings.manage_ai_connection` 的角色（管理员默认拥有） | 未授予时 ✗ | 未授予时 ✗ |
| 配置项 — 分配参数 | 拥有 `settings.manage_config` 的角色（管理员默认拥有） | 未授予时 ✗ | 未授予时 ✗ |
| 部门接口人 — WeLink 通知开关 | 拥有 `department.manage` 的角色（管理员 / HR 默认拥有） | 默认 ✗ | 默认 ✗ |
| 处理任务 — 页面与共享记录 | ✓（管理员 / HR，`pipeline.view`） | 默认 ✗ | 默认 ✗ |
| 招聘分析 | ✓（管理员 / HR，`analytics.view`） | ✗ | ✗ |
| 业务规则配置 | 按权限码授权 HR / 管理员 | ✗ | ✗ |

## 四、目标页面清单与当前状态
0. 登录页：路由 `/login`，无回调参数时读取 `/api/auth/w3/status/` 并在 `ready=true` 时自动跳转 W3，不展示 W3 按钮或本地账号表单；W3 回跳成功后调用 `/api/auth/w3/complete/` 一次性领取项目 Token，错误码、状态请求失败或配置未就绪时只展示最小状态/重试界面，URL 不携带 Token，不接受任意回跳参数。

2. 处理任务：路由 `/processing-tasks`，独立展示共享任务、阶段、耗时、结果、手工刷新、候选人跳转与取消审计；`pipeline.view` 控制页面和记录查看，`pipeline.run` 控制取消。

4. 岗位需求、院校清单、部门接口人：主数据维护、导入、表头筛选和列宽拖拽；岗位需求支持编辑和删除；院校清单支持新增/编辑学校名称、院校标签和所在省份；部门接口人展示并筛选邮箱，新增/编辑时邮箱必填，由后端同步账号工号、邮箱、接口人角色和启停状态；部门接口人页承载 WeLink 通知开关，只有 `department.manage` 可操作。
5. 配置项与 AI 模型连接：配置项维护院校标签、院校准入、专业词表等业务规则，并为 `settings.manage_config` 提供只含 HC 系数的“分配参数”页签，不再提供任意系统参数编辑；拥有 `settings.manage_ai_connection` 的角色在独立「AI 模型连接」页通过“模型连接”“AI 运行参数”“AI 专项”三个页签维护连接、运行参数及专项开关/阈值/目标链路。连接测试成功后，上传和处理简历时才可选择 AI 模式；专项内部命中、证据和审计不进入业务页面。

7. 用户权限：维护用户、角色、权限绑定和接口人绑定关系，支撑 RBAC 前端配置。
