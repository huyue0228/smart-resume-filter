# 智能简历筛选系统 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 2026-07-31 前交付一套内网可部署的校招简历 5 步处理系统（查重排序 / 岗位分类 / 院校分类 / 需求录入 / 简历分配），前后端 + 一键部署。

**Architecture:** FastAPI 后端以「批次」为单位运行 5 步流水线，Celery 异步执行 + 进度反馈；规则与 LLM 经统一适配层可配置切换；React/Ant Design Pro 前端做操作与多角色工作台；PostgreSQL + MinIO 存储；Docker Compose 内网部署。

**Tech Stack:** Python 3.11 / FastAPI / SQLAlchemy + Alembic / Celery + Redis / PostgreSQL / MinIO / React + Ant Design Pro / OpenAI 兼容 LLM 客户端 / Docker Compose。

**对应设计文档：** `docs/superpowers/specs/2026-06-23-smart-resume-filter-design.md`

## Global Constraints

- 交付截止：**2026-07-31**。
- 部署：内网/私有，Docker Compose 一键起全栈；简历含隐私，数据默认不出内网。
- 单批次规模：约 3 万条，所有流水线步骤异步执行 + 进度反馈。
- 智能策略：每步规则 / LLM 可配置开关；LLM 经 OpenAI 兼容协议（base_url/key/model 可配），失败回退规则或标"待人工确认"，不阻断流程。
- 业务定义：主体 = GW/YLS；同一同学 = 姓名+手机号；南北 = 可配置省份清单；院校标签 = 数据驱动查目标院校清单（含简称 LLM 模糊识别）。
- 简历ID 在表格行与原始文件名一一对应，上传时校验。

## 一·补2 模块/接口边界（用于分工，每块可独立开发与测试）

| 模块 | 职责 | 关键接口/产物 | 依赖 |
|---|---|---|---|
| `auth` | 登录、JWT、RBAC | `get_current_user()`、`require_role()` | DB |
| `batch` | 批次生命周期、步骤状态机 | `Batch` 模型、批次 CRUD API | DB |
| `ingest` | Excel 导入校验、简历ID↔文件比对、MinIO 存取 | `import_resumes()`、`validate_table()`、`presign_download()` | DB/MinIO |
| `mappings` | 4 张映射/配置表导入与管理 | 各表 CRUD、版本化读取 | DB |
| `pipeline.core` | 步骤统一抽象、异步任务、进度 | `Step` 接口：`run(batch, config)→Result`、进度上报 | Celery/Redis |
| `pipeline.step1..5` | 五步业务逻辑（纯函数为主） | 各 `Step` 实现 + 单测 | core/mappings |
| `llm` | OpenAI 兼容适配、开关、重试、缓存、审计 | `complete()`、`match_school()`、`match_job()` | 外部端点 |
| `allocation` | 步骤5 筛选+分配引擎+下发 | `allocate()`、`Assignment` 产物 | demand/接口人 |
| `frontend.*` | 各页面，按上面 API 契约对接 | 页面 + API client | 后端 OpenAPI |

**接口先行原则：** W1 先把 OpenAPI 契约和 `Step`/`llm` 接口签名定下来，前端、流水线、LLM 三条线即可并行，互相用 mock 对接。

## 一·补4 待团队拍板的技术决策（讨论重点）

- **D0 团队规模与分工认领**：几人？谁认领 A/B/C/D 轨道？决定能否按 6 周并行排期。
- **D1 单一同学跨主体识别口径**：姓名+手机号确定；手机号缺失/格式不一（带区号、空格）如何归一化？是否需姓名+身份证兜底？
- **D2 "专业匹配"定义**：规则态用什么字段/词表匹配？LLM 态的判定标准与阈值。
- **D3 "同类型/相似岗位"判定**：步骤5 同比例分配里"同类型"以岗位类别标签为准，还是更细？
- **D4 LLM 端点形态**：内网已有大模型网关吗？模型、并发、限流、成本上限？（影响 B5 截止日与缓存策略）
- **D5 数据隐私合规**：脱敏在导入前还是系统内做？原始简历下载是否需水印/审计留痕到人？
- **D6 重跑语义**：某步改了映射表重跑，是否级联使下游步骤失效？默认"本步覆盖、下游需重跑"。
- **D7 前端框架终选**：React+AntD Pro vs Vue+Element Plus（按团队熟悉度，下午定）。

## 四、风险与缓解

- **业务数据/LLM 端点延期**（最大风险）：按第二节倒排日盯进度；LLM 端点未就绪时先以规则态交付，LLM 作为可开启增强，不阻断主线。
- **规则口径反复**：每步产出即让业务确认（B7），避免 W5 集中返工。
- **真实数据质量差**（脏数据、校名不规范）：导入校验 + 错误行汇总 + 模糊识别 + "待人工确认"兜底。
- **工期紧**：W2–W4 为强并行（后端流水线 / 前端页面 / LLM 模块可分头推进），必要时前端用 AntD Pro 现成组件压缩工时；LLM 高级匹配、性能极致优化列为可降级项。

## 五、降级预案（若工期吃紧）

按优先级保主线，以下可后置到交付后迭代：LLM 专业语义匹配（步骤5）、需求录入的 LLM 辅助结构化、更大规模极致性能调优、精细化看板统计。**五步规则态全链路 + 内网部署为不可降级的交付底线。**
