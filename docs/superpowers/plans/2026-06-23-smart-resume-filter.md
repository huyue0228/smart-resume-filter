# 智能简历筛选系统 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 2026-07-31 前交付一套内网可部署的校招简历 5 步处理系统（查重排序 / 岗位分类 / 院校分类 / 需求录入 / 简历分配），前后端 + 一键部署。

**Architecture:** 后端优先、核心先行——先把五步简历处理流水线做成可独立运行的纯逻辑（Excel 进 / Excel 出，脚本与测试驱动），验证业务规则；再服务化（FastAPI + PostgreSQL + Celery 异步），最后做上传 / 文件存储 / 鉴权 / 前端 / 部署。规则与 LLM 经统一适配层可配置切换。

**Tech Stack:** Python 3.11 / FastAPI / SQLAlchemy + Alembic / Celery + Redis / PostgreSQL / MinIO / React + Ant Design Pro / OpenAI 兼容 LLM 客户端 / Docker Compose / pandas + openpyxl。

**对应设计文档：** `docs/superpowers/specs/2026-06-23-smart-resume-filter-design.md`

## Global Constraints

- 交付截止：**2026-07-31**。
- 部署：内网/私有，Docker Compose 一键起全栈；简历含隐私，数据默认不出内网。
- 单批次规模：**约 3 万条**，所有流水线步骤异步执行 + 进度反馈。
- 智能策略：每步规则 / LLM 可配置开关；LLM 经 OpenAI 兼容协议（base_url/key/model 可配），失败回退规则或标"待人工确认"，不阻断流程。
- 业务定义：主体 = GW/YLS；同一同学 = 姓名+手机号；南北 = 可配置省份清单；院校标签 = 数据驱动查目标院校清单（含简称 LLM 模糊识别）。
- 简历ID 在表格行与原始文件名一一对应，上传时校验。

## 一·补2 模块/接口边界（用于分工，每块可独立开发与测试）

| 模块 | 职责 | 关键接口/产物 | 阶段 |
|---|---|---|---|
| `data.loader` | 直接读/写 Excel（pandas），结构化为内部数据 | `load_resumes()`、`export_result()` | W0 |
| `models` | 数据模型定义（先类型/Pydantic，后落 DB） | `Resume`、`Batch`、映射表、`Demand`、`Assignment` | W0 |
| `pipeline.core` | 步骤统一抽象、进度上报 | `Step` 接口：`run(data, config)→Result` | W1 |
| `pipeline.step1..5` | 五步业务逻辑（纯函数为主，可单测） | 各 `Step` 实现 + 单测 | W1–W2 |
| `llm` | OpenAI 兼容适配、开关、重试、缓存、审计 | `complete()`、`match_school()`、`match_job()` | W2 |
| `allocation` | 步骤5 筛选+分配引擎+下发 | `allocate()`、`Assignment` 产物 | W2 |
| `api` | FastAPI 路由、批次编排、步骤触发 | OpenAPI 契约 | W3 |
| `persistence` | SQLAlchemy + Alembic，批次/结果落库 | repository 层 | W3 |
| `tasks` | Celery 任务、进度模型 | 任务启动/进度/重试 | W3 |
| `ingest` | 上传、MinIO、简历ID↔文件比对、导入校验 | `import_resumes()`、`presign_download()` | W4 |
| `auth` | 登录、JWT、RBAC | `require_role()` | W4 |
| `frontend.*` | 各页面 + 工作台 | 页面 + API client | W4（W3 契约定后起步） |

**接口先行：** W2 末定 OpenAPI 草案与 `Step`/`llm` 签名，前端、服务化两条线即可并行对接 mock。

## 一·补4 待团队拍板的技术决策（讨论重点）

- **D0 团队规模与分工认领**：几人？谁认领 A/B/C/D 轨道？
- **D1 单一同学识别口径**：姓名+手机号确定；手机号缺失/格式不一（区号、空格）如何归一化？是否需姓名+身份证兜底？
- **D2 "专业匹配"定义**：规则态用什么字段/词表？LLM 态判定标准与阈值。
- **D3 "同类型/相似岗位"判定**：步骤5 同比例分配中"同类型"以岗位类别标签为准还是更细？
- **D4 LLM 端点形态**：内网已有大模型网关吗？模型、并发、限流、成本上限？（决定 B5 能否在 W2 前就绪）
- **D5 数据隐私合规**：脱敏在导入前还是系统内？原始简历下载是否需水印/审计到人？
- **D6 重跑语义**：改了映射表重跑，是否级联使下游失效？默认"本步覆盖、下游需重跑"。
- **D7 前端框架终选**：React+AntD Pro vs Vue+Element Plus（按团队熟悉度）。

## 三、开发阶段与任务分解

> 任务 = 可独立验收的最小单元，执行时由 subagent-driven-development 展开为 TDD 步骤（先写失败测试 → 实现 → 通过 → 提交）。各任务默认继承「Global Constraints」。

### 阶段 0（W0, 06/23–06/27）脚手架 · 数据模型 · 数据契约

- [ ] T0.1 后端仓库结构与依赖：`backend/`（FastAPI + uv/poetry，含 pandas/openpyxl/pydantic）、`templates/`、`deploy/`、`tests/`。
- [ ] T0.2 数据模型（先 Pydantic/类型，暂不落 DB）：`Resume`、`Batch`、四张映射/配置表、`Demand`、`Assignment`。
- [ ] T0.3 `data.loader`：用 pandas 直接读样例 Excel → 内部结构；`export_result()` 写回 Excel。
- [ ] T0.4 **数据契约**：定稿 6 份 Excel 模板（表头+字段类型+必填+示例行）+ 字段说明文档（交付 B1）。
- [ ] T0.5 测试脚手架：pytest + 构造样例数据 fixtures。
- [ ] **M0 验收：** 能用 loader 读入样例 Excel 并打印结构化数据；模板冻结发给业务。

### 阶段 1（W1, 06/30–07/04）核心流水线（上）：步骤抽象 + 步骤1、2

- [ ] T1.1 `pipeline.core`：`Step` 抽象（`run(data, config)→Result`）、进度回调、步骤串接 runner。
- [ ] T1.2 步骤1 查重+志愿排序：姓名+手机号聚合；主体内按时间标第一/二志愿；跨主体按南北规则排第一~四志愿；户籍缺失回退学校所在地。单测覆盖边界。
- [ ] T1.3 步骤2 岗位分类：投递岗位→岗位类别映射打标签；未命中标"待确认"（为 LLM 预留）。单测。
- [ ] T1.4 端到端脚本：读样例 Excel → 步骤1→2 → 导出结果 Excel。
- [ ] **M1 验收：** 样例数据上前两步规则跑通、导出正确清单；业务确认口径。

### 阶段 2（W2, 07/07–07/11）核心流水线（下）：步骤3、4、5 + LLM

- [ ] T2.1 `llm` 适配层：OpenAI 兼容客户端，base_url/key/model 配置化，超时/重试/失败回退、调用审计、每步开关、结果缓存。mock 测试。
- [ ] T2.2 步骤3 院校分类：第一/最高学历按目标院校清单规则匹配打标签。
- [ ] T2.3 步骤3 **校名简称模糊识别（LLM）**：规则未命中→LLM 归一化标准校名，带置信度，低置信标"待确认"，命中缓存；LLM 关闭回退规则。单测 + mock LLM。
- [ ] T2.4 步骤2 LLM 岗位模糊匹配兜底（复用 T2.1）。
- [ ] T2.5 步骤4 需求录入：解析需求汇总表→结构化需求表（部门/岗位/HC/目标院校/专业），可选 LLM 辅助结构化。
- [ ] T2.6 步骤5 简历分配：筛选(待处理∧第一志愿∧符合目标院校) + 分配引擎（最大HC×5 可配；志愿优先→专业匹配→同类型同比例分配）+ 下发对象产物。单测覆盖同比例/边界。
- [ ] T2.7 全链路脚本：读 Excel → 五步 → 导出各步结果 + 分配结果 Excel。
- [ ] **M2 验收：** 五步全流程后端跑通（Excel 进→Excel 出），业务确认全部口径。

### 阶段 3（W3, 07/14–07/18）服务化：API + 持久化 + 异步

- [ ] T3.1 持久化：SQLAlchemy 模型 + Alembic 迁移，把 W0 数据模型落 PostgreSQL；repository 层。

- [ ] T3.4 FastAPI 路由：触发各步骤、查进度、取结果、导出；OpenAPI 契约定稿。
- [ ] T3.5 导入校验正式化：表头/必填校验 + 错误行汇总（不中断整批）。
- [ ] T3.6 前端骨架起步（按 OpenAPI mock）：AntD Pro 布局、路由、API client。
- [ ] **M3 验收：** 通过 API 异步触发五步、查进度、取/导出结果；数据落库。

### 阶段 4（W4, 07/21–07/25）外壳：上传 · 文件 · 鉴权 · 前端 · 工作台

- [ ] T4.1 上传 + MinIO：简历库表格 + 原始文件上传，受控下载（预签名）。

## 四、风险与缓解

- **业务数据/LLM 端点延期**（最大风险，因核心前置而更突出）：按第二节倒排日盯进度；样例数据先行，真实数据滚动补充；LLM 端点未就绪时步骤3/4/5 先以规则态开发，LLM 作为可开启增强。
- **规则口径反复**：每步产出即让业务确认（B7，W1 起），避免后期返工。
- **真实数据质量差**（脏数据、校名不规范）：导入校验 + 错误行汇总 + 模糊识别 + "待人工确认"兜底。
- **前端工期压缩到 W4**：W3 定 OpenAPI 后前端即并行起步；内部工具 UI 用 AntD Pro 现成组件保持精简。

## 五、降级预案（若工期吃紧）

按优先级保主线，以下可后置到交付后迭代：LLM 专业语义匹配（步骤5）、需求录入的 LLM 辅助结构化、更大规模极致性能调优、精细化看板统计。**五步规则态全链路 + 内网部署为不可降级的交付底线。**
