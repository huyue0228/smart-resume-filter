# 简历库工作流合并优化方案

> 更新日期：2026-07-10
> 状态：历史优化记录，核心结论已同步到 `需求描述.md`、`前端设计.md`、`后端设计.md`、`数据库设计.md`。本文不再作为需求、字段、API 或页面实现的 source of truth；存在差异时以四份核心设计文档为准。

## 一、优化目标

本次优化把 HR 视角下重复的候选人级页面收敛到「简历库」：

- 简历库成为候选人主控台，统一展示候选人基础信息、当前志愿、当前应聘ID、当前投递、岗位部门、流程状态、分配理由和归档理由。
- 「候选人工作流」和「归档候选人」不再作为 HR 的独立候选人级列表入口；相关信息合并到简历库列表和详情抽屉。
- 「分配尝试」继续保留为接口人处理和 HR 下发、转派、反馈、导出、预览的操作台。
- 当当前志愿已经匹配到岗位和二级部门，但没有可用二级接口人时，系统停留在当前志愿，不自动切换到下一志愿，也不把候选人归档。

## 二、核心原则

- **候选人主视图唯一**：HR 查候选人的入口应是简历库，避免同一候选人在简历库、工作流、归档候选人三个页面重复展示。
- **流程原因可解释**：列表要直接看到“为什么停在这里”，原因字段统一承载分配理由、归档理由和主数据缺口说明。
- **状态机不掩盖主数据问题**：找不到可用二级接口人属于主数据维护缺口，不代表当前志愿不合适，不应推进下一志愿。
- **接口人操作台保持稳定**：二级/三级接口人仍只处理分配尝试，不进入简历库；数据范围和权限边界不因 HR 页面合并而放松。
- **可扩展而不过度抽象**：为流程阻塞原因补充清晰的模型字段，列表展示由后端 presenter 统一生成；不新增复杂报表模型，等原因统计或全文搜索变复杂后再考虑派生表。

二级/三级接口人：

- 简历分配
  - 分配尝试

### 页面职责

| 页面 | 保留职责 | 调整点 |
| ---- | -------- | ------ |
| 简历库 | 候选人聚合、上传、撤销、处理简历、筛选、导出、详情、预览、手动强制分配 | 增加岗位部门、流程状态、原因；合并工作流和归档候选人信息 |

## 四、简历库列表字段

简历库主列表以 `Candidate` 为一行，建议字段如下：

| 字段 | 来源 | 说明 |
| ---- | ---- | ---- |
| 姓名 | `Candidate.name` | 支持姓名、全拼、拼音首字母筛选 |
| 手机 | `Candidate.phone` | 支持筛选 |
| 最高学历专业 | `Candidate.highest_major` | 不从投递岗位反推 |
| 当前志愿 | `CandidateWorkflow.current_rank` 或当前投递 `volunteer_rank` | 展示当前有效志愿 |
| 应聘ID | 当前投递 `Resume.apply_id` | 解决工作流页中应聘ID为空的问题 |
| 当前主体 | 当前投递 `Resume.entity` | GW / YLS 等主体编码 |
| 当前投递 | 当前投递 `Resume.position_name` | 当前有效投递岗位 |
| 岗位类别 | 当前投递 `Resume.job_category` | 分类结果 |
| 岗位部门 | 当前 workflow/current_resume 下最新非取消尝试的二级部门，或当前投递匹配岗位所属二级部门 | 用于定位业务部门和主数据缺口 |
| 系统简历状态 | 后端推导状态 | 待处理、已分类、已分配、待筛选、筛选通过、筛选不通过 |
| 流程状态 | `CandidateWorkflow.status` | pending / in_progress / passed / archived |
| 原因类型 | 后端派生枚举 | archive / assignment / block / classification / none |
| 原因 | 后端派生文案 | 归档理由、分配理由、阻塞原因或分类理由 |

岗位部门取值规则：

1. 如果当前流程已通过，优先使用 `passed_attempt` 的二级部门。
2. 否则取当前 `workflow.current_resume_id` 下最新一条非 `cancelled` 的 `AssignmentAttempt.department_name_snapshot` / `department.name`。
3. 如果当前流程已归档且没有当前投递下的有效尝试，使用当前投递匹配岗位所属二级部门。
4. 不使用历史志愿上的 rejected/cancelled 尝试覆盖当前志愿展示。

原因字段拆成两个 API 字段：

- `reason_type`：稳定枚举，用于表头筛选和后端分页前过滤。
- `reason_text`：人类可读文案，用于列表展示和导出。

原因取值优先级：

1. `workflow.status=archived`：`reason_type=archive`，显示 `archive_detail`，没有 detail 时显示 `archive_reason`。
2. 当前流程存在非终态阻塞原因：`reason_type=block`，显示 `block_detail`，没有 detail 时显示 `block_reason`。
3. 当前 `workflow.current_resume_id` 下存在最新非 `cancelled` 的 `AssignmentAttempt`：`reason_type=assignment`，显示 `match_reason`；手动分配可补充 `manual_reason`。
4. 当前投递完成分类但未生成尝试：`reason_type=classification`，显示 `Resume.category_reason`。
5. 以上都没有：`reason_type=none`，显示 `-`。

## 五、当前志愿停留规则

自动分配处理当前志愿时，按以下顺序判断：

1. 院校准入不通过：归档。
2. 当前志愿未匹配岗位或专业不通过：可继续尝试下一志愿。
3. 当前志愿匹配岗位，但岗位没有有效二级部门：本次优化不改变现有口径，仍按 `department_not_found` 进入归档；后续如要把部门缺失也改成阻塞态，需单独调整状态机和文档。
4. 当前志愿匹配岗位和二级部门，但没有可用二级接口人：不创建分配尝试，不归档，不切换下一志愿；流程保持 `in_progress`，当前志愿保持不变，并写入 `block_reason=contact_not_found`、`block_detail=当前志愿已匹配岗位和二级部门，但二级部门下没有可用二级接口人`。
5. 当前志愿匹配到二级接口人：创建 `pending_dispatch` 或 `pending_review` 等分配尝试。
6. 三级反馈未通过：这是业务筛选结果，系统才进入下一志愿；志愿耗尽后归档为全部志愿未通过。

这个规则的核心判断是：岗位/专业不匹配说明当前志愿不适配，可以继续看下一志愿；缺二级接口人说明当前志愿适配但主数据不完整，应先修主数据或人工处理当前志愿。

## 六、后端设计边界

候选人列表 API 继续使用 `/api/candidates/`，新增或补齐展示字段：

- `current_apply_id`
- `current_position_name`
- `current_entity`
- `current_job_category`
- `workflow_status`
- `job_department_name`
- `reason_type`
- `reason_text`

筛选参数建议补齐：

- `current_apply_id`
- `job_department_name`
- `workflow_status`
- `reason_type`

`CandidateWorkflow` 增加非终态阻塞字段：

- `block_reason`：稳定枚举，第一版至少包含 `contact_not_found`，用于表示当前志愿不能继续自动生成尝试但也不应归档。
- `block_detail`：人类可读说明，记录具体岗位、部门和缺口上下文。

`archive_reason/archive_detail` 只表示终态归档原因；`block_reason/block_detail` 只表示 `status=in_progress` 下的待处理阻塞原因。状态机重新生成有效尝试、手动强制分配或流程归档/通过时，应清空 `block_reason/block_detail`。

列表展示使用一个后端 presenter/helper 统一生成 `job_department_name`、`reason_type` 和 `reason_text`，避免在多个 serializer 或前端页面重复拼接。`reason_type` 必须在 QuerySet 阶段或明确的后端过滤层参与筛选，不能在分页后只做前端过滤；`reason_text` 第一版不做全文筛选，确需全文搜索时再考虑 QuerySet annotation 或派生表。

`/api/workflows/` 可在过渡期保留，避免破坏既有接口或测试；前端 HR 菜单不再暴露独立页面。

## 七、前端设计边界

- `ResumesPage.jsx` 继续作为简历库主页面，增加岗位部门、流程状态、原因列，并纳入表头筛选。
- 详情抽屉保留投递志愿、简历预览、分配尝试，并在分配尝试表中展示 `match_reason` / `manual_reason`。
- 左侧菜单移除 HR 视角的「候选人工作流」「归档候选人」入口；接口人仍默认进入「分配尝试」。
- 原有 `WorkflowsPage.jsx` 可以先保留为过渡代码，但不应再作为主导航入口；后续确认无外部链接依赖后再删除。

## 八、测试与验收

后端测试：

- 候选人列表返回 `current_apply_id`、`job_department_name`、`workflow_status`、`reason_type`、`reason_text`。
- 候选人列表支持按岗位部门、流程状态、原因类型筛选。
- 当前志愿匹配岗位和二级部门但没有可用二级接口人时：
  - 不创建 `AssignmentAttempt`。
  - `CandidateWorkflow.current_resume/current_rank` 保持当前志愿。
  - `CandidateWorkflow.status` 保持 `in_progress`。
  - `CandidateWorkflow.block_reason` 记录 `contact_not_found`。
  - 不切换下一志愿。
  - 不归档。
  - 列表原因展示二级接口人缺失。
- 候选人存在历史未通过志愿和当前缺二级接口人志愿时，简历库展示当前志愿的岗位部门和原因，不展示历史未通过 attempt 的岗位部门和原因。
- 重新生成有效尝试、手动强制分配、流程归档或流程通过时，清空 `block_reason/block_detail`。
- 三级反馈未通过仍会进入下一志愿，确保新规则只影响接口人缺失场景。

前端验证：

- HR 左侧菜单不再展示「候选人工作流」「归档候选人」。
- 简历库表格展示应聘ID、岗位部门、流程状态、原因。
- 简历库能通过系统简历状态、流程状态和原因类型筛选定位归档、待处理和接口人缺失候选人。
- 分配尝试页面仍可执行 HR 下发、二级转派、三级反馈和导出。

## 十、实施清单

本次实现只处理本优化项，不顺手重构其它页面或规则。

后端改动边界：

- 修改 `apps.core.models.CandidateWorkflow`，增加 `block_reason` / `block_detail`，并生成 `core` migration。
- 增加候选人列表展示 helper，集中计算 `current_apply_id`、`job_department_name`、`reason_type`、`reason_text`，避免前端和多个 serializer 重复拼接规则。
- 修改 `CandidateSerializer` 和候选人查询过滤，使简历库列表支持新增字段展示与 `current_apply_id`、`job_department_name`、`workflow_status`、`reason_type` 后端筛选。
- 修改自动分配状态机：当当前志愿已匹配岗位和二级部门但缺可用二级接口人时，写入 `block_reason=contact_not_found` 和 `block_detail`，保持 `status=in_progress`、`current_resume/current_rank` 不变，不创建 `AssignmentAttempt`，不推进下一志愿。
- 在生成有效自动尝试、手动强制分配、流程通过、流程归档、流程重开时清空 `block_reason/block_detail`。

前端改动边界：

- 修改 `BasicLayout.jsx` / 路由配置，HR/管理员菜单不再暴露「候选人工作流」「归档候选人」，接口人仍默认进入「分配尝试」。
- 修改 `ResumesPage.jsx`，新增应聘ID、岗位部门、流程状态、原因类型/原因展示和对应筛选；详情抽屉的分配尝试表展示分配理由/手动原因。
- 不删除 `WorkflowsPage.jsx`，只从主导航和常规路由入口移除，降低一次性清理风险。

正式文档同步边界：

- `需求描述.md`：同步简历库主控台、缺二级接口人停留当前志愿、归档口径和输出清单。
- `前端设计.md`：同步菜单、简历库列、详情抽屉和页面清单。
- `后端设计.md`：同步状态机、候选人 API 字段/筛选、`block_reason/block_detail` 清空时机。
- `数据库设计.md`：同步 `CandidateWorkflow` 字段、归档原因与阻塞原因边界、索引/筛选口径。

回归保护：

- 保留分配尝试页的下发、批量下发、二级转派、三级反馈、导出和预览流程。
- 保留简历库上传、撤销、处理简历、导出、详情和预览流程。

- 不提交或回退与本优化无关的既有未提交代码变更。
